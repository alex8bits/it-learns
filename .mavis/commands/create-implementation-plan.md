# Command: Create Implementation Plan (it-learns)

This is the **planning step** of the feature workflow for the **it-learns** project
(Laravel 13 / PHP 8.3 — онлайн-платформа обучения IT-навыкам). The full
orchestration flow lives in `AGENTS.md` под **"Процесс реализации фичи"**.

You turn a feature description (or a research/design document) into a detailed,
actionable implementation plan split into individual task files. You **plan and
document** — you do not write any production code.

---

## Цель

Разложить фичу на упорядоченные, **независимо исполнимые** таски, по которым
`worker` сможет идти параллельно или последовательно без потери контекста.

---

## Hard rules

- **DO NOT implement anything.**
- **DO NOT modify source files.**
- **ONLY create task files in `.mavis/tasks/<topic>/`.**
- Каждый таск self-contained и исполни́м независимо (если не указаны явные зависимости).
- Если план затрагивает API-поверхность, **явно указывать** её в каждом таске, который создаёт route или controller (`public|admin|ai|practice × v1|v2`).

---

## Process

### 1. Initial Response

Ответить:

```
Готов составить план реализации. Опишите задачу или укажите research/дизайн-документ, и какие поверхности/слои затрагивает фича (public/admin/ai/practice, премиум/ИИ/изоляция среды, v1/v2).
```

### 2. Understand the Feature

После получения входа:

1. Если есть research/design — прочитать **полностью**.
2. Если упомянуты исходные файлы — прочитать **полностью**.
3. Определить: что меняется, какие файлы затрагиваются, что такое end-state.
4. Свериться с `AGENTS.md` (15 правил) и `docs/concept.md` (домен) — никаких решений в противоречии с ними без явного обоснования.
5. Определить **topic slug** для имени папки: короткий, kebab-case, английский (например: `premium-subscription`, `ai-prompt-resolver`, `course-catalog`, `practice-environment`).

### 3. Decompose into Tasks

Разложить реализацию на **упорядоченные, пронумерованные таски** (01, 02, 03…).

Правила:

- Каждый таск трогает **один логический concern** (один класс, одна группа методов, одна миграция, одна группа маршрутов).
- Независимые таски помечаются как параллельные.
- Зависимости указываются явно.
- Рекомендуемое число тасков: **3–7** (меньше для маленьких фич, больше для сложных).
- Первый таск — всегда низкоуровневый строительный блок (enum + миграция + cast раньше, чем Action; Action раньше, чем Controller).
- **Тесты — по правилу №15 `AGENTS.md`:**
  - **Unit — максимальное покрытие**: вся бизнес-логика, граничные случаи, ошибки, enum'ы, политики, форматирование.
  - **Feature — только smoke**: 1 happy-path + ключевые HTTP-ошибки для каждого затронутого эндпоинта.
- Если таск затрагивает премиум/ИИ/изоляцию среды — это явно отмечается в `Контексте` (см. структуру ниже).

### 4. Write Task Files

Сохранять каждый таск как: `.mavis/tasks/YYYY-MM-DD-<topic>/<NN>-<kebab-name>.md`

**Структура файла** (соблюдать точно):

```markdown
# Таск <N> — <Короткое название>

## Цель

[1–3 предложения: что таск достигает и зачем]

## Контекст

- Эталон/аналог: `path/to/file.php:lines` — [что зеркалим]
- Ключевые факты из research/дизайна или кодовой базы, важные для реализации
- Структуры данных, API-контракты, payload-примеры (если применимо)
- **API surface / version:** [public|admin|ai|practice] × [v1|v2] — только если этот таск создаёт или меняет route/controller
- **Премиум / ИИ / изоляция среды:** [если затрагивается — короткая пометка]

## Что нужно реализовать

### 1. [Sub-step name]

[Точные инструкции: какой метод добавить/изменить, точные сигнатуры, шаги алгоритма пронумерованные 1–N, code-snippets где полезно]

### 2. [Next sub-step]

...

## Файлы для изменения

- `path/to/file.php` — [что добавить/изменить]

## Что НЕ нужно менять

- [Явный список того, что выглядит релевантным, но трогать нельзя — например, "не трогать v1-маршруты публичной части, если фича только для v2", "не менять сигнатуру DummyLlmClient — её используют другие таски"]

## Проверка

После реализации убедиться:
- [Concrete checkable assertion — например: метод возвращает X при Y, бросает Z при W]
- [Another assertion]
- [Test commands — `php artisan test --filter=...` если применимо]

## Тесты

- **Unit:** [что покрыть — перечислить классы/методы, например `tests/Unit/Actions/Auth/RegisterActionTest.php`]
- **Feature (smoke):** [если есть HTTP-граница — перечислить файл и сценарии, например `tests/Feature/Auth/RegisterTest.php`: happy-path, валидация, дубликат email]

## Зависимости

- Зависит от: Таск N (если есть)
- Можно выполнять параллельно с: Таск N, Таск M (если применимо)
```

### 5. Output Summary

После сохранения всех файлов вывести:

```
Создано X тасков в .mavis/tasks/YYYY-MM-DD-<topic>/

01-<name>.md — [one-line description]
02-<name>.md — [one-line description]
...

Порядок выполнения:
- Параллельно: 01, 02
- После них: 03
- Последним: 04
```

## Quality Rules

1. **Всегда `path/to/file.php:line` ссылки** — никакого расплывчатого «см. сервис».
2. **Читать исходники перед написанием тасков** — никогда не выдумывать сигнатуры или структуру.
3. **Code-snippets в тасках — blueprints**, не финальный код. Implementer адаптирует.
4. **«Что НЕ нужно менять»** обязательно заполнить — предотвращает случайные side-effects (особенно: не трогать v1-маршруты, если фича для v2; не ломать сигнатуры, от которых зависят другие таски).
5. **«Проверка»** — конкретная, проверяемая без запуска приложения (например, «метод доступен через DI», «возвращает null при отсутствии url»).
6. **«Зависимости»** — обязательная секция, даже если ответ «нет зависимостей».
7. **Тесты** — для каждого таска, который меняет логику, явно решить: Unit (большая часть логики) или Feature (HTTP-уровень). Указать файл-паттерн (например, `tests/Unit/Actions/Auth/RegisterActionTest.php`).
8. **API surface/version** — объявлять явно в `Контексте` каждого таска, который создаёт/меняет route/controller. Не давать `worker` додумывать.
9. **Премиум/ИИ/изоляция среды** — если фича затрагивает, пометить в `Контексте` и при необходимости выделить в отдельный таск.
10. **Согласованность с `AGENTS.md`** — никаких решений, нарушающих 15 правил, без явного обоснования.

---

## Good vs Bad

BAD: «Добавить Action для подписки» — без сигнатуры, без тестов, без зависимостей.

GOOD: «Таск 02 — `CreateSubscriptionAction`. Сигнатура `__invoke(User $user, SubscriptionTier $tier): Subscription`. Проверки: tier = Premium; подписки в `DB::transaction`; вызывает `PaymentGateway::createCheckoutSession()` и создаёт запись `Subscription` со статусом `Pending`. Тесты Unit в `tests/Unit/Actions/Subscriptions/CreateSubscriptionActionTest.php` покрывают: успешный flow, tier = Free отклонён, ошибка провайдера откатывает транзакцию. Зависит от Таск 01 (модель + enum + миграция).»
