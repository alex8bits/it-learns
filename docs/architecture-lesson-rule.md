# Правила составления урока (курс «Архитектура ПО: PHP / Laravel»)

> Применяется к урокам курса по плану [plan.md](courses/architecture/plan.md).
> Урок сначала составляется как markdown-файл по этим правилам, затем переносится в админку.

**Главный принцип: файл — единственный источник правды.** Урок создаётся **только
как markdown-файл**: на этапе составления никаких записей в БД и никаких сидеров.
Файл обязан быть машиночитаемым — строго по шаблону раздела 6, так чтобы по нему можно
было механически создать урок в БД: через админку, сгенерированный по файлам сидер или
бот. Всё, чего нет в файле, в БД не попадёт.

Исключение составляют **артефакты php-практики** (стартовая ветка, тесты, эталонное
решение): они хранятся в репозитории практики по путям, которые файл урока указывает
явно (раздел 4). Файл урока описывает их контракт полностью, а ссылка на путь обязательна.

При составлении урока необходимо написать три части: материал, теоретическую проверку
и (если для урока предусмотрена практика) практические задания.

---

## 1. Материал урока

- **Исчерпывающая статья по теме урока**: определения, принцип, пример «до» и «после»,
  типичные ошибки, условия применимости. Читатель, не знакомый с темой, должен понять её
  по одному этому тексту, без внешних источников.
- **Ориентир объёма — по значению `format` из frontmatter:**

  | `format` | Для каких уроков | Объём материала | Вопросов в теории |
  |---|---|---|---|
  | `full` | все уроки по умолчанию | 1800–3500 слов (≈15–25 минут чтения), код не считается | 3–5 |
  | `short` | уроки, помеченные в плане «короткий» | 800–1500 слов | 3–5 |
  | `overview` | уроки, помеченные в плане «обзорный» | 800–1500 слов | 2–3 |

  Тонкая «выжимка» — не исчерпывающая статья: разворачивайте мотивацию, сравнения с
  альтернативами, терминологию-синонимы, граничные случаи и «когда это не нужно».
  При этом вода недопустима: каждый абзац должен сообщать что-то новое. Практический
  тест: если абзац можно удалить, и тема всё равно понятна, а вопросы урока отвечаются —
  это вода, удаляйте. Не добирайте объём украшениями (награды и регалии, вымышленная
  статистика, ссылки на «известные компании» без источника, повторы уже сказанного
  другими словами).
- **Структура секции `## Материал`** — фиксированный набор заголовков `###`, в
  указанном порядке:

  | № | Заголовок | Обязателен | Содержание |
  |---|---|---|---|
  | — | (абзац без заголовка) | да | Короткое обзорное введение: зачем эта тема и как она связана с пройденным, 1–3 предложения, без списка уроков |
  | 1 | `### Что нужно знать о Laravel к этому уроку` | **только уровень «Начинающий»** | 2–3 абзаца: ровно то, что нужно из Laravel для понимания материала и выполнения практики (без пересказа документации) |
  | 2 | `### Проблема` | да | Боль на примере сквозного проекта — код или сценарий «до». Читатель должен увидеть, чем это мешает: изменению, тестированию, пониманию |
  | 3 | `### Идея и решение` | да | Сначала принцип словами, затем код «после» на том же примере. Внутри допустимы подразделы `####` |
  | 4 | `### Как это выглядит вне Laravel` | уровни 2–4 | Короткая framework-agnostic версия (чистый PHP или псевдокод). Если урок целиком не зависит от фреймворка — одно-два предложения об этом вместо кода |
  | 5 | `### Цена и когда НЕ применять` | да | Конкретные условия, при которых приём вреден или избыточен, и признаки того, что вы в такой ситуации. Без «всегда» и «никогда», если нет условий |
  | 6 | `### Связь с другими уроками` | да | На что урок опирается и что подготавливает; будущие уроки — только названием и одной фразой, без использования их терминов (граница тем — раздел 5) |
  | 7 | `### Резюме` | да | Ключевые мысли списком |

  В уроках **уровня «Основы»** блок 4 не нужен: примеры там — на чистом PHP, и
  «вне Laravel» не имеет смысла.
- **«Ранее в курсе» — краткое содержание всех предыдущих уроков курса.**
  Самостоятельная секция `## Ранее в курсе` между H1 и `## Материал`
  (не подраздел материала); заголовок фиксированный — `## Ранее в курсе`.
  Появляется со второго урока курса; в первом уроке курса секции нет.
  Формат — маркированный список с одним пунктом на каждый предыдущий урок
  **всего курса**, в порядке прохождения: «Урок <N> уровня «<Уровень>»
  «<Тема>» — одна фраза сути (что ученик теперь знает или умеет)»; пункты
  предыдущих уровней не выбрасываются. Ограничения: только пройденный
  материал (границы тем — раздел 5), без новых терминов, не больше строки на
  урок — это ориентация, а не конспект.
  Назначение секции — контекст для автора, ревьюера и бота-составителя:
  явная карта разобранного (текущий урок может опираться на
  перечисленное без пересказа, и это не пробел материала).
  **В БД секция не переносится** — ученик её не видит. Повторение для
  ученика — через обзорное введение секции `## Материал` (1–3 предложения,
  связывающие пройденное с темой урока).
- Примеры по возможности пишутся на сквозном проекте курса (интернет-магазин:
  `Product`, `Category`, `Customer`, `Order`, `OrderItem`, `Money` и т.д.; стадия
  проекта на каждом уровне — см. [architecture.md](architecture.md)). Спец-мини-домены
  (бронирование мест, рассылка уведомлений, аудит действий) — только там, где указано
  в плане.
- Опираться только на уже пройденные темы и общую компьютерную грамотность; новые термины
  вводятся и объясняются в самом материале.

### Требования к коду в материале

- PHP 8.3+, `declare(strict_types=1);`, PSR-12. Laravel 11/12: только реально
  существующие API этих версий. Если урок использует сторонний пакет (Pest, Deptrac,
  PHPStan/Larastan, spatie/laravel-data и т.п.) — назвать пакет и мажорную версию,
  совместимую с контрактом runtime.
- **Код «после» автор обязан реально прогнать** (тесты и/или PHPStan на заданном
  уровне); код «до» должен выполняться и демонстрировать описанную проблему, а не быть
  сконструированным в голове. «До» в материале совпадает по сути с плохим местом
  стартовой ветки практики.
- Листинги — минимально достаточные: пара «до/после» на одну идею, ориентир ≤ 40 строк
  на листинг; без полных классов, если для идеи достаточно метода. Не использовать
  вымышленные пакеты, методы и конфигурационные ключи.
- На уровне «Основы» — только чистый PHP: без фасадов, Eloquent и контейнера Laravel.
- Любой приём подаётся вместе с ценой: у каждого листинга «после» в разделе
  «Цена и когда НЕ применять» должна быть соответствующая оговорка.

## 2. Теоретическая проверка

- **3–5 вопросов** на урок (в уроках `format: overview` — **2–3**); один вопрос — одна идея.
- У каждого вопроса **несколько вариантов ответа** (рекомендуется 3–4), из которых
  **ровно один правильный**.
- **К каждому неправильному варианту — комментарий** (`error_text` в админке), который
  увидит пользователь, выбрав его. В комментарии указать, **почему именно этот вариант
  неверен** — конкретно и обучающе, а не «неверно, попробуйте ещё раз». Правдоподобные
  «ловушки» (перепутанные концепции, отличающиеся на одну деталь формулировки) ценятся
  выше очевидно абсурдных вариантов.
- **В архитектуре часто нет единственного ответа.** Формулируйте вопрос про условия
  («при каких обстоятельствах X оправдан», «что из перечисленного является признаком Y»,
  «какое решение подходит при данных ограничениях»), а не про «лучшую практику вообще».
  Условия должны быть в самом вопросе, так чтобы верный вариант был единственным при
  этих условиях.
- Хорошие темы вопросов: перепутанные принципы (SRP vs «один публичный метод»,
  связанность vs связность), композиция vs наследование, «куда положить логику»
  (контроллер / модель / сервис), Repository над Eloquent, Active Record vs Data Mapper,
  где валидировать, где граница транзакции, идемпотентность, события vs прямые вызовы,
  модульный монолит vs микросервисы, «когда кеш врёт», eventual consistency — в той мере,
  в какой они входят в тему урока.
- **Формат вопроса — текст в одну строку.** Короткий код — инлайн-кодом
  (`` `new Mailer()` ``); многострочные блоки кода в вопросах не используются.
  Ситуацию описывайте словами.
- Формат в markdown-файле (строгий — парсится при переносе в БД):

```markdown
### Вопрос N: текст вопроса?

- ✅ правильный вариант
- ❌ неверный вариант — error_text: почему именно этот вариант неверен
- ❌ неверный вариант — error_text: ...
```

- ✅-строка содержит **только текст варианта** (без авторских пояснений);
  пояснения, если нужны, — HTML-комментарием `<!-- … -->` на отдельной строке:
  при переносе в БД комментарии игнорируются.

## 3. Практические задания: общие правила

- Только если для урока в плане ([architecture.md](architecture.md), колонка «Практика»)
  **не стоит «—»**. Значение `runtime` каждого задания (`php` или `mysql`) берётся из
  той же колонки.
- **1–3 задания** нарастающей сложности. В мини-проектах («Спасаем обработчик заказа»,
  «Слоистый магазин», «Домен заказов») — 2–3 сквозных задания на пройденное.
  Capstone (последний урок курса) — одно задание-кейс.
- В одном уроке допустимо смешивать runtime только если план это предусматривает.
- Для каждого задания указать: формулировку, описание ожидаемого результата и всё,
  что нужно для автоматической проверки (по разделу 3.1 или 3.2 в зависимости от runtime).
- Задание проверяет **навык урока**, а не посторонние знания: если задание можно решить,
  не поняв идею урока (например, механической заменой строки), оно составлено неверно.

### 3.1. Runtime `mysql`

Используется там, где результат задания — схема, ограничения, миграция, витрина или
состояние данных. Механика — как в курсе MySQL:

- Задание описывается полями: `statement`, `expected_result_text`, `seed_sql`,
  `expected_rows`, `runtime`. Поле `expected_hash` вычисляется платформой из
  `expected_rows` каноническим сериализатором.
- Изолированная среда под каждую попытку поднимается **с нуля из `seed_sql`**: скрипт
  каждого задания самодостаточен, общего состояния между заданиями и попытками нет.
- Решение студента исполняется в этой среде; итоговый result set сравнивается с
  `expected_rows` по каноническому хешу; при несовпадении студент видит diff
  «Эталон / Ваш результат». Поэтому `expected_rows` — **результат эталонного решения,
  который автор обязан реально прогнать**, а не сконструировать в голове.
- Запись специальных значений в `expected_rows`: SQL NULL — литерал `NULL` в ячейке;
  пустая строка `''` — пустая ячейка. Это разные значения. Строка `"NULL"` эталоном
  SQL NULL не является.
- Порядок строк — часть эталона: строки `expected_rows` записываются в том порядке, в
  котором их возвращает эталонное решение.
- Результат должен быть **детерминированным**: явный `ORDER BY`, без reliance на порядок
  вставки, без `NOW()`-зависимостей (или зафиксированные даты в сид-данных).
- Решение может состоять из **нескольких SQL-инструкций** через `;` (одна client-сессия
  движка: доступны эффекты предыдущих инструкций). Лимит числа инструкций и blacklist
  команд — на стороне платформы.
- **Контракт результата:** зачёт по result set **последней** инструкции; инструкции до
  неё не должны возвращать данных (типовой паттерн: изменения, затем финальный `SELECT`).
- **Задания на схему и ограничения.** Результат нельзя «увидеть» по самой схеме, поэтому
  автор проектирует контракт результата: финальный `SELECT` к `information_schema`
  (ограничения, индексы, типы столбцов) или запрос, фиксирующий поведение схемы после
  заданного набора операций. Контракт должен однозначно отличать верную схему от
  неверной и не зависеть от имён, которые студент выбирает сам (если имена не заданы
  в формулировке).
- **Задания на конкурентность и согласованность.** Реальная гонка не воспроизводится:
  `seed_sql` задаёт детерминированную последовательность операций (проверка-потом-
  действие на устаревших данных, повторная доставка запроса), а контракт результата —
  итоговое состояние таблиц. Формулировка прямо описывает эту модель, чтобы студент
  понимал, что именно моделируется.

### 3.2. Runtime `php`

Используется для заданий на рефакторинг и проектирование кода. Задание считается
выполненным, когда проходят **все** проверки из списка ниже.

**Артефакты практики.** Для каждого практического урока:

- **стартовая ветка** `starter/<level>-<NN>` репозитория практики: стартовый код +
  видимые студенту тесты. Задания одного урока разделяются группами Pest
  (`<level>-<NN>-t<K>`), а не отдельными ветками;
- **скрытые тесты и эталонное решение** хранятся вне стартовой ветки, в закрытом
  каталоге репозитория практики (`practice/<level>-<NN>/hidden/`,
  `practice/<level>-<NN>/reference/`), студенту недоступны;
- **сквозной проект.** Стартовая ветка урока строится от **эталонного решения
  предыдущего практического урока** того же уровня (для первого практического урока
  уровня — от зафиксированного стартового состояния уровня) плюс новое «плохое место»
  этого урока. Решения студента на следующий урок не переносятся: каждый урок
  стартует из эталона, поэтому ошибка в одном уроке не блокирует остальные.
- Starter и эталон **не используют конструкций будущих уроков** (граница тем — раздел 5):
  например, в уроке «SRP и OCP» эталон без DI-контейнера, агрегатов и событий.

**Проверки (в порядке применения):**

1. **Поведенческие тесты (Pest).** Видимые — показывают студенту, что именно проверяется;
   **скрытые** — на других данных и сценариях, чтобы нельзя было пройти подгонкой под
   видимые тесты или хардкодом результата. Каталоги тестов, конфигурация проверок
   (`phpstan.neon`, `deptrac.yaml`, правила arch-тестов, `composer.json`) помечаются как
   `protected` — их изменение не принимается.
2. **Архитектурные правила** (`pest-plugin-arch`, Deptrac). Правила описывают
   **инварианты** — чего нельзя («домен не зависит от инфраструктуры», «нет прямых
   `new` для сервисов в контроллерах», «`env()` только в `config/`»), а не единственную
   допустимую структуру. Слишком жёсткие правила отвергнут корректные решения — это
   дефект задания. Для уроков, где arch-правил по смыслу нет, указывается «—».
3. **Статический анализ** (PHPStan/Larastan). Уровень указывается в задании явно.
4. **Детерминированность.** Время фиксируется (`Carbon::setTestNow` или внедрённые
   часы), случайность — с фиксированным seed или через внедряемый источник; сеть и
   брокеры — только фейки (`Http::fake`, `Queue::fake` и подобные); ограничения по времени
   и ресурсам — по контракту runtime.

**Обязательные проверки автора перед сдачей задания (аналог «обязательно прогнать эталон»):**

- эталонное решение проходит все проверки — **реально прогнано**;
- **стартовая ветка не проходит проверки** («красный старт»): иначе задание тривиально;
- минимум два «неправильных» решения заведомо не проходят: (а) тривиальный обход
  (удаление/правка теста, хардкод результата), (б) типичное неполное решение —
  такое, которое выглядит правильным, но нарушает скрытый тест или arch-правило;
- тест не зависит от порядка выполнения, текущего времени и внешней сети.

**Задачи без единственного решения** (выбор границ, ADR, защита компромиссов — в плане
это capstone и уроки о границах) проверяются структурно: набор допустимых инвариантов
(arch-правила + тесты) **плюс чек-лист ADR**. Чек-лист ADR проверяет только наличие
и непустоту разделов, а не качество рассуждения:

```markdown
# ADR-NNNN: <решение одной фразой>

## Контекст
## Рассмотренные варианты   (не менее двух)
## Решение
## Последствия              (плюсы и минусы, оба непустые)
```

ИИ-ревью текстового обоснования — опциональное расширение, не условие прохождения.

## 4. Формат php-практики в файле урока

Поля, обязательные для каждого `php`-задания (подробно — в шаблоне раздела 6):

| Поле | Содержание |
|---|---|
| `statement` | Формулировка для студента: контекст сквозного проекта, что нужно сделать, какие ограничения |
| `expected_result_text` | Что должно быть верно после решения: поведение + архитектурные инварианты (человекочитаемо) |
| `runtime` | `php` |
| `starter` | Ветка `starter/<level>-<NN>` |
| `group` | Группа Pest этого задания: `<level>-<NN>-t<K>` |
| `editable` | Список путей/масок, которые студент может менять |
| `protected` | Список путей/масок, изменение которых отклоняется |
| `visible_tests` | Пути/группы видимых студенту тестов |
| `hidden_tests` | Что проверяют скрытые тесты (описание сценариев) и путь к ним |
| `arch_rules` | Перечень arch-правил (инвариантами) или «—» |
| `static_analysis` | Инструмент и уровень (например, `phpstan level 6`) или «—» |
| `acceptance` | Критерии приёмки: полный список того, что должно пройти |
| `reference` | Путь к эталонному решению |

## 5. Границы тем (обязательное правило)

- Теоретические вопросы (квиз) и практика должны **в основном касаться темы текущего урока**.
- **Допустимо и порой желательно**, чтобы они **косвенно касались ранее пройденного
  материала** (повторение и закрепление).
- **Недопустимо**, чтобы они касались **ещё не пройденных тем** — порядок определяется
  планом: уровень за уровнем, урок за уроком ([architecture.md](architecture.md)).
  Примеры: в уроке «SRP и OCP» нельзя требовать DI-контейнер Laravel (он в уроке «DIP, DI
  и IoC»), но можно попросить разделить класс, написанный в «Спасаем обработчик заказа»;
  в уроке «Repository» нельзя требовать агрегат и доменные события (уровень «Средний»),
  но можно использовать `Money` и DTO из пройденного.
- Для упоминаний в материале (раздел «Связь с другими уроками»): будущий урок можно
  назвать и одной фразой сказать, зачем он, но нельзя использовать его понятия в
  объяснении, теории или практике.

## 6. Сохранение урока

Составленный урок сохраняется по пути:

```
docs/courses/architecture/<level>-<lesson number>-<lesson theme>.md
```

- `<level>` — латинский slug уровня:

  | Уровень (в плане) | slug |
  |---|---|
  | Основы | `basics` |
  | Начинающий | `beginner` |
  | Средний | `intermediate` |
  | Продвинутый | `advanced` |

- `<lesson number>` — двузначный номер урока из плана (`01`, `02`, …). На уровне
  «Продвинутый» нумерация сквозная по тематическим блокам; блоки A–E в имени файла и
  frontmatter не отражаются.
- `<lesson theme>` — тема урока латиницей в kebab-case.

Примеры: `docs/courses/architecture/basics-01-what-is-architecture.md`,
`docs/courses/architecture/intermediate-12-transactions-concurrency-idempotency.md`,
`docs/courses/architecture/advanced-19-capstone.md`.

| `practice_tasks.seed_sql` (`mysql`) | SQL-блок после маркера `**seed_sql:**` |

- frontmatter обязателен и заполнен полностью; секции идут в фиксированном порядке:
  `## Ранее в курсе` (опционально — со второго урока курса) → `## Материал` →
  `## Теоретические задания` → `## Практические задания`
  (последней нет при `practice: no`);
- внутри `## Материал` — только заголовки `###` из таблицы раздела 1, в указанном
  порядке; подразделы внутри них — `####`; подраздела `### Ранее в курсе` быть не должно —
  карта пройденного живёт только в отдельной секции `## Ранее в курсе`;
- внутри тел вопросов и заданий не использовать заголовки `###` и маркеры вида
  `**statement:**` / `**seed_sql:**` / `**starter:**` и остальные маркеры полей практики;
- `expected_rows` — markdown-таблица точного результата эталонного прогона
  (см. раздел 3.1): одна строка таблицы = одна строка результата;
- маркеры полей практики записываются жирным с двоеточием на отдельной строке
  (`**editable:**`), значение — под ним; исключения — однострочные `**runtime:**`,
  `**starter:**`, `**group:**`, `**static_analysis:**`, `**reference:**`;
- всё нужное для БД есть в файле: перенос не требует домысливания.

## 7. Что зависит от контракта php-runtime

Эти правила рассчитаны на runtime `php` с Pest, `pest-plugin-arch`, Deptrac и
PHPStan/Larastan. Окончательный контракт runtime утверждается отдельно (в плане —
шаг «Определить контракт `php`-runtime») и фиксирует:

- версии PHP, Laravel, Pest, пакетов проверок и уровень PHPStan по умолчанию;
- лимиты времени и ресурсов, формат запуска и вывода тестов;
- структуру репозитория практики и способ хранения `hidden/` и `reference/`;
- способ защиты `protected`-путей и формат отчёта об ошибке для студента;
- как поля `php`-практики (раздел 4) хранятся и передаются в среду.

Если контракт изменит имена полей или структуру путей, меняется этот файл, а уроки
правятся механически.

## Чек-лист перед сдачей урока

- [ ] Материал — исчерпывающая статья, понятная без внешних источников.
- [ ] Секция `## Материал` содержит фиксированные `###`-разделы в правильном порядке:
      (на уровне «Начинающий» — «Что нужно знать о Laravel к этому уроку»), «Проблема»,
      «Идея и решение», «Как это выглядит вне Laravel» (уровни 2–4), «Цена и когда НЕ
      применять», «Связь с другими уроками», «Резюме»; открывается обзорным введением.
- [ ] Со второго урока курса файл содержит секцию `## Ранее в курсе` перед
      `## Материал`: по одному краткому пункту на каждый предыдущий урок
      всего курса, в порядке прохождения (первый урок курса — без секции);
      `## Материал` не содержит списка пройденных уроков.
- [ ] Объём материала — в ориентире для своего `format` (`full` 1800–3500 слов;
      `short` / `overview` 800–1500), без воды.
- [ ] Код «после» реально прогнан; код «до» выполняется и показывает проблему;
      версии пакетов и API Laravel проверены; на уровне «Основы» — только чистый PHP.
- [ ] «Цена и когда НЕ применять» содержит конкретные условия и признаки, а не общие слова.
- [ ] 3–5 теоретических вопросов (2–3 при `format: overview`); в каждом ровно один
      правильный вариант; условия вопроса однозначно определяют верный ответ.
- [ ] У каждого неверного варианта есть обучающий комментарий «почему неверен».
- [ ] В вопросах нет многострочных блоков кода.
- [ ] Если `practice: yes` — 1–3 задания (capstone — одно) с формулировкой, ожидаемым
      результатом и всем нужным для проверки; значение `runtime` совпадает с планом.
- [ ] Для `mysql`-заданий: `seed_sql` самодостаточен, `expected_rows` — прогнанный
      результат эталонного решения (финальный `SELECT`; NULL — литералом `NULL`; порядок
      строк — как в результате эталона); для схемы и конкурентности контракт результата
      описан по разделу 3.1.
- [ ] Для `php`-заданий заполнены все поля раздела 4; эталон прогнан и проходит все
      проверки; стартовая ветка не проходит проверки; два «неправильных» решения
      (обход и типичное неполное) не проходят; arch-правила — инварианты, а не одна
      структура; в starter и эталоне нет конструкций будущих уроков.
- [ ] Для задач без единственного решения — чек-лист ADR и допустимые инварианты вместо
      единственной структуры.
- [ ] Ни в теории, ни в практике нет ещё не пройденных тем; ранее пройденное — только косвенно.
- [ ] Файл сохранён по пути `docs/courses/architecture/<level>-<NN>-<theme>.md`,
      frontmatter заполнен.
- [ ] Урок создан **только в файле** (плюс артефакты `php`-практики в репозитории практики) —
      ничего не писалось в БД и в сидеры; формат строго машиночитаем: по файлу можно
      сгенерировать сидер или создать урок ботом.
