# Логические операторы: AND, OR, NOT

## Материал

### Обещание урока 8 «Основ»

Уровень «Основы» закрылся мини-проектом, и его резюме закончилось фразой
«дальше — новые уровни над этим фундаментом». Первый кирпич нового уровня
был заложен ещё уроком 8 «Основ», в списке «чего WHERE пока не умеет»: несколько
условий сразу — операторы `AND`/`OR`/`NOT`, тема следующего уровня; сейчас
— одно сравнение. Обещание пора выполнять.

Повод самый житейский. Реальные вопросы к базе почти никогда не укладываются
в одно сравнение. «Товары дороже двух тысяч, **которые есть на складе**» —
два условия. «Покупатели **из Москвы или из Санкт-Петербурга**» — два.
«Всё, **кроме** закончившегося» — снова два. До сих пор выкручивались:
несколькими запросами со сверкой глазами или одним условием с миром к
лишним строкам. Сегодня учимся говорить такое одним `WHERE`: три
логических оператора, скобки и правило, кто из операторов главный.

Всё разобранное работает в `WHERE` оператора `SELECT` — и ровно так же в
`UPDATE` и `DELETE` (урок 10 «Основ»). Про пишущие команды — отдельный разговор
в конце: там цена пропущенных скобок совсем другая.

и остатком. Демо-наборы уроков самостоятельны, как всегда; шестёрка на

```sql
SELECT id, name, category_id, price, stock FROM products ORDER BY id;
```

```sql
SELECT id, name, city, phone FROM customers ORDER BY id;
```

```text
+----+-----------------------------+-----------------+---------------+

|  1 | Анна Петрова                | Москва          | NULL          |

|  3 | Мария Волкова               | Москва          | NULL          |

+----+-----------------------------+-----------------+---------------+
```

### AND: строгий союз

«Покажи товары дороже 2000, которые есть на складе». Это два вопроса
каждой строке — «цена больше 2000?» и «остаток больше нуля?» — и в
результат должны попасть строки, ответившие «да» на **оба**. Союз «и»
по-английски — `AND`:

```sql
SELECT name, price, stock
FROM products
WHERE price > 2000 AND stock > 0
ORDER BY id;
```

```text
+--------------------------+----------+-------+
| name                     | price    | stock |
+--------------------------+----------+-------+
| Монитор 27"              | 15990.00 |     3 |
| Веб-камера               |  2450.00 |    12 |
+--------------------------+----------+-------+
```

Механика — та же, что в уроке 8 «Основ», только вопросов теперь два: сервер
обходит таблицу строка за строкой, отвечает на оба и сводит ответы в
один:

| Товар                | `price > 2000`? | `stock > 0`? | `AND` |
| -------------------- | --------------- | ------------ | ----- |
| Коврик для мыши      | нет             | да           | нет   |
| Мышь беспроводная    | нет             | да           | нет   |
| Клавиатура мех.      | да              | нет          | нет   |
| Монитор 27"          | да              | да           | да    |
| Кабель HDMI 2 м      | нет             | да           | нет   |
| Веб-камера           | да              | да           | да    |

`AND` строг: одного «нет» достаточно, чтобы обнулить пару, — какой бы
солидной ни была вторая половина. Клавиатура ответила «да» на цену и
«нет» на остаток — мимо. Половины при этом могут быть про разные столбцы:
«цена» и «остаток» друг о друге ничего не знают, `AND` просто требует
«да» от каждой.

Полезная мысленная картинка: `WHERE price > 2000` вернуло бы три строки,
`WHERE stock > 0` — пять. `AND` возвращает не «меньшее из чисел»,
а **пересечение** — строки, попавшие в оба списка. Здесь пересечение
трёх и пяти оказалось двумя.

### OR: добрый союз

Другая задача: «вывести на витрину "Скоро снова" то, что закончилось или
дорогое». Строка подходит, если ответила «да» хотя бы на один вопрос, —
какой именно, неважно. Союз «или» — `OR`:

```sql
SELECT name, price, stock
FROM products
WHERE stock = 0 OR price > 10000
ORDER BY id;
```

```text
+---------------------------+----------+-------+
| name                      | price    | stock |
+---------------------------+----------+-------+
| Клавиатура механическая   |  4990.00 |     0 |
| Монитор 27"               | 15990.00 |     3 |
+---------------------------+----------+-------+
```

Клавиатура прошла по остатку (четыре тысячи до десяти не дотянули),
монитор — по цене (три штуки в наличии). Картинка — зеркальная к `AND`:
**объединение** списков, «да» от любой половины достаточно. Если строка
ответит «да» сразу на обе половины, она вернётся один раз — дубликатов
`OR` не плодит.

И тонкость перевода: русское «или» часто слышится как «либо-либо», одно
из двух. SQL-`OR` шире: «хотя бы одно, можно оба». Для «ровно одно из
двух» в MySQL есть отдельный оператор `XOR`, но на практике он редок, и
курс его не касается.

Второй ежедневный шаблон — **один столбец, несколько допустимых
значений**: «покупатели из Москвы или Казани»:

```sql
SELECT name, city
FROM customers
WHERE city = 'Москва' OR city = 'Казань'
ORDER BY id;
```

```text
+-----------------------------+--------------+
| name                        | city         |
+-----------------------------+--------------+
| Анна Петрова                | Москва       |
| Иван Сидоров                | Казань       |
| Мария Волкова               | Москва       |
+-----------------------------+--------------+
```

Да, `city =` пишется дважды: каждая половина `OR` — полноценное
сравнение. Короткая запись для «один из» — оператор `IN` — следующий
урок; пока тренируем полную. И не сокращайте её способом из раздела
про `'Казань'` без сравнения — это ловушка, до неё несколько разделов.

### NOT: наоборот

Иногда проще назвать, чего **не** нужно: «все, кроме Москвы». Оператор
`NOT` меняет ответ на противоположный:

```sql
SELECT name, city
FROM customers
WHERE NOT (city = 'Москва')
ORDER BY id;
```

```text
+-----------------------------+-----------------+
| name                        | city            |
+-----------------------------+-----------------+
| Иван Сидоров                | Казань          |
| Дмитрий Козлов              | Санкт-Петербург |
| Ольга Смирнова              | Новосибирск     |
+-----------------------------+-----------------+
```

Результат узнаваем: это же `city <> 'Москва'` из урока 8 «Основ». Для равенства
`NOT` и `<>` взаимозаменяемы: `NOT (city = 'Москва')` и `city <> 'Москва'`
делают одно и то же — пишите то, что читается естественнее. Но у `NOT`
две особенности, которых у `<>` нет.

Первая — границы. Отрицание переворачивает не только ответ, но и знак:
`NOT (price > 2000)` — это в точности `price <= 2000`, а не `price <> 2000`.
Товар ровно за 2000 пройдёт: строгое «больше» при отрицании превратилось
в нестрогое «меньше или равно». Правило границ урока 8 «Основ» работает и здесь,
только зеркально: перевернули условие — перевернулась и граница.

Вторая — `NOT` берёт не только сравнения. После него в скобках стоит
условие любой сложности: `NOT (price > 2000 AND stock = 0)` — «не
одновременно дорогое и законченное» — монитор дорогой, но в наличии,
проходит. На составное условие `<>` уже не растянуть. Плюс знакомая
связка урока 11 «Основ»: `NOT (phone IS NULL)` — то же, что `phone IS NOT NULL`;
в чужом коде встречаются обе записи.

### Кто главный: приоритет операторов

Арифметика, известная со школы: в `2 + 3 * 4` умножение сильнее сложения,
ответ 14, а не 20. Логика устроена так же: **`NOT` сильнее `AND`, `AND`
сильнее `OR`**. Пока в условии один оператор, правило не ощущается. Когда
их два разных и скобок нет — сервер группирует сам, по приоритету.

Задача: «дорогие товары из периферии или аксессуаров». Задумано:
«(периферия ИЛИ аксессуары), И при этом дороже 2000». Пишем наивно,
без скобок:

```sql
SELECT name, category_id, price
FROM products
WHERE category_id = 1 OR category_id = 2 AND price > 2000
ORDER BY id;
```

```text
+---------------------------+-------------+---------+
| name                      | category_id | price   |
+---------------------------+-------------+---------+
| Коврик для мыши           |           1 |  690.00 |
| Клавиатура механическая   |           2 | 4990.00 |
| Кабель HDMI 2 м           |           1 |  450.00 |
| Веб-камера                |           2 | 2450.00 |
+---------------------------+-------------+---------+
```

Коврик за 690? Кабель за 450? Сервер прочитал условие так:

```sql
WHERE category_id = 1 OR (category_id = 2 AND price > 2000)
```

«Любой аксессуар — ИЛИ периферия, но только если она дороже 2000». `AND`
как более сильный забрал себе правую пару и сгруппировал её прежде
`OR`. Задуманное условие выглядит иначе — и возвращает другое:

```sql
WHERE (category_id = 1 OR category_id = 2) AND price > 2000
```

```text
+---------------------------+-------------+---------+
| name                      | category_id | price   |
+---------------------------+-------------+---------+
| Клавиатура механическая   |           2 | 4990.00 |
| Веб-камера                |           2 | 2450.00 |
+---------------------------+-------------+---------+
```

Одна пара скобок — два разных ответа на одних данных. На шести строках
странность видно глазами; на шестидесяти тысячах «коврик» в выдаче
никто не заметит. Отсюда правило следующего раздела.

### Скобки: явное лучше угаданного

Скобки в `WHERE` — не украшение, а способ сказать серверу — и коллеге, и
себе через месяц, — **что с чем комбинируется**. Правило стиля этого
курса: везде, где `OR` встречается с `AND` в одном условии, — скобки.
Даже когда приоритет и так на вашей стороне. Причины три:

- читаемость: `(city = 'Москва' OR city = 'Казань') AND registered_at >= '2026-06-01'`
  понятно без мысленного разбора приоритетов;
- правки: завтра внутрь скобки добавится третье условие — группировка
  не поедет;
- цена: скобки бесплатны, ошибка группировки — нет.

Скобки вкладываются друг в друга: `((a AND b) OR (c AND d))` — законно.
Если вложенность перевалила за два уровня, условие, скорее всего, пора
упрощать или разбивать на несколько запросов.

### `OR 'Казань'`: ловушка значения без условия

Самая коварная ошибка урока — даже не приоритет. Хотим «Москва или
Казань» и пишем по-человечески, сэкономив на втором `city =`:

```sql
SELECT name, city
FROM customers
WHERE city = 'Москва' OR 'Казань'
ORDER BY id;
```

```text
+-----------------------------+--------------+
| name                        | city         |
+-----------------------------+--------------+
| Анна Петрова                | Москва       |
| Мария Волкова               | Москва       |
+-----------------------------+--------------+
```

Только Москва. Куда делась Казань — в таблице-то она есть? Ответ
спрятан в вопросе, **что вообще может стоять по сторонам `OR`**.
Полноценное условие: сравнение, `IS NULL`, выражение в скобках. А
`'Казань'` — не условие, а строка-значение. Синтаксис, однако, не
запрещает и значение. Вспомните урок 5 «Основ»: `TRUE` и `FALSE` — имена единицы
и нуля. Условие — просто выражение со значением, где 1 значит «да»,
0 — «нет»; и наоборот: любое значение, оказавшееся на месте условия,
MySQL приводит к числу — ноль и NULL означают «нет», всё остальное
«да». Строка `'Казань'` начинается не с цифры, её числовое значение —
0, то есть «нет». Запрос обернулся в `city = 'Москва' OR «нет»`, то
есть в просто `city = 'Москва'`.

Итог: запрос молча вернул не то, Казань исчезла без единой ошибки.
Сервер, правда, оставит предупреждение 1292 «Truncated incorrect DOUBLE
value: 'Казань'» — «строка усечена до числа» — но выполнение не
остановит и результат не изменит. Три вывода. По обе стороны `AND`/`OR` —
всегда полное условие. Повторяющийся `city =` — не многословие, а
страховка. И «выполнилось без ошибок» не значит «сделало то, что нужно».

Из того же факта — маленький бонус: раз флаг из урока 5 «Основ» уже хранит
единицу или ноль, `WHERE activated` — законная краткая запись условия
`WHERE activated = TRUE` (подарочные карты урока 8 «Основ»). Обе формы делают
одно и то же.

### «Неизвестно» в логике: NULL и операторы

Урок 11 оставил вопрос на сегодня: сравнение с NULL даёт «неизвестно», а
что происходит с этим третьим ответом внутри `AND`, `OR` и `NOT`?
Проверим. `SELECT` умеет возвращать и просто выражения — без `FROM`;
заголовки колонок, как в уроке 11 «Основ», — просто текст выражений:

```sql
SELECT NOT NULL, 1 AND NULL, 0 AND NULL, 1 OR NULL, 0 OR NULL;
```

```text
+----------+------------+------------+-----------+-----------+
| NOT NULL | 1 AND NULL | 0 AND NULL | 1 OR NULL | 0 OR NULL |
+----------+------------+------------+-----------+-----------+
|     NULL |       NULL |          0 |         1 |      NULL |
+----------+------------+------------+-----------+-----------+
```

Читаем по порядку, держа в голове характеры союзов. `NOT` «неизвестно» —
«неизвестно». Дальше `AND`, строгий: уверенное «нет» одной половины
решает дело сразу, второй можно не ждать — «нет» `AND` «неизвестно» =
«нет» (третья колонка). А вот «да» `AND` «неизвестно» ответа ещё не
даёт: вдруг «неизвестная» половина окажется «нет» — итог «неизвестно»
(вторая колонка). У `OR`, доброго, зеркально: «да» одной половины
достаточно сразу — «да» `OR` «неизвестно» = «да» (четвёртая колонка), а
«нет» оставляет надежду — «нет» `OR` «неизвестно» = «неизвестно» (пятая).
Сводные таблицы:

| `AND`       | да | нет | неизвестно |
| ----------- | -- | --- | ---------- |
| да          | да | нет | неизвестно |
| нет         | нет | нет | нет      |
| неизвестно  | неизвестно | нет | неизвестно |

| `OR`        | да | нет | неизвестно |
| ----------- | -- | --- | ---------- |
| да          | да | да  | да         |
| нет         | да | нет | неизвестно |
| неизвестно  | да | неизвестно | неизвестно |

Запоминать таблицы целиком не нужно — достаточно характеров союзов:
`AND` строгий, «нет» побеждает сразу; `OR` добрый, «да» побеждает сразу;
что не решилось — «неизвестно». А главный факт урока 11 «Основ» не изменился:
`WHERE` пропускает только «да», поэтому строки с «неизвестно» из
результата выпадают — как и с «нет».

Два практических следствия.

Первое: **NULL не вытащить отрицанием**. «Все, кроме Ивана»:

```sql
SELECT name
FROM customers
WHERE NOT (phone = '912-345-67-89');
```

```text
+-----------------------------+
| name                        |
+-----------------------------+
| Дмитрий Козлов              |
+-----------------------------+
```

Один Дмитрий — результат урока 11 «Основ» один в один (там был
`phone <> '912-345-67-89'`). У Анны, Марии и Ольги сравнение с NULL —
«неизвестно», `NOT` перевернул его — в «неизвестно»: отрицание третьего
ответа не делает его «да». Отсутствие не ловится ни сравнением, ни его
отрицанием — только `IS NULL` / `IS NOT NULL`.

Второе: **`OR` может «спасти» строку**. «У кого известен телефон — или
его нет вовсе»:

```sql
SELECT name
FROM customers
WHERE phone = '912-345-67-89' OR phone IS NULL;
```

```text
+-----------------------------+
| name                        |
+-----------------------------+
| Анна Петрова                |
| Иван Сидоров                |
| Мария Волкова               |
| Ольга Смирнова              |
+-----------------------------+
```

Четыре из пяти. У NULL-строк первая половина — «неизвестно», зато
вторая, `IS NULL`, — уверенное «да», а доброму союзу одного «да»
достаточно. Комбинировать обычные условия с `IS NULL` — ежедневный
приём. Помните только: строка, давшая «неизвестно» во **всех** половинах
условия, не пройдёт ни через какой оператор — «неизвестно» не
накапливается до «да».

### Пишущие команды: скобки дороже золота

Всё разобранное работает и в `UPDATE`/`DELETE`: там `WHERE` отбирает
строки на изменение, и условие — ровно то же. Разница — цена ошибки. В
`SELECT` промах группировки стоит лишнего взгляда; в пишущей команде —
данных. Задумали «снять с витрины периферию и всё дороже десяти тысяч,
у чего остаток меньше трёх»:

```sql
UPDATE products
SET stock = 0
WHERE (category_id = 2 OR price > 10000) AND stock < 3;
```

Потеряли скобки — и сервер сгруппировал `category_id = 2 OR (price >
10000 AND stock < 3)`: под раздачу идёт **вся** периферия. Мышь и
веб-камера обнулились бы ни за что, и никакое предупреждение не
спасёт — с точки зрения сервера всё законно. Правила урока 10 «Основ» действуют
с удвоенной силой: контрольный `SELECT` с тем же `WHERE` до запуска
(«посмотреть жертв»), скобки в пишущих командах — всегда, перечитать
фильтр до выполнения, а не после.

### Чего в этом уроке нет

Честные границы на сегодня — всё перечисленное тема следующего урока:

- `IN` — короткая запись «один из»: `city IN ('Москва', 'Казань')`
  вместо цепочки `OR`;
- `BETWEEN` — диапазон одним условием вместо `x >= a AND x <= b`;
- `LIKE` — поиск по шаблону: `'Моск%'`.

### Резюме

- `AND` — строгий союз: «да» от обеих половин; `OR` — добрый: хотя бы
  одно «да»; `NOT` переворачивает ответ; при отрицании строгая граница
  становится нестрогой.
- Приоритет: `NOT` → `AND` → `OR`. Смешали `AND` с `OR` — ставьте скобки:
  читаемость, страховка правок, а в `UPDATE`/`DELETE` — без исключений.
- По сторонам `AND`/`OR` — полное условие. `OR 'Казань'` — не «Казань»:
  значение на месте условия приводится к числу, нецифровая строка — 0,
  «нет»; Казань исчезает молча, с предупреждением 1292.
- «Неизвестно» живёт по характерам союзов: «нет» `AND` «неизвестно» =
  «нет»; «да» `OR` «неизвестно» = «да»; `NOT` «неизвестно» =
  «неизвестно». Строки-«неизвестно» `WHERE` не пропускает.
- NULL не ловится отрицанием — только `IS NULL` / `IS NOT NULL`; `IS
  NULL` комбинируется с обычными условиями свободно.
- Дальше: `IN`, `BETWEEN`, `LIKE` — урок 2 уровня.

## Теоретические задания

### Вопрос 1: В таблице три товара: клавиатура (4990.00, stock 0), коврик (690.00, stock 34) и веб-камера (2450.00, stock 12). Какие из них вернёт запрос `SELECT name FROM products WHERE price > 2000 AND stock > 0;`?

- ✅ только веб-камеру
<!-- у неё «да» на оба вопроса -->
- ❌ клавиатуру и веб-камеру: обе дороже 2000 — error_text: «дороже 2000» — только половина условия: у клавиатуры stock = 0 — «нет» на вторую половину, а AND не пропускает строку без обоих «да».
- ❌ все три товара: у коврика ведь есть остаток — error_text: у коврика цена 690 — «нет» на первую половину; AND требует «да» от каждой половины, одного «да» недостаточно.

### Вопрос 2: Как сервер сгруппирует условие `WHERE category_id = 1 OR category_id = 2 AND price > 2000`?

- ✅ `category_id = 1 OR (category_id = 2 AND price > 2000)`
<!-- AND сильнее OR и забирает себе правую пару -->
- ❌ `(category_id = 1 OR category_id = 2) AND price > 2000` — error_text: так читалась бы запись со скобками; без них действует приоритет: AND связывает сильнее и группируется прежде OR — результат будет другим.
- ❌ откажется выполнять: смешивать OR и AND без скобок нельзя — error_text: запрос синтаксически корректен, приоритеты операторов определены; ошибкой будет не отказ сервера, а неправильный состав строк в результате.

### Вопрос 3: `SELECT name, city FROM customers WHERE city = 'Москва' OR 'Казань';` — что вернёт запрос?

- ✅ только покупателей из Москвы
<!-- одиночная 'Казань' — значение, а не условие -->
- ❌ покупателей из Москвы и из Казани — error_text: для этого нужно полное условие с обеих сторон: city = 'Москва' OR city = 'Казань'; 'Казань' без сравнения — не «казанские строки», а самостоятельное значение, приведённое к нулю.
- ❌ всех покупателей таблицы — error_text: это случилось бы, будь одиночная строка истиной; нецифровая строка приводится к числу 0 — «нет», поэтому запрос равносилен просто city = 'Москва'.
- ❌ ошибку выполнения — error_text: запрос выполнится и молча вернёт не то: сервер лишь запишет предупреждение 1292 об усечении строки до числа, но выполнение не остановит.

### Вопрос 4: У части покупателей phone = NULL. Вернёт ли их запрос `SELECT name FROM customers WHERE NOT (phone = '912-345-67-89');`?

- ✅ нет
<!-- NOT «неизвестно» — по-прежнему «неизвестно», а WHERE пропускает только «да» -->
- ❌ да: NULL ведь не равен номеру — error_text: отрицание «неизвестно» не делает его «да»: строки без значения выпадают и из сравнения, и из его отрицания — их ловит только IS NULL.
- ❌ сервер вернёт ошибку — error_text: ошибки нет: запрос синтаксически корректен; NULL-строки просто молча не попадут в результат — в этом и коварство.

### Вопрос 5: Строка покупателя с city = 'Казань' и phone = NULL. Что даст для неё условие `city = 'Москва' OR phone = '912-345-67-89'`?

- ✅ «неизвестно»
<!-- строка в результат не попадёт -->
- ❌ «да» — вдруг телефон именно этот — error_text: «вдруг» — это и есть «неизвестно», а не «да»; OR пропускает строку только за уверенное «да» хотя бы одной половины, а первая половина уже ответила «нет».
- ❌ «нет» — error_text: Казань действительно не Москва — «нет» на первую половину; но вторая — не «нет», а «неизвестно» (сравнение с NULL), и «нет» OR «неизвестно» = «неизвестно». Для WHERE итог тот же — не пройдёт, — но диагноз другой.

## Практические задания

### Задание 1: И дорогие, и в наличии

Первый составной фильтр: AND по двум столбцам.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT name, price, stock FROM products WHERE price > 2000 AND stock > 0 ORDER BY id; -->

**statement:**

Таблица `products` заполнена шестью товарами. Выведите название, цену и
остаток товаров, которые стоят **строго дороже** 2000 **и** есть на
складе (stock больше 0), — только name, price, stock, в порядке id.

**expected_result_text:**

Финальный SELECT возвращает две строки: монитор и веб-камера. Клавиатура
дороже 2000, но закончилась (stock = 0) — одного «нет» AND-у достаточно,
чтобы строка выпала. Остальные товары не прошли по цене.

**seed_sql:**

```sql
CREATE TABLE products (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(8,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0
);

INSERT INTO products (name, price, stock) VALUES
    ('Коврик для мыши', 690.00, 34),
    ('Мышь беспроводная', 1290.50, 12),
    ('Клавиатура механическая', 4990.00, 0),
    ('Монитор 27"', 15990.00, 3),
    ('Кабель HDMI 2 м', 450.00, 51),
    ('Веб-камера', 2450.00, 12);
```

**expected_rows:**

| name        | price    | stock |
| ----------- | -------- | ----- |
| Монитор 27" | 15990.00 | 3     |
| Веб-камера  | 2450.00  | 12    |

**runtime:** mysql

### Задание 2: Столицы с лета

Скобки в деле: OR внутри, AND снаружи, плюс дата.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT name, city, registered_at FROM customers WHERE (city = 'Москва' OR city = 'Санкт-Петербург') AND registered_at >= '2026-06-01' ORDER BY id; -->

**statement:**

В таблице `customers` шесть покупателей с датами регистрации. Выведите
имя, город и дату регистрации покупателей **из Москвы или из
Санкт-Петербурга**, зарегистрированных **не раньше 2026-06-01**, — name,
city, registered_at, в порядке id.

**expected_result_text:**

Финальный SELECT возвращает две строки: Мария и Пётр. Иван (Казань) и
Ольга (Новосибирск) исключены городом, Дмитрий — датой. Анна из Москвы,
но зарегистрирована 2026-05-28: без скобок сервер сгруппировал бы
`city = 'Москва' OR (city = 'Санкт-Петербург' AND ...)` и вернул бы её —
скобки удерживают фильтр по дате над обоими городами.

**seed_sql:**

```sql
CREATE TABLE customers (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    city VARCHAR(50) NOT NULL,
    registered_at DATE NOT NULL
);

INSERT INTO customers (name, city, registered_at) VALUES
    ('Анна Петрова', 'Москва', '2026-05-28'),
    ('Иван Сидоров', 'Казань', '2026-06-02'),
    ('Мария Волкова', 'Москва', '2026-06-15'),
    ('Дмитрий Козлов', 'Санкт-Петербург', '2026-05-30'),
    ('Ольга Смирнова', 'Новосибирск', '2026-07-05'),
    ('Пётр Иванов', 'Санкт-Петербург', '2026-06-20');
```

**expected_rows:**

| name          | city            | registered_at |
| ------------- | --------------- | ------------- |
| Мария Волкова | Москва          | 2026-06-15    |
| Пётр Иванов   | Санкт-Петербург | 2026-06-20    |

**runtime:** mysql

### Задание 3: Не столицы, но на связи

Отрицание плюс NULL: кого исключили города, а кого — отсутствие телефона.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT name, city, phone FROM customers WHERE city <> 'Москва' AND city <> 'Казань' AND phone IS NOT NULL ORDER BY id; — эквивалентно NOT (city = 'Москва' OR city = 'Казань') AND phone IS NOT NULL -->

**statement:**

В таблице `customers` шесть покупателей; столбец `phone` необязателен.
Выведите имя, город и телефон покупателей **не из Москвы и не из
Казани**, у которых телефон указан — `phone` не NULL, — только name,
city, phone, в порядке id.

**expected_result_text:**

Финальный SELECT возвращает две строки: Дмитрий и Ольга. Анна и Мария —

бы по городу, но phone у него NULL — отсутствие ловится только IS NULL /

```sql
CREATE TABLE customers (
```

**expected_rows:**
