### Кодировка (charset): как байты превращаются в символы

**Кодировка символов** (character set, `charset`) определяет, как текстовые символы представляются в виде последовательности байт при хранении на диске и передаче по сети. Исторически самая известная проблема без правильно выбранной кодировки — «кракозябры»: текст, введённый в одной кодировке, но прочитанный так, как будто он в другой, превращается в нечитаемый набор символов. MySQL поддерживает множество кодировок (`latin1`, `ascii`, `utf8`, `utf8mb4` и другие), но для нового проекта, ожидающего работать с текстом на любом языке (включая кириллицу, эмодзи, иероглифы), рекомендованный по умолчанию выбор в MySQL 8.x — **`utf8mb4`**.

### Почему именно utf8mb4, а не просто utf8

MySQL исторически ввёл кодировку с именем `utf8` **раньше**, чем это имя стало означать полноценный стандарт Unicode UTF-8 — по историческим причинам совместимости `utf8` в MySQL до сих пор означает **усечённую** реализацию, поддерживающую только символы до 3 байт в UTF-8-представлении. Этого достаточно для большинства кириллических и латинских текстов, но недостаточно для многих символов за пределами базовой плоскости Unicode — в частности, для большинства эмодзи и некоторых редких иероглифов, которым требуется 4 байта. Попытка сохранить такой символ в столбец с кодировкой `utf8` (не `utf8mb4`) в MySQL завершится либо ошибкой, либо (в нестрогом режиме) молчаливой заменой символа на знак вопроса — оба варианта нежелательны для реального приложения, если оно вообще допускает свободный пользовательский ввод текста (например, в `reviews.body` или `customers.name`). **`utf8mb4`** («UTF-8, multi-byte, до 4 байт») — это полная, корректная реализация UTF-8 без урезания, и с версии MySQL 8.0 она стала кодировкой **по умолчанию** для новых баз данных и таблиц именно по этой причине. Устоявшаяся рекомендация — всегда явно использовать `utf8mb4`, даже если текущие данные состоят только из кириллицы и латиницы: разница в занимаемом месте на диске между `utf8` и `utf8mb4` для «обычного» текста минимальна, а риск столкнуться с ошибкой из-за неподходящего символа в пользовательском вводе — вполне реален и растёт с популярностью эмодзи в отзывах и сообщениях.

### Collation: правила сравнения и сортировки

Если кодировка определяет, *как символ хранится в байтах*, то **collation** (правило сопоставления, часто в русскоязычной практике оставляют английский термин без перевода) определяет, *как строки сравниваются и сортируются друг с другом* — то есть какая из двух строк «больше», а какая «меньше» при `ORDER BY`, и считаются ли две строки равными при `=` в `WHERE`. Для каждой кодировки MySQL предлагает несколько вариантов collation — например, для `utf8mb4` есть `utf8mb4_general_ci`, `utf8mb4_unicode_ci`, `utf8mb4_0900_ai_ci` (последний — рекомендованный по умолчанию для MySQL 8.0, основанный на актуальном алгоритме сортировки Unicode) и другие.

### Суффиксы _ci, _cs, _ai: что они означают

Суффиксы в имени collation расшифровывают конкретные правила сравнения:

- **`_ci`** (case-insensitive) — сравнение **без учёта регистра**: `'Клавиатура'` и `'клавиатура'` считаются равными строками;
- **`_cs`** (case-sensitive) — сравнение **с учётом регистра**: те же две строки считаются различными;
- **`_ai`** (accent-insensitive) — сравнение без учёта диакритических знаков (ударений, умлаутов): например, `'resume'` и `'résumé'` могут считаться равными;
- **`_as`** (accent-sensitive) — сравнение с учётом диакритических знаков, эти строки различны;
- **`_bin`** (binary) — самый строгий и самый быстрый вариант: сравнение происходит на уровне байтов исходного представления, без каких-либо лингвистических правил вообще — с этим collation регистр, диакритика, любые языковые особенности значения не имеют, важна только точная побайтовая идентичность.

Практический эффект различия видно на простом примере. Если столбец `customers.email` использует `utf8mb4_general_ci` (регистронезависимый collation), то `WHERE email = 'user@example.com'` найдёт строку со значением `'USER@Example.com'` — для многих реальных сценариев (email, логин пользователя) это правильное и ожидаемое поведение, потому что почтовые адреса традиционно считаются регистронезависимыми на уровне домена. Но если по недосмотру тот же регистронезависимый collation используется для столбца, где регистр значим содержательно (например, кода купона `PROMO2026` против `promo2026`, если это разные, отдельно учитываемые купоны), результат может оказаться неожиданным для того, кто не задумывался об этом при проектировании схемы.

### Явное указание кодировки и collation

Кодировка и collation задаются на трёх уровнях — сервера, базы данных и конкретного столбца (более узкий уровень переопределяет более широкий, если указан явно):

```sql
CREATE DATABASE shop
CHARACTER SET utf8mb4
COLLATE utf8mb4_0900_ai_ci;

CREATE TABLE customers (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL COLLATE utf8mb4_general_ci,
    city VARCHAR(100),
    registered_at DATETIME NOT NULL
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

Здесь для столбца `email` явно указан отдельный collation (`utf8mb4_general_ci`), отличный от collation таблицы по умолчанию — это осознанное решение для конкретного столбца, для которого регистронезависимость логически обоснована, тогда как остальные текстовые столбцы таблицы наследуют collation, заданный на уровне таблицы.

### CONVERT: явное преобразование строки в другую кодировку

Функция `CONVERT(значение USING кодировка)` явно преобразует строковое значение в другую кодировку — типичный сценарий использования — сравнение или соединение (`JOIN`) столбцов из таблиц, изначально созданных с разными кодировками (что реально встречается в базах данных, которые росли и эволюционировали годами, до того как весь проект унифицировали на `utf8mb4`):

```sql
SELECT c.name
FROM customers c
WHERE CONVERT(c.city USING utf8mb4) = 'Москва';
```

Отдельно от `CONVERT` для смены кодировки существует конструкция `CAST(значение AS CHAR CHARACTER SET кодировка)`, решающая ту же задачу другим синтаксисом, — обе формы равнозначны по эффекту, выбор между ними обычно определяется стилем конкретного проекта или удобством внутри более сложного выражения.

### Практическая проблема: ошибка сравнения из-за разных collation

Наиболее частый практический симптом, с которым сталкивается разработчик при смешивании кодировок/collation в одной базе — ошибка вида `Illegal mix of collations` при попытке сравнить или соединить (`JOIN`) два строковых значения с разными collation:

```sql
-- Ошибка, если orders.customer_note использует utf8mb4_general_ci,
-- а customers.name — utf8mb4_0900_ai_ci
SELECT *
FROM orders o
INNER JOIN customers c ON o.customer_note = c.name;
```

Решение — либо унифицировать collation на уровне схемы (предпочтительный, системный подход — привести все текстовые столбцы проекта к единому collation при проектировании, чтобы такая ошибка не возникала вовсе), либо точечно привести одну из сторон сравнения к нужному collation прямо в запросе через `CONVERT` или явное указание `COLLATE` в самом выражении:

```sql
SELECT *
FROM orders o
INNER JOIN customers c
    ON o.customer_note COLLATE utf8mb4_0900_ai_ci = c.name;
```

### Кириллица и производительность сравнения

Отдельная практическая тонкость: `_unicode_`/`_0900_`-варианты collation, реализующие полноценные лингвистические правила сортировки (в том числе корректный алфавитный порядок для кириллицы, учёт особенностей конкретных языков), несколько медленнее при сравнении и сортировке, чем `_general_` или, тем более, `_bin`-варианты, которые используют упрощённые или чисто байтовые правила. Для большинства таблиц с текстом на кириллице этой разницей в реальной практике можно пренебречь — она становится заметна только на очень больших объёмах данных с интенсивной сортировкой строковых столбцов; упоминание этого факта здесь — не руководство к действию «всегда используйте `_bin`», а контекст для осознанного, а не случайного выбора конкретного collation, если производительность сортировки строковых столбцов действительно стала измеримой проблемой (способ измерить эту проблему — `EXPLAIN`/`EXPLAIN ANALYZE` из второго урока этого уровня, показывающие реальное время выполнения операции сортировки).

### Резюме

- **Кодировка** (`charset`) определяет, как символы представлены в байтах при хранении; **`utf8mb4`** — полная, не урезанная реализация UTF-8 (до 4 байт на символ), рекомендованная по умолчанию для новых баз в MySQL 8.x — в отличие от исторического, урезанного до 3 байт `utf8`, который может не вместить некоторые символы (в частности, многие эмодзи).
- **Collation** определяет правила *сравнения и сортировки* строк — какая строка «больше», а какие строки считаются равными; для одной кодировки доступно несколько collation с разными правилами.
- Суффиксы: **`_ci`**/**`_cs`** — без учёта/с учётом регистра; **`_ai`**/**`_as`** — без учёта/с учётом диакритики; **`_bin`** — побайтовое сравнение без лингвистических правил вообще, самый строгий и быстрый вариант.
- Кодировка и collation задаются на уровне сервера, базы данных, таблицы и отдельного столбца — более узкий уровень переопределяет более широкий; осознанный выбор collation для конкретного столбца (например, регистронезависимость для email) — распространённая и разумная практика.
- **`CONVERT(значение USING кодировка)`** (и равнозначный `CAST(... AS CHAR CHARACTER SET ...)`) явно преобразует строку в другую кодировку — типично нужно при работе со старыми таблицами, созданными с разными кодировками/collation.
- Смешивание разных collation в одном сравнении или `JOIN` порождает ошибку `Illegal mix of collations` — решается унификацией collation на уровне схемы или явным `COLLATE`/`CONVERT` в самом запросе.
- Лингвистически полные collation (`_unicode_`/`_0900_`) чуть медленнее упрощённых/байтовых при сортировке — заметно только на больших объёмах и не повод отказываться от корректной лингвистической сортировки по умолчанию.

## Теоретические задания

### Вопрос 1: Чем `utf8mb4` отличается от `utf8` в MySQL?

- ✅ `utf8` — исторически урезанная реализация UTF-8 с потолком в 3 байта на символ (не вместит многие эмодзи); `utf8mb4` — полная реализация до 4 байт
<!-- utf8mb4 — кодировка по умолчанию для новых баз начиная с MySQL 8.0 -->
- ❌ `utf8mb4` нужен для кириллицы, `utf8` — только для латиницы — error_text: И кириллица, и латиница кодируются максимум 2–3 байтами и поддерживаются обеими кодировками. Разница проявляется на символах вне базовой плоскости Unicode — прежде всего на эмодзи и некоторых иероглифах, требующих 4 байта.
- ❌ `utf8` не поддерживает кириллицу вообще — error_text: Поддерживает: кириллица укладывается в 2 байта UTF-8 и входит даже в урезанную реализацию. Слабое место `utf8` — не кириллица, а 4-байтовые символы вроде большинства эмодзи.
- ❌ Ничем, кроме имени: обе кодировки реализуют полный UTF-8 — error_text: В MySQL имя `utf8` не равно стандартному UTF-8: это усечённая реализация до 3 байт на символ, сохранённая ради исторической совместимости. Полный UTF-8 в MySQL — это именно `utf8mb4`, и с версии 8.0 она стала кодировкой по умолчанию.

### Вопрос 2: Что определяет collation — в отличие от кодировки?

- ✅ Правила сравнения и сортировки строк: какие строки считаются равными при `=` и какая «больше» при `ORDER BY`
<!-- кодировка — как символы хранятся в байтах; collation — как строки сравниваются -->
- ❌ Способ представления символов в байтах при хранении — error_text: Это определение кодировки (charset), а не collation. Кодировка отвечает за хранение, collation — за сравнение; смешение этих двух ролей — корень большинства недоразумений темы.
- ❌ Максимальную длину строки в байтах — error_text: Байтовый объём значения определяют тип столбца и кодировка. Collation на хранение не влияет вообще — только на результат `=`, `<>`, `ORDER BY` и подобных строковых операций.
- ❌ Совместимость сервера с внешними приложениями и драйверами — error_text: Совместимость с клиентами — свойство кодировки соединения и клиентского протокола. Collation живёт внутри сервера и определяет сравнение строк между собой, а не обмен данными с внешним миром.

### Вопрос 3: Столбец `promo_code` использует `utf8mb4_0900_ai_ci`. Найдёт ли `WHERE promo_code = 'promo2026'` строку со значением `'PROMO2026'`?

- ✅ Найдёт: `_ci` не различает регистр, и строки считаются равными
<!-- регистронезависимость удобна для email/логинов и опасна, когда регистр в кодах содержательно значим -->
- ❌ Не найдёт: это разные строки — error_text: Различение регистра — поведение `_cs`-collation. Здесь же `ai_ci` — акценто- и регистронезависимое сравнение, при котором `'promo2026'` и `'PROMO2026'` равны. Для кодов купонов, где регистр содержательно значим, такой collation — ошибка проектирования из материала.
- ❌ Возникнет ошибка `Illegal mix of collations` — error_text: Эта ошибка возникает при сравнении значений с разными collation — например, столбцов двух по-разному настроенных таблиц в `JOIN`. Здесь обе стороны сравнения приводятся к collation столбца: конфликтовать нечему.
- ❌ Зависит от кодировки столбца: utf8mb4 различает регистр — error_text: Регистрочувствительность определяется не кодировкой, а collation: у одной кодировки utf8mb4 есть и `_ci`, и `_cs`, и `_bin`-варианты. Кодировка лишь хранит символы; равенство строк задаёт collation.

### Вопрос 4: Что означает суффикс `_bin` в имени collation (например, `utf8mb4_bin`)?

- ✅ Побайтовое сравнение без лингвистических правил: важна только точная последовательность байтов — регистр и диакритика различаются
<!-- самый строгий и одновременно самый быстрый вариант сравнения -->
- ❌ Сравнение по алфавиту без учёта регистра — error_text: Это описание `_ci`. `_bin` различает всё подряд: «Клавиатура» и «клавиатура» — разные строки, потому что различаются их байтовые представления; никакие лингвистические правила не применяются.
- ❌ Сравнение двоичных данных — BLOB, к текстовым столбцам неприменимо — error_text: `_bin`-collation существует именно для текстовых столбцов и сравнивает байты их представления в кодировке столбца. BLOB — отдельный тип данных; текстовый столбец с `_bin` остаётся текстовым.
- ❌ Устаревший вариант, не поддерживаемый в MySQL 8 — error_text: `_bin` — полноценный актуальный вариант: самый строгий и при этом самый быстрый, потому что сравнение идёт по байтам без лингвистических алгоритмов. В MySQL 8 он полностью поддерживается.

### Вопрос 5: Из-за чего возникает ошибка `Illegal mix of collations`?

- ✅ Из-за сравнения или `JOIN` строковых значений с разными collation без явного приведения к общему
<!-- лечение — CONVERT/COLLATE в запросе или унификация collation на уровне схемы -->
- ❌ Из-за вставки эмодзи в столбец с кодировкой `utf8` — error_text: Это другая проблема: 4-байтовый символ не влезает в урезанную кодировку, и в строгом режиме вставка завершится ошибкой кодировки. `Illegal mix of collations` — про несовместимые правила сравнения в одном выражении, а не про невозможность сохранить символ.
- ❌ Из-за несовпадения кодировок клиента и сервера — error_text: Кодировка соединения влияет на передачу текста между клиентом и сервером (не угадали — получили кракозябры), но не порождает эту ошибку. Она возникает внутри SQL — при сравнении столбцов с разными collation.
- ❌ Из-за `ORDER BY` по текстовому столбцу с collation `_ci` — error_text: Сортировка текста с единым collation работает штатно. Ошибка появляется, только когда в одном выражении встречаются значения с несовместимыми collation — типично при `JOIN` таблиц, созданных с разными настройками.
