### Зачем этот урок

Уровень «Начинающий» собирал всё по кусочкам: один урок — одна
конструкция, одна идиома, одна ловушка. На «Среднем» уровне

туда переходить, нужно собрать всё пройденное в один цельный
отчёт, как в реальной магазинной задаче.

Сегодняшний мини-проект — четыре сквозных отчёта на едином датасете
из шести: покупатели, заказы, позиции, товары, категории,
сотрудники. В практику войдут паттерны двух из них — Отчёта 2

два показаны как образцы, не как задания. Заказы и позиции — уже знакомая модель из уроков 13–15.
Категории — из уроков 11 и 15. Сотрудники — из уроков 12 и 15.
К этим таблицам мы вернёмся и на «Среднем» уровне; сегодня —

### Отчёт 1: выручка по месяцам

Первый отчёт — классика аналитики: «сколько магазин заработал
по месяцам». Здесь сходятся три вещи: ключ месяца из даты,
группировка по этому ключу, агрегат `SUM(quantity * price)`.

```sql
SELECT DATE_FORMAT(o.created_at, '%Y-%m') AS month,
       COUNT(DISTINCT o.id) AS orders_count,
       SUM(oi.quantity * oi.price) AS revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY DATE_FORMAT(o.created_at, '%Y-%m')
ORDER BY month;
```

```text
+---------+--------------+---------+
| month   | orders_count | revenue |
+---------+--------------+---------+
| 2026-06 |            2 | 8561.00 |
| 2026-07 |            3 | 5880.50 |
+---------+--------------+---------+
```

Июнь: 2 заказа на 8561.00. Июль: 3 заказа на 5880.50. Сумма —
`SUM(quantity * price)` по позициям, как в уроке 15 на примере
`line_total`. Месячный ключ строит `DATE_FORMAT` урока 5
«Начинающего»: `'%Y-%m'` даёт «2026-06», «2026-07» — формат для
сортировки по алфавиту и группировки «по году-месяцу».

`COUNT(DISTINCT o.id)` — заказы, а не позиции: у заказа №2 две
позиции, и если бы считали `COUNT(*)`, заказ №2 дал бы +1 к июню
за каждую позицию. `DISTINCT` решает эту двойку — урок 3
«Начинающего». Логика отчёта «заказов в месяце» против
«позиций в месяце» — это вопрос бизнес-логики: в одних отчётах считают
заказы, в других — позиции, и SQL эту разницу не разрулит без
нашего указания.

Этот же отчёт естественно строит «деревом»: `SUM(oi.quantity *
oi.price)` — сумма построчных умножений урока 3. Агрегат `SUM`
урока 8 «Начинающего» сводит строки позиций в одно число на
группу. `GROUP BY` урока 9 — закрытый список SELECT (`month` и
агрегаты), `ORDER BY` урока 9 «Основ» — сортировка по месячному
ключу. Шесть этажей конвейера урока 6 «Начинающего» работают как
часы.

### Отчёт 2: топ-категории по выручке

Второй отчёт — «категории товаров, ранжированные по выручке».
Здесь цепочка JOIN из четырёх таблиц (`order_items → products →
categories`) и группировка по категории.

```sql
SELECT c.name AS category,
       SUM(oi.quantity * oi.price) AS revenue,
       SUM(oi.quantity) AS units_sold
FROM order_items AS oi
JOIN products AS p ON p.id = oi.product_id
JOIN categories AS c ON c.id = p.category_id
GROUP BY c.id, c.name
ORDER BY revenue DESC;
```

```text
+------------+---------+-------------+
| category   | revenue | units_sold |
+------------+---------+-------------+
| Клавиатуры | 4990.00 |           1 |
| Мыши       | 4321.50 |           4 |
| Аксессуары | 2670.00 |           3 |
| Коврики    | 2460.00 |           4 |
+------------+---------+-------------+
```

Цепочка JOIN урока 15: `order_items` кладёт позиции, `products`
 подтягивает имя и категорию, `categories` — имя категории. На
каждом шаге ON ссылается на ключ присоединяемой таблицы:
`oi.product_id = p.id`, потом `c.id = p.category_id`. Закрытый
список SELECT урока 9: `c.id`, `c.name` — зерно отчёта,
остальное — агрегаты.

«Клавиатуры» лидируют за счёт одной дорогой позиции — 4990.00
одним ударом. «Мыши» собраны из четырёх позиций двух разных
товаров; средняя цена позиции ниже, но объём компенсирует.
USB-хаб находится непосредственно в категории «Аксессуары»
(`category_id = 2`). «Коврики» — дочерняя категория «Аксессуаров»
(`parent_id = 2`), и их выручка считается отдельно: обычный JOIN
по `category_id` не складывает родителя и потомков автоматически.
Студент видит, что наличие `parent_id` само по себе не означает
рекурсивной агрегации дерева — для этого нужен рекурсивный CTE,
средний уровень.

### Отчёт 3: покупатели с ценовыми сегментами

Третий отчёт — пример «бизнес-логики в SELECT»: разбиваем
покупателей на сегменты по объёму покупок. Здесь встречаются
JOIN, GROUP BY, агрегаты и CASE WHEN урока 7.

```sql
SELECT c.name AS customer,
       COUNT(DISTINCT o.id) AS orders_count,
       SUM(oi.quantity * oi.price) AS total_spent,
       CASE
           WHEN SUM(oi.quantity * oi.price) >= 5000 THEN 'крупный'
           WHEN SUM(oi.quantity * oi.price) >= 2000 THEN 'средний'
           ELSE 'мелкий'
       END AS segment
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY c.id, c.name
HAVING COUNT(DISTINCT o.id) >= 1
ORDER BY total_spent DESC;
```

```text
+----------------+--------------+-------------+----------+
| customer       | orders_count | total_spent | segment  |
+----------------+--------------+-------------+----------+
| Анна Петрова   |            2 |     8561.00 | крупный  |
| Иван Сидоров   |            2 |     3700.00 | средний  |
| Мария Волкова  |            1 |     2180.50 | средний  |
+----------------+--------------+-------------+----------+
```

Здесь три конструкции пройденного уровня встречаются на одном
этаже SELECT:

- **CASE WHEN** урока 7 — порядок WHEN важен: условия проверяются
  сверху вниз, первое сработавшее и есть результат. «Анна»
  проходит первое WHEN (>= 5000) и получает «крупный»; «Иван»
  и «Мария» — нет, проходят второе WHEN (>= 2000) и получают
  «средний»; никто из показанных не падает до ELSE.
- **Агрегаты в CASE WHEN** — обе ссылки используют один и тот же
  агрегатный показатель группы; в тексте запроса выражение
  приходится повторить (физически оптимизатор может вычислить
  его один раз и переиспользовать, но это деталь реализации, не
  гарантия SQL). Ссылаться на алиас `total_spent` в CASE нельзя —
  алиас SELECT ещё не существует на этаже CASE (урок 6). Поэтому
  приходится повторить выражение `SUM(oi.quantity * oi.price)`.
  Это шум, но он ожидаемый.
- **HAVING вместо WHERE** урока 10: в этом запросе HAVING избыточен —
  INNER JOIN урока 13 уже исключил покупателей без заказов до
  GROUP BY. Он оставлен намеренно как демонстрация фильтрации
  групп; при LEFT JOIN такое условие стало бы содержательно
  полезным. Если бы использовался LEFT JOIN (Пётр в результате с
  NULL), HAVING отсёк бы его по `COUNT(o.id) >= 1` (считая по
  `o.id`, не по `*` — урок 14: `COUNT(*)` на LEFT JOIN считает
  «пустые пары»).

Тот же отчёт с LEFT JOIN дал бы четыре строки, и `HAVING COUNT(o.id) >= 1`,
считая по `o.id` — не по `*`, оставил бы только реальных
покупателей: Петра с NULL в `o.id` отсёк бы счётчик. Урок 14
напомнил, что `COUNT(*)` на LEFT JOIN считает «пустые пары», а
`COUNT(o.id)` — только реальные.

### Отчёт 4: оргсхема + мини-аналитика по сотрудникам

Последний штрих мини-проекта — self-join урока 15 в сочетании с
агрегатами урока 8: «у каждого руководителя — сколько
непосредственных подчинённых». Здесь две роли одной таблицы +
GROUP BY + HAVING.

```sql
SELECT m.name AS manager,
       COUNT(e.id) AS subordinates_count
FROM employees AS m
JOIN employees AS e ON e.manager_id = m.id
GROUP BY m.id, m.name
HAVING COUNT(e.id) > 0
ORDER BY subordinates_count DESC, m.id;
```

```text
+----------------+--------------------+
| manager        | subordinates_count |
+----------------+--------------------+
| Ольга Смирнова |                  2 |
| Игорь Морозов  |                  2 |
+----------------+--------------------+
```

Self-join урока 15: `employees` под именем `m` (менеджер) и под
именем `e` (сотрудник); `e.manager_id = m.id` соединяет
подчинённого с его руководителем. INNER JOIN отсеивает тех, у
кого нет подчинённых: Анна, Иван и Мария сами никого не
руководят, и в результате их нет. HAVING `> 0` — лишняя строка
для INNER-результата (строки без подчинённых уже отсеяны), но
она показывает, как фильтровать по группам, если бы мы взяли
LEFT JOIN, чтобы видеть всех руководителей (включая тех, у кого
подчинённых нет, с 0).

Такой же приём с LEFT JOIN:

```sql
SELECT m.name AS manager,
       COUNT(e.id) AS subordinates_count
FROM employees AS m
LEFT JOIN employees AS e ON e.manager_id = m.id
GROUP BY m.id, m.name
ORDER BY subordinates_count DESC, m.id;
```

```text
+----------------+--------------------+
| manager        | subordinates_count |
+----------------+--------------------+
| Ольга Смирнова |                  2 |
| Игорь Морозов  |                  2 |
| Анна Петрова   |                  0 |
| Иван Сидоров   |                  0 |
| Мария Волкова  |                  0 |
+----------------+--------------------+
```

Здесь `COUNT(e.id)` — не `COUNT(*)`: у Анны, Ивана и Марии нет
подчинённых, поэтому `e.id` для них NULL, и `COUNT(e.id)`
возвращает 0 (урок 14). `COUNT(*)` бы дал 1 для каждого из них,
потому что «пустая пара» в LEFT JOIN — это всё равно строка.

### Сводный отчёт: всё вместе

Если собрать четыре отчёта на едином датасете, получается полная
картина магазина: «кто покупает, что покупают, когда, в каких
категориях, и кто из сотрудников обрабатывает». Всё это —
комбинация JOIN, GROUP BY, агрегатов, HAVING, CASE WHEN и дат.
Никаких новых конструкций; всё — на пройденном уровне.

На среднем уровне этот же набор отчётов можно будет построить
иначе: через подзапросы (урок 1 «Среднего»), CTE (урок 4),
оконные функции (уроки 5–6). Там же появятся вопросы
производительности: индексы на столбцах соединения, планы
запросов. Сегодня — фундамент: что вообще можно собрать из
пройденных кусочков.

### Типичные ошибки мини-проекта

Всё, что мы разбирали по кусочкам, встречается теперь в одном
запросе — и шансы ошибиться выше.

**Забытый `GROUP BY` при агрегатах.** Если в SELECT появился
`SUM(...)`, но GROUP BY нет, MySQL вернёт одну свёрнутую строку
для всей таблицы. Ошибка 1140 из урока 8 «Начинающего» —
защита, но не для всех выражений. Привычка: посчитал агрегат —
проверь, что зерно отчёта стоит и в SELECT, и в GROUP BY.

**Алиас `total_spent` в `CASE`.** Алиас SELECT существует только
после этажа SELECT, а CASE — внутри SELECT. Использовать алиас
в CASE нельзя; нужно повторить выражение. Это не оптимизация —
это правило порядка выполнения (урок 6 «Начинающего»).

**`COUNT(*)` вместо `COUNT(правый.pk)` на LEFT JOIN.** Урок 14:
`COUNT(*)` считает строки группы, в том числе «пустые пары»;
`COUNT(правый.pk)` считает только реальные совпадения. В нашем
примере с оргсхемой LEFT JOIN это бы дало «1 подчинённый» у
каждого рядового сотрудника — неверно.

**Фильтр по правой таблице в WHERE при LEFT JOIN.** Урок 14
же: `WHERE e.salary > 1000` после LEFT JOIN отсеял бы строки
без подчинённых, превратив LEFT в INNER. В нашем `manager_id`
примере это бы выкинуло руководителей без подчинённых —
возможно, как раз тех, ради кого запрос строился.

**Случайный `*` в SELECT.** В агрегированном запросе `SELECT *`
почти всегда приводит к тому, что в SELECT попадают
неагрегированные столбцы, которые не покрыты GROUP BY: при
дефолтном `sql_mode` MySQL 8 это даёт ошибку (1140 при отсутствии
GROUP BY или 1055, если GROUP BY есть, но не покрывает все
неагрегированные столбцы SELECT). Привычка: всегда перечислять
столбцы явно.

### Чего в этом уроке нет

- Подзапросы и CTE — средний уровень, уроки 1–4 «Среднего».
- Оконные функции (ROW_NUMBER, LAG, накопительные суммы) —
  средний уровень, уроки 5–6.
- Рекурсивные CTE для обхода деревьев любой глубины — средний
  уровень, урок 4.
- Индексы на столбцах соединения и планы запросов (EXPLAIN) —
  продвинутый уровень, блок производительности.
- Производственные таблицы `payments` и `reviews` —
  упоминались в платформенной модели урока 11, но на уровне
  «Начинающий» мы их ещё не вводили; они появятся позже, когда
  понадобятся для среднего уровня.

### Резюме

- Мини-проект собирает пройденное: JOIN, GROUP BY, агрегаты,
  HAVING, CASE WHEN, функции дат. Никаких новых конструкций —
  только комбинации того, что было разобрано по кусочкам.
- Выручка по месяцам: `DATE_FORMAT(..., '%Y-%m')` как месячный
  ключ урока 5 + `SUM(oi.quantity * oi.price)` как свёртка
  строк позиций в одно число на группу. `COUNT(DISTINCT o.id)` —
  число заказов, не позиций.
- Топ-категории по выручке: цепочка JOIN из `order_items`,
  `products`, `categories` урока 15; GROUP BY по категории;
  ORDER BY по убыванию выручки.
- Покупатели с сегментами: CASE WHEN поверх агрегата, тот же
  `SUM(...)` повторяется в SELECT и в WHEN. Алиас SELECT в CASE
  использовать нельзя (урок 6).
- Self-join + GROUP BY: две роли одной таблицы через алиасы;
  `COUNT(правый.pk)` на LEFT JOIN считает только реальные
  совпадения (урок 14).
- HAVING vs WHERE: HAVING фильтрует группы после агрегации,
  WHERE — строки до. В нашем проекте INNER JOIN отсеивает
  лишнее до GROUP BY, и HAVING становится страховкой; с LEFT
  JOIN HAVING был бы осмысленным фильтром.
- Типичные ошибки мини-проекта: забытый GROUP BY, алиас в CASE,
  COUNT(*) на LEFT JOIN, фильтр правой таблицы в WHERE,
  случайный `*` в SELECT — все из пройденных уроков.
- Граница уровня: подзапросы, CTE, оконные функции, рекурсия,
  индексы и планы запросов — на «Среднем» уровне и далее.

## Теоретические задания

### Вопрос 1: Какой `DATE_FORMAT` даст ключ «год-месяц» для группировки выручки по месяцам?

- ✅ `DATE_FORMAT(o.created_at, '%Y-%m')`
<!-- стандартный формат ISO для сортировки строкой и для визуального разбора; урок 5 «Начинающего» -->
- ❌ `DATE_FORMAT(o.created_at, '%M %Y')` — error_text: `%M %Y` даёт название месяца текстом (June 2026), поэтому сортировка по строке не совпадает с календарным порядком даже в пределах одного года («February» по алфавиту раньше «January», хотя январь идёт раньше февраля). Формат `'%Y-%m'` сохраняет хронологический порядок при обычной строковой сортировке.
- ❌ `DATE(o.created_at)` — error_text: DATE вернёт полную дату '2026-06-28' — это группировка по дню, а не по месяцу. Месячный ключ требует отбросить день.
- ❌ `EXTRACT(MONTH FROM o.created_at)` — error_text: даст число от 1 до 12, но не различает годы; для июня 2026 и июня 2027 ключ будет одинаковым. '%Y-%m' фиксирует и год, и месяц.

### Вопрос 2: В отчёте «покупатели с ценовыми сегментами» хочется отфильтровать группы, у которых `total_spent` больше нуля. Какой инструмент использовать?

- ✅ `HAVING SUM(...) > 0` — после GROUP BY фильтрует готовые группы
<!-- HAVING урока 10: фильтр групп, после агрегации -->
- ❌ `WHERE SUM(...) > 0` — error_text: WHERE видит строки до группировки — он не может ссылаться на агрегат, потому что агрегата ещё нет. MySQL отвергнет это с ошибкой 1111 или вернёт не то.
- ❌ `CASE WHEN SUM(...) > 0` в SELECT — error_text: CASE в SELECT строит колонку, а не фильтрует строки. Группа с total_spent = 0 всё равно появится в результате — просто со значением 'мелкий' (или NULL без ELSE). Фильтр групп — это HAVING.
- ❌ `LIMIT` — error_text: LIMIT режет уже готовый результат, но не выбрывает по значению агрегата. Если сортировка по total_spent DESC, LIMIT 1 даст верхнюю строку — не то же самое, что отбросить нулевые.

### Вопрос 3: Что вернёт `SELECT c.name, SUM(oi.quantity * oi.price) AS revenue FROM order_items AS oi JOIN products AS p ON p.id = oi.product_id JOIN categories AS c ON c.id = p.category_id` без GROUP BY при дефолтном `sql_mode` MySQL 8?

- ✅ ошибку 1140: неагрегатный столбец `c.name` не покрыт GROUP BY
<!-- 1140 возникает при попытке вернуть неагрегатный столбец без группировки: MySQL не знает, какое из значений `c.name` показать для одной свёрнутой строки -->
- ❌ одну строку с суммой по всем категориям — error_text: так бывает, если убрать `c.name` из SELECT — остался бы только агрегат, и запрос вернул бы одну свёрнутую строку. С `c.name` MySQL отказывается: одно имя не соответствует одной свёртке.
- ❌ строку на каждую категорию, как обычно — error_text: для этого нужен `GROUP BY c.id, c.name` (или `GROUP BY c.name` — функциональная зависимость от PK в MySQL 8 не всегда выводится автоматически). Без GROUP BY такого результата не получить.
- ❌ NULL для неизвестных групп — error_text: NULL-группа — это когда GROUP BY явно содержит выражение с NULL; здесь запрос просто не дойдёт до результата, потому что нечем сгруппировать.

### Вопрос 4: В `SELECT c.name, COUNT(o.id) FROM customers c LEFT JOIN orders o ON o.customer_id = c.id GROUP BY c.name` что покажет `COUNT(o.id)` для покупателя без заказов?

- ✅ 0 — `COUNT(o.id)` считает только не-NULL значения `o.id` (урок 14)
<!-- NULL в агрегатах не считается; LEFT JOIN подставил NULL в o.id для пустой пары -->
- ❌ 1 — error_text: 1 был бы у `COUNT(*)` — он считает строки, и «пустая» пара из LEFT JOIN — это строка. `COUNT(o.id)` же считает только не-NULL значения столбца.
- ❌ NULL — error_text: COUNT возвращает число; NULL в COUNT не «заразен» — функция возвращает число строк или число значений, никогда не NULL.
- ❌ ошибку «column ... is ambiguous» — error_text: 1052 — про одинаковые столбцы в SELECT; здесь `c.name` и `o.id` уточнены алиасами, неоднозначности нет.

### Вопрос 5: В `SELECT m.name, COUNT(e.id) FROM employees m LEFT JOIN employees e ON e.manager_id = m.id GROUP BY m.name` — зачем здесь два алиаса одной таблицы?

- ✅ чтобы различить роли одной таблицы: «менеджер» и «подчинённый» — это разные роли, и без разных имён MySQL выдаст ошибку 1066
<!-- self-join требует двух ролей; 1066 Not unique table/alias без алиасов -->
- ❌ для ускорения запроса — error_text: производительность JOIN — отдельная тема продвинутого уровня. Алиасы нужны для читаемости и разрешения имён, не для скорости.
- ❌ для сортировки — error_text: алиасы не влияют на сортировку; ORDER BY работает с выражениями и столбцами независимо от алиасов.
- ❌ это требование SQL-стандарта — error_text: стандарт разрешает запрос `FROM employees JOIN employees ON ...`, но MySQL в этом случае выдаст 1066 на этапе разбора FROM — до любой стандартной логики. Это техническая причина MySQL, не «требование стандарта».
