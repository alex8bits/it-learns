### Граница между JOIN, подзапросами и UNION

В уроке 13 «Начинающего» появился `INNER JOIN` — **горизонтальное**
комбинирование: рядом с каждой строкой левой таблицы становятся
столбцы подходящих строк правой. Каждая строка результата живёт на
стыке двух сущностей.

Урок 1 «Среднего» добавил подзапросы — **вложенное** комбинирование:
один SELECT работает **внутри** другого как число, список или
таблица. Строка результата внешнего запроса и строка результата
внутреннего — это разные строки разных конвейеров; «комбинирование»
здесь не означает склейку строк в один набор, а использование
результата одного запроса как параметра другого.

Сегодня — `UNION` и `UNION ALL` — **вертикальное** комбинирование:
два (или более) SELECT-результата ставятся друг под другом, как
страницы из двух отчётов сшиты в одну стопку. Строки результата
состоят из строк первого и последующих `SELECT`. Если нужен
определённый порядок, его задают внешним `ORDER BY`. Схема таблицы
результата — общая: число столбцов и их типы должны совпадать у
всех запросов-участников.

Три оси одного языка:

- `JOIN` — горизонтально: столбцы рядом. `JOIN` меняет **ширину**
  результата.
- Подзапрос — вложенно: SELECT внутри другого SELECT.
- `UNION` — вертикально: стопка результатов нескольких запросов.
  `UNION` меняет **высоту** результата — строки ставятся друг под
  другом.

Каждая ось закрывает свой класс задач; это не «три способа сделать
одно и то же».

### Актёры урока

Чтобы было что соединять по вертикали, нужны два запроса с
одинаковой формой результата, но разным содержанием. Возьмём тот же
магазин из уроков 14–16 «Начинающего» и урока 2 «Среднего»:
покупатели и заказы.

Сцена первая — **сводка по покупателям**: имя и число заказов.

```text
+----+---------------+-------------+
| id | name          | city        |
+----+---------------+-------------+
|  1 | Анна Петрова  | Москва      |
|  2 | Иван Сидоров  | Казань      |
|  3 | Мария Волкова | Самара      |
|  4 | Пётр Смирнов  | Новосибирск |
+----+---------------+-------------+

+----+-------------+------------+
| id | customer_id | created_at |
+----+-------------+------------+
|  1 |           1 | 2026-06-28 |
|  2 |           1 | 2026-06-30 |
|  3 |           2 | 2026-07-05 |
+----+-------------+------------+
```

Сцена вторая — **сводка по товарам**: имя и цена. Схема результата
та же (два текстовых/числовых столбца), но содержимое — другое
поле домена. Удобно для склейки двух мини-отчётов в один
«событийный» лог.

### UNION ALL: склейка стопкой, с дублями

`UNION ALL` ставит результат первого SELECT под результат второго.
Никакой обработки дублей — каждая строка остаётся в выходе столько
раз, сколько встретилась в исходных запросах.

Сводка по покупателям (с числом заказов через `LEFT JOIN ... COUNT`,
урок 14 «Начинающего»):

```sql
SELECT c.name AS who, COUNT(o.id) AS value
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

```text
+---------------+-------+
| who           | value |
+---------------+-------+
| Анна Петрова  |     2 |
| Иван Сидоров  |     1 |
| Мария Волкова |     0 |
| Пётр Смирнов  |     0 |
+---------------+-------+
```

Сводка по товарам (урок 1 «Среднего» — производная таблица с
`AVG(price)` по категории):

```sql
SELECT CONCAT('avg category ', category_id) AS who,
       ROUND(avg_price, 2) AS value
FROM (
    SELECT category_id, AVG(price) AS avg_price
    FROM products
    GROUP BY category_id
) AS cat;
```

Стопка — оба результата под одним заголовком. Чтобы столбец `value`
не «побеждался» `DECIMAL(10,2)` от `ROUND` и не превращал `COUNT` в
`2.00`, обе части приведены явно к целому через `CAST(... AS SIGNED)`:

```sql
SELECT c.name AS who, CAST(COUNT(o.id) AS SIGNED) AS value
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.id, c.name
UNION ALL
SELECT CONCAT('avg category ', category_id),
       CAST(ROUND(avg_price, 2) AS SIGNED)
FROM (
    SELECT category_id, AVG(price) AS avg_price
    FROM products
    GROUP BY category_id
) AS cat
ORDER BY who;
```

```text
+--------------------------+---------+
| who                      | value   |
+--------------------------+---------+
| Анна Петрова             |       2 |
| avg category 1           |     570 |
| avg category 2           |    2910 |
| avg category 3           |   15990 |
| Иван Сидоров             |       1 |
| Мария Волкова            |       0 |
| Пётр Смирнов             |       0 |
+--------------------------+---------+
```

`ORDER BY` снаружи сортирует итоговый результат UNION. Именно его
используют, если нужно задать порядок строк итоговой выборки;
порядок отдельных частей `UNION` не задаёт порядок итогового
результата.

### UNION: склейка без дублей

`UNION` (без `ALL`) делает то же, что `UNION ALL`, плюс удаляет
**полные дубли строк**. `UNION` требует дополнительной обработки
для удаления дублей; `UNION ALL` эту обработку не выполняет.
Если удалять дубли не требуется, берите `UNION ALL`: он сохраняет
исходные строки и не выполняет эту обработку.

Тот же пример с `UNION` (тот же приём с `CAST` для согласования
типов):

```sql
SELECT c.name AS who, CAST(COUNT(o.id) AS SIGNED) AS value
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
GROUP BY c.id, c.name
UNION
SELECT CONCAT('avg category ', category_id),
       CAST(ROUND(avg_price, 2) AS SIGNED)
FROM (
    SELECT category_id, AVG(price) AS avg_price
    FROM products
    GROUP BY category_id
) AS cat
ORDER BY who;
```

Результат совпадает с `UNION ALL`: в исходных данных нет совпадающих
строк («Мария Волкова» с `value = 0` не равен ни одной строке
`avg category ...`). На небольших разнородных наборах `UNION` и `UNION ALL`
часто дают одинаковый результат — но семантика разная. Если
объединяете два одинаковых по форме отчёта, где в одном из них
встречаются дубли, выбор `UNION` молча уберёт их — и отчёт
перестанет отражать данные.

### Правила совместимости

Чтобы `UNION` или `UNION ALL` работали, оба запроса-участника должны
**по форме** совпадать:

1. **Одинаковое число столбцов** в списке `SELECT`. Три столбца
   слева — три столбца справа, иначе ошибка 1222.
2. **Совместимые типы** в соответствующих позициях. MySQL при
   необходимости приводит значения к общему типу результата по
   своим правилам приведения типов. Строка и число без явного
   `CAST` — несовместимы: `UNION` в этом случае упадёт на
   нечисловом значении либо потребует явного приведения.
3. **Имена столбцов** итогового результата берутся из **первого**
   `SELECT`. Алиасы соответствующих столбцов последующих `SELECT`
   не переименовывают итоговые столбцы. Если нужен общий заголовок —
   дайте алиас в первом запросе.

Сравнение разных типов в одном столбце — самая частая ошибка:

```sql
SELECT name, price FROM products
UNION ALL
SELECT name, created_at, id FROM orders;
```

```text
ERROR 1222 (21000): The used SELECT statements have a different number of columns
```

Слева два столбца, справа три — MySQL завершается с ошибкой 1222.
Лекарство — привести обе части к одному числу столбцов и
совместимым типам. `CAST(... AS CHAR)` или `CONCAT('', ...)` помогают,
когда хочется смешать число и строку осознанно (например, собрать
«событийный лог» из разных таблиц). Слепое смешивание — почти всегда
ошибка проектирования отчёта.

### Сортировка результата UNION

Если нужен порядок итогового результата `UNION`, ставьте `ORDER BY`
после всего `UNION`, в самом конце. Порядок отдельных частей
`UNION` не задаёт порядок итогового результата. Ссылаться `ORDER BY`
должен на **алиасы первого SELECT** (или на позиции столбцов
первого SELECT). Имена столбцов второго SELECT в `ORDER BY` обычно
не работают — алиас берётся из головы стопки.

```sql
SELECT name AS who, price AS value FROM products WHERE category_id = 1
UNION ALL
SELECT name, price FROM products WHERE category_id = 2
ORDER BY who;
```

Сортировка здесь идёт по `who` — алиасу первого SELECT. Если бы
второй SELECT имел свой алиас `name`, скажем `item_name`, это бы не
помогло: `ORDER BY` снаружи видит только заголовки первого SELECT.

`LIMIT` тоже ставится снаружи, в самом конце. Полезно для
«первые N строк объединённого отчёта».

### Типичные ошибки

**Несовпадение числа столбцов.** Ошибка 1222. Самая частая.
Лекарство — явно привести обе части к одному числу и типам
(часто `SELECT NULL AS ...` или `CAST(... AS CHAR)`).

**`ORDER BY` внутри подзапроса UNION.** В большинстве случаев
отбрасывается — это часть стандарта SQL. Если нужен порядок —
`ORDER BY` ставится на весь UNION, в самом конце.

**`UNION` там, где важны дубли.** Если склеиваете два отчёта,
где один из них специально содержит повторы (например, список
заказов с одинаковыми суммами), `UNION` молча уберёт совпадающие
строки. Здесь нужен `UNION ALL`.

**`UNION` для «одинаковых таблиц» вместо `JOIN`.** Если нужно
соединить таблицу с самой собой по условию — это `JOIN` (урок 13
«Начинающего»), а не `UNION`. `UNION` склеивает результаты двух
**SELECT**, а не две таблицы в один отчёт «по строкам сущности».

**Путаница вертикального и горизонтального.** `UNION` не добавляет
столбцы — он ставит строки друг под другом. Если задача «у меня
есть таблица покупателей, и я хочу одним запросом получить и имя,
и город, и почту» — это обычный `SELECT` с тремя столбцами, не
`UNION` двух SELECT.

**Смешение целого и `DECIMAL` в `UNION`.** При `UNION ALL` столбец
получает общий приведённый тип: `DECIMAL(10,2)` «побеждает» целое,
и `COUNT` начинает выводиться как `2.00`. Если формат важен —
приведите явно через `CAST(... AS SIGNED)` или `CAST(... AS
DECIMAL(10,2))`. Это та же ловушка, что и раздел «Правила
совместимости» описывает для смешения строки и числа, только внутри
числовых типов.

### UNION, JOIN и подзапрос: сводная карта

Тот же вопрос «покупатели и их заказы» в трёх формах:

- **Горизонтально (`INNER JOIN`)**: одна строка на каждую пару
  покупатель–заказ; у Анны две строки. Столбцы обеих таблиц.
- **Вложенно (подзапрос)**: внешний запрос ссылается на агрегат
  внутреннего, например «покупатели, у которых число заказов выше
  среднего». Одна строка на покупателя.
- **Вертикально (`UNION ALL`)**: список покупателей под списком
  чего-то ещё — например, «покупатели, потом товары». Каждая
  строка результата живёт в одной из двух таблиц, не на их стыке.

`UNION` применяют, когда:
— у вас **несколько источников одной формы** (два отчёта одинаковой
структуры, и хочется один сводный лог);
— вы строите **событийный лог** из разнородных таблиц с приведённой
формой (заказы + возвраты + платежи в одну временную шкалу);
— вы делаете **стопку «лучших N»** (например, top-3 заказа и top-3
клиента одним запросом, со столбцом-меткой источника).

Другие конструкции подходят, когда задача проще решается одним
запросом с `WHERE`/`JOIN`/подзапросом. Если два `SELECT` описывают
разные сущности и при этом их столбцы имеют искусственно приведённую
форму, стоит проверить, действительно ли вертикальное объединение
отражает смысл отчёта.

### Чего в этом уроке нет

- `INTERSECT` / `EXCEPT` (вертикальная разность/пересечение) —
  в плане курса не вводятся; в MySQL 8 поддерживаются с версии 8.0.31,
  но для нашего курса это отдельная тема.
- Цепочки CTE, рекурсивные CTE, календарная таблица — урок 4
  «Среднего».
- Оконные функции (`ROW_NUMBER`, `LAG`, накопительные суммы) —
  уроки 5–6 «Среднего».
- `INSERT ... SELECT` (загрузка данных через подзапрос) — урок 7
  «Среднего».
- Сравнение производительности `UNION` vs `UNION ALL` на больших
  объёмах — продвинутый уровень, блок про индексы и `EXPLAIN`.

### Резюме

- `UNION` и `UNION ALL` склеивают результаты двух (или более)
  `SELECT` **по вертикали**: строки одного ставятся под строки
  другого.
- `UNION ALL` оставляет все строки, включая дубли. `UNION` ещё и
  удаляет полные дубли строк — если удалять дубли не требуется,
  берите `UNION ALL`: он сохраняет исходные строки и не выполняет
  эту обработку.
- Оба запроса-участника должны иметь **одинаковое число столбцов**
  и **совместимые типы**. Иначе ошибка 1222 или молчаливое
  приведение.
- `ORDER BY` и `LIMIT` ставятся **снаружи**, на весь UNION, и
  ссылаются на алиасы **первого** SELECT.
- Это третья ось после `JOIN` (горизонтально) и подзапросов
  (вложенно); не «способ заменить их», а способ собрать
  **разнородные источники одной формы** в один отчёт.

## Теоретические задания

### Вопрос 1: Чем `UNION ALL` отличается от `UNION`?

- ✅ `UNION ALL` сохраняет все строки результата, включая дубли; `UNION` дополнительно удаляет полные дубли строк
<!-- единственное содержательное различие: UNION дополнительно удаляет дубли, UNION ALL — нет -->
- ❌ `UNION ALL` сортирует строки, а `UNION` — нет — error_text: ни `UNION`, ни `UNION ALL` не сортируют результат. Сортировка задаётся явным `ORDER BY` на весь UNION в самом конце. Без внешнего `ORDER BY` порядок строк не гарантирован.
- ❌ `UNION ALL` объединяет таблицы, а `UNION` — запросы — error_text: оба оператора объединяют результаты `SELECT`, а не таблицы. Таблицы в `FROM` — это работа `JOIN`. `UNION` и `UNION ALL` имеют дело только с результатами `SELECT` и ставят их строки друг под другом.
- ❌ `UNION ALL` работает с разным числом столбцов, `UNION` — нет — error_text: оба оператора требуют одинакового числа столбцов в обеих частях (правило совместимости). Различие между ними — только в обработке дублей; число столбцов к этому не относится.

### Вопрос 2: Запрос `SELECT name FROM products WHERE category_id = 1 UNION ALL SELECT name FROM products WHERE category_id = 2`. Что вернёт запрос?

- ✅ все товары обеих категорий в одном столбце `name`; дубли, если имена совпадают, остаются
<!-- UNION ALL не удаляет дубли; порядок строк определяется ORDER BY снаружи или, при его отсутствии, выбором сервера -->
- ❌ только уникальные имена товаров — error_text: `UNION ALL` не удаляет дубли. Это делает `UNION`. Здесь использован `UNION ALL`, поэтому если в обеих категориях есть товар с одинаковым именем, он появится дважды.
- ❌ ошибку: разные категории нельзя объединять — error_text: разные категории объединять можно, если число столбцов и типы совпадают. Здесь оба запроса возвращают один столбец `name` одинакового типа — правило совместимости выполнено.
- ❌ пары `(category_id, name)` — error_text: в списке SELECT только `name`, столбец `category_id` не выбран. `UNION ALL` не «догадывается», что нужно добавить столбец из условия `WHERE`. Чтобы получить пары, нужно явно добавить `category_id` в оба SELECT.

### Вопрос 3: Что произойдёт, если в первом SELECT три столбца, а во втором — два?

- ✅ ошибка 1222: число столбцов в частях UNION должно совпадать
<!-- правило совместимости; сервер отказывается выполнять запрос -->
- ❌ сервер автоматически дополнит недостающий столбец NULL — error_text: MySQL не дополняет недостающие столбцы NULL. Это противоречило бы правилу совместимости и делало бы результат зависимым от того, в каком порядке написаны SELECT. Синтаксический отказ сразу — единственный честный вариант.
- ❌ возьмётся общий префикс из двух столбцов — error_text: сервер не «отрезает» лишние столбцы и не берёт префикс. Это исказило бы смысл запроса без явного указания автора. Ошибка 1222 — единственный правильный ответ.
- ❌ результат будет, но вторая строка выровняется по типам первой — error_text: при разном числе столбцов MySQL не выполняет запрос вообще. Никакого «выравнивания типов» при разной форме не происходит — синтаксический разбор останавливается до этапа исполнения.

### Вопрос 4: Где должен стоять `ORDER BY` для сортировки результата UNION?

- ✅ в самом конце, на весь UNION; ссылки на столбцы берутся из алиасов первого SELECT
<!-- внутренние ORDER BY в UNION не задают порядок итогового результата; сортировка результата — снаружи -->
- ❌ в каждом SELECT, который участвует в UNION — error_text: `ORDER BY` внутри отдельных частей не задаёт порядок итогового `UNION`. Если нужен порядок всего результата, сортировку задают внешним `ORDER BY` после последнего SELECT.
- ❌ только в первом SELECT, потому что порядок строк определяет голова стопки — error_text: голова стопки задаёт имена столбцов, но не порядок строк. Порядок строк UNION-результата определяется явным `ORDER BY` снаружи, на весь UNION.
- ❌ нигде, UNION не сортируется — error_text: `UNION` действительно сам по себе не сортирует, но это не отменяет возможности отсортировать результат явно. Сортировка делается через внешний `ORDER BY`, на весь UNION.

### Вопрос 5: `SELECT name FROM products UNION SELECT name FROM customers`. Что нужно, чтобы запрос был корректным?

- ✅ оба SELECT должны возвращать одинаковое число столбцов, а соответствующие столбцы должны иметь совместимые типы
<!-- products.name и customers.name — строки; число столбцов совпадает; правило совместимости выполнено -->
- ❌ запрос уже корректен без дополнительных условий — error_text: здесь достаточно проверить оба условия правила совместимости — число столбцов и типы. «Уже корректен без условий» говорит, будто проверять нечего, хотя правило именно в этой проверке.
- ❌ нужно добавить `ALL` — иначе дубли склеятся — error_text: `UNION` без `ALL` удаляет полные дубли строк, это не делает запрос некорректным. Если цель — собрать все имена и дубли безразличны, `UNION` валиден. `ALL` влияет на дубль, не на корректность.
- ❌ нужно обернуть каждый SELECT в скобки — error_text: скобки вокруг подзапросов в UNION не обязательны и не делают запрос корректным сами по себе. Корректность определяется правилом совместимости и реальной схемой таблиц.

### Задание 1: Сводка покупателей и средних по категориям

`UNION ALL` двух запросов одинаковой формы: сводка по покупателям и
сводка по категориям товаров.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT CONCAT('customer ', c.id) AS who, CAST(COUNT(o.id) AS SIGNED) AS value FROM customers AS c LEFT JOIN orders AS o ON o.customer_id = c.id GROUP BY c.id UNION ALL SELECT CONCAT('cat ', category_id) AS who, CAST(ROUND(AVG(price), 2) AS SIGNED) AS value FROM products GROUP BY category_id ORDER BY who, value DESC; -->

**statement:**

Таблицы `customers` (четыре покупателя с `id` от 1 до 4),
`orders` (три заказа: два у покупателя с `id = 1`, один у покупателя
с `id = 2`; `customer_id` объявлен `NOT NULL`) и `products` (шесть
товаров: коврик 690.00, мышь 1290.50, клавиатура 4990.00,
монитор 15990.00, кабель 450.00, веб-камера 2450.00; с
`category_id`: 1 — два товара (коврик, кабель), 2 — три товара
(мышь, клавиатура, веб-камера), 3 — один товар (монитор)).
Напишите запрос, который склеит по вертикали два мини-отчёта одним
`UNION ALL`:

1. Для каждого покупателя — строка вида `'customer <id>'` (через
   `CONCAT`) и `COUNT(o.id)` его заказов (через `LEFT JOIN` +
   `GROUP BY`). Используйте именно `COUNT(o.id)`, а не `COUNT(*)`:
   у покупателя без заказов `LEFT JOIN` оставляет одну
   `NULL`-расширенную строку, которую `COUNT(*)` посчитает как `1`.
   `COUNT(o.id)` эту строку не считает — это приём из урока 14
   «Начинающего». У покупателей без заказов должно быть `0`.
2. Обе части `UNION ALL` должны возвращать целое число: используйте
   `CAST(COUNT(o.id) AS SIGNED)` и `CAST(ROUND(AVG(price), 2) AS
   SIGNED)`. Без явного `CAST` MySQL приведёт столбец `value` к
   общему типу `DECIMAL(10,2)`, и `COUNT`-значения отобразятся как
   `2.00` — это ловушка смешения типов в `UNION` (см. «Типичные
   ошибки»).
2. Для каждой категории — строка вида `'cat <category_id>'` (через
   `CONCAT`) и `ROUND(AVG(price), 2)` по категории.

Финальный SELECT — два столбца: `who` и `value`. Отсортируйте по
`who`, при равных `who` — по убыванию `value`.

**expected_result_text:**
