### Проблема плохо спроектированной таблицы

Рассмотрим таблицу заказов, спроектированную «наивно» — со всей информацией о клиенте прямо внутри неё, без отдельной таблицы `customers`:

```sql
CREATE TABLE orders_bad (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_name VARCHAR(255),
    customer_email VARCHAR(255),
    customer_city VARCHAR(100),
    product_name VARCHAR(255),
    product_price DECIMAL(10, 2),
    quantity INT
);
```

У такой структуры сразу несколько практических проблем:

- **Аномалия обновления** (update anomaly): если у клиента поменялся email, придётся обновить его во **всех** строках `orders_bad`, где он упоминается — забыть хотя бы одну строку означает получить два разных email у одного и того же человека в одной и той же таблице, и непонятно, какой из них верный.
- **Аномалия вставки** (insertion anomaly): чтобы просто зарегистрировать нового клиента, у которого пока нет ни одного заказа, придётся вставлять «фиктивную» строку заказа — потому что данных о клиенте вне заказа в этой структуре просто негде хранить.
- **Аномалия удаления** (deletion anomaly): если удалить единственный заказ клиента (например, отменённый), пропадёт и вся информация о самом клиенте — вместе с «водой» удалится и нужные данные.
- **Избыточное дублирование**: имя, email и город клиента повторяются в каждой строке каждого его заказа — если у клиента десять заказов, его email физически хранится на диске десять раз, занимая место и создавая риск рассинхронизации.

**Нормализация** — процесс проектирования схемы таким образом, чтобы избежать этих аномалий: каждый факт о реальном мире хранится в базе данных **ровно в одном месте**, а связи между фактами выражаются через `FOREIGN KEY`, а не через повторение данных.

### 1НФ (первая нормальная форма): атомарные значения, никаких повторяющихся групп

**Первая нормальная форма** требует, чтобы каждая ячейка таблицы содержала одно **атомарное** (неделимое) значение, а не список или составную структуру, и чтобы в таблице не было повторяющихся групп столбцов вроде `product_1`, `product_2`, `product_3` для «нескольких товаров одного заказа». Пример нарушения 1НФ:

```sql
-- Нарушение 1НФ: список товаров в одной ячейке
CREATE TABLE orders_1nf_violation (
    id INT PRIMARY KEY,
    customer_id INT,
    product_ids VARCHAR(255) -- например, '5,12,7'
);
```

Столбец `product_ids`, хранящий несколько идентификаторов товаров как одну текстовую строку через запятую, нарушает атомарность: чтобы найти заказы с конкретным товаром, пришлось бы использовать текстовый поиск по подстроке (`LIKE '%,12,%'` — ненадёжная и медленная конструкция, к тому же неверно сработавшая бы для `product_ids = '5,120,7'` при поиске товара `12`), вместо простого и надёжного `WHERE product_id = 12`. Решение — именно та структура, что уже используется в сквозном датасете курса: отдельная таблица `order_items(id, order_id, product_id, quantity, price)`, где каждая строка — один товар одного заказа, и каждая ячейка содержит одно атомарное значение.

### 2НФ (вторая нормальная форма): нет частичной зависимости от части составного ключа

**Вторая нормальная форма** применима к таблицам с **составным** первичным ключом (состоящим из нескольких столбцов) и требует, чтобы каждый неключевой столбец зависел от **всего** составного ключа целиком, а не только от его части. Представим таблицу позиций заказа с составным ключом `(order_id, product_id)`, куда по ошибке добавили название товара:

```sql
-- Нарушение 2НФ
CREATE TABLE order_items_2nf_violation (
    order_id INT,
    product_id INT,
    quantity INT,
    product_name VARCHAR(255), -- зависит только от product_id, не от order_id
    PRIMARY KEY (order_id, product_id)
);
```

`product_name` зависит только от `product_id` — названию товара совершенно не важно, из какого заказа на него смотрят, то есть это **частичная** зависимость от части составного ключа, а не от ключа целиком (в отличие от `quantity`, которое действительно осмысленно только в контексте конкретной пары «этот заказ + этот товар»). Дублирование `product_name` в каждой строке `order_items` для одного и того же товара, купленного в разных заказах, — та же проблема аномалии обновления, что и в самом первом примере урока: переименование товара потребовало бы правки во множестве строк. Решение — убрать `product_name` из `order_items` и получать его через `JOIN` с таблицей `products`, где он хранится ровно один раз (как уже сделано во всех примерах курса, начиная с тринадцатого урока уровня «Начинающий»).

### 3НФ (третья нормальная форма): нет зависимости неключевых столбцов друг от друга

**Третья нормальная форма** идёт ещё дальше: требует, чтобы неключевые столбцы зависели **только** от первичного ключа, а не друг от друга (такая зависимость столбца от другого неключевого столбца называется транзитивной). Пример нарушения — таблица заказов, где город клиента продублирован рядом с его идентификатором:

```sql
-- Нарушение 3НФ
CREATE TABLE orders_3nf_violation (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT,
    customer_city VARCHAR(100), -- зависит от customer_id, не от id заказа
    created_at DATETIME
);
```

`customer_city` зависит не от первичного ключа `id` (заказа), а от `customer_id` — то есть неключевой столбец `customer_city` находится в зависимости от другого неключевого столбца `customer_id`, а не напрямую от ключа. Если клиент переедет в другой город, придётся обновлять `customer_city` во всех его заказах — снова та же аномалия обновления. Решение — хранить город только в таблице `customers`, там, где он логически принадлежит, и получать его через `JOIN` по `customer_id`, когда он нужен в отчёте.

### Практическое правило нормализации

Общая идея всех трёх нормальных форм сводится к простой формулировке: **каждый факт должен храниться в базе данных ровно в одном месте**, и это место определяется тем, «о чём» этот факт на самом деле — email принадлежит клиенту (значит, живёт в `customers`), название товара принадлежит товару (значит, живёт в `products`), а количество товара в конкретном заказе принадлежит именно этой паре «заказ + товар» (значит, живёт в `order_items`). Схема сквозного датасета курса, с которой мы работаем с самого первого урока уровня «Начинающий», уже спроектирована в третьей нормальной форме именно по этому принципу — что и позволило избежать проблем-аномалий на всём протяжении курса без специального упоминания.

### Денормализация: осознанное нарушение правил ради скорости

Нормализация устраняет дублирование и аномалии, но не бесплатно: чем более нормализована схема, тем больше `JOIN` требуется, чтобы собрать «полную картину» одной сущности (например, полные данные заказа с именем клиента и названиями товаров требуют соединения четырёх таблиц). Для аналитических отчётов, читаемых очень часто и с большим объёмом данных, такие соединения могут оказаться дорогими по времени выполнения. **Денормализация** — осознанное, документированное решение сохранить некоторое дублирование данных ради ускорения самых частых операций чтения; например, хранить `order_total` (сумму заказа) прямо в таблице `orders`, пересчитывая и обновляя её при каждом изменении `order_items`, чтобы не пересчитывать `SUM(quantity * price)` заново при каждом обращении к списку заказов.

Денормализация — не признак «плохого» проектирования, если применяется обдуманно: это компромисс, у которого есть явная цена (дублирующееся значение может рассинхронизироваться с исходными данными, если про его обновление забыли в одном из мест, где оно меняется) и явная выгода (ускорение конкретных, измеримо частых запросов). Правильная практика — начинать с нормализованной схемы (третья нормальная форма как разумный стандарт по умолчанию) и денормализовывать только конкретные, обоснованные измерениями места, а не наоборот.

### VIEW: сохранённый запрос, работающий как таблица

**Представление** (view) — это сохранённый на сервере `SELECT`-запрос, к которому можно обращаться по имени, как к обычной таблице, но который не хранит собственных данных — при каждом обращении к view MySQL заново выполняет вложенный в неё запрос над актуальными данными исходных таблиц:

```sql
CREATE VIEW customer_order_summary AS
SELECT
    c.id AS customer_id,
    c.name AS customer_name,
    COUNT(DISTINCT o.id) AS orders_count,
    COALESCE(SUM(oi.quantity * oi.price), 0) AS total_spent
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
LEFT JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.id, c.name;
```

После создания `customer_order_summary` можно использовать это имя в любом месте, где уместна обычная таблица:

```sql
SELECT * FROM customer_order_summary WHERE total_spent > 50000 ORDER BY total_spent DESC;
```

Практическая ценность view — двойная. Во-первых, она **прячет сложность**: сложный запрос с несколькими `JOIN`, `GROUP BY` и агрегатами записывается один раз при создании view, а дальше используется простым `SELECT ... FROM customer_order_summary` — любой, кто читает этот финальный запрос, не обязан заново разбирать всю логику соединений и агрегации. Во-вторых, view не хранит собственных данных отдельно от исходных таблиц (в отличие, например, от денормализованной копии данных) — при каждом обращении она вычисляется заново из актуального состояния `customers`, `orders`, `order_items`, поэтому результат **никогда не рассинхронизируется** с исходными данными, в отличие от денормализованного столбца, который требует ручного или триггерного обновления. Обновление или удаление view выполняется командами `CREATE OR REPLACE VIEW ...` и `DROP VIEW имя` — по аналогии с `ALTER`/`DROP` для обычных таблиц из седьмого урока уровня «Основы».

### Резюме

- Плохо спроектированная, ненормализованная таблица порождает **аномалии** обновления, вставки и удаления — данные дублируются и рассинхронизируются, часть фактов невозможно сохранить без создания «фиктивных» строк.
- **1НФ** — атомарные значения в каждой ячейке, никаких списков и повторяющихся групп столбцов; решение — отдельная таблица-связка (`order_items`) вместо списка id в одной ячейке.
- **2НФ** — для таблиц с составным ключом: каждый неключевой столбец должен зависеть от ключа целиком, а не от его части; решение — не хранить в таблице-связке столбцы, зависящие только от одной из частей ключа.
- **3НФ** — неключевые столбцы должны зависеть только от первичного ключа, а не друг от друга (без транзитивных зависимостей); решение — хранить факт там, к какой сущности он на самом деле относится, и получать его через `JOIN`.
- Схема сквозного датасета курса спроектирована в 3НФ по принципу «каждый факт — в одном месте».
- **Денормализация** — осознанное, обоснованное измерениями нарушение нормализации ради скорости частых запросов, с явной ценой (риск рассинхронизации дублирующихся данных).
- **VIEW** — сохранённый `SELECT`, доступный по имени как таблица; прячет сложность повторяющихся аналитических запросов и всегда согласована с исходными данными, поскольку не хранит их копии.

## Теоретические задания

### Вопрос 1: У клиента изменился email. В таблице, где email клиента хранится в каждой строке каждого его заказа, адрес обновили не во всех строках — и теперь у одного клиента в одной таблице два разных email. Как называется эта проблема?

- ✅ Аномалия обновления (update anomaly)
<!-- один факт хранится во многих местах и рассинхронизировался -->
- ❌ Аномалия вставки (insertion anomaly) — error_text: Аномалия вставки — невозможность сохранить факт о клиенте без «фиктивного» заказа, потому что данные клиента негде хранить вне заказа. Здесь факт о клиенте продублирован по многим строкам и обновлён не везде — это аномалия обновления.
- ❌ Аномалия удаления (deletion anomaly) — error_text: Аномалия удаления — потеря информации о клиенте вместе с удалением его последнего заказа. В сценарии ничего не удаляли: email продублирован и обновлён не во всех строках — это аномалия обновления.
- ❌ Нарушение первой нормальной формы — error_text: 1НФ требует атомарных значений в ячейках, а email в каждой ячейке атомарен. Проблема в дублировании одного факта по многим строкам; лечится выносом email в таблицу `customers` — ровно один раз на клиента.

### Вопрос 2: Таблица заказов хранит столбец `product_ids VARCHAR(255)` со значениями вида `'5,12,7'`. Какую нормальную форму нарушает такая структура?

- ✅ Первую (1НФ): значения не атомарны — в одной ячейке список идентификаторов
<!-- поиск по такому столбцу вырождался бы в ненадёжный LIKE по подстроке -->
- ❌ Вторую (2НФ): неключевой столбец зависит от части составного ключа — error_text: 2НФ — про частичную зависимость неключевых столбцов от части составного первичного ключа. Здесь речь не о зависимостях от ключа, а о неатомарном значении в ячейке — это нарушение 1НФ.
- ❌ Третью (3НФ): неключевые столбцы зависят друг от друга — error_text: 3НФ — про транзитивные зависимости между неключевыми столбцами. Список идентификаторов в одной ячейке — проблема атомарности, то есть 1НФ; решение — отдельная таблица-связка `order_items`.
- ❌ Никакую: строка — законный тип данных, нарушения нет — error_text: Тип допустим, но нормальную форму нарушает не тип, а смысл значения: поиск по товару потребовал бы `LIKE '%,12,%'`, который ненадёжен (перепутает 12 и 120) и медлен. Атомарность значения — требование 1НФ.

### Вопрос 3: Таблица позиций заказа имеет составной первичный ключ `(order_id, product_id)`, и в ней же хранится столбец `product_name`. Какую нормальную форму нарушает `product_name`?

- ✅ Вторую (2НФ): название зависит только от `product_id` — части составного ключа
<!-- частичная зависимость от части ключа, а не от ключа целиком -->
- ❌ Первую (1НФ): название товара — неатомарное значение — error_text: Название товара атомарно: одно значение в одной ячейке, не список и не повторяющаяся группа столбцов. Проблема в другом: `product_name` зависит только от части составного ключа — это 2НФ.
- ❌ Третью (3НФ): транзитивная зависимость между неключевыми столбцами — error_text: 3НФ — про зависимость неключевого столбца от другого неключевого. Здесь `product_name` зависит от ключевого столбца `product_id`, но не от всего ключа целиком — это частичная зависимость, то есть 2НФ.
- ❌ Никакую: хранить название рядом с позициями удобно для отчётов — error_text: Удобство отчёта не отменяет аномалию обновления: переименование товара потребует правки во множестве строк. Дублирование ради скорости — осознанная денормализация, обоснованная измерениями, а по умолчанию это нарушение 2НФ.

### Вопрос 4: В таблице `orders` есть столбцы `customer_id` и `customer_city`. Почему это нарушение третьей нормальной формы?

- ✅ `customer_city` зависит от неключевого `customer_id`, а не напрямую от первичного ключа заказа (транзитивная зависимость)
<!-- город принадлежит клиенту, а не заказу -->
- ❌ Потому что у таблицы нет составного первичного ключа — error_text: Составной ключ — предпосылка разговора о 2НФ, а не требование 3НФ. Таблица `orders` с простым ключом `id` сама по себе корректна; нарушена 3НФ из-за зависимости города от неключевого столбца `customer_id`.
- ❌ Потому что город — неатомарное значение, составленное из нескольких полей — error_text: Название города атомарно: одно значение в одной ячейке, 1НФ соблюдена. Нарушение в другом: город клиента зависит от неключевого столбца, а не от ключа заказа, — транзитивная зависимость, 3НФ.
- ❌ Потому что VARCHAR для города — слишком длинный тип — error_text: Длина типа — не критерий нормальных форм. 3НФ нарушена семантикой данных: один и тот же факт (город клиента) хранится многократно и должен обновляться во всех заказах при переезде клиента.

### Вопрос 5: Что произойдёт с результатом `SELECT` из VIEW, если изменить данные в исходных таблицах после создания представления?

- ✅ VIEW выполнит свой запрос заново над актуальными данными — результат всегда отражает текущее состояние исходных таблиц
<!-- представление — сохранённый запрос, а не копия данных -->
- ❌ Ничего: VIEW хранит снимок данных на момент создания и не меняется — error_text: Представление — это сохранённый `SELECT`, а не копия данных: при каждом обращении MySQL заново выполняет вложенный запрос. Именно поэтому view не может рассинхронизироваться с исходными таблицами.
- ❌ Результат изменится только после явного обновления view командой `CREATE OR REPLACE VIEW` — error_text: `CREATE OR REPLACE VIEW` меняет определение (сам запрос) представления, а не его «данные». Данных у view нет вовсе — каждый `SELECT` из view вычисляется заново.
- ❌ VIEW устареет и станет возвращать ошибку о неактуальности данных — error_text: Никакой ошибки не будет: view не кэширует результат и не следит за «актуальностью». Она просто выполняет свой запрос над текущими данными при каждом обращении.
