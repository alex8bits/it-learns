### Кто охраняет ссылки

Урок 11 построил модель: покупатели и заказы живут в разных таблицах,
заказ носит столбец-ссылку `customer_id`. Но кто помешает вписать в
`orders` заказ с `customer_id = 99`, когда покупателя №99 не существует?
Пока никто: столбец — просто число. Ссылка без охраны — это договорённость
на бумаге: приложение может ошибиться, админ — опечататься, а база
молча сохранит «заказ в никуда».

В уроке 6 «Основ» у таблицы уже были стражи: PRIMARY KEY не пускает
дубликаты, NOT NULL — пустоту, UNIQUE — повторы, CHECK — недопустимые
значения. Сегодня страж получает седьмое звание — **внешний ключ**
(FOREIGN KEY): ограничение, которое защищает ссылку из одной таблицы
на другую. В нашем простом случае ссылка хранится в одном столбце —
это и будем разбирать дальше; составные FK (пара столбцов) оставим
для среднего уровня. И второй герой урока — **каскады**:
правила, по которым дети ведут себя, когда родителя удаляют или меняют.

### Внешний ключ: ограничение на ссылку

Пара таблиц урока 11 — покупатели и заказы. Ссылку охраняет строка
`FOREIGN KEY ... REFERENCES` внутри CREATE TABLE:

```sql
CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    total DECIMAL(10,2) NOT NULL,
    created_at DATE NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
```

Читается: «столбец `customer_id` ссылается на `customers.id`». Всё,
что слева от точки, — таблица-ребёнок (заказы), всё, что справа, —
таблица-родитель (покупатели). Имя ограничения `fk_orders_customer` —
наша забота: безымянный FK сервер назовёт сам, но для управления
ограничением (снять, заменить — ниже) имя нужно, поэтому именуем сразу
по схеме «fk_ребёнок_родитель».

Три требования к связи, о которых MySQL сообщает ошибками, если их
нарушить: типы и характеристики столбцов должны быть совместимы по
правилам MySQL (для INT важно, чтобы совпадали размер и знаковость —
урок 5 «Основ»); родительский столбец — PRIMARY KEY или UNIQUE;
обе таблицы живут на движке InnoDB — в MySQL 8 это умолчание.

Корректная вставка проходит как обычно:

```sql
INSERT INTO orders (customer_id, total, created_at) VALUES
    (1, 4990.00, '2026-06-28');
```

```text
+----+-------------+---------+------------+
| id | customer_id | total   | created_at |
+----+-------------+---------+------------+
|  1 |           1 | 4990.00 | 2026-06-28 |
+----+-------------+---------+------------+
```

А вставка «заказа в никуда» — нет:

```sql
INSERT INTO orders (customer_id, total, created_at) VALUES
    (99, 100.00, '2026-07-01');
```

```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key
constraint fails (`shop`.`orders`, CONSTRAINT `fk_orders_customer`
FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`))
```

Ошибка 1452: «нельзя добавить строку-ребёнка: внешний ключ не
сходится». Покупателя №99 нет — заказа на него не будет. В показанном
INSERT нарушение внешнего ключа приводит к ошибке, и оператор не
вставляет ни одной строки.

Связь с уроком 11: NULL-семантика работает и здесь. Наш столбец —
`customer_id INT NOT NULL`, и связка NOT NULL + FOREIGN KEY делает
связь **обязательной**: каждый заказ имеет реального покупателя. Будь
столбец просто `INT` (nullable) — внешний ключ пропустил бы NULL
(«покупатель неизвестен», как `manager_id` у директора), но по-прежнему
отвергал бы несуществующие номера. Обязательность — от NOT NULL,
корректность ссылки — от FOREIGN KEY: два независимых стража.

### Сироты запрещены: удаление родителя

Обратная сторона: в базе есть заказы Анны — а кто-то удаляет Анну.
Заказ-сирота, ссылающийся на несуществующего покупателя, — та же
порча данных, только с другого конца. По умолчанию (опция ON DELETE
не написана) MySQL отвечает отказом:

```sql
DELETE FROM customers WHERE id = 1;
```

```text
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key
constraint fails (`shop`.`orders`, CONSTRAINT `fk_orders_customer`
FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`))
```

Ошибка 1451 — зеркало 1452: «нельзя удалить родителя, пока на него
смотрят дети». В MySQL поведение по умолчанию называется **RESTRICT**
(«ограничить»). NO ACTION в MySQL фактически является синонимом
RESTRICT для внешних ключей; в других СУБД эти варианты могут
различаться — здесь, в MySQL, это одно и то же. База не даст удалить половину связи: сначала
разберитесь с заказами, потом удаляйте покупателя.

### ON DELETE: три судьбы детей

Отказ — не единственный сценарий. Клауза ON DELETE говорит серверу,
что делать с детьми при удалении родителя. Три варианта:

Каскад — не «более правильный» вариант: это бизнес-решение «дети
не нужны без родителя». Полный разбор трёх вариантов ниже; первое
знакомство — здесь.

**CASCADE — следовать за родителем.** Дети удаляются вместе с ним:

```sql
ALTER TABLE orders DROP FOREIGN KEY fk_orders_customer;

ALTER TABLE orders ADD CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customers(id)
    ON DELETE CASCADE;
```

(Сначала сняли старое ограничение по имени — вот зачем именовали,
потом повесили новое, с опцией.) Три заказа — два Анны и один Ивана:

```text
+----+-------------+---------+
| id | customer_id | total   |
+----+-------------+---------+
|  1 |           1 | 4990.00 |
|  2 |           1 |  899.00 |
|  3 |           2 | 1290.50 |
+----+-------------+---------+
```

Удаляем Анну — и следом, без единого нашего DELETE, исчезают её
заказы:

```sql
DELETE FROM customers WHERE id = 1;
```

```text
+----+-------------+---------+
| id | customer_id | total   |
+----+-------------+---------+
|  3 |           2 | 1290.50 |
+----+-------------+---------+
```

Один оператор — две таблицы приведены в согласие. `customers` после
удаления: один Иван.

**SET NULL — остаться без родителя.** Дети живут, ссылка обнуляется
(столбец обязан быть nullable). Естественный полигон — самосвязь
сотрудников из урока 11: уволился руководитель — подчинённые остаются,
но остаются без руководителя:

```sql
CREATE TABLE employees (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    manager_id INT NULL,
    CONSTRAINT fk_employees_manager
        FOREIGN KEY (manager_id) REFERENCES employees(id)
        ON DELETE SET NULL
);
```

Пять сотрудников: Ольга — директор (NULL), у Игоря и Марии руководитель
Ольга, у Анны и Ивана — Игорь:

```text
+----+-----------------------------+------------+
| id | name                        | manager_id |
+----+-----------------------------+------------+
|  1 | Ольга Смирнова              |       NULL |
|  2 | Игорь Морозов               |          1 |
|  3 | Анна Петрова                |          2 |
|  4 | Иван Сидоров                |          2 |
|  5 | Мария Волкова               |          1 |
+----+-----------------------------+------------+
```

Увольняем Игоря:

```sql
DELETE FROM employees WHERE id = 2;
```

```text
+----+-----------------------------+------------+
| id | name                        | manager_id |
+----+-----------------------------+------------+
|  1 | Ольга Смирнова              |       NULL |
|  3 | Анна Петрова                |       NULL |
|  4 | Иван Сидоров                |       NULL |
|  5 | Мария Волкова               |          1 |
+----+-----------------------------+------------+
```

Строки Игоря нет; Анна и Иван на месте, их `manager_id` стал NULL.
Никаких сирот с битыми ссылками — законные строки с «руководителя
нет» (урок 11 «Основ»: NULL — отсутствие значения, здесь это точно
по смыслу).

**RESTRICT — отказ (умолчание).** Третья судьба уже знакома: ничего
не удаляется, возвращается ошибка 1451. Явная запись — `ON DELETE
RESTRICT` — ничего не меняет, но подсвечивает решение в DDL.

### ON UPDATE: каскад на изменение

ON UPDATE решает ту же задачу для изменения родительского ключа.
Изменим Ивана с `id = 2` на `id = 20` под охраной `ON UPDATE
CASCADE`:

```sql
ALTER TABLE orders DROP FOREIGN KEY fk_orders_customer;

ALTER TABLE orders ADD CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customers(id)
    ON UPDATE CASCADE;

UPDATE customers SET id = 20 WHERE id = 2;
```

```text
+----+-------------------------+
| id | name                    |
+----+-------------------------+
| 20 | Иван Сидоров            |
+----+-------------------------+
```

```text
+----+-------------+---------+
| id | customer_id | total   |
+----+-------------+---------+
|  3 |          20 | 1290.50 |
+----+-------------+---------+
```

Иван сменил номер — и его заказ сам переехал на новый: ссылка
продолжает указывать на того же покупателя. ON UPDATE SET NULL
устроен аналогично: при изменении значения родительского ключа
связанные ссылки детей становятся NULL (если столбец допускает
NULL). Сценарий другой — не удаление родителя, а переписывание
его ключа — но механизм для детей тот же.

Насколько это нужно на практике — вопрос частоты: суррогатные ключи
AUTO_INCREMENT (урок 6 «Основ») обычно не меняют, и для них ON UPDATE
— страховка без дела. Актуален он для естественных ключей, которые
иногда переписывают: табельный номер, номер документа. Поведение по
умолчанию без опции — тот же RESTRICT: изменить ключ родителя, на
которого смотрят дети, сервер не даст.

### Внешний ключ в существующей таблице

Таблица без FK досталась по наследству — ограничение добавляется
ALTER'ом урока 7 «Основ»:

```sql
ALTER TABLE payments ADD CONSTRAINT fk_payment_order
    FOREIGN KEY (order_id) REFERENCES orders(id);
```

Нюанс, который стоит знать заранее: навешивая FK, сервер проверяет
**все существующие строки**. В `payments` лежит платёж на заказ №999,
которого нет, — ALTER упадёт с уже знакомой ошибкой 1452, пока данные
не почищены. При обычном добавлении FK через ALTER TABLE MySQL
проверяет существующие строки, поэтому сначала данные должны
удовлетворять новому ограничению — иначе ALTER упадёт с той же
ошибкой 1452. После чистки ALTER проходит, и новые строки
проверяются уже как положено.

### Как выбрать поведение

ON DELETE — не техническая, а бизнес-решение: «что должно происходить
с заказами удалённого покупателя?» Три подсказки:

- **Дети бессмысленны без родителя, история не нужна** — CASCADE:
  позиции заказа без заказа, строки корзины без сессии. Удаление
  родителя без следа тянет за собой хвост.
- **Исторические данные должны сохраниться** — в реальных системах
  удаление покупателя часто вообще запрещено бизнес-правилами:
  обычно выбирают RESTRICT в БД и отдельно решают
  архивирование/анонимизацию пользователя. RESTRICT — честный
  «сначала разберись», и он же умолчание.
- **Связь необязательна** — SET NULL: подчинённые без руководителя,
  товар без скидки. Требует nullable-столбца; на NOT NULL-ссылке
  (наш `orders.customer_id`) вариант невозможен синтаксически — и по
  смыслу: обязательная связь не может стать «нет значения».

И осторожность с CASCADE: одно DELETE с уровнем вложенности «категория
→ товары → позиции заказов» способно снести цепочку таблиц. При
длинной каскадной цепочке проверяйте не только непосредственных
детей, но и связанные с ними данные: цепочка
`category → products → order_items` удалит вместе с категорией и
позиции заказов, даже если в уроке о них не упомянуто. Урок 10
«Основ» требовал WHERE для каждого DELETE — с каскадами WHERE
родителя решает судьбу детей тоже. Перед удалением родителя
контрольный SELECT детей (сколько строк уйдут следом) — та же
привычка, что и до UPDATE.

### Чего в этом уроке нет

- JOIN — сборка данных из связанных таблиц в один ответ — урок 13:
  следующий шаг после охраны ссылок;
- систематическое чтение кодов ошибок (1054, 1064, 1062, 1451,
  1452, 1048 и другие) — урок 8 среднего уровня; сегодня — два
  героя-кода в их естественной среде;
- составные внешние ключи (пара столбцов, как у связующих таблиц
  M:N) и нормальные формы — проектирование схемы, средний уровень;
- влияние FOREIGN KEY на скорость записи и индексы — продвинутый
  уровень, блок производительности.

### Резюме

- FOREIGN KEY (столбец) REFERENCES таблица(ключ) — ограничение на
  ссылку: каждое ненулевое значение ребёнка должно существовать у
  родителя; NULL допускается, если столбец не объявлен NOT NULL.
  Требования: совместимые тип и характеристики (размер, знаковость
  для INT), ключ родителя PK/UNIQUE, InnoDB.
- INSERT с несуществующей ссылкой — ошибка 1452, строка не вставлена.
  DELETE родителя с детьми — ошибка 1451 (поведение RESTRICT —
  умолчание; NO ACTION — синоним).
- ON DELETE CASCADE — дети удаляются следом; SET NULL — дети
  остаются, ссылка в NULL (столбец nullable); RESTRICT — отказ.
- ON UPDATE CASCADE — дети следуют за новым ключом родителя; нужен
  для естественных ключей, для AUTO_INCREMENT — страховка без дела.
- Обязательность связи — от NOT NULL ссылки, корректность — от
  FOREIGN KEY; nullable-ссылка + FK пропускает NULL, но не мусор.
- FK добавляется и снимается ALTER'ом по имени ограничения; при
  добавлении проверяются существующие строки — грязные данные не
  дадут ограничению включиться.
- Выбор ON DELETE — бизнес-решение: дети бессмысленны — CASCADE,
  история важна — RESTRICT, связь необязательна — SET NULL. Каскады
  умножают цену одного DELETE — контрольный SELECT детей прежде.

## Теоретические задания

### Вопрос 1: Что гарантирует `FOREIGN KEY (customer_id) REFERENCES customers(id)` в таблице orders?

- ✅ в этом orders каждый заказ ссылается на существующего покупателя (обязательность ссылки — от NOT NULL, корректность ссылки — от FOREIGN KEY)
<!-- FK сверяет каждое значение ссылки с ключами родителя: «заказ в никуда» невозможен; обязательность даёт NOT NULL -->
- ❌ покупатель не может иметь больше одного заказа — error_text: «не больше одного ребёнка» дала бы связь 1:1 — UNIQUE на ссылку (урок 11); FK без UNIQUE разрешает покупателю сколько угодно заказов — это охрана 1:N.
- ❌ данные покупателей копируются в orders — error_text: FK ничего не копирует: ссылка остаётся номером, данные живут у родителя; копирование — это как раз плоская таблица, от которой модель ушла в уроке 11.
- ❌ SELECT из orders автоматически возвращает и имя покупателя — error_text: данные разных таблиц собирает JOIN — урок 13; FK — охрана целостности, к чтению данных отношения не имеет.

### Вопрос 2: В customers есть покупатели с id 1 и 2. Что произойдёт с `INSERT INTO orders ... VALUES (99, ...)` при действующем FK?

- ✅ ошибка 1452, строка не вставится
<!-- «Cannot add or update a child row»: покупателя 99 нет — INSERT отвергнут целиком -->
- ❌ вставится со значением customer_id = NULL — error_text: FK не подменяет значение на NULL: несуществующая ссылка — ошибка 1452; NULL был бы, только если бы вставляли его явно, — и то при nullable-столбце.
- ❌ вставится, но SELECT её скроет — error_text: SELECT ничего не скрывает: строки либо в таблице, либо нет; ограничения не «помечают» данные, а не пускают их.
- ❌ предупреждение, строка вставится — error_text: для FK нет «мягкого» режима: нарушение ограничения — ошибка, а не предупреждение; INSERT IGNORE — отдельная тема среднего уровня.

### Вопрос 3: У покупателя Анны (id = 1) есть заказы; FK объявлен без опций ON DELETE. Что вернёт `DELETE FROM customers WHERE id = 1`?

- ✅ ошибку 1451 — удалять родителя с детьми нельзя
<!-- умолчание RESTRICT: «Cannot delete or update a parent row», покупатель и заказы останутся на месте -->
- ❌ Анна удалится, заказы останутся с битой ссылкой — error_text: сироты — именно то, от чего FK защищает; «битая ссылка» — порча данных, а не результат работы ограничения.
- ❌ Анна удалится вместе с заказами — error_text: это поведение ON DELETE CASCADE; без опций действует умолчание RESTRICT — отказ (1451), а не каскад.
- ❌ Анна удалится, заказы получат customer_id = NULL — error_text: это ON DELETE SET NULL; без опции — RESTRICT, и вдобавок наш customer_id — NOT NULL: обнулить его невозможно.

### Вопрос 4: В orders действует `ON DELETE CASCADE` на customer_id. У Анны три заказа. Что произойдёт после `DELETE FROM customers WHERE id = 1` (Анна)?

- ✅ Анна и все три её заказа будут удалены
<!-- CASCADE: дети следуют за родителем — один оператор приводит две таблицы в согласие -->
- ❌ ошибку 1451 — error_text: 1451 даёт RESTRICT — умолчание без опций; CASCADE на то и объявлен, чтобы удаления не блокировать.
- ❌ Анна удалится, заказы получат customer_id = NULL — error_text: это SET NULL; CASCADE обнуления не делает — дети удаляются вместе с родителем.
- ❌ ничего: с CASCADE родителя удалить нельзя — error_text: наоборот: CASCADE — разрешение с последствиями; блокирует как раз RESTRICT.

### Вопрос 5: Для какой связи `ON DELETE SET NULL` уместен?

- ✅ необязательной, где дети осмысленны без родителя: подчинённые остаются при увольнении руководителя
<!-- manager_id: NULL — «руководителя нет», законное состояние (урок 11 «Основ») -->
- ❌ обязательной связи «заказ → покупатель» — error_text: заказ без покупателя — сирота, потеря смысла; для обязательных связей — RESTRICT (история важна) или CASCADE (дети не нужны), а не обнуление.
- ❌ любой: SET NULL всегда лучше CASCADE — error_text: «всегда лучше» не бывает: SET NULL оставляет детей без родителя — для осмысленных без него; и он требует nullable-столбца — на NOT NULL-ссылке не работает.
- ❌ связи, где ссылка объявлена NOT NULL — error_text: SET NULL физически невозможен на NOT NULL-столбце: обнулять нечего — сервер откажет ещё на CREATE TABLE; ссылка обязана быть nullable.

### Задание 2: Проверить каскад

Удаление родителя с `ON DELETE CASCADE` — дети уходят следом.

<!-- Эталонное решение (для автора/бота-верификатора): DELETE FROM categories WHERE id = 2; SELECT id, name, category_id FROM products ORDER BY id; -->

**statement:**

Таблицы `categories` (три категории) и `products` (шесть товаров)

**expected_result_text:**

Финальный SELECT возвращает три строки: коврик (категория 1), кабель

<!-- Эталонное решение (для автора/бота-верификатора): DELETE FROM employees WHERE id = 2; SELECT id, name, manager_id FROM employees ORDER BY id; -->

**statement:**

Таблица `employees` с самосвязью `manager_id` под внешним ключом
