# Изменение и удаление строк

## Материал

### Данные живут дольше вставки

`INSERT` урока 4 умел одно: добавлять новые строки. Но таблица — не музей:
цены меняются, склады заканчиваются, заказы отменяются, черновые строки
устаревают. Данным нужно уметь меняться — и уходить.

Сегодня закрываются сразу два обещания. Урок 7 сказал: «`DELETE` с условием
`WHERE` и `UPDATE ... WHERE` — урок 10». Урок 8 добавил: условие там будет
то же, что в `SELECT`. Ментальная модель знакомая: `WHERE` задаёт каждой
строке вопрос «да/нет» — только теперь «да» означает не «попасть в
результат», а «быть изменённой» (для `UPDATE`) или «исчезнуть» (для
`DELETE`).

Кстати, о грубом способе: «удалить строку и вставить новую с исправленной
ценой» — не то же самое. У новой строки будет другой `id`, а на старый
ссылаются заказы (урок 1: заказ ссылается на покупателя по
`customer_id`). `UPDATE` чинит значения на месте — строка и её «имя»
остаются прежними. Потому изменение — отдельная команда, а не трюк с
удалением и вставкой.

### Четыре действия над данными

Соберём репертуар курса: `SELECT` — читать, `INSERT` — создавать,
`UPDATE` — обновлять, `DELETE` — удалять. Эти четыре операции настолько
базовые, что в разработке их называют одной аббревиатурой — CRUD: Create,
Read, Update, Delete. Встретите «CRUD-приложение» — в основе его работы
с данными лежат эти четыре операции. Сегодняшний урок закрывает
последние две буквы — и с ним весь базовый репертуар работы с данными
собран целиком. Это не предел — впереди фильтры поточнее, вычисления и
связи между таблицами, — но базовые манипуляции со строками закрыты.

### UPDATE: новые значения для подходящих строк

Монитор подешевел. Правим:

```sql
UPDATE products
SET price = 13990.00
WHERE id = 4;
```

Читается: «обнови `products`: поставь `price = 13990.00` — где `id = 4`».
Синтаксис — почти разговорный: `SET` перечисляет, **что** изменить в
столбцах, `WHERE` отбирает, **какие строки** трогать. Разделение труда то
же, что в `SELECT`: список и условие — независимые решения. А форма
`столбец = значение` в `SET` — родня формы `INSERT` урока 4: `SET price =
13990.00` сообщает то же, что столбец `price` со значением `13990.00` в
`VALUES`, — только теперь значения получают существующие строки, а не
одна новая.

Ответ сервера не таблица, а короткий отчёт:

```text
Query OK, 1 row affected (0.02 sec)
Rows matched: 1  Changed: 1  Warnings: 0
```

Читать его полезно построчно. `Rows matched` — сколько строк подошло под
`WHERE` (вопрос урока 8); `Changed` — сколько реально изменилось;
`Warnings` — счётчик предупреждений, знакомый по уроку 5. Убедиться
глазами — обычным `SELECT` с тем же условием:

```sql
SELECT name, price FROM products WHERE id = 4;
```

```text
+------------+----------+
| name       | price    |
+------------+----------+
| Монитор 27"| 13990.00 |
+------------+----------+
```

### Забытый WHERE: все строки

А теперь самое важное место урока. Тот же `UPDATE` без `WHERE`:

```sql
UPDATE products SET price = 4990.00;
```

`Query OK, 6 rows affected` — и весь каталог стоит по 4990: и коврик,
и монитор. Никакой ошибки, ни одного предупреждения — сервер сделал ровно
то, что попросили, как с молчаливым `MODIFY` из урока 7. В изменяющих
командах `WHERE` — не необязательное украшение. Дисциплина такая: сперва
условие — какие строки трогаем (проверьте их пробным `SELECT`, привычка №1
ниже), затем `SET` — что именно меняем. В тексте запроса порядок обратный
и строгий: `SET` всегда стоит до `WHERE`. Забытая строка
`WHERE` в пятницу вечером — профессиональная классика; строки вернутся
только из резервной копии, если она есть.

### Несколько столбцов, несколько строк

`SET` принимает список столбцов через запятую, а `WHERE` — любое условие
урока 8. Распродаем дорогое: обнулить остатки и поставить единую цену
у всего, что дороже трёх тысяч. Правка массовая, поэтому сперва — взгляд
на будущих жертв: `SELECT id, name, price FROM products WHERE price > 3000;`
отвечает — клавиатура и монитор. Теперь правим:

```sql
UPDATE products
SET stock = 0, price = 4490.00
WHERE price > 3000;
```

```text
Query OK, 2 rows affected (0.02 sec)
Rows matched: 2  Changed: 2  Warnings: 0
```

```text
+----+--------------------------+---------+-------+
| id | name                     | price   | stock |
+----+--------------------------+---------+-------+
|  1 | Коврик для мыши          |  690.00 |    34 |
|  2 | Мышь беспроводная        | 1290.50 |    12 |
|  3 | Клавиатура механическая  | 4490.00 |     0 |
|  4 | Монитор 27"              | 4490.00 |     0 |
|  5 | Кабель HDMI 2 м          |  450.00 |    51 |
|  6 | Веб-камера               | 2450.00 |    15 |
+----+--------------------------+---------+-------+
```

Под условие попали клавиатура и монитор — обе изменились; каждая строка
получила **оба** новых значения сразу. Отчёт подскажет и крайние случаи:
`Rows matched: 0` — условие никого не нашло, это не ошибка, данные не
тронуты (как пустой результат `WHERE` урока 8). А `Rows matched: 1,
Changed: 0` — строка нашлась, но новое значение равно старому: менять
нечего, и сервер честно пишет ноль изменений.

Новое значение умеет считаться из старого — `SET price = price * 1.1`
поднимет цену на десятую часть; но вычисления внутри запросов — тема
следующего уровня, пока держим литералы.

И граница возможностей: `UPDATE` работает только с существующими строками.
Новую он не создаст — это работа `INSERT`; несуществующую не «обновит» —
получит `Rows matched: 0`; сами строки не удаляет — это `DELETE`. Его
ремесло — заменить значения в строках, которые нашёл `WHERE`, и только.

### Ограничения не спят

`UPDATE` проходит те же проверки, что `INSERT` из уроков 5–6, — меняется
способ записи значений, не законы таблицы. Пытаемся отдать Марии email
Анны:

```sql
UPDATE customers SET email = 'anna@example.com' WHERE id = 2;
```

```text
ERROR 1062 (23000): Duplicate entry 'anna@example.com' for key 'email'
```

Уникальность по-прежнему под охраной — 1062, знакомая по урокам 6–7. Уводим
баланс подарочной карты в минус:

```text
ERROR 3819 (HY000): Check constraint 'balance_nonneg' is violated.
```

Та же 3819, что при вставке: `CHECK` проверяет каждое новое значение —
откуда бы оно ни пришло. Работают и остальные стражи: `NOT NULL` (1048),
длины и диапазоны типов (1406, 1264 — урок 5). И действует «всё или
ничего» урока 4: если в массовом `UPDATE` третья строка нарушает правило —
не изменится ни первая, ни вторая: инструкция едина, частичных результатов
не бывает, недописанных строк не существует.

### DELETE: убрать строки целиком

Отменённые заказы через месяц не нужны — убираем:

```sql
DELETE FROM orders
WHERE status = 'отменён';
```

У `DELETE` нет `SET` — и не нужно: строка удаляется целиком, столбцы
выбирать нельзя. Ответ — тот же короткий отчёт: `Query OK, 2 rows
affected`; слово affected здесь стоит читать как «удалено»: сколько строк
нашлось условием — столько и исчезло. Условие — любое из урока 8:
неуникальное снесёт **все** подходящие строки, прицел по `id` — максимум
одну. Нулевой отчёт — `Query OK, 0 rows affected` — опять же не ошибка:
удалять нечего (у `DELETE` нет строки `Rows matched`: нашёл — значит
удалил, считать раздельно нечего).

Три связи с уроком 7, чтобы картина сошлась. Без `WHERE` команда удалит
все строки таблицы — то самое «`DELETE FROM t;`» из сводки. Счётчик
`AUTO_INCREMENT` после `DELETE` не сбрасывается: удалили строку с
наибольшим `id = 5` — следующая вставка получит 6, счётчик помнит
наибольший использованный номер (урок 6). Начать нумерацию с чистого листа
умеет `TRUNCATE` — он про всю таблицу, `DELETE` — про строки.

### Рабочий цикл: посмотрел — изменил — проверил

Соберём уроки 8–10 в ежедневную рутину администратора магазина. Задача:
распродать дорогое и вычистить мелочь. Шаг 1 — осмотр: `SELECT` с будущим
условием показывает жертв: `WHERE price > 3000` — клавиатура и монитор,
`WHERE total < 800` — два черновых заказа. Шаг 2 — изменение: один
`UPDATE` со списком столбцов, один `DELETE` с прицелом. Шаг 3 — контроль:
итоговый `SELECT` (при желании — с `ORDER BY` урока 9) показывает
результат, а отчёты сервера подтверждают: `Rows matched` сошёлся с
ожиданиями. Все три шага собрались из пройденного — ни одной новой команды.

### Техника безопасности

Изменяющие команды — единственное место курса, где ошибка стоит данных.
Пять привычек, которые стоят дешевле:

1. **Сначала посмотри на жертв.** Тот же `WHERE` в `SELECT` покажет строки,
   которые собираетесь изменить или удалить: условие то же — строки те же.
2. **Прицеливайся по `id`.** Условие по первичному ключу трогает не более
   одной строки (урок 8) — худший случай ограничен.
3. **Не трогай `id` в `SET`.** Технически можно, но `id` — «имя строки»
   (урок 6): ссылка на строку сломается.
4. **Разрушающее — последним.** В скрипте проверки `SELECT` пишут до
   `UPDATE`/`DELETE`, а не после.
5. **Помни, что отката нет.** Корзины для строк не существует (урок 7).
   Инструмент «выполнить и при ошибке отменить всё» — транзакции — ждёт в
   средней части курса; до него Ваша страховка — пункты выше.
6. **Читай отчёт сервера.** `Rows matched` и `affected` — честный счётчик
   затронутых строк: ожидали одну, а увидели сто — условие вышло шире, чем
   думали; масштаб проблемы лучше знать сразу.

### Резюме

- `UPDATE таблица SET столбец = значение WHERE условие` — `SET` отвечает за
  столбцы, `WHERE` — за строки; разделение труда как в `SELECT`.
- Отчёт сервера: `Rows matched` нашёл, `Changed` изменил, `Warnings` —
  предупреждения; `matched: 0` — не ошибка.
- Без `WHERE` `UPDATE` меняет **все** строки — без ошибок и предупреждений;
  условие продумывайте первым и проверяйте пробным `SELECT` (в тексте
  запроса порядок обратный: `SET` до `WHERE`).
- `SET` принимает несколько столбцов через запятую; формулы над старыми
  значениями — следующий уровень.
- Ограничения урока 6 работают и на `UPDATE`: 1062 (уникальность), 3819
  (`CHECK`), 1048 (`NOT NULL`); инструкция — «всё или ничего».
- `DELETE FROM таблица WHERE условие` — строка целиком, без выбора столбцов;
  без `WHERE` — все строки; счётчик `AUTO_INCREMENT` продолжает расти,
  сбросить его умеет `TRUNCATE`.
- Безопасность: `SELECT` с тем же `WHERE` до изменения, прицел по `id`,
  не менять `id`, проверки раньше разрушений, отката нет — транзакции
  впереди.

## Теоретические задания

### Вопрос 1: Что сделает `UPDATE products SET price = 4990;` (без WHERE)?

- ✅ изменит цену во всех строках таблицы
- ❌ вернёт ошибку: UPDATE требует условие WHERE — error_text: WHERE в UPDATE необязателен — и в этом опасность: без условия команда применяется ко всем строкам, молча и без предупреждений.
- ❌ изменит только первую строку — error_text: UPDATE не работает с «первой строкой»: без WHERE и порядка (урок 9) выбранной строки не существует — меняются все строки сразу.

### Вопрос 2: `UPDATE products SET price = 4490 WHERE id = 3;` Сколько строк изменится?

- ✅ одну: id уникален, условие по ключу находит не более одной строки
- ❌ все строки, у которых price = 4490 — error_text: перепутаны роли: SET назначает значение, WHERE выбирает строки; выбирает здесь id = 3, а текущая цена значения не имеет.
- ❌ все строки: SET применяется без условие… — error_text: WHERE id = 3 работает в UPDATE точно так же, как в SELECT урока 8: подходит максимум одна строка — «не более одного ответа» по ключу.

### Вопрос 3: В таблице есть `CHECK (balance >= 0)`. Что произойдёт при `UPDATE gift_cards SET balance = -100 WHERE id = 1;`?

- ✅ ошибка 3819: проверка нарушена, значение не изменится
- ❌ значение изменится с предупреждением — error_text: CHECK — не предупреждение, а правило таблицы (урок 6): нарушено — инструкция отклоняется целиком; предупреждения — про спасаемые мелочи вроде округления (урок 5).
- ❌ значение изменится: CHECK работает только при INSERT — error_text: ограничение проверяет каждое новое значение, откуда бы оно ни пришло — и при вставке, и при обновлении.

### Вопрос 4: Как до выполнения узнать, какие строки затронет `UPDATE ... WHERE city <> 'Москва';`?

- ✅ выполнить `SELECT * FROM t WHERE city <> 'Москва';` — условие то же, строки те же
- ❌ никак: строки видны только после изменения — error_text: видны и до: WHERE урока 8 выбирает одни и те же строки и в SELECT, и в UPDATE — превентивный SELECT и есть штатный приём.
- ❌ выполнить UPDATE, посмотреть и откатить назад — error_text: отката у обычного UPDATE нет (транзакции — средняя часть курса); смотреть надо до, через SELECT с тем же условием.

### Вопрос 5: В `orders` (AUTO_INCREMENT, наибольший id = 5) удалили строку `id = 5`. Какой id получит следующая вставка без указания id?

- ✅ 6 — счётчик помнит наибольший использованный номер
- ❌ 5 — номер освободился и будет использован заново — error_text: счётчик не переиспользует номера: «наибольший использованный» — урок 6; освобождение значения ничего не откатывает.
- ❌ 1 — после удаления счётчик сбрасывается — error_text: сброс счётчика — поведение TRUNCATE (урок 7); DELETE строки не возвращает и нумерацию не начинает заново.

### Задание 1: Переоценка монитора

Первая правка данных: один столбец, прицел по ключу.

<!-- Эталонное решение (для автора/бота-верификатора): UPDATE products SET price = 13990.00 WHERE id = 4; SELECT id, name, price FROM products ORDER BY id; -->

**statement:**

Таблица `products` заполнена шестью товарами. Монитор (id 4) подешевел:
установите ему цену 13990.00 и выведите id, name и price всех товаров.

**expected_result_text:**

Финальный SELECT возвращает шесть строк; у монитора цена 13990.00,

CREATE TABLE products (

### Задание 2: Массовая отмена

UPDATE по неуникальному условию: несколько строк одним движением.

<!-- Эталонное решение (для автора/бота-верификатора): UPDATE orders SET status = 'отменён' WHERE total > 5000; SELECT id, customer, total, status FROM orders ORDER BY id; -->

**statement:**

В таблице `orders` пять заказов со статусом «новый». Покупатели передумали:
отмените — установите статус «отменён» — все заказы дороже 5000 и выведите
все строки таблицы (id, customer, total, status).

**expected_result_text:**

Финальный SELECT возвращает пять строк: заказы Ивана Сидорова (15990.00)
и Марии Волковой (7500.00) — со статусом «отменён», остальные три —
«новый». Одно условие изменило две строки — неуникальный WHERE в UPDATE
действует на все подходящие строки.

**seed_sql:**

```sql
CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer VARCHAR(100) NOT NULL,
    total DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    status VARCHAR(20) NOT NULL DEFAULT 'новый'
);

INSERT INTO orders (customer, total) VALUES
    ('Анна Петрова', 4990.00),
    ('Иван Сидоров', 15990.00),
    ('Мария Волкова', 7500.00),
    ('Дмитрий Козлов', 790.00),
    ('Ольга Смирнова', 450.00);
```

**expected_rows:**

| id | customer       | total    | status   |
| -- | -------------- | -------- | -------- |
| 1  | Анна Петрова   | 4990.00  | новый    |
| 2  | Иван Сидоров   | 15990.00 | отменён  |
| 3  | Мария Волкова  | 7500.00  | отменён  |
| 4  | Дмитрий Козлов | 790.00   | новый    |
| 5  | Ольга Смирнова | 450.00   | новый    |

**runtime:** mysql

### Задание 3: Разбор полётов

Комбо: сначала изменение, потом удаление — и взгляд на остаток.

<!-- Эталонное решение (для автора/бота-верификатора): UPDATE orders SET status = 'отменён' WHERE total > 5000; DELETE FROM orders WHERE total < 800; SELECT id, customer, total, status FROM orders ORDER BY id; -->

**statement:**

Таблица `orders` — та же, пять заказов. Проведите чистку в два шага:
сначала отмените (статус «отменён») все заказы дороже 5000, затем удалите
совсем все заказы дешевле 800. После этого выведите оставшиеся строки
(id, customer, total, status).
