Четвёртый урок уровня «Основы» научил нас добавлять строки командой `INSERT INTO ... VALUES (...)` — но там значения всегда были заданы буквально, вручную, прямо в тексте запроса. Реальные системы регулярно сталкиваются с другой задачей: перенести данные, которые уже существуют **в результате какого-то запроса**, в другую таблицу — например, скопировать заказы за прошлый год в архивную таблицу, или построить сводную таблицу статистики на основе агрегации из основных данных. Кроме того, при повторной загрузке одних и тех же данных (например, если по ошибке или намеренно один и тот же файл экспорта запускается дважды) обычный `INSERT` либо создаст дубликаты, либо упадёт с ошибкой нарушения `UNIQUE`/`PRIMARY KEY` — для таких ситуаций нужны специальные, «умные» формы вставки. Обе темы — предмет этого урока.

### INSERT ... SELECT: вставка результата запроса

`INSERT ... SELECT` заменяет список значений `VALUES (...)` на произвольный `SELECT`-запрос — MySQL вставляет в целевую таблицу ровно те строки, которые вернул бы этот `SELECT`, если бы его выполнили самостоятельно:

```sql
INSERT INTO archived_orders (id, customer_id, status, created_at)
SELECT id, customer_id, status, created_at
FROM orders
WHERE created_at < '2024-01-01';
```

Список столбцов после имени целевой таблицы (`archived_orders (id, customer_id, status, created_at)`) обязателен по тем же соображениям, что и в обычном `INSERT` из четвёртого урока: явное указание столбцов защищает от ошибки, если порядок столбцов в двух таблицах когда-нибудь окажется разным, и делает намерение запроса очевидным для любого, кто его читает позже. Число и порядок столбцов в списке `SELECT` должны точно соответствовать списку столбцов `INSERT` — значения подставляются позиционно, а не по имени.

Источником для `SELECT` может быть что угодно из уже пройденного материала — `JOIN`, агрегация, `CASE`, даже CTE. Например, сохранить сводную статистику по клиентам в отдельную таблицу-отчёт для быстрого доступа без пересчёта на каждый визит:

```sql
INSERT INTO customer_stats_snapshot (customer_id, orders_count, total_spent, snapshot_date)
SELECT
    c.id,
    COUNT(DISTINCT o.id),
    COALESCE(SUM(oi.quantity * oi.price), 0),
    CURDATE()
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
LEFT JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.id;
```

Эта конструкция объединяет практически весь набор инструментов уровня «Начинающий» (`LEFT JOIN`, `GROUP BY`, `COUNT(DISTINCT ...)`, `COALESCE`) в один шаг подготовки данных для последующей вставки — типичный паттерн ETL (Extract, Transform, Load): данные извлекаются и преобразуются одним `SELECT`, а затем загружаются в целевую таблицу одной командой.

### Проблема повторной загрузки: дубликаты и ошибки уникальности

Представим, что импорт заказов из внешней системы запускается регулярно (например, раз в час) и каждый раз выгружает не только новые заказы, но и уже ранее загруженные — потому что внешняя система не умеет отдавать только «свежие» изменения. Обычный `INSERT` в этом случае обречён на одно из двух: если у таблицы есть `UNIQUE`/`PRIMARY KEY` на внешнем идентификаторе заказа (что и должно быть по шестому уроку уровня «Основы» — иначе не от чего защищаться), повторная вставка того же `id` вызовет ошибку 1062 (Duplicate entry) и прервёт весь запрос; если такого ограничения нет — данные просто задублируются молча, что не лучше. Нужен способ вставки, который явно говорит: «если такая строка уже есть — не создавай новую, а поступи иначе».

### INSERT IGNORE: молча пропустить конфликтующие строки

Простейший вариант — `INSERT IGNORE`: при конфликте с `UNIQUE`/`PRIMARY KEY` MySQL не прерывает выполнение ошибкой, а просто **пропускает** конфликтующую строку, продолжая со следующей:

```sql
INSERT IGNORE INTO products (id, name, price, stock)
VALUES
    (1, 'Клавиатура механическая', 4500.00, 12),
    (2, 'Мышь беспроводная', 1200.00, 30);
```

Если товар с `id = 1` уже существует, MySQL просто не станет его вставлять повторно (и не станет обновлять существующую строку данными из `VALUES` — старая строка остаётся полностью нетронутой), но продолжит попытку вставить товар с `id = 2`. `INSERT IGNORE` уместен, когда повторная загрузка одних и тех же строк ожидаема и достаточно просто «оставить как было» — например, при импорте справочника, где новые записи должны появиться, а существующие не нужно ни трогать, ни дублировать.

Важная оговорка: `INSERT IGNORE` подавляет не только ошибки уникальности, но и некоторые другие предупреждения (например, попытку вставить `NULL` в столбец с `NOT NULL` — вместо ошибки MySQL вставит значение по умолчанию для типа столбца и выдаст лишь предупреждение). Из-за этого «тихого» поведения `INSERT IGNORE` стоит использовать осознанно, а не как универсальный способ «подавить любую ошибку» — если цель — именно защита от дубликатов, обычно точнее выражает намерение следующая конструкция.

### REPLACE: удалить и вставить заново

`REPLACE INTO` работает противоположно `INSERT IGNORE`: при конфликте с `UNIQUE`/`PRIMARY KEY` MySQL **удаляет** старую конфликтующую строку целиком и вставляет новую строку из `VALUES`/`SELECT` на её место:

```sql
REPLACE INTO products (id, name, price, stock)
VALUES (1, 'Клавиатура механическая (обновлённая цена)', 4200.00, 15);
```

Если товар с `id = 1` существовал, старая строка будет полностью удалена, а взамен появится новая — с новыми значениями всех столбцов, включая те, что не были указаны в `VALUES` (для них применятся значения по умолчанию, как для совершенно новой строки, а не сохранятся старые значения). Это ключевое и часто недооценённое отличие `REPLACE` от `UPDATE`: если реальный столбец `stock` не упомянут в `REPLACE`, а в таблице для него есть `DEFAULT 0`, старое значение `stock` пропадёт и станет `0`, а не сохранится. Кроме того, полное удаление и повторная вставка строки означает, что `AUTO_INCREMENT`-счётчики других таблиц, ссылающихся на удалённую строку через `FOREIGN KEY`, могут спровоцировать каскадные эффекты (`ON DELETE CASCADE`/`SET NULL` из двенадцатого урока уровня «Начинающий») — то есть `REPLACE` физически выполняет `DELETE`, со всеми его последствиями, а не «безопасное» изменение на месте. По этим причинам `REPLACE` требует большей осторожности, чем следующая, наиболее гибкая форма.

### INSERT ... ON DUPLICATE KEY UPDATE: настоящий upsert

Третья, самая точная и самая часто рекомендуемая форма — `INSERT ... ON DUPLICATE KEY UPDATE`: при конфликте с `UNIQUE`/`PRIMARY KEY` MySQL не удаляет старую строку и не пропускает новую, а **обновляет** уже существующую строку по явно указанным правилам, не трогая остальные столбцы:

```sql
INSERT INTO products (id, name, price, stock)
VALUES (1, 'Клавиатура механическая', 4200.00, 15)
ON DUPLICATE KEY UPDATE
    price = VALUES(price),
    stock = VALUES(stock);
```

Здесь `VALUES(price)` — специальная конструкция, означающая «то значение `price`, которое пытались вставить» (то есть `4200.00` из `VALUES` выше), а не значение из какой-либо другой строки. При конфликте по `id = 1` MySQL обновит только `price` и `stock` существующей строки, оставив, например, `name` нетронутым, даже если в `VALUES` он был указан иначе, — потому что в `ON DUPLICATE KEY UPDATE` для `name` явно не написано правило обновления. Если конфликта не произошло (такого `id` ещё не существовало), выполняется обычная вставка новой строки со всеми значениями из `VALUES` — часть после `ON DUPLICATE KEY UPDATE` в этом случае просто не используется.

Именно эта форма правильно называется **upsert** (от «update» + «insert» — «обновить, если есть; вставить, если нет») и считается наиболее предсказуемым инструментом среди трёх, потому что позволяет отдельно и явно решить, что делать со **старыми** значениями остальных столбцов, вместо неявного «всё стирается» (`REPLACE`) или «всё игнорируется» (`INSERT IGNORE`). Практический пример осмысленного upsert — «наращивать» счётчик вместо простой перезаписи:

```sql
INSERT INTO product_view_counters (product_id, views_count)
VALUES (42, 1)
ON DUPLICATE KEY UPDATE
    views_count = views_count + 1;
```

При первом заходе на товар строка не существует — вставится новая с `views_count = 1`. При каждом следующем заходе конфликт по `product_id` сработает, и `views_count = views_count + 1` увеличит существующее значение на единицу — конструкция, недоступная ни `INSERT IGNORE` (пропустил бы конфликт целиком, не увеличив счётчик), ни `REPLACE` (стёр бы строку и создал заново с `views_count = 1`, потеряв накопленное значение).

### Идемпотентность: зачем всё это в контексте повторных запусков

Все три конструкции этого урока решают одну общую задачу — **идемпотентность** загрузки: свойство операции, при котором повторный запуск с теми же входными данными не создаёт нового, отличного от первого результата (в отличие от обычного `INSERT`, где второй запуск того же скрипта либо дублирует данные, либо ломается на ошибке уникальности). Выбор конкретной конструкции — вопрос того, что должно произойти со старыми данными при повторном запуске: полностью проигнорировать новые (`INSERT IGNORE`), полностью заменить строку (`REPLACE`), или аккуратно обновить только нужные столбцы, сохранив остальное (`ON DUPLICATE KEY UPDATE`) — в большинстве практических сценариев ETL и импорта данных именно последний вариант оказывается наиболее правильным по умолчанию.

### Резюме

- **`INSERT INTO ... SELECT ...`** вставляет в целевую таблицу результат произвольного `SELECT` (с `JOIN`, `GROUP BY`, `CASE` и любыми другими уже изученными инструментами) вместо буквального списка `VALUES`; список столбцов при вставке обязателен и должен позиционно соответствовать списку `SELECT`.
- Повторный запуск обычного `INSERT` с теми же данными либо создаёт дубликаты (без `UNIQUE`), либо завершается ошибкой 1062 (с `UNIQUE`/`PRIMARY KEY`) — для идемпотентной загрузки нужны специальные конструкции.
- **`INSERT IGNORE`** при конфликте с `UNIQUE`/`PRIMARY KEY` молча пропускает новую строку, оставляя существующую нетронутой; также подавляет некоторые другие предупреждения — использовать осознанно.
- **`REPLACE INTO`** при конфликте удаляет старую строку целиком и вставляет новую — столбцы, не указанные явно, теряют старые значения и получают значения по умолчанию; физически это `DELETE` + `INSERT`, со всеми последствиями для внешних ключей.
- **`INSERT ... ON DUPLICATE KEY UPDATE`** — настоящий upsert: при конфликте обновляет только явно указанные столбцы существующей строки (доступ к вставляемому значению — через `VALUES(col)`), оставляя остальные без изменений; поддерживает инкрементальные обновления вроде счётчиков (`col = col + 1`).
- Идемпотентность загрузки — практическое требование к любому импорту/ETL-скрипту, который может быть запущен повторно; из трёх конструкций `ON DUPLICATE KEY UPDATE` обычно даёт наиболее предсказуемый и контролируемый результат.

### Вопрос 1: Выполняется `REPLACE INTO products (id, name, price) VALUES (1, 'Мышь', 1200.00)` для таблицы, где у столбца `stock` объявлено `DEFAULT 0`, а у товара с `id = 1` было `stock = 30`. Что окажется в `stock` после выполнения?

- ✅ `0` — REPLACE удаляет старую строку целиком и вставляет новую, поэтому неперечисленные столбцы получают значения по умолчанию, а не старые значения
<!-- REPLACE — это физически DELETE + INSERT, а не UPDATE на месте -->
- ❌ `30` — старое значение сохранится — error_text: так ведёт себя `INSERT ... ON DUPLICATE KEY UPDATE`: столбцы, для которых не написано правило, не трогаются. `REPLACE` же удаляет конфликтующую строку со всеми её значениями и вставляет новую — всё неперечисленное берётся из `DEFAULT` (или становится `NULL`, если умолчания нет).
- ❌ `NULL` — error_text: `NULL` был бы, только если у столбца нет `DEFAULT` и он допускает `NULL`. Здесь объявлено `DEFAULT 0`, и новая строка, вставленная взамен удалённой, получает именно `0`.
- ❌ `1` — error_text: `REPLACE` ничего не инкрементирует. Единица в примере — это `id` вставляемой строки, а `stock` в ней не указан, поэтому после удаления старой строки (`stock = 30` ушёл вместе с ней) столбец получит значение по умолчанию `0`.

- ✅ `INSERT INTO counters (product_id, views_count) VALUES (42, 1) ON DUPLICATE KEY UPDATE views_count = views_count + 1`
<!-- инкрементальное обновление доступно только upsert: новое значение выражается через старое -->
- ❌ `INSERT IGNORE INTO counters (product_id, views_count) VALUES (42, 1)` — error_text: при конфликте `INSERT IGNORE` пропустит новую строку целиком — существующий счётчик не изменится и перестанет расти. Он умеет только «оставить как было», но не нарастить значение.
- ❌ `REPLACE INTO counters (product_id, views_count) VALUES (42, 1)` — error_text: `REPLACE` удалит старую строку вместе с накопленным значением и вставит новую с `views_count = 1` из `VALUES` — счётчик будет сбрасываться при каждом заходе. Выражение «старое значение + 1» внутри `REPLACE` написать нельзя.
- ❌ обычный `INSERT` — строки же всё равно разные — error_text: если на `product_id` есть `UNIQUE`/`PRIMARY KEY` (а для счётчика он обязателен — шестой урок уровня «Основы»), второй `INSERT` с тем же значением упадёт с ошибкой 1062 Duplicate entry и прервёт запрос. Именно этот сценарий и требует upsert-конструкции.

### Вопрос 3: Что произойдёт при выполнении `INSERT IGNORE INTO t (a, b) VALUES (1, NULL)`, если столбец `b` объявлен `NOT NULL` без `DEFAULT`?

- ✅ строка вставится со значением по умолчанию для типа столбца `b` вместо ошибки — `INSERT IGNORE` превращает отказ в предупреждение; из-за этого «тихого» поведения его применяют осознанно
<!-- INSERT IGNORE подавляет не только конфликты уникальности, но и некоторые другие ошибки -->
- ❌ ошибка 1048 Column cannot be null, как при обычном INSERT — error_text: без `IGNORE` вы получили бы именно её. `IGNORE` превращает ошибку в предупреждение и вставляет значение по умолчанию для типа столбца — поэтому использовать его как «подавитель любых ошибок» опасно: можно не заметить испорченные данные.
- ❌ строка будет пропущена, как при конфликте уникальности — error_text: пропуск — реакция на конфликт `UNIQUE`/`PRIMARY KEY`, когда строка не может быть вставлена без нарушения чужой уникальности. Здесь строка вставляется — просто `NULL` молча заменяется значением по умолчанию для типа столбца.
- ❌ `NULL` сохранится, потому что IGNORE отключает проверку NOT NULL — error_text: проверка остаётся — меняется реакция на неё: вместо ошибки появляется предупреждение, а в таблицу попадает значение по умолчанию для типа столбца. Хранить `NULL` в `NOT NULL`-столбце невозможно в принципе.

### Вопрос 4: Выполняется `INSERT INTO products (id, name, price) VALUES (1, 'Мышь', 1200.00) ON DUPLICATE KEY UPDATE price = VALUES(price)`; строка с `id = 1` уже существует (`name = 'Старая мышь'`, `price = 900.00`). Что станет с `name`?

- ✅ останется «Старая мышь» — `ON DUPLICATE KEY UPDATE` меняет только столбцы, явно перечисленные после него
<!-- name нет в списке обновления — конфликтной строке он не переприсваивается -->
- ❌ станет «Мышь» — error_text: значения из `VALUES` подставляются только в столбцы, для которых написано правило в `ON DUPLICATE KEY UPDATE`. Для `name` правила нет — существующее значение не трогается. В этой точности upsert и превосходит `REPLACE`.
- ❌ станет `NULL` — error_text: «стереть неперечисленное» — это поведение `REPLACE`, который удаляет старую строку и вставляет новую (неперечисленное берётся из `DEFAULT`). `ON DUPLICATE KEY UPDATE` обновляет существующую строку на месте, и нетронутые столбцы сохраняют значения.
- ❌ запрос упадёт с ошибкой 1062 — error_text: именно эту ошибку `ON DUPLICATE KEY UPDATE` и призван заменить: при конфликте уникальности вместо отказа выполняется `UPDATE` по указанным правилам. Ошибка 1062 осталась бы у обычного `INSERT`.

### Вопрос 5: `INSERT INTO archive (id, total, created_at) SELECT id, amount, created_at FROM orders WHERE status = 'delivered'` — как должны соответствовать столбцы SELECT столбцам INSERT?

- ✅ по числу и порядку: значения подставляются позиционно — первый столбец SELECT в первый столбец INSERT, второй во второй и так далее
<!-- соответствие позиционное, а не по именам -->
- ❌ по именам: MySQL сопоставляет столбцы SELECT и INSERT по названиям — error_text: соответствие строго позиционное. Если поменять местами `amount` и `created_at` в SELECT, значения «уедут» не в свои столбцы без всякой ошибки. Совпадение имён ничего не гарантирует.
- ❌ по именам таблиц: столбцы должны называться как таблица-приёмник — error_text: имена таблиц в подстановке значений не участвуют. Важны только явный список столбцов после имени целевой таблицы и позиционное соответствие списку SELECT.
- ❌ достаточно совпадения числа столбцов, типы MySQL приведёт сам — error_text: число столбцов совпадать обязано, но полагаться на неявное приведение типов опасно: вставка даты в числовой столбец может обернуться нулём или мусором вместо отказа. Типы должны быть совместимы по смыслу, а порядок — совпадать позиционно.

### Задание 2: Upsert-загрузка цен из staging

`INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`: существующие товары обновляются точечно, новые вставляются; повторный прогон ничего не меняет.

<!-- Эталонное решение (для автора/бота-верификатора): INSERT INTO products (id, name, price, stock) SELECT id, name, price, stock FROM products_stage ON DUPLICATE KEY UPDATE price = VALUES(price), stock = VALUES(stock); SELECT id, name, price, stock FROM products ORDER BY id; -->

**statement:**

Таблица `products` (`id` — первичный ключ, `name`, `price`, `stock`) —
целевой каталог из трёх товаров; `products_stage` (`id`, `name`,
`price`, `stock`) — свежая выгрузка поставщика: существующие `id` с
новыми ценами и остатками (названия в выгрузке — черновые и меняться не
должны), плюс один новый товар. Загрузите выгрузку в каталог одним
запросом `INSERT INTO products (id, name, price, stock) SELECT id,
name, price, stock FROM products_stage ON DUPLICATE KEY UPDATE price =

### Задание 3: Импорт справочника без перезаписи

<!-- Эталонное решение (для автора/бота-верификатора): INSERT IGNORE INTO customers (name, email, city) SELECT name, email, city FROM customers_stage; SELECT name, email, city FROM customers ORDER BY email; -->
