### Долги трёх уроков

Уровень «Начинающий» закрылся мини-проектом — горизонтальной сборкой.
Сегодня — другой способ: **вложить один SELECT в другой**. Три
обещания ждали:

- Урок 8 «Начинающего»: ошибка 1111; вопрос «товары дороже средней»
  просит сравнить строку с одним числом.
- Урок 2 «Начинающего»: `IN` со списком литералов; отложенный
  `IN (SELECT ...)`.
- Урок 14: отложенный анти-join через `NOT IN`.

Все три закрываются одной идеей: SELECT умеет быть **деталью** другого
SELECT — числом, списком или таблицей.

### Мост: от двух запросов к одному вложенному

Вопрос дня: «какие товары дороже средней цены?». Руками — посчитать
среднее, затем подставить в WHERE. После добавления товара средняя
уедет, литерал соврёт. Настоящее решение — посчитать среднее
**внутри** внешнего запроса:

```sql
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price DESC;
```

```text
+--------------------------+----------+
| name                     | price    |
+--------------------------+----------+
| Монитор 27"              | 15990.00 |
| Клавиатура механическая  |  4990.00 |
+--------------------------+----------+
```

Внутренний SELECT — **подзапрос** (subquery). Его можно вырезать и
выполнить отдельно. Внешний SELECT берёт его результат как значение.
Скобки обязательны: так сервер отличает «вложенный запрос» от «ещё
одно имя столбца».

Это и есть мост уровня. Простой SELECT читает таблицу. SELECT с
агрегатом сворачивает её в число. Подзапрос делает это число
**источником для другого SELECT**. Дальше по мосту — когда результат
внутреннего запроса это не число, а таблица (производная таблица в
FROM), и когда этой таблице дают имя заранее (CTE). Подзапрос и CTE —
способы **композиции**: собрать сложный вопрос из простых запросов.

JOIN склеивает таблицы **по горизонтали**, подзапрос вкладывает запрос
**внутрь** другого, UNION склеит результаты **по вертикали** (урок 3
«Среднего»).

Проверка на сегодня: внутренний SELECT можно скопировать в клиент и
запустить без внешнего. Если для работы ему нужна колонка внешней
строки — это уже **коррелированный** подзапрос, урок 2 «Среднего».
Все сегодняшние внутренние запросы самостоятельны.

### Скалярный подзапрос: одно значение

**Скалярный** подзапрос возвращает **не более одной строки** (0 строк
даёт NULL, две и больше — ошибку 1242) и **ровно один столбец** — число,
строку или NULL. Ставится туда, где ждут значение: WHERE, список SELECT,
HAVING.

WHERE мы уже видели. Тот же порог можно показать рядом с ценой:

```sql
SELECT name,
       price,
       (SELECT ROUND(AVG(price), 2) FROM products) AS avg_price
FROM products
ORDER BY id;
```

```text
+--------------------------+----------+-----------+
| name                     | price    | avg_price |
+--------------------------+----------+-----------+
| Коврик для мыши          |   690.00 |   4310.08 |
| Мышь беспроводная        |  1290.50 |   4310.08 |
| Клавиатура механическая  |  4990.00 |   4310.08 |
| Монитор 27"              | 15990.00 |   4310.08 |
| Кабель HDMI 2 м          |   450.00 |   4310.08 |
| Веб-камера               |  2450.00 |   4310.08 |
+--------------------------+----------+-----------+
```

На каждой строке одно и то же 4310.08: внутренний запрос не смотрит
на текущий товар — это свойство некоррелированного подзапроса. Для
отчёта «цена и порог рядом» это то, что нужно.

Почему это не ошибка 1111? `AVG(price)` стоит не в WHERE внешнего
запроса, а во внутреннем SELECT: у того свой конвейер, и он
заканчивается одним числом. Внешний WHERE сравнивает `price` строки
с готовым числом.

Пустой внутренний результат — это NULL, не ошибка. Сравнение с NULL
даёт «неизвестно», и WHERE строку отбрасывает (урок 11 «Основ»):

```sql
SELECT name
FROM products
WHERE price > (SELECT AVG(price) FROM products WHERE 1 = 0);
```

Пустой набор. `AVG` по нулю строк — NULL (урок 8 «Начинающего»),
`price > NULL` — не «да».

Две строки во внутреннем запросе — уже ошибка. Скаляру не из чего
выбрать «главную»:

```sql
SELECT name
FROM products
WHERE price > (SELECT price FROM products WHERE category_id = 2);
```

```text
ERROR 1242 (21000): Subquery returns more than 1 row
```

В категории 2 три товара — три цены. Лекарство — сузить внутренний
запрос до одной строки (`AVG`, `MIN`, `MAX`) либо перейти к `IN`.

Несколько столбцов там, где ждут один, ловятся отдельно:

```sql
SELECT name
FROM products
WHERE id IN (SELECT id, name FROM products);
```

```text
ERROR 1241 (21000): Operand should contain 1 column(s)
```

`IN` ждёт столбец значений, не пару «id + имя».

#### `=` против `IN`: где граница

Один и тот же внутренний запрос для категории 2 даёт три цены. Слева —
разный оператор, и результат разный:

```sql
-- скаляр: три строки — ошибка 1242
SELECT name FROM products
WHERE price = (SELECT price FROM products WHERE category_id = 2);

-- список: три строки — корректное членство
SELECT name FROM products
WHERE price IN (SELECT price FROM products WHERE category_id = 2);
```

`=` ждёт одно значение, `IN` допускает множество. Поэтому скаляр требует
сужения внутреннего запроса до одной строки; `IN` — нет. Скаляр падает
там, где `IN` работает.

### IN (подзапрос): список из другого запроса

Урок 2 научил `city IN ('Москва', 'Казань')` — членство в заранее
известном списке. Когда список живёт в другой таблице, его собирает
SELECT:

```sql
SELECT name
FROM customers
WHERE id IN (SELECT customer_id FROM orders)
ORDER BY id;
```

```text
+---------------+
| name          |
+---------------+
| Анна Петрова  |
| Иван Сидоров  |
+---------------+
```

Смысл тот же, что у `IN (1, 2)`: «id покупателя — один из `customer_id`,
которые встречаются в заказах». Тот же вопрос через INNER JOIN:

```sql
SELECT c.name
FROM customers AS c
INNER JOIN orders AS o ON o.customer_id = c.id
ORDER BY c.id, o.id;
```

```text
+---------------+
| name          |
+---------------+
| Анна Петрова  |
| Анна Петрова  |
| Иван Сидоров  |
+---------------+
```

У Анны два заказа — JOIN дал две строки. `IN` оставляет Анну **один
раз**: внешняя строка учитывается независимо от числа совпадений,
потому что у `customers.id` уникальный ключ. `IN` сам по себе
дубликаты не «схлопывает» — он проверяет членство. Если нужен
список тех, у кого заказ **есть**, без повторов — `IN` (или JOIN
плюс `DISTINCT` / `GROUP BY`, но это уже обход).

Перед выбором спросите про **зерно результата**: одна строка на
покупателя → `IN` или `EXISTS`; одна строка на заказ → `JOIN`;
одна строка на покупателя с числом заказов → `JOIN + GROUP BY`. Это
правило связывает урок с JOIN предыдущего уровня.

`NOT IN` — отрицание членства, второй ответ на «покупатели без
заказов»:

```sql
SELECT id, name
FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders)
ORDER BY id;
```

```text
+----+---------------+
| id | name          |
+----+---------------+
|  3 | Мария Волкова |
|  4 | Пётр Смирнов  |
+----+---------------+
```

Тот же результат, что у анти-join урока 14:

```sql
SELECT c.id, c.name
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.id;
```

JOIN честнее, когда нужны столбцы правой таблицы (даже NULL). `NOT IN`
короче, когда нужна только левая сторона и внутренний столбец **без
NULL**.

NULL в списке `NOT IN` урока 2 уже был чёрной дырой. Подзапрос открывает ту же дыру, если внутренняя колонка может быть NULL:

```sql
-- если подзапрос вернул хотя бы один NULL,
-- `id NOT IN (...)` для обычных id даёт UNKNOWN
-- (трёхзначная логика урока 2 «Начинающего»)
-- и ни одна строка не проходит WHERE
SELECT id, name
FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);
```

Трёхзначная логика та же: «не равно NULL» — «неизвестно», после NOT —
снова не «да». В нашей схеме `orders.customer_id` — NOT NULL под
внешним ключом, и дыра закрыта. Если NULL возможен — либо
`WHERE столбец IS NOT NULL` внутри, либо анти-join через LEFT JOIN.
`EXISTS` / `NOT EXISTS` — следующий урок.

### Производная таблица: SELECT в FROM

Иногда внутренний запрос должен вернуть не число и не список id, а
**таблицу** — несколько строк и столбцов, с которыми внешний запрос
работает как с обычной. Такой подзапрос ставят в FROM и называют
**производной таблицей** (derived table).

Задача, которую GROUP BY в одном запросе не решит: «товары дороже
средней цены **своей** категории». Если сгруппировать `products` по
`category_id`, строки товаров исчезнут — останется по одной строке на
категорию. Нужны оба зерна: внутри — среднее по категории, снаружи —
товары.

Внутренний запрос считает средние:

```sql
SELECT category_id, AVG(price) AS avg_price
FROM products
GROUP BY category_id
ORDER BY category_id;
```

```text
+-------------+--------------+
| category_id | avg_price    |
+-------------+--------------+
|           1 |   570.000000 |
|           2 |  2910.166667 |
|           3 | 15990.000000 |
+-------------+--------------+
```

Аксессуары (коврик 690 и кабель 450) — 570. Периферия — 2910.17. Монитор
один в категории, среднее совпадает с его ценой.

`ORDER BY` внутреннего запроса нужен только ради читаемости его
собственного вывода: порядок строк внешнего результата он не задаёт —
для упорядочивания результата `ORDER BY` должен быть снаружи.

Внешний запрос присоединяет эту таблицу к товарам:

```sql
SELECT p.name,
       p.price,
       ROUND(cat_avg.avg_price, 2) AS category_avg
FROM products AS p
JOIN (
    SELECT category_id, AVG(price) AS avg_price
    FROM products
    GROUP BY category_id
) AS cat_avg ON cat_avg.category_id = p.category_id
WHERE p.price > cat_avg.avg_price
ORDER BY p.id;
```

```text
+--------------------------+---------+--------------+
| name                     | price   | category_avg |
+--------------------------+---------+--------------+
| Коврик для мыши          |  690.00 |       570.00 |
| Клавиатура механическая  | 4990.00 |      2910.17 |
+--------------------------+---------+--------------+
```

Коврик дороже среднего по аксессуарам, хотя дешевле средней **всего**
каталога. Клавиатура дороже среднего по периферии. Монитор равен
своему среднему — `>` его не берёт; веб-камера ниже. Два разных
порога, один приём: внутренний SELECT стал таблицей с именем
`cat_avg`, внешний JOIN и WHERE работают с её столбцами как с
настоящими.

Алиас производной таблицы **обязателен**. Без него MySQL 8 не принимает
запрос:

```sql
SELECT p.name
FROM products AS p
JOIN (
    SELECT category_id, AVG(price) AS avg_price
    FROM products
    GROUP BY category_id
) ON ... ;
```

```text
ERROR 1248 (42000): Every derived table must have its own alias
```

Имя — как у любой таблицы в FROM: дальше `cat_avg.avg_price`, иначе
ошибка 1052.

Бонус конвейера: алиас `avg_price` внутреннего SELECT во внешнем
запросе — обычный столбец, его можно ставить в WHERE, JOIN, ORDER BY.
Во внутреннем запросе этот алиас в WHERE по-прежнему недоступен —
этажи не смешались, просто появился второй запрос со своим
конвейером.

Тот же приём заменяет HAVING, когда после группировки с результатом ещё
предстоит JOIN или построчный WHERE — как с `cat_avg`. Простое
`HAVING COUNT(*) > 1` здесь короче; сила производной таблицы — в
сохранении зерна строк.

### CTE: именованный промежуточный результат

Производная таблица живёт в середине FROM — читать запрос снизу вверх.
MySQL 8 умеет вынести внутренний SELECT **наверх** и дать ему имя до
основного запроса. Это **CTE** — common table expression; синтаксис —
`WITH`:

```sql
WITH cat_avg AS (
    SELECT category_id, AVG(price) AS avg_price
    FROM products
    GROUP BY category_id
)
SELECT p.name, p.price
FROM products AS p
JOIN cat_avg ON cat_avg.category_id = p.category_id
WHERE p.price > cat_avg.avg_price
ORDER BY p.id;
```

`WITH cat_avg AS (SELECT ...)` объявляет имя; основной SELECT
использует его как таблицу. Для наших простых примеров CTE можно
рассматривать как именованный промежуточный результат, похожий по
роли на производную таблицу. Читать легче, когда вложенность растёт.

Сегодня — последний пролёт моста: «назвать промежуточный SELECT».
Цепочки `WITH`, рекурсия и календарная таблица — урок 4 «Среднего».

### Где живёт подзапрос

Краткая карта мест, которые сегодня законны:

- **WHERE / HAVING** — скаляр (`=`, `>`, `<`) или членство (`IN` /
  `NOT IN`).
- **список SELECT** — только скаляр; на каждой внешней строке —
  одно значение.
- **FROM** — производная таблица, обязательно с алиасом.
- **WITH** — именованный вариант производной таблицы.

Во всех четырёх внутренний запрос сегодня **самостоятелен**. Скобки
вокруг подзапроса в WHERE/SELECT/FROM обязательны.

### Типичные ошибки

**Агрегат внешнего запроса в WHERE.** `WHERE AVG(price) > 100` по-прежнему
ошибка 1111: подзапрос не отменяет правило, а переносит агрегат во
внутренний конвейер.

**Скаляр получил несколько строк.** Ошибка 1242. Источник —
забытый агрегат: хотели среднюю, а написали `SELECT price FROM ...`.

**Лишние столбцы во внутреннем SELECT.** Ошибка 1241. `IN` сравнивает
с одним столбцом. `SELECT *` внутри подзапроса — почти всегда лишний.

**Производная таблица без алиаса.** Ошибка 1248. Даже если таблица
«очевидно одна» — имя всё равно нужно.

**`NOT IN` и NULL.** Пустой результат при живых строках, которые «должны
были пройти». Сначала проверьте, может ли внутренний столбец быть NULL.

**Размножение вместо членства.** `INNER JOIN orders` вместо `IN`, и в
отчёте «кто заказывал» Анна в двух экземплярах.

### Чего в этом уроке нет

- Коррелированные подзапросы и `EXISTS` / `NOT EXISTS` — урок 2
  «Среднего».
- `UNION` / `UNION ALL` — урок 3 «Среднего».
- Цепочки CTE, рекурсивные CTE, календарная таблица — урок 4
  «Среднего».
- Оконные функции — уроки 5–6 «Среднего».
- Что быстрее — JOIN или `IN` — продвинутый уровень, блок про индексы
  и EXPLAIN.

### Резюме

- Подзапрос — SELECT внутри другого SELECT. Сегодня он самостоятелен.
- Скаляр — не более одной строки (0 → NULL, ≥ 2 → 1242) и ровно один
  столбец (иначе 1241).
- `WHERE price > (SELECT AVG(price) FROM products)` закрывает долг
  ошибки 1111: агрегат во внутреннем конвейере, внешний WHERE
  сравнивает строку с числом.
- `IN (SELECT ...)` — список урока 2, собранный запросом.
- `NOT IN` — анти-join списком, пока во внутреннем столбце нет NULL.
- Производная таблица — подзапрос в FROM с обязательным алиасом
  (1248). Так сравнивают строку со статистикой группы.
- CTE (`WITH имя AS (SELECT ...)`) — именованная производная таблица.

## Теоретические задания

### Вопрос 1: Почему `WHERE AVG(price) > 100` даёт ошибку 1111, а `WHERE price > (SELECT AVG(price) FROM products)` выполняется?

- ✅ потому что AVG считается отдельным внутренним SELECT и возвращает одно число; внешний WHERE сравнивает строку с этим готовым числом, не вычисляя агрегат сам
<!-- два конвейера: внутренний сворачивает таблицу в скаляр, внешний WHERE работает построчно, как в уроке 6 -->
- ❌ потому что MySQL 8 разрешил агрегаты в WHERE, если они в скобках — error_text: скобки сами по себе правило не меняют. `WHERE AVG(price) > 100` с скобками вокруг AVG по-прежнему 1111: агрегат внешнего запроса в WHERE запрещён. Нужен именно отдельный SELECT внутри скобок.
- ❌ потому что подзапрос выполняется после HAVING, и к этому моменту AVG уже есть — error_text: порядок внешнего конвейера не переставляет агрегат в WHERE. Внутренний SELECT — свой конвейер, он не «ждёт HAVING» внешнего запроса.
- ❌ потому что AVG в подзапросе считается заново для каждой строки товара — error_text: сегодняшние подзапросы не коррелированы: внутренний `SELECT AVG(price) FROM products` считается как самостоятельный запрос и даёт одно и то же число. Построчный пересчёт с оглядкой на внешнюю строку — урок 2 «Среднего».

### Вопрос 2: Скалярный подзапрос в `WHERE price > (SELECT price FROM products WHERE category_id = 2)` вернул три строки. Что сделает MySQL 8?

- ✅ ошибку 1242: Subquery returns more than 1 row
<!-- скаляру нужна одна ячейка; три цены категории 2 — не одно число -->
- ❌ возьмёт первую из трёх цен и сравнит с ней — error_text: сервер не выбирает «первую» молча. Неоднозначный скаляр — ошибка 1242, а не эвристика. Чтобы получить одно число, нужен агрегат или условие, оставляющее одну строку.
- ❌ автоматически превратит сравнение в `IN` по трём ценам — error_text: `>` и `IN` — разные операторы. Несколько значений требуют явного `IN` (или `= ANY`); сервер сам `>` в членство не переписывает.
- ❌ вернёт NULL и отфильтрует все строки — error_text: NULL скаляр даёт, когда внутренний запрос **пуст**. Несколько строк — не пустота, а ошибка 1242.

### Вопрос 3: У Анны два заказа. Сколько строк с её именем вернут `WHERE id IN (SELECT customer_id FROM orders)` и `INNER JOIN orders ON orders.customer_id = customers.id` (без DISTINCT)?

- ✅ IN — одну строку; JOIN — две
<!-- IN проверяет членство и не размножает внешнюю строку; JOIN даёт пару на каждый заказ -->
- ❌ оба вернут две строки — error_text: JOIN даст две, потому что пар две. IN не создаёт пары: «id есть в списке customer_id» — один ответ на покупателя, сколько бы заказов ни стояло в списке.
- ❌ оба вернут одну строку — error_text: JOIN без DISTINCT/GROUP BY повторит Анну по числу заказов. Одна строка была бы у IN или у JOIN с последующим DISTINCT.
- ❌ IN вернёт две, JOIN — одну — error_text: наоборот: размножает соединение, а не проверка членства. Если в отчёте всплыли дубли имён, ищите JOIN, не IN.

### Вопрос 4: `WHERE id NOT IN (SELECT customer_id FROM orders)` вернул пустой результат, хотя покупатели без заказов в таблице есть. Какая причина из разобранных сегодня это объясняет?

- ✅ подзапрос вернул хотя бы один NULL — тогда NOT IN не пропускает никого
<!-- трёхзначная логика урока 2: «не равно NULL» — неизвестно; после NOT ни одной «да» -->
- ❌ NOT IN нельзя применять к целым числам, только к строкам — error_text: тип ни при чём: IN/NOT IN работают с числами, строками и датами. Пустота здесь — семантика NULL, не «не тот тип».
- ❌ покупатели без заказов находятся только LEFT JOIN, подзапрос их принципиально не видит — error_text: при NOT NULL во внутреннем столбце NOT IN даёт тот же набор, что анти-join. Подзапрос «не видит» их только если сработал NULL в списке или условие написано иначе.
- ❌ во внутреннем SELECT забыли DISTINCT, и повторы customer_id обнулили результат — error_text: повторы в IN/NOT IN на членство не влияют: значение либо есть в списке, либо нет. Пустой результат даёт NULL, не дубликат.

### Вопрос 5: Что обязательно указать у подзапроса в FROM, чтобы MySQL 8 принял производную таблицу?

- ✅ алиас таблицы после скобок — иначе ошибка 1248
<!-- Every derived table must have its own alias; дальше внешний запрос ссылается на это имя -->
- ❌ DISTINCT во внутреннем SELECT — error_text: DISTINCT убирает дубликаты строк, но не заменяет имя таблицы. Без алиаса запрос не разберёт FROM, даже если строки уникальны.
- ❌ GROUP BY во внутреннем SELECT — error_text: группировка нужна, только если внутренний запрос сам сворачивает строки. Производная таблица может быть и простым `SELECT id, name FROM products` — алиас всё равно обязателен.
- ❌ CTE (`WITH`) вместо подзапроса в FROM — error_text: CTE — удобная форма той же идеи, не требование. Производная таблица в FROM законна сама по себе, если у неё есть алиас.

### Задание 1: Дороже среднего

Скалярный подзапрос: сравнить цену товара со средней по всей таблице.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT name, price FROM products WHERE price > (SELECT AVG(price) FROM products) ORDER BY price DESC; -->

`(SELECT AVG(price) FROM products)` — не подставляйте число руками.
Финальный SELECT — два столбца: `name`, `price`. Отсортируйте по
