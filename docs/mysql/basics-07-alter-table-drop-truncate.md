# Изменение и удаление таблиц

## Материал

### Обещанный ALTER TABLE

Урок 6 научил создавать таблицу правильной с первого раза: с ключом,
умолчаниями и проверками. Но требования живут дольше любой спецификации:
понадобится столбец, которого никто не предусмотрел; тип окажется тесным;
столбец объявится лишним; а то и вся таблица станет не нужна. В уроке 6 мы
дважды отложили это «на потом»: «изменить готовую таблицу или удалить её —
команды `ALTER TABLE` и `DROP` ждут вас в следующем уроке» — и «правило
задаётся при создании таблицы или добавляется к готовой». Момент настал.

План урока: сначала `ALTER TABLE` в четырёх лицах — добавить столбец,
изменить определение, удалить столбец, добавить ограничение; затем
`DROP TABLE` — таблица целиком; и финал — три способа «удалить» (`DELETE`,
`TRUNCATE`, `DROP`), которые путают чаще всего. Инструмент наблюдения —
знакомый по урокам 5–6 `DESCRIBE`: любое изменение схемы сразу отражается
в его колонках.

Героиня примеров — `suppliers` из урока 6: `id INT AUTO_INCREMENT PRIMARY
KEY`, `name VARCHAR(100) NOT NULL`, `city VARCHAR(50) NOT NULL DEFAULT
'Москва'`; в таблице три поставщика — «Аква-Сервис», «ТехноДом» и
«Северный поставщик».

### ADD COLUMN: новый столбец

Таблица живёт, и в ней появляется место для email:

```sql
ALTER TABLE suppliers ADD COLUMN email VARCHAR(100);
```

Читается как обычное предложение: «измени таблицу `suppliers` — добавь
столбец `email` типа `VARCHAR(100)`». Выполняется как `CREATE TABLE` урока 6:
мгновенно и без таблицы-результата, коротким `Query OK`. А смотрим — снова
`DESCRIBE`:

```text
+-------+--------------+------+-----+---------+----------------+
| Field | Type         | Null | Key | Default | Extra          |
+-------+--------------+------+-----+---------+----------------+
| id    | int          | NO   | PRI | NULL    | auto_increment |
| name  | varchar(100) | NO   |     | NULL    |                |
| city  | varchar(50)  | NO   |     | Москва  |                |
| email | varchar(100) | YES  |     | NULL    |                |
+-------+--------------+------+-----+---------+----------------+
```

Новый столбец встал в конец таблицы — MySQL не спрашивает, куда его
положить (при желании позицию задают явно словами `FIRST` или `AFTER
имя_столбца`, но это уже украшение). Что увидят существующие строки?
Столбец необязательный, умолчания нет — значит, `NULL`, «значение
отсутствует» из урока 5 (полноценно работать с NULL научимся в уроке 11):

```text
+----+----------------------+--------------+-------+
| id | name                 | city         | email |
+----+----------------------+--------------+-------+
|  1 | Аква-Сервис          | Казань       | NULL  |
|  2 | ТехноДом             | Москва       | NULL  |
|  3 | Северный поставщик   | Архангельск  | NULL  |
+----+----------------------+--------------+-------+
```

С умолчанием картина другая:

```sql
ALTER TABLE suppliers ADD COLUMN discount DECIMAL(4,2) NOT NULL DEFAULT 0.00;
```

Теперь существующие строки получили `0.00` — `DEFAULT` из урока 6 работает
и здесь: сервер как будто «пропустил» новый столбец за каждую строку сразу,
и на пропуск сработало значение по умолчанию. Какое умолчание напишете —
такое сразу получат все существующие строки, сколько бы их ни было: в
MySQL 8 добавление столбца — правка схемы, и сами строки сервер не
переписывает (а вот `MODIFY`, меняющий тип, данные перестраивает
по-настоящему — отсюда осторожность ниже). Поэтому формулируйте умолчание
сразу, в самой команде: неудачное значение потом пришлось бы исправлять
уже в данных, а не в схеме.

Ошибки у семейства свои. Добавить столбец с уже занятым именем нельзя:

```text
ERROR 1060 (42S21): Duplicate column name 'email'
```

Читается по схеме урока 3: код → текст → имя. Имена столбцов, как всегда,
надёжнее копировать из `DESCRIBE`, а не набирать по памяти.

### MODIFY COLUMN: определение целиком

Бизнес-требование поменялось: в поле «город» теперь записывают «город,
склад» — 50 символов стало тесно. Меняем тип:

```sql
ALTER TABLE suppliers MODIFY COLUMN city VARCHAR(80) NOT NULL DEFAULT 'Москва';
```

Присмотритесь: определение написано **целиком** — тип плюс все ограничения,
ровно как в `CREATE TABLE` урока 6. Это не педантизм, а главное правило
`MODIFY`: он **заменяет определение столбца полностью**. Что напишете — то
и будет; что забудете — исчезнет. Забыли `NOT NULL` и `DEFAULT`:

```sql
ALTER TABLE suppliers MODIFY COLUMN city VARCHAR(80);
```

Инструкция выполнится без единого предупреждения, а `DESCRIBE` покажет:

```text
+----------+--------------+------+-----+---------+----------------+
| Field    | Type         | Null | Key | Default | Extra          |
+----------+--------------+------+-----+---------+----------------+
| id       | int          | NO   | PRI | NULL    | auto_increment |
| name     | varchar(100) | NO   |     | NULL    |                |
| city     | varchar(80)  | YES  |     | NULL    |                |
| email    | varchar(100) | YES  |     | NULL    |                |
| discount | decimal(4,2) | NO   |     | 0.00    |                |
+----------+--------------+------+-----+---------+----------------+
```

Город стал необязательным, умолчание «Москва» исчезло — молча. Это не
«плохое значение» из урока 5, на которое строгий режим отвечает ошибкой:
сервер сделал ровно то, что просили, — просто просили не то. За схему
отвечаете вы, `DESCRIBE` до и после правки — ваша страховка. (Вернуть
как было — та же команда с полным определением: `Null` снова `NO`,
`Default` снова «Москва».)

Осторожнее с сужением типа: сузить `name` до `VARCHAR(10)`, когда в таблице
лежит «Северный поставщик» (18 символов), строгий режим не даст — ошибка
знакома по уроку 5:

```text
ERROR 1406 (22001): Data too long for column 'name' at row 1
```

При `MODIFY` сервер приводит существующие значения к новому определению —
и если какое-то из значений ему не соответствует, команда завершится
ошибкой; особенно осторожно относитесь к сужению типов. Расширение
`VARCHAR` снимает проблему длины, сужение должно вместить все имеющиеся
значения. Сами данные при `MODIFY` сохраняются — в этом и смысл команды:
поменять определение, не теряя строки.

### Ограничение задним числом

Столбец `email` добавлен — время выполнить второе обещание урока 6:
добавить правило к уже готовой таблице:

```sql
ALTER TABLE suppliers ADD UNIQUE (email);
```

В `DESCRIBE` у `email` появляется пометка `UNI` в колонке `Key` — всё как
у столбцов, родившихся с ограничением. Форма повторяет `CREATE TABLE`:
`ADD UNIQUE (столбец)`, `ADD CHECK (условие)`, `ADD PRIMARY KEY (столбец)`;
именованный вариант — `ADD CONSTRAINT имя UNIQUE (...)` — те же
ограничения урока 6, только со словом `ADD` впереди.

Одна существенная деталь: сервер сначала проверит **существующие**
данные — правило должно выполняться и для строк, которые уже лежат
в таблице. Если повторы есть, команда отклонится знакомой ошибкой:

```text
ERROR 1062 (23000): Duplicate entry 'a@example.com' for key 'email'
```

Та же 1062, что в уроке 6, — только теперь она про старые данные,
а не про новую вставку. Обещание закрыто: правило задаётся при создании
таблицы или добавляется позже, третьего не дано — а проверить, честно ли
оно выполняется, сервер умеет в обе стороны.

### DROP COLUMN: столбец долой

Передумали — email оказался не нужен:

```sql
ALTER TABLE suppliers DROP COLUMN email;
```

Столбец исчезает из схемы, а его значения — из всех строк. Не «стали
`NULL`» — именно исчезли: `SELECT` их больше не покажет, корзины для
столбцов нет. Вместе со столбцом уходит и его уникальность: правило
жило на столбце, столбца нет — правила нет.

Удалить несуществующий столбец нельзя:

```text
ERROR 1091 (42000): Can't DROP 'email'; check that column/key exists
```

Схема чтения та же, из урока 3: код → текст → имя столбца. Код 1091
новый, но приёмы разбора ошибок не меняются с третьего урока.

### DROP TABLE: таблица целиком

Если не нужна вся таблица:

```sql
DROP TABLE gift_cards;
```

Исчезает всё: данные, схема, счётчик `AUTO_INCREMENT`. Таблицы больше нет —
чтобы она появилась снова, нужен `CREATE TABLE` с нуля, пустая. Удалить
несуществующую таблицу — ошибка:

```text
ERROR 1051 (42S02): Unknown table 'shop.gift_cards'
```

(в тексте названы и база, и таблица — удобно, когда сессий открыто
несколько). Для повторно запускаемых скриптов есть та же страховка, что
в уроке 6 у `CREATE TABLE IF NOT EXISTS`:

```sql
DROP TABLE IF EXISTS gift_cards;
```

— молча пропустит отсутствие. Пара `CREATE TABLE IF NOT EXISTS` +
`DROP TABLE IF EXISTS` — стандартный каркас скриптов, которые запускают
много раз: каждый прогон начинает с чистого листа. Базы данных удаляются
по тем же правилам — `DROP DATABASE` из урока 2, с той же осторожностью,
помноженной на масштаб: таблицу пересоздать — минуты, базу со всеми
таблицами — уже история.

### Очистить, но сохранить: TRUNCATE

Чаще, чем удалять таблицы, их приходится очищать: тестовые данные перед
боевым наполнением, черновые строки после экспериментов. Для этого —

```sql
TRUNCATE TABLE orders;
```

`TRUNCATE` — «обрезать»: строк не остаётся, но таблица — та же, схема
на месте, `DESCRIBE` не изменится. Сервер не удаляет строки по одной,
а отбрасывает данные таблицы разом — поэтому на больших таблицах очистка
мгновенная.

И главная деталь: счётчик `AUTO_INCREMENT` сбрасывается. В `orders` лежали
три заказа с id 1–3; после `TRUNCATE` и новой вставки без id:

```sql
TRUNCATE TABLE orders;
INSERT INTO orders (customer, total) VALUES ('Дмитрий Козлов', 3200.00);
SELECT * FROM orders;
```

```text
+----+----------------+---------+
| id | customer       | total   |
+----+----------------+---------+
|  1 | Дмитрий Козлов | 3200.00 |
+----+----------------+---------+
```

Нумерация началась заново: данные ушли — счётчик ушёл вместе с ними.

### DELETE: строки, и только строки

Ту же задачу решает и команда про строки:

```sql
DELETE FROM orders;
```

`DELETE` удаляет строки: без условия `WHERE` — все до единой (с условием —
только подходящие, но условия — большая тема урока 10, не забегаем).
Внешний результат тот же: таблица пуста, схема на месте.

Но счётчик продолжает жить своей жизнью — тот же эксперимент после
`DELETE FROM orders;` даст новой строке id 4:

```text
+----+----------------+---------+
| id | customer       | total   |
+----+----------------+---------+
|  4 | Дмитрий Козлов | 3200.00 |
+----+----------------+---------+
```

Счётчик запоминает наибольший использованный номер — урок 6: строки
удалили, а номер 3 был использован, значит следующий — 4. «Начать
нумерацию заново» через `DELETE` нельзя.

### DELETE, TRUNCATE или DROP?

Три команды с похожим эффектом «таблица пуста» — и тремя разными
последствиями. В одну таблицу, в духе урока 6:

| Команда            | Что удаляется       | Схема        | Счётчик id            |
| ------------------ | ------------------- | ------------ | --------------------- |
| `DELETE FROM t;`   | все строки, по одной | остаётся     | продолжает расти      |
| `TRUNCATE TABLE t;`| все строки, разом   | остаётся     | сбрасывается, с 1     |
| `DROP TABLE t;`    | строки + схема      | таблицы нет  | исчезает с таблицей   |

Выбор: оставить таблицу под новое наполнение с чистой нумерацией —
`TRUNCATE`; удалить часть строк — `DELETE` с условием (урок 10); убрать
таблицу целиком — `DROP`. Репертуар ошибок урока: 1060 (дубликат столбца),
1091 (нет такого столбца), 1051 (нет такой таблицы) — плюс знакомые 1406
и 1062, если правка задевает данные.

И общая осторожность: всё, что в этом уроке, применяется сразу и без
корзины. Перед `DROP COLUMN`, `TRUNCATE` и тем более `DROP TABLE`
дважды посмотрите на имя — чужая таблица с таким же именем не простит.

### Резюме

- `ALTER TABLE ... ADD COLUMN` — новый столбец в конец; существующие строки
  получают `NULL`, а при `DEFAULT` — умолчание; дубликат имени — ошибка 1060.
- `ALTER TABLE ... MODIFY COLUMN` — определение столбца пишется целиком;
  забытое исчезает молча; сужение типа под существующие данные — ошибка 1406.
- `ALTER TABLE ... DROP COLUMN` — столбец и его значения исчезают совсем;
  несуществующий столбец — ошибка 1091.
- `ALTER TABLE ... ADD UNIQUE / CHECK / PRIMARY KEY` — ограничение задним
  числом; существующие данные проверяются, повторы — ошибка 1062.
- `DROP TABLE` — таблица целиком: схема, данные, счётчик; несуществующая —
  ошибка 1051; `IF EXISTS` — страховка скриптов.
- `TRUNCATE TABLE` — быстрая очистка: схема остаётся, счётчик начинается
  с 1.
- `DELETE FROM t;` без условия — удаляет все строки, счётчик продолжает
  расти; `DELETE` с `WHERE` — урок 10.
- Правило выбора: строки — `DELETE`, данные целиком — `TRUNCATE`,
  таблица — `DROP`.

## Теоретические задания

### Вопрос 1: Таблицу `orders` с `id INT AUTO_INCREMENT PRIMARY KEY` очистили командой `TRUNCATE TABLE orders;` и вставили новую строку без указания id. Какой id она получит?

- ✅ 1 — счётчик сброшен вместе с данными
- ❌ следующий после наибольшего прежнего (например, 4) — error_text: так ведёт себя DELETE: строки удаляются, а счётчик продолжает расти; TRUNCATE вместе с данными сбрасывает и нумерацию — новая строка получит id 1.
- ❌ NULL — сервер не знает номера после очистки — error_text: пропущенный id в AUTO_INCREMENT-столбце — сигнал «пронумеруй сам», а не «оставь пустым»: после TRUNCATE счётчик равен нулю, и строке достанется номер 1.

### Вопрос 2: Что останется после выполнения `DROP TABLE orders;`?

- ✅ ничего: ни строк, ни схемы — чтобы работать с таблицей снова, её придётся создать заново
- ❌ пустая таблица со схемой — error_text: это результат TRUNCATE (или DELETE без условия): они очищают данные, но таблицу оставляют; DROP удаляет таблицу целиком — и схему, и строки, и счётчик.
- ❌ таблица со схемой, но без автонумерации — error_text: DROP не «отключает» части таблицы: удаляется всё сразу; схему при очистке данных сохраняют TRUNCATE и DELETE.

### Вопрос 3: Столбец объявлен как `name VARCHAR(20) NOT NULL`. Выполнили `ALTER TABLE products MODIFY COLUMN name VARCHAR(100);` Что стало с обязательностью столбца?

- ✅ исчезла: MODIFY заменяет определение целиком, а NOT NULL в новом определении не указан
- ❌ сохранилась: MODIFY меняет только тип — error_text: MODIFY не дополняет определение, а заменяет его: раз NOT NULL не написан, столбец стал необязательным. Правильно — MODIFY COLUMN name VARCHAR(100) NOT NULL.
- ❌ сервер отклонит инструкцию без явного NOT NULL — error_text: такой проверки нет: MODIFY с неполным определением выполняется без ошибок и предупреждений — «забытые» части определения просто исчезают, в этом и ловушка.

### Вопрос 4: В таблице с данными выполнили `ALTER TABLE suppliers ADD COLUMN discount DECIMAL(4,2) NOT NULL DEFAULT 0.00;` Что увидят существующие строки в новом столбце?

- ✅ 0.00 — умолчание применяется и к уже существующим строкам
- ❌ NULL — error_text: существующие строки получают значение по умолчанию — сервер «пропускает» столбец за каждую из них; NULL к тому же невозможен в NOT NULL-столбце.
- ❌ сервер отклонит команду: NOT NULL-столбец нельзя добавить в таблицу с данными — error_text: можно: DEFAULT сообщает, чем заполнить существующие строки, поэтому добавление проходит — без умолчания вот такое добавление действительно стало бы проблемой.

### Вопрос 5: Чем `TRUNCATE TABLE t;` отличается от `DELETE FROM t;` (без условия)?

- ✅ TRUNCATE очищает таблицу разом и сбрасывает счётчик AUTO_INCREMENT; DELETE удаляет строки по одной, и счётчик продолжает расти
- ❌ ничем: TRUNCATE — просто короткая запись DELETE без условия — error_text: различие наблюдаемо: после TRUNCATE первая новая строка получает id 1, после DELETE — следующий за наибольшим прежним; ещё TRUNCATE быстрее на больших таблицах.
- ❌ DELETE быстрее, потому что не трогает схему — error_text: быстрее как раз TRUNCATE — он не перебирает строки по одной; схему, кстати, сохраняют обе команды — это их сходство, а не различие.

## Практические задания

### Задание 1: Скидка поставщикам

Новое поле в живой таблице — без пересоздания и потери данных.

<!-- Эталонное решение (для автора/бота-верификатора): ALTER TABLE suppliers ADD COLUMN discount DECIMAL(4,2) NOT NULL DEFAULT 0.00; INSERT INTO suppliers (name, city, discount) VALUES ('ТехноДом', 'Москва', 5.00); SELECT * FROM suppliers; -->

**statement:**

Таблица `suppliers` уже создана и заполнена двумя поставщиками. Добавьте
в конец таблицы столбец `discount DECIMAL(4,2)` — обязательный, по
умолчанию 0.00 (обычный ADD COLUMN, без указания позиции). Затем добавьте
новой строкой поставщика «ТехноДом» из Москвы со скидкой 5.00 — скидку
укажите явно, id не указывайте — и выведите все строки таблицы.

**expected_result_text:**

### Задание 3: Чистый лист

Очистка с оглядкой на счётчик — выбор команды решает всё.

<!-- Эталонное решение (для автора/бота-верификатора): TRUNCATE TABLE orders; INSERT INTO orders (customer, total) VALUES ('Ольга Смирнова', 790.00), ('Дмитрий Козлов', 3200.00); SELECT * FROM orders; -->

**statement:**

Таблица `orders` заполнена тремя старыми заказами, и бизнес решил начать
нумерацию с чистого листа: очистите таблицу так, чтобы первая новая строка
получила id 1 (вспомните сводную таблицу урока — какая из команд очистки
сбрасывает счётчик). Затем вставьте два заказа без указания id —
«Ольга Смирнова» на 790.00 и «Дмитрий Козлов» на 3200.00 — и выведите все
строки таблицы.

**expected_result_text:**

Финальный SELECT возвращает две строки с id 1 и 2 — счётчик начал
заново; старых заказов нет. Если бы очистка была сделана командой, не
сбрасывающей счётчик, новые строки получили бы id 4 и 5 — и результат
не совпал бы с эталоном.

**seed_sql:**

```sql

    id INT AUTO_INCREMENT PRIMARY KEY,
    customer VARCHAR(100) NOT NULL,

    ('Иван Сидоров', 1290.50),

```

**expected_rows:**

| id | customer        | total   |
| -- | --------------- | ------- |
| 1  | Ольга Смирнова  | 790.00  |
| 2  | Дмитрий Козлов  | 3200.00 |
