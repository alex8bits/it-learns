# Типы данных MySQL

## Материал

### Обещание из первого урока

В первом уроке у столбца таблицы были названы два жёстких свойства: имя и тип
данных. Там же пообещали разобрать типы отдельно — время пришло. Вспомните,
зачем это нужно: у Кости в Excel в столбец «Цена» попадало «договориться», и
таблица это молча проглатывала. СУБД как раз и обещала не проглатывать —
проверками целостности. А опираются эти проверки на тип: `price` в нашей
`products` — не «какой-то текст», а `DECIMAL(10,2)`, и уже поэтому «дёшево»
туда не пройдёт.

Тип столбца — это его договор с сервером: какие значения он принимает, как
хранится, как сравнивается и сортируется. Из урока 4 вы уже видели договор
в действии: чисто числовой текст сервер преобразует, а строку с «мусором»
в числовой столбец не пустит. Сейчас соберём полную картину: научимся читать
типы готовой таблицы, разберём семейства — целые числа, точные дробные,
строки, даты, «булевы» значения, — затем строгий режим и чтение ошибок,
а в конце коротко поговорим о кодировках.

### Как увидеть типы: DESCRIBE

В уроке 2 мы осматривали сервер сверху: `SHOW DATABASES` → `USE` →
`SHOW TABLES`. Таблицу нашли — теперь спросим о её устройстве. Команда
`DESCRIBE` («опишите») показывает столбцы таблицы и их типы. В учебной базе
появилась таблица отгрузок `shipments` — отправления товаров со склада Кости:

```sql
DESCRIBE shipments;
```

```text
+-----------+--------------+------+-----+---------+-------+
| Field     | Type         | Null | Key | Default | Extra |
+-----------+--------------+------+-----+---------+-------+
| id        | int          | NO   |     | NULL    |       |
| carrier   | varchar(40)  | NO   |     | NULL    |       |
| cost      | decimal(8,2) | NO   |     | NULL    |       |
| express   | tinyint(1)   | NO   |     | NULL    |       |
| shipped   | date         | NO   |     | NULL    |       |
| delivered | datetime     | NO   |     | NULL    |       |
+-----------+--------------+------+-----+---------+-------+
```

Главная для нас колонка — `Type`: `int`, `varchar(40)`, `decimal(8,2)`,
`tinyint(1)`, `date`, `datetime`. Таблица собрана не случайно: в ней есть все
типы сегодняшнего урока. Колонка `Null` со значением `NO` — знакомое «все
столбцы обязательны» из урока 4: пустое значение здесь не допускается. Колонки
`Key`, `Default` и `Extra` пока пусты — они станут содержательными в уроке 6,
когда мы сами создадим таблицу с ограничениями; до тех пор просто не обращайте
на них внимания.

Потренируемся на знакомой таблице — опишем каталог из уроков 1–4:

```sql
DESCRIBE products;
```

```text
+-------+---------------+------+-----+---------+-------+
| Field | Type          | Null | Key | Default | Extra |
+-------+---------------+------+-----+---------+-------+
| id    | int           | NO   |     | NULL    |       |
| name  | varchar(100)  | NO   |     | NULL    |       |
| price | decimal(10,2) | NO   |     | NULL    |       |
| stock | int           | NO   |     | NULL    |       |
+-------+---------------+------+-----+---------+-------+
```

`id` и `stock` — целые `INT`, `name` — строка `VARCHAR(100)`, `price` —
точная дробная `DECIMAL(10,2)`. Примеры следующих разделов будут опираться
на эту четвёрку — теперь тип каждого столбца известен явно.

Кстати, `tinyint(1)` в столбце `express` выглядит непривычно, но это не
опечатка: так MySQL отображает «булев» столбец — вернёмся к нему в своём
разделе.

### Целые числа: INT

Целочисленное семейство в MySQL — это `TINYINT`, `SMALLINT`, `MEDIUMINT`,
`INT`, `BIGINT` на 1, 2, 3, 4 и 8 байтах соответственно; различаются только
диапазоном. Рабочая
лошадка — `INT`: от −2 147 483 648 до 2 147 483 647, то есть примерно
±2,1 миллиарда. Для остатков на складе и номеров заказов хватает с запасом;
счётчики астрономических размеров (логи, просмотры) держат в `BIGINT`.

Литерал для целого — число без кавычек, как в уроке 4. Диапазон — не
формальность: напишем остаток за границей —

```sql
INSERT INTO products (id, name, price, stock)
VALUES (8, 'Мышь', 1290.50, 2147483648);
```

```text
ERROR 1264 (22003): Out of range value for column 'stock' at row 1
```

— и инструкция отклонена целиком, по правилу «всё или ничего» из урока 4.
Сервер не «подрезает» значение и не округляет: оно выходит за диапазон
`INT` — за то, что можно закодировать отведёнными ему четырьмя байтами, —
и вместо неверных данных не остаётся никаких.

### Деньги и точные дробные: DECIMAL

`decimal(8,2)` из DESCRIBE читается так: 8 — **точность**, сколько всего
цифр в записи числа (точка и знак минус не считаются), 2 — **масштаб**,
сколько из них после запятой. Максимум для
`(8,2)` — 999 999.99; для знакомого по `products` `DECIMAL(10,2)` —
99 999 999.99. Важно не путать: число в скобках — про количество цифр
в записи, а не про величину значения.

Почему для цен нужен отдельный тип, ведь «обычные дроби» в программировании
давно есть? Те «обычные дроби» — типы `FLOAT` и `DOUBLE` — приближённые:
компьютер хранит двоичные дроби, а 0,1 в двоичной системе — бесконечная
дробь (как ⅓ в десятичной). Одна цена с ошибкой в пятнадцатом знаке
незаметна, но сложите тысячи таких цен — копейки «поплывут», и отчёт
перестанет сходиться с кассой. `DECIMAL` устроен иначе: он хранит десятичную
дробь цифра за цифрой, точно. 1290.50 — это ровно 1290.50. Отсюда правило
курса: деньги и вообще величины, где важна каждая цифра, — `DECIMAL`;
`FLOAT`/`DOUBLE` остаются для физики и статистики, где десятый знак после
запятой не важен.

Два поведения `DECIMAL` стоит знать заранее. Первое: лишние цифры после
запятой не ошибка, а округление с предупреждением — `1290.555` в столбце
`(8,2)` превратится в `1290.56`; покажем это ниже, в разделе о `SHOW WARNINGS`.
Второе: переполнение точности — ошибка: `12345.00` в `DECIMAL(6,2)`
(максимум 9999.99) даёт уже знакомый `1264 Out of range value`.

### Строки: VARCHAR и TEXT

`varchar(40)` — строка переменной длины не длиннее 40 **символов**:
фактическая длина может быть любой до лимита, хранится ровно она. Перебор
лимита — ошибка:

```sql
INSERT INTO shipments (id, carrier, cost, express, shipped, delivered)
VALUES (3, 'Экспресс-доставка документов и грузов по всей России и странам СНГ',
        990.00, TRUE, '2026-09-05', '2026-09-06 12:00:00');
```

Название перевозчика — 66 символов, лимит 40:

```text
ERROR 1406 (22001): Data too long for column 'carrier' at row 1
```

Для сравнения: «Деловые линии транспортная компания» — 35 символов,
помещается свободно.

Подчеркнём: лимит считается в символах, а не в байтах. Строка `'Мышь 😉'` —
это 6 символов и 13 байт (эмодзи весит 4 байта) — и в `VARCHAR(10)` она
помещается. Почему так и причём тут utf8mb4 — в разделе о кодировках.

`TEXT` — тип для длинных текстов, у которых нет осмысленного потолка:
описания товаров, отзывы, комментарии. Лимит объявлять не нужно, влезает
до 65 535 байт текста — именно байт, не символов: символ может занимать
и несколько байт, о различии поговорим ниже. В нашем сквозном датасете так
устроен столбец `body` таблицы отзывов. Как выбирать: короткие поля предсказуемой длины (имена,
email, города, названия) — `VARCHAR(n)` с честным лимитом; неограниченно
длинные тексты — `TEXT`. Есть ещё `CHAR(n)` — строка, которая добивается
пробелами до ровно n символов; нишевая история, в курсе мы им не пользуемся,
но в чужом коде узнать можно.

### Дата и время: DATE и DATETIME

`DATE` — календарная дата, `DATETIME` — момент «дата плюс время». Литералы
пишутся строками в кавычках — правило «строки — в кавычках» из урока 4
распространяется и на них:

- `DATE`: `'2026-09-01'`;
- `DATETIME`: `'2026-09-03 14:20:00'`.

Порядок частей всегда машинный: год, месяц, день, затем часы:минуты:секунды.
А вот знак разделителя MySQL прощает любой — `'2026/01/30'` и даже
`'2026^01^30'` для него то же самое, что `'2026-01-30'`. Не прощается
порядок: привычная «человеческая» запись `'30.01.2026'` будет прочитана
по тем же правилам — 30 как год, 01 как месяц, 2026 как день — и отвергнута:
дня 2026 не существует. Поэтому в курсе даты записываем каноническим
`'ГГГГ-ММ-ДД'` — так их одинаково читают и сервер, и человек.

Ключевое отличие столбца-даты от столбца-строки: сервер **знает**, что внутри
дата, и проверяет её по настоящему календарю. 30 февраля не бывает —
и в базу не попадёт:

```text
ERROR 1292 (22007): Incorrect date value: '2026-02-30' for column 'shipped' at row 1
```

Та же ошибка ждёт несуществующий 31 сентября. Отдельного внимания стоит
29 февраля: год должен быть високосным по правилам календаря — каждый
четвёртый; «круглые» века — исключение, но кратные 400 всё же високосные
(1900 — нет, 2000 — да). `'2026-02-29'` отвергнется, а `'2028-02-29'` —
законная дата. В нашем практическом задании такая строка будет.

Зачем хранить дату датой, а не текстом? Кроме проверки календаря, знание типа
— фундамент всего будущего курса: даты можно сравнивать («доставленные позже
1 сентября»), сортировать, считать периоды. Функции работы с датами — тема
следующего уровня; одну полезную покажем сразу, в духе `DATABASE()` из урока
2: `NOW()` возвращает текущие дату и время сервера, и её удобно подставлять
в `DATETIME`-столбец: `VALUES (..., NOW())`. В заданиях курса даты, правда,
фиксируем явными литералами — чтобы результат не зависел от момента запуска.

У `DATETIME` есть родственник `TIMESTAMP` — момент с привязкой к часовому
поясу. Отдельного урока о нём в курсе не будет: учебному магазину хватает
`DATETIME`, а нюансы часовых поясов остаются за рамками курса; пока
достаточно знать, что такой тип существует и в чужих схемах встречается.

### BOOL: «да» или «нет»

Вернёмся к `tinyint(1)` в столбце `express`. Отдельного «настоящего»
булевого типа в MySQL нет: `BOOL` и `BOOLEAN` — синонимы для `TINYINT(1)`,
маленького целого, а `TRUE` и `FALSE` — литералы для `1` и `0`. Единица
в скобках — не предел значений: `TINYINT` остаётся полноценным целым
от −128 до 127, но в «булевом» столбце по договорённости живут только
`0` и `1`. Вставим отгрузку:

```sql
INSERT INTO shipments (id, carrier, cost, express, shipped, delivered)
VALUES (1, 'СДЭК', 590.00, FALSE, '2026-09-01', '2026-09-03 14:20:00');

SELECT * FROM shipments;
```

```text
+----+---------+--------+---------+------------+---------------------+
| id | carrier | cost   | express | shipped    | delivered           |
+----+---------+--------+---------+------------+---------------------+
|  1 | СДЭК    | 590.00 |       0 | 2026-09-01 | 2026-09-03 14:20:00 |
+----+---------+--------+---------+------------+---------------------+
```

В `express` лежит `0`; с `TRUE` лежало бы `1`. Привыкайте: прочитали из
булева столбца — увидели число.

Кавычки — та же история, что с числами в уроке 4: `'да'` или `'true'`
в кавычках — строки, и числовой столбец их отвергнет:

```text
ERROR 1366 (HY000): Incorrect integer value: 'да' for column 'express' at row 1
```

Пишите `TRUE` и `FALSE` без кавычек — это литералы, а не текст. Почему MySQL
устроен так лаконично и при чём тут условия — станет ясно в уроке о фильтрации
(`WHERE`), там значения «да/нет» раскрываются по-настоящему.

### Строгий режим: ошибки вместо тихих исправлений

Соберём все проверки значений этого урока в одну таблицу:

| Что не так со значением | Реакция сервера |
| ----------------------- | --------------- |
| число за диапазоном типа (`INT`, `DECIMAL`) | ошибка 1264 `Out of range value` |
| строка не похожа на число (`'дёшево'` в цену, `'да'` в BOOL) | ошибка 1366 `Incorrect integer/decimal value` |
| строка длиннее `VARCHAR(n)` | ошибка 1406 `Data too long` |
| дата не существует или не в формате `ГГГГ-ММ-ДД` | ошибка 1292 `Incorrect date value` |

Вместе с двумя из урока 4 — 1054 (забыли кавычки, сервер ищет столбец)
и 1136 (число значений не равно числу столбцов) — это основные ошибки
первых вставок; свои коды ошибок добавят ещё ограничения таблиц из урока 6.

За первой четвёркой стоит одна настройка — **строгий режим**. Это режим
работы сервера, определяющий реакцию на «плохие» значения. В стандартной
настройке MySQL 8 строгий режим включён по умолчанию: плохое значение —
ошибка, инструкция отклонена, данных не появилось. В старом, нестрогом поведении сервер вставлял бы «сколько
получилось»: 0 вместо непохожей на число строки, обрезанную строку, ближайшее
граничное число — с предупреждением. Для новых проектов полагаются на строгий
режим, и весь наш курс на нём; а встретив «молчаливые исправления» в старой
базе, вы будете знать, откуда они.

Даже в строгом режиме есть место предупреждениям — на случай, когда значение
не идеально, но спасаемо. Классический пример — округление лишних цифр
у `DECIMAL`:

```sql
INSERT INTO shipments (id, carrier, cost, express, shipped, delivered)
VALUES (2, 'Деловые линии', 1290.555, TRUE, '2026-09-02', '2026-09-04 10:00:00');

SHOW WARNINGS;
```

Инструкция прошла, `1290.555` превратилось в `1290.56`, а прочитать
предупреждение можно командой `SHOW WARNINGS` — она показывает сообщения
последней выполненной инструкции:

```text
+-------+------+-------------------------------------------+
| Level | Code | Message                                   |
+-------+------+-------------------------------------------+
| Note  | 1265 | Data truncated for column 'cost' at row 1 |
+-------+------+-------------------------------------------+
```

Вот и разгадка строки `Warnings: 0` из отчёта многострочного INSERT в уроке 4:
это счётчик предупреждений, и обычно он нулевой.

Читаются все эти сообщения по схеме урока 3: код → текст → место. В
`Out of range value for column 'stock'` назван и столбец, и причина — текст
ошибки экономит часы, если его просто прочитать.

### Кодировки: почему кириллица «просто работает»

Последний штрих — коротко, обзорно. Символ и байт — не одно и то же:
латиница занимает 1 байт, кириллица в Unicode — 2, эмодзи — 4. **Кодировка** —
договор о том, как символы упаковываются в байты; сервер и клиент должны
понимать её одинаково, иначе вместо букв появятся «кракозябры».

Современный стандарт в MySQL — `utf8mb4`: полноценный Unicode, до 4 байт
на символ. В стандартной установке MySQL 8 это кодировка по умолчанию —
потому кириллические названия из наших примеров вставляются и читаются
без всяких настроек.
Лимиты `VARCHAR` считаются в символах именно поэтому: `'Мышь 😉'` — 6
символов, 13 байт, и для `VARCHAR(10)` это шесть, а не тринадцать.

Одно предостережение на будущее: в старых таблицах встречается кодировка
с именем `utf8` — исторический обрезок MySQL до 3 байт. Кириллица в него
влезает, эмодзи — нет. В новых таблицах используем только `utf8mb4` — как
его задавать, увидим в уроке 6 при создании таблиц. Сравнение и сортировка
строк (collation) — отдельная большая тема, она ждёт в продвинутой части
курса.

### Резюме

- `DESCRIBE таблица` показывает столбцы и их типы; `Null` — обязательность
  значения, а `Key`/`Default`/`Extra` оживут в уроке 6.
- `INT` — целые примерно до ±2,1 млрд (семейство от `TINYINT` до `BIGINT`);
  выход за диапазон — ошибка 1264.
- `DECIMAL(точность, масштаб)` — точная десятичная дробь; деньги — только
  здесь: `FLOAT`/`DOUBLE` приближённые, копейки «плывут». Лишние цифры после
  запятой округляются с предупреждением, переполнение — ошибка 1264.
- `VARCHAR(n)` — до n символов (перебор — ошибка 1406), `TEXT` — длинные
  тексты без объявления лимита.
- `DATE` — `'ГГГГ-ММ-ДД'`, `DATETIME` — `'ГГГГ-ММ-ДД ЧЧ:ММ:СС'`; сервер
  проверяет календарь, включая високосные годы (ошибка 1292).
- `BOOL` — синоним `TINYINT(1)`; `TRUE`/`FALSE` — литералы для `1`/`0`,
  SELECT возвращает числа.
- Строгий режим (по умолчанию в MySQL 8) превращает плохие значения в ошибки
  вместо тихих исправлений; `SHOW WARNINGS` — предупреждения последней
  инструкции.
- `utf8mb4` — Unicode-кодировка по умолчанию; `VARCHAR` считает символы,
  а не байты.

## Теоретические задания

### Вопрос 1: Столбец объявлен как `DECIMAL(8, 2)`. Что означают числа 8 и 2?

- ✅ 8 — всего цифр в записи числа, из них 2 — после запятой; максимум — 999 999.99
- ❌ значения ограничены восемью, а после запятой останется два знака — error_text: числа в скобках — не величина значения, а количество цифр в его записи: 8 цифр всего, из них 2 после запятой. Отсюда и максимум: 999 999.99, а вовсе не 8.
- ❌ до 8 байтов на значение, из них 2 — на дробную часть — error_text: хранение DECIMAL тут ни при чём: в скобках объявляют число цифр (точность и масштаб), а не размер в байтах; размер сервер выбирает сам.

### Вопрос 2: В таблице нужно хранить цену товара — например, 4990.00. Какой тип выбрать?

- ✅ DECIMAL — он хранит десятичные дроби точно, копейки при суммировании не «плывут»
- ❌ DOUBLE — у него тоже есть дробная часть, и места он экономнее — error_text: DOUBLE — приближённый тип: 0,1 не представимо двоичной дробью точно, и при сложении тысяч цен набегают ошибки в копейках. Для денег нужен точный DECIMAL.
- ❌ VARCHAR — записывать числа строкой, чтобы ничего не терялось — error_text: строка отключает и числовые проверки сервера (цена «дёшево» прошла бы), и будущую арифметику со столбцом. Текстовый тип — для текстов, цену хранят в DECIMAL.

### Вопрос 3: В столбец `carrier VARCHAR(40)` вставляют строку из 66 символов. Сервер работает в стандартной настройке MySQL 8. Что будет?

- ✅ ошибка 1406: значение длиннее лимита, инструкция отклонена
- ❌ строка обрежется до 40 символов и вставится с предупреждением — error_text: тихая обрезка — поведение нестрогого режима. По умолчанию в MySQL 8 включён строгий: перебор длины — ошибка 1406, а не укороченное значение.
- ❌ ошибка 1136: число значений не равно числу столбцов — error_text: 1136 — про несовпадение количества значений и столбцов списка (урок 4). Здесь счёт сходится — проблема в длине одного значения, и это код 1406.

### Вопрос 4: Какое из четырёх значений столбца типа DATE сервер примет?

- ✅ '2028-02-29'
<!-- 2028 делится на 4 — високосный год, 29 февраля существует; формат ГГГГ-ММ-ДД соблюдён. -->
- ❌ '2026-02-29' — error_text: сервер сверяется с настоящим календарём: 2026 не делится на 4, февраль в нём — 28 дней, даты 29 февраля не существует.
- ❌ '30.01.2026' — error_text: сервер читает части даты всегда в порядке год-месяц-день: 30 — год, 01 — месяц, 2026 — день. Дня 2026 не существует — ошибка 1292, хотя сама дата (30 января 2026) вполне реальна.
- ❌ '2026-09-31' — error_text: в сентябре 30 дней; «почти правильное» число месяца календарную проверку не проходит — ошибка 1292.

### Вопрос 5: В столбец типа BOOL вставили TRUE. Что вернёт SELECT по этому столбцу?

- ✅ 1
- ❌ TRUE — error_text: BOOL в MySQL — синоним TINYINT(1), а TRUE — литерал для 1. Хранится и возвращается число; клиент показывает его как 1.
- ❌ строку 'true' — error_text: TRUE без кавычек — не текст, а литерал числа 1. Строкой была бы запись 'true' — и числовой столбец отверг бы её ошибкой 1366.
