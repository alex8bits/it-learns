# Создание таблиц с ограничениями

## Материал

### Из гостей — в хозяева

Пять уроков все таблицы доставались вам готовыми: «вот `products`, работайте».
В первом уроке при этом было обещано, что ограничение уникальности для `id` мы
зададим сами — когда начнём создавать таблицы. В пятом обещание повторилось
уже про DESCRIBE: молчаливые колонки `Key`, `Default` и `Extra` оживут
в уроке 6. Время расплачиваться: сегодня вы создаёте таблицы сами — и сразу
правильные.

Зачем вообще что-то «задавать»? Вспомните контролёра из первых уроков: сервер
проверяет всё, что в него приходит. Ограничение (англ. *constraint*) — это
правило схемы таблицы: сервер проверяет его автоматически при каждом
изменении данных — для каждого INSERT из любого приложения. Задают правило
при создании таблицы (сегодня этим и займёмся) или добавляют к готовой —
командой следующего урока. Не «дисциплина программистов», а закон внутри
самой базы: инструкцию, нарушающую правило, сервер отклоняет целиком.
Мы уже видели первые законы такого рода — типы столбцов урока 5; сегодня
добавляем правила поверх типов.

План урока: скелет `CREATE TABLE`, затем ограничения по одному — `NOT NULL`,
`DEFAULT`, `PRIMARY KEY`, `AUTO_INCREMENT`, `UNIQUE`, `CHECK` — и в конце
собираем таблицу под полную спецификацию, как в настоящем ТЗ.

### Скелет: CREATE TABLE

Минимальная таблица — имя и список столбцов с типами:

```sql
CREATE TABLE suppliers (
    id INT,
    name VARCHAR(100),
    city VARCHAR(50)
);
```

Имя таблицы — идентификатор: конвенции те же, что для баз в уроке 2 и имён
в уроке 3 — латиница, строчные, подчёркивание. В скобках — определения
столбцов через запятую, каждое — имя плюс тип из урока 5. SQL — язык
свободной формы: столбцы можно было бы перечислить и в одну строку, но
построчная запись — стандарт хорошего тона: таблицу видно глазами.

Команда выполнится мгновенно и без таблицы-результата — сервер ответит
коротким `Query OK`. Таблица пуста: ноль строк, но уже есть структура —
проверим её знакомым по уроку 5 `DESCRIBE`:

```text
+-------+--------------+------+-----+---------+-------+
| Field | Type         | Null | Key | Default | Extra |
+-------+--------------+------+-----+---------+-------+
| id    | int          | YES  |     | NULL    |       |
| name  | varchar(100) | YES  |     | NULL    |       |
| city  | varchar(50)  | YES  |     | NULL    |       |
+-------+--------------+------+-----+---------+-------+
```

Все `YES`, ключей нет, умолчаний нет — таблица беззащитна: `id` можно
продублировать, имя оставить пустым, город не указать. Ограничения пишутся
в определении столбца прямо в `CREATE TABLE` — по одному и разберём.

### NOT NULL: значение обязательно

Первое правило — самое простое: столбец обязан быть заполнен:

```sql
name VARCHAR(100) NOT NULL
```

В DESCRIBE колонка `Null` для такого столбца показывает `NO` — вы видели
эту картинку во всех учебных таблицах курса: «все столбцы обязательны»
из урока 4 — это и был `NOT NULL`, просто без имени. Пустое значение —
`NULL`, «значение отсутствует» (урок 5), теперь официально существует
в нашем словаре; полностью работать с ним научимся в уроке 11.

Нарушить `NOT NULL` можно двумя способами. Напрямую — передать `NULL`
литералом:

```text
ERROR 1048 (23000): Column 'name' cannot be null
```

И косвенно — вообще не упомянуть столбец в INSERT, если у него нет значения
по умолчанию:

```text
ERROR 1364 (HY000): Field 'name' doesn't have a default value
```

Так отвечает строгий режим — стандартная настройка MySQL 8, на которой идёт
весь курс (урок 5); нестрогий вставил бы «сколько получилось» — молча,
с предупреждением. Про вторую ошибку стоит запомнить формулировку: она про
**умолчание**, а не про запрет NULL — и лечится следующим ограничением.

### DEFAULT: значение по умолчанию

Если у столбца есть значение по умолчанию, пропуск столбца в INSERT — не
ошибка, а команда «возьми как обычно»:

```sql
city VARCHAR(50) NOT NULL DEFAULT 'Москва'
```

Теперь `INSERT INTO suppliers (id, name) VALUES (1, 'Аква-Сервис');`
пройдёт, и город окажется «Москва» — DESCRIBE честно показывает его в колонке
`Default`.

Здесь закрывается хвост урока 4: «число столбцов и число значений должны
совпадать точно» — это правило про перечисленные столбцы. А опускать столбцы
в списке можно — как раз те, у которых есть `DEFAULT` (или разрешённый NULL):
умолчание и есть их «значение на случай пропуска». Важная деталь: `DEFAULT`
срабатывает только при пропуске. Явно переданный `NULL` умолчанием не
заменяется — для столбца `NOT NULL` это по-прежнему ошибка 1048.

### PRIMARY KEY: главный идентификатор

Главное ограничение урока — то самое, обещанное ещё в первом уроке:

```sql
id INT PRIMARY KEY
```

`PRIMARY KEY` (первичный ключ) означает сразу три вещи: значения
**уникальны** — двух строк с одинаковым `id` не бывает; столбец **обязателен**
— как `NOT NULL`; и это **официальное имя строки** таблицы, по которому на
неё ссылаются. Первичный ключ у таблицы один.

Попробуем повторить `id = 1` при уже существующей строке — обещанный «отказ
дубликата»:

```text
ERROR 1062 (23000): Duplicate entry '1' for key 'suppliers.PRIMARY'
```

Текст читается по схеме урока 3: код → повторяющееся значение → какой ключ
нарушен. Инструкция отклонена целиком — «всё или ничего» из урока 4 работает
и здесь. В DESCRIBE первичный ключ виден в колонке `Key` как `PRI`.

Зачем это бизнесу — вспомните урок 1: заказ ссылается на покупателя по
`customer_id`, и уникальность `id` — гарантия, что ссылка ведёт ровно к одной
строке. Как базы ссылаются друг на друга на уровне сервера (внешние ключи) —
тема следующего уровня; фундамент закладывается сегодня.

### AUTO_INCREMENT: сервер нумерует сам

Пара к первичному ключу, разгадка «честных явных номеров» из урока 4:

```sql
id INT AUTO_INCREMENT PRIMARY KEY
```

`AUTO_INCREMENT` — счётчик сервера: если в INSERT столбец `id` пропущен (или
передан как NULL), сервер подставляет следующий номер сам — 1, 2, 3 и так
далее. Кажущееся противоречие с разделом DEFAULT («явно переданный NULL
умолчанием не заменяется») — не противоречие: обычное умолчание — заявленное
значение, а для счётчика NULL — специальный сигнал «пронумеруй сам». Именно
так теперь выглядит типовая вставка:

```sql
INSERT INTO suppliers (name, city) VALUES ('Аква-Сервис', 'Казань');
```

Список столбцов стал короче — id в нём просто нет. Почему в реальных базах
id обычно не выбирают руками: во-первых, сервер не ошибётся и не повторит
номер; во-вторых, двум одновременным приложениям не нужно договариваться,
кто взял какой номер, — счётчик один, раздаёт его сервер. В уроке 4 мы
вводили номера вручную, потому что механизма ещё не было; теперь он есть.

Явный `id` тоже разрешён — если номер свободен: `VALUES (5, 'Южный
поставщик', 'Сочи')` вставится со своим номером 5, а следующий
автоматический будет уже 6: счётчик запоминает наибольший использованный.
В DESCRIBE автонумерация видна в колонке `Extra`: `auto_increment`.

### UNIQUE: бизнес-уникальность

Персональный номер строки — не единственное, что должно быть уникальным.
Email покупателя, код товара, номер заказа — повторы таких значений ломают
бизнес-логику. Представим таблицу покупателей `customers` со столбцом
`email` — обязательным и уникальным:

```sql
email VARCHAR(100) NOT NULL UNIQUE
```

Повтор значения даёт уже знакомую ошибку 1062 — но называет другой ключ:

```text
ERROR 1062 (23000): Duplicate entry 'anna@example.com' for key 'customers.email'
```

В DESCRIBE такой столбец помечается в `Key` как `UNI`. Разница с первичным
ключом принципиальна: `PRIMARY KEY` — один на таблицу, «имя строки»,
обычно безликий номер; `UNIQUE` — сколько угодно, по одному на каждое
бизнес-поле, которое обязано не повторяться. Классическая схема: `id` для
ссылок (о нём никто не думает) плюс `UNIQUE` на полях, о которых все думают.

### CHECK: бизнес-правило

Последнее ограничение — произвольное правило, которому должно подчиняться
значение:

```sql
balance DECIMAL(10,2) NOT NULL CHECK (balance >= 0)
```

В скобках — условие, которому должна удовлетворять строка; при вставке
сервер его проверяет.
Баланс `-100.00` отклоняется:

```text
ERROR 3819 (HY000): Check constraint 'gift_cards_chk_1' is violated.
```

Имя ограничения сервер сгенерировал сам; можно задать и своё, тогда
в ошибке будет оно — и искать правило в большом `CREATE TABLE` проще:

```sql
CONSTRAINT balance_nonneg CHECK (balance >= 0)
```

Одна деталь инструментальная: в DESCRIBE проверка не видна — DESCRIBE
рассказывает про столбцы, а CHECK — правило таблицы; помните, что «нет
в DESCRIBE» не значит «нет в таблице». И кусочек истории: старые версии
MySQL (до 8.0.16) молча игнорировали CHECK — принимали синтаксис, но не
проверяли ничего. Наш курс идёт под MySQL 8 — здесь правило работает.

### Полный пример: таблица под спецификацию

Соберём всё. Спецификация: подарочные карты магазина Кости — номер
присваивается сервером; код карты уникален и обязателен; баланс
неотрицательный, по умолчанию ноль; карта по умолчанию активна.

```sql
CREATE TABLE gift_cards (
    id INT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(10) NOT NULL UNIQUE,
    balance DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    activated BOOL NOT NULL DEFAULT TRUE,
    CONSTRAINT balance_nonneg CHECK (balance >= 0)
);
```

И её DESCRIBE — сравните с «беззащитным» скелетом из начала урока:

```text
+-----------+---------------+------+-----+---------+----------------+
| Field     | Type          | Null | Key | Default | Extra          |
+-----------+---------------+------+-----+---------+----------------+
| id        | int           | NO   | PRI | NULL    | auto_increment |
| code      | varchar(10)   | NO   | UNI | NULL    |                |
| balance   | decimal(10,2) | NO   |     | 0.00    |                |
| activated | tinyint(1)    | NO   |     | 1       |                |
+-----------+---------------+------+-----+---------+----------------+
```

Все три молчаливые колонки из урока 5 ожили: `Key` показывает `PRI`
и `UNI`, `Default` — умолчания (`TRUE` хранится как 1 — урок 5), `Extra` —
автонумерацию. Наполним:

```sql
INSERT INTO gift_cards (code, balance, activated) VALUES ('GIFT-001', 5000.00, TRUE);
INSERT INTO gift_cards (code) VALUES ('GIFT-002');
INSERT INTO gift_cards (code, balance, activated) VALUES ('GIFT-003', 1500.00, FALSE);

SELECT * FROM gift_cards;
```

```text
+----+----------+---------+-----------+
| id | code     | balance | activated |
+----+----------+---------+-----------+
|  1 | GIFT-001 | 5000.00 |         1 |
|  2 | GIFT-002 |    0.00 |         1 |
|  3 | GIFT-003 | 1500.00 |         0 |
+----+----------+---------+-----------+
```

Номера проставлены сервером, у второй карты сработали оба умолчания —
таблица сама следит за своими правилами.

### Кодировка таблиц: обещание урока 5

Во всех `CREATE TABLE` этого урока — от `suppliers` до `gift_cards` — нет
ни слова про кодировку, хотя урок 5 обещал: как задавать `utf8mb4`, увидим
здесь. Обещание выполняется само: в стандартной установке MySQL 8 новые
таблицы создаются в `utf8mb4` по умолчанию — потому кириллица в наших
примерах вставляется и читается без дополнительных указаний. Явно кодировку
задают так — на случай старой базы, где умолчание другое:

```sql
CREATE TABLE suppliers (
    id INT,
    name VARCHAR(100)
) DEFAULT CHARSET=utf8mb4;
```

В новой базе такая строка — не ошибка, а избыточность. А сравнение и
сортировка строк (collation) — по-прежнему тема продвинутой части курса.

### Таблица уже существует

Повторный `CREATE TABLE suppliers (...)` для существующей таблицы завершится
ошибкой:

```text
ERROR 1050 (42S01): Table 'suppliers' already exists
```

Для скриптов, которые запускают повторно, — та же страховка, что у
`CREATE DATABASE` в уроке 2: `CREATE TABLE IF NOT EXISTS suppliers (...)`
молча пропустит создание, если таблица уже есть. А вот изменить готовую
таблицу или удалить её — отдельная тема: команды `ALTER TABLE` и `DROP` ждут
вас в следующем уроке.

### Сводка нарушений

Все отказы урока — в одну таблицу, в духе урока 5:

| Что не так | Реакция сервера |
| ---------------------------------- | ------------------------------------------- |
| явный `NULL` в столбце `NOT NULL` | ошибка 1048 `Column cannot be null` |
| пропущен обязательный столбец без `DEFAULT` (строгий режим) | ошибка 1364 `Field doesn't have a default value` |
| повтор значения `PRIMARY KEY` или `UNIQUE` | ошибка 1062 `Duplicate entry` |
| значение провалило `CHECK` | ошибка 3819 `Check constraint is violated` |
| таблица с таким именем уже существует | ошибка 1050 `Table already exists` |

Читать их — по схеме урока 3: код → текст → место. Систематическому разбору
кодов ошибок MySQL посвящён отдельный урок среднего уровня; ваш репертуар
уже покрывает почти всё, что встретится при создании и наполнении таблиц.

### Резюме

- `CREATE TABLE имя (столбцы)` создаёт структуру; определения столбцов —
  имя + тип + ограничения; пустая таблица без ограничений беззащитна.
- `NOT NULL` — обязательность: явный NULL даёт 1048, пропуск столбца без
  умолчания — 1364.
- `DEFAULT` — значение на случай пропуска столбца; срабатывает только при
  пропуске, явный NULL не заменяет.
- `PRIMARY KEY` — уникальность + обязательность + «имя строки»; один
  на таблицу; повтор значения — ошибка 1062.
- `AUTO_INCREMENT` — сервер нумерует сам при пропуске id; явный свободный
  номер разрешён; счётчик запоминает наибольший.
- `UNIQUE` — уникальность бизнес-полей (email, код): сколько нужно; в DESCRIBE
  помечается `UNI`, повтор — та же 1062.
- `CHECK (условие)` — бизнес-правило; нарушение — 3819; в DESCRIBE не виден;
  реально работает с MySQL 8.0.16.
- `CREATE TABLE IF NOT EXISTS` — страховка повторных запусков; изменение
  и удаление таблиц — урок 7.

## Теоретические задания

### Вопрос 1: В таблице `id INT AUTO_INCREMENT PRIMARY KEY`. Строку вставляют инструкцией `INSERT INTO t (name) VALUES ('Товар');` — столбец id не упомянут. Что произойдёт?

- ✅ сервер сам подставит следующий номер счётчика, и строка вставится
- ❌ ошибка 1364: у столбца id нет значения по умолчанию — error_text: у AUTO_INCREMENT-столбца роль умолчания играет «следующий номер»: пропуск столбца — штатный сигнал «пронумеруй сам», а не нарушение.
- ❌ вставится строка с id = NULL — error_text: NULL для AUTO_INCREMENT — тот же сигнал «пронумеруй сам», вставится следующий номер; а NULL-значения в PRIMARY KEY не бывают вовсе.

### Вопрос 2: Столбец `email VARCHAR(100) NOT NULL UNIQUE`. Что делает UNIQUE?

- ✅ запрещает вторую строку с тем же email — повтор отвергается ошибкой 1062
- ❌ делает email вторым первичным ключом таблицы — error_text: первичный ключ один; UNIQUE — «обычное» ограничение уникальности для бизнес-поля, таких столбцов в таблице может быть несколько.
- ❌ сервер будет автоматически гарантированно разными значениями заполнять email — error_text: UNIQUE ничего не генерирует (генерация номеров — работа AUTO_INCREMENT); он только проверяет, что повторов нет.

### Вопрос 3: Столбец `name VARCHAR(100) NOT NULL` без DEFAULT. В INSERT (строгий режим) столбец name пропущен. Что ответит сервер?

- ✅ ошибку 1364: у поля name нет значения по умолчанию
- ❌ вставится пустая строка '' — error_text: пустая строка — это значение, и подставлять его сервер не станет: пропущенному столбцу нужно DEFAULT или разрешённый NULL, иначе строгий режим даёт 1364.
- ❌ вставится NULL — error_text: NULL запрещён самим NOT NULL; NULL при пропуске подставлялся бы лишь столбцу без NOT NULL — у нас не тот случай.

### Вопрос 4: Столбец `balance DECIMAL(10,2) NOT NULL DEFAULT 0.00`. Строка вставляется без упоминания balance. Что окажется в таблице?

- ✅ строка вставится, balance = 0.00
- ❌ ошибка 1364 — error_text: 1364 бывает только у столбца без умолчания; DEFAULT существует ровно для этого случая — пропуск столбца заполняется заявленным значением.
- ❌ balance = NULL — error_text: NULL в NOT NULL-столбце невозможен, а DEFAULT прямо говорит, чем заполнить пропуск — нулём.

### Вопрос 5: В определении таблицы есть `CHECK (balance >= 0)`. Пытаются вставить строку с balance = −100. Что произойдёт в MySQL 8?

- ✅ ошибка 3819: проверка нарушена, строка не вставится
- ❌ строка вставится: CHECK в MySQL не работает — error_text: это верно только для версий до 8.0.16, где CHECK молча игнорировался; курс идёт под MySQL 8 — правило проверяется и нарушается ошибкой.
- ❌ вставится balance = 0: сервер подрежет значение до границы — error_text: CHECK не «чинит» значения: правило либо выполнено, либо инструкция отклоняется целиком; подстановка граничного числа — не его работа.

### Задание 3: Отказ дубликата

Обещанный планом курса момент: сервер на страже уникальности.

<!-- Эталонное решение (для автора/бота-верификатора): INSERT INTO customers (name, email) VALUES ('Мария Волкова', 'maria@example.com'); INSERT INTO customers (id, name, email) VALUES (5, 'Дмитрий Козлов', 'dmitry@example.com'); SELECT * FROM customers; -->

**statement:**

Таблица `customers` уже создана — с первичным ключом на `id`
(автонумерация) и уникальным обязательным `email`; в ней два покупателя:
id 1 — Анна Петрова, anna@example.com и id 2 — Иван Сидоров,
ivan@example.com.

Ниже четыре кандидата на вставку (прочерк в id — «пронумеруй сам»):

| id  | name           | email             |
| --- | -------------- | ----------------- |
| 1   | Пётр Смирнов   | petr@example.com  |
| —   | Мария Волкова  | maria@example.com |
| —   | Ольга Смирнова | anna@example.com  |
| 5   | Дмитрий Козлов | dmitry@example.com |

Сначала попробуйте вставить каждого кандидата по отдельности и прочитайте
ответы сервера (дважды это будет ошибка 1062 — какой ключ повторён в каждом
случае?). Затем отправьте в решение только два проходящих INSERT — и именно
в таком порядке: сначала Марию Волкову (id пусть проставит сервер), потом
Дмитрия Козлова с явным id 5. Порядок существен: номер Марии выдаёт
счётчик, и он зависит от того, что вставлено до неё. Падающие INSERT
в решение не включайте: строк они не добавляют, а номера счётчика
расходуют. В конце выведите все строки таблицы.

**expected_result_text:**

Финальный SELECT возвращает четыре строки: исходные покупатели 1–2,
Мария Волкова с автоматически проставленным id 3 и Дмитрий Козлов
с явно заданным свободным id 5. Кандидаты «Пётр Смирнов» (повтор первичного
ключа 1) и «Ольга Смирнова» (повтор уникального email) отвергнуты.

**seed_sql:**

```sql
CREATE TABLE customers (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE

INSERT INTO customers (name, email) VALUES
    ('Анна Петрова', 'anna@example.com'),
    ('Иван Сидоров', 'ivan@example.com');
```

| 3  | Мария Волкова   | maria@example.com  |
