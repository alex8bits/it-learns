### Урок без новых команд

Урок 3 оставил неоплаченный долг — и самый интригующий: псевдоним,
рождённый в списке SELECT, отлично работает в ORDER BY и невидим в WHERE
того же запроса («ошибка 1054, почему — урок 6»). Сегодня платим. Как и
мини-проект урока 12, этот урок не вводит **ни одной новой команды**:
только SELECT, FROM, WHERE, ORDER BY, LIMIT — всё пройдено. Новым будет
взгляд: как запрос исполняется изнутри, этаж за этажом.

Это урок-фундамент. После него сами собой объяснятся факты, которые мы
пока принимали на веру: почему WHERE раньше LIMIT (урок 8 «Основ»),
почему ORDER BY понимает псевдонимы (урок 3), почему группировку по
месячным ключам из урока 5 нельзя было посчитать в WHERE. А впереди на
эту же опору встанут агрегаты (урок 8), HAVING (урок 10) и разница
ON/WHERE в соединениях (урок 14).

### Актёры урока

Шестёрка товаров — прежняя:

```sql
SELECT id, name, price, stock FROM products ORDER BY id;
```

```text
+----+-----------------------------------------------+----------+-------+
| id | name                                          | price    | stock |
+----+-----------------------------------------------+----------+-------+
|  1 | Коврик для мыши                               |   690.00 |    34 |
|  2 | Мышь беспроводная                             |  1290.50 |    12 |
|  3 | Клавиатура механическая                       |  4990.00 |     0 |
|  4 | Монитор 27"                                   | 15990.00 |     3 |
|  5 | Кабель HDMI 2 м                               |   450.00 |    51 |
|  6 | Веб-камера                                    |  2450.00 |    12 |
+----+-----------------------------------------------+----------+-------+
```

### Два порядка: как пишут и как исполняют

У запроса два порядка, и они разные. **Порядок написания** — то, как
запрос обязан выглядеть на бумаге (уроки 8–9 «Основ» требовали его
жёстко: WHERE до ORDER BY, LIMIT последним):

```text
SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT …
```

**Порядок выполнения** — то, в какой очереди сервер логически обрабатывает
части запроса:

```text
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

Сопоставьте: `SELECT` пишется первым — а исполняется пятым из семи, почти
последним. В этой перестановке — весь сегодняшний урок. GROUP BY и HAVING
пока для нас имена из будущего (уроки 8–10); сегодня конвейер проходит их
насквозь, как выключенные рубильники.

Почему нельзя писать части в порядке выполнения? Исторически SQL —
декларативный язык: запрос описывает, **что** хочется получить, а не
**как** исполнять. Первой строкой принято называть желаемый результат
(SELECT), а уж потом — источники и условия. Синтаксис требует именно
порядка написания: WHERE не примут раньше FROM, LIMIT — раньше ORDER BY.
Две очереди — написания и выполнения — сосуществуют, и путать их не
стоит: первая для сервера-контролёра, вторая — для вашего понимания.

Модель для запоминания — конвейер: каждая стадия получает таблицу (набор
строк), делает свою работу и передаёт результат следующей стадии. На
входе — таблица FROM, на выходе — результат запроса. Конвейер — модель
учебная: мы мысленно раскладываем работу запроса по стадиям; MySQL при
этом не обязан физически строить промежуточные таблицы — подробности в
конце урока. Пройдём все этажи одного запроса и посмотрим, что лежит на
ленте между ними.

### Конвейер: этаж за этажом

Запрос-пациент — «три самые выгодные скидки на дорогих товарах»:

```sql
SELECT name, price * 0.9 AS discounted
FROM products
WHERE price > 1000
ORDER BY discounted DESC
LIMIT 3;
```

**Этаж 1: FROM.** На ленту ложится вся таблица целиком — шесть строк, все
столбцы. Никто ничего не отбросил и не вычислил:

```text
+----+-----------------------------------------------+----------+-------+
| id | name                                          | price    | stock |
+----+-----------------------------------------------+----------+-------+
|  1 | Коврик для мыши                               |   690.00 |    34 |
|  2 | Мышь беспроводная                             |  1290.50 |    12 |
|  3 | Клавиатура механическая                       |  4990.00 |     0 |
|  4 | Монитор 27"                                   | 15990.00 |     3 |
|  5 | Кабель HDMI 2 м                               |   450.00 |    51 |
|  6 | Веб-камера                                    |  2450.00 |    12 |
+----+-----------------------------------------------+----------+-------+
```

**Этаж 2: WHERE.** Каждой строке — вопрос «цена больше 1000?» (построчно,
как в уроке 8 «Основ»). Коврик, кабель отвечают «нет» и покидают ленту:

```text
+----+-----------------------------------------------+----------+-------+
| id | name                                          | price    | stock |
+----+-----------------------------------------------+----------+-------+
|  2 | Мышь беспроводная                             |  1290.50 |    12 |
|  3 | Клавиатура механическая                       |  4990.00 |     0 |
|  4 | Монитор 27"                                   | 15990.00 |     3 |
|  6 | Веб-камера                                    |  2450.00 |    12 |
+----+-----------------------------------------------+----------+-------+
```

**Этажи 3–4: GROUP BY и HAVING.** Не написаны — лента проходит их
насквозь, те же четыре строки. Что эти этажи делают с включёнными
агрегатами — уроки 8–10; сегодня достаточно знать их место в очереди.

**Этаж 5: SELECT.** Только теперь строятся колонки результата: выражение
`price * 0.9` вычисляется построчно (урок 3), получает псевдоним
`discounted`. Здесь же работает и `DISTINCT` урока 3: повторяющиеся строки
вычёркиваются из уже построенного списка. Обратите внимание, что делает
этаж: берёт четыре строки со **всеми** столбцами FROM и отдаёт четыре
строки только с двумя колонками — name и discounted:

```text
+-----------------------------------------------+------------+
| name                                          | discounted |
+-----------------------------------------------+------------+
| Мышь беспроводная                             |   1161.450 |
| Клавиатура механическая                       |   4491.000 |
| Монитор 27"                                   |  14391.000 |
| Веб-камера                                    |   2205.000 |
+-----------------------------------------------+------------+
```

**Этаж 6: ORDER BY.** Сортирует то, что пришло с этажа SELECT, — и по
столбцу результата, и по псевдониму:

```text
+-----------------------------------------------+------------+
| name                                          | discounted |
+-----------------------------------------------+------------+
| Монитор 27"                                   |  14391.000 |
| Клавиатура механическая                       |   4491.000 |
| Веб-камера                                    |   2205.000 |
| Мышь беспроводная                             |   1161.450 |
+-----------------------------------------------+------------+
```

**Этаж 7: LIMIT.** Отрезает три первые строки отсортированного — это и
есть результат запроса:

```text
+-----------------------------------------------+------------+
| name                                          | discounted |
+-----------------------------------------------+------------+
| Монитор 27"                                   |  14391.000 |
| Клавиатура механическая                       |   4491.000 |
| Веб-камера                                    |   2205.000 |
+-----------------------------------------------+------------+
```

Семь этажей, семь маленьких таблиц на ленте. Теперь загадки урока 3
решаются в одну строчку каждая.

### Загадка алиаса: WHERE против ORDER BY

Вспомним факт урока 3: `WHERE discounted < 2000` — ошибка 1054, unknown
column; `ORDER BY discounted` — работает. Почему?

Псевдоним `discounted` **рождается на этаже SELECT** — пятом. WHERE —
второй этаж: когда он работает, выражение ещё не вычислено и имени ещё не
существует. Спрашивать у WHERE про `discounted` — как спрашивать у приёмки
завода, какую упаковку поставил цех фасовки: фасовка сработает позже.
ORDER BY же — шестой этаж, этаж ниже SELECT (в смысле конвейера — после):
имя уже создано, сортировка им пользуется. Вот и вся тайна: **не запрет,
а очередь**. В WHERE условие пишут по исходным столбцам FROM — `WHERE
price * 0.9 < 2000` работает, потому что `price` существует с первого
этажа.

### Что видит ORDER BY

Раз ORDER BY работает после SELECT — ему доступно всё, что создано
раньше: и псевдонимы (только что видели), и столбцы FROM, которые **не
попали** в список SELECT. Сортировка по цене, вывод — только имена:

```sql
SELECT name
FROM products
ORDER BY price DESC
LIMIT 3;
```

```text
+-----------------------------------------------+
| name                                          |
+-----------------------------------------------+
| Монитор 27"                                   |
| Клавиатура механическая                       |
| Веб-камера                                    |
+-----------------------------------------------+
```

`price` в результате нет — но ORDER BY его видит: столбец живёт на ленте
с первого этажа. То же касается выражений: `ORDER BY price * stock`
отсортирует по стоимости остатка, не показывая её. А вот WHERE наоборот —
видит только исходные столбцы (он раньше SELECT) и не видит псевдонимов.

### Прежние факты получают механику

Урок 8 «Основ» сказал: «сначала WHERE отбирает подходящие строки, потом
LIMIT обрезает уже отфильтрованное». Теперь видна очередь: WHERE — второй
этаж, LIMIT — седьмой, последний. Порядок «сначала фильтр, потом обрезка»
— не договорённость документации, а следствие конвейера.

И заглянем на один урок вперёд — зачем это всё. Мы умеем делать месячные
ключи (урок 5), и скоро научимся считать «сколько заказов в каждом
месяце» — агрегаты, урок 8. Агрегатные выражения вычисляются на этажах
**после** WHERE — в списке SELECT и в HAVING (а GROUP BY — способ
образовать для них группы). Значит, в WHERE агрегату места нет: он сводит
много строк к одному числу, а WHERE проверяет строки по одной — раньше
любой группировки. Для условия по агрегату («месяцы, где заказов больше
десяти») существует этаж HAVING — урок 10. Запоминать пока ничего не надо — просто заметьте, как конвейер
сам расставляет инструменты по местам.

### Как читать чужой запрос

Правило чтения: **начинайте не с первой строки, а с FROM**. Порядок
глаз: FROM (какие строки на ленте) → WHERE (какие из них выжили) → SELECT
(что попало в результат) → ORDER BY/LIMIT (как подано). Попробуйте на
запросе-пациенте: «товары products (FROM), дороже тысячи (WHERE), к
показу — имя и скидку (SELECT), самые выгодные сверху (ORDER BY),
первые три (LIMIT)».

Прогоним глазами и отчёт урока 5 — заказы с месячным ключом и сроком
оплаты. FROM: пять заказов на ленте. WHERE (`paid_at IS NOT NULL AND
DATEDIFF(paid_at, created_at) > 0`): выжили три — оплаченные и с
ненулевым сроком (заказ Марии, оплаченный в тот же день, отсеялся).
SELECT: к каждому выжившему приклеились месячный ключ и срок. ORDER BY id
— подача по порядку. Ни одной новой мысли — просто другой маршрут по
уже знакомому запросу. Чужие запросы с этажами GROUP BY читаются так же —
просто два этажа больше.

### «Логический» — значит про результат

Мы говорим «порядок выполнения», и это правда про **логику** — про то, в
какой очередности стадии концептуально зависят друг от друга. Реальный
движок может исполнять запрос иначе, если результат тот же, — порядок
строк на ленте его не волнует, волнует состав. Гарантия MySQL: любой
запрос ведёт себя так, будто этажи отработали ровно в этой очереди. Как
сервер на самом деле ищет быстрые пути — тема оптимизатора, продвинутый
уровень; для чтения и написания запросов логической модели достаточно.

### Чего в этом уроке нет

- агрегатные функции COUNT, SUM, AVG — урок 8;
- GROUP BY — урок 9; HAVING и «WHERE vs HAVING» — урок 10;
- разница ON и WHERE в соединениях — урок 14.

### Резюме

- Два порядка: пишем `SELECT … FROM … WHERE … ORDER BY … LIMIT`,
  исполняется `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY →
  LIMIT`.
- Модель — конвейер: каждая стадия получает таблицу строк, отдаёт
  таблицу строк следующей; SELECT — пятый этаж, почти последний.
- Псевдоним рождается на SELECT: поэтому WHERE его не видит (1054 — не
  запрет, а очередь), а ORDER BY — видит и им пользуется.
- ORDER BY доступны и столбцы FROM, не попавшие в список SELECT; WHERE
  видит только исходные столбцы.
- «Сначала WHERE, потом LIMIT» (урок 8 «Основ») — следствие конвейера.
- Агрегатные выражения вычисляются после WHERE (в SELECT и HAVING):
  условия по ним — HAVING, урок 10.
- Читать запрос — с FROM: строки → выжившие → результат → подача.
- «Логический» порядок гарантирует результат; как движок ищет быстрые
  пути — оптимизатор, продвинутый уровень.

## Теоретические задания

### Вопрос 1: Что работает раньше — WHERE или список SELECT?

- ✅ WHERE отбирает строки до вычисления колонок результата
<!-- конвейер: FROM → WHERE → … → SELECT: фильтр — второй этаж, SELECT — пятый -->
- ❌ SELECT: сначала вычисляются колонки, потом фильтруются строки — error_text: очередь обратная: SELECT — пятый этаж, WHERE — второй; фильтр получает на ленту все строки FROM и работает по исходным столбцам.
- ❌ одновременно: это независимые части запроса — error_text: части связаны конвейером: SELECT получает только те строки, которые WHERE пропустил, — значит, WHERE отработал раньше.
- ❌ порядок зависит от запроса — error_text: логический порядок фиксирован для любого SELECT: FROM → WHERE → … → SELECT → ORDER BY → LIMIT.

### Вопрос 2: Почему `WHERE discounted < 2000` даёт ошибку 1054, если `discounted` объявлен в этом же запросе через AS?

- ✅ псевдоним создаётся на этаже SELECT, который работает позже WHERE
<!-- не запрет, а очередь: имени ещё не существует, когда WHERE проверяет строки -->
- ❌ псевдонимы в WHERE запрещены синтаксисом MySQL — error_text: дело не в запрете: любой столбец WHERE знает — доступен; просто псевдоним рождается позже фильтра, на пятом этаже конвейера.
- ❌ WHERE не умеет читать имена колонок — error_text: умеет — но только те, что уже существуют: исходные столбцы FROM фильтру видны, псевдонимы SELECT — нет.
- ❌ сервер требует писать условие по алиасу в HAVING — error_text: HAVING — этаж для условий по агрегатам и группам (урок 10), а не способ обойти очередь для обычного псевдонима; условие по исходным данным пишут прямо в WHERE: price * 0.9 < 2000.

### Вопрос 3: Почему `ORDER BY discounted` с псевдонимом из SELECT работает?

- ✅ ORDER BY работает после SELECT, псевдоним уже создан
<!-- конвейер: SELECT (пятый) → ORDER BY (шестой) -->
- ❌ ORDER BY выполняется первым и видит весь запрос — error_text: ORDER BY — шестой этаж, ближе к концу конвейера; видит он много, но потому, что работает после FROM и SELECT, а не первым.
- ❌ ORDER BY — особый случай, не связанный с конвейером — error_text: связан напрямую: сортировка получает таблицу, которую построил SELECT, — с псевдонимами и колонками результата.
- ❌ потому что псевдоним объявлен с AS — error_text: AS не при чём: без AS результат тот же — псевдоним в WHERE всё равно невидим, а в ORDER BY работает; решает очередь этажей.

### Вопрос 4: Сработает ли `SELECT name FROM products ORDER BY price DESC LIMIT 3;` — цена в список SELECT не входит?

- ✅ да, сработает
