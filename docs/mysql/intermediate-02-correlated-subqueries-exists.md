### Граница между уроками 1 и 2

Урок 1 разобрал **самостоятельные** подзапросы: внутренний SELECT не
смотрит на внешнюю строку, его можно вырезать и выполнить отдельно.
«Магазин дороже средней цены своего отдела» и «покупатели, у которых
не NULL в `customer_id`» решаются без корреляции.

Сегодня — **коррелированные** подзапросы: логически условие внутреннего
SELECT зависит от столбца внешней строки — для каждого покупателя
проверяется свой `c.id`. Конкретный физический план выполнения
выбирает оптимизатор MySQL. Главный сюжет — оператор `EXISTS`,
который отвечает на вопрос «есть ли такая строка?», не возвращая саму
строку. Это второй шаг лестницы: самостоятельный подзапрос →
подзапрос, привязанный к внешней строке.

Два знакомых инструмента — `NOT IN` (урок 1) и анти-join через
`LEFT JOIN ... WHERE правый.pk IS NULL` (урок 14 «Начинающего») — тоже
решают эти задачи. Сегодняшний урок показывает, где `EXISTS` /
`NOT EXISTS` работают чище, и закрывает дыру `NOT IN` с NULL.

### EXISTS: есть ли хоть одна строка

`EXISTS` принимает подзапрос и возвращает `1` (true), если тот вернул
**хотя бы одну строку**, и `0` (false), если тот вернул **ноль строк**.
Никакие столбцы из внутреннего SELECT наружу не уходят — важно только,
существует ли строка в принципе.

```sql
SELECT id, name
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
)
ORDER BY c.id;
```

```text
+----+---------------+
| id | name          |
+----+---------------+
|  1 | Анна Петрова  |
|  2 | Иван Сидоров  |
+----+---------------+
```

У Анны два заказа, у Ивана один — `EXISTS` для обоих возвращает true,
поэтому оба попадают в результат. У Марии и Петра заказов нет —
подзапрос возвращает ноль строк, `EXISTS` даёт false, строка
отбрасывается.

`EXISTS` проверяет условие для строки внешнего запроса и не размножает
её: покупатель с двумя, десятью или ста заказами в результате остаётся
одной строкой.

Обратите внимание на корреляцию: внутренний запрос ссылается на
`c.id` — столбец **внешней** строки. Для каждого покупателя MySQL
выполняет `SELECT 1 FROM orders WHERE customer_id = ?` заново. Это
уже **коррелированный** подзапрос — вчерашние подзапросы так не делали.

`SELECT 1` — идиома: `EXISTS` интересует только факт наличия хотя бы
одной подходящей строки, содержимое `SELECT` не важно. Оптимизатор
может использовать это свойство при выполнении запроса, поэтому в
`EXISTS` можно безопасно писать `SELECT 1` или `SELECT *`.

Сравнение с уроком 1: `IN` тоже отвечает «кто из покупателей
заказывал?», но через **членство в списке**. `EXISTS` отвечает на тот
же вопрос через **проверку наличия** связанной строки. Список и
наличие — два способа выразить одно и то же отношение «один-ко-многим».

### NOT EXISTS: точно нет ни одной строки

`NOT EXISTS` — отрицание `EXISTS`: true, если подзапрос вернул **ноль
строк**, false — если вернул хотя бы одну. Готовая замена `NOT IN`
для анти-join:

```sql
SELECT id, name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
)
ORDER BY c.id;
```

```text
+----+---------------+
| id | name          |
+----+---------------+
|  3 | Мария Волкова |
|  4 | Пётр Смирнов  |
+----+---------------+
```

Мария и Пётр — покупатели, у которых `NOT EXISTS` дал true. Это тот
же набор, что у `LEFT JOIN ... WHERE правый.pk IS NULL` урока 14
«Начинающего» и у `NOT IN` урока 1. Третий инструмент, тот же
ответ.

Главное отличие `NOT EXISTS` от `NOT IN` — в том, что `EXISTS`
проверяет наличие строки, а `NOT IN` сравнивает значение с множеством.
`NOT EXISTS` часто используют вместо `NOT IN`, когда наличие `NULL`
во внутреннем результате может изменить поведение `NOT IN`: `NOT IN`
в этом случае даёт пустой результат, `NOT EXISTS` остаётся корректным.
Здесь `NOT EXISTS` проверяет каждого покупателя против множества его
заказов: если ни одной подходящей строки нет — покупатель проходит.

### Три инструмента анти-join: когда что

Один и тот же вопрос «покупатели без заказов» решается тремя
способами. Все три в плане курса уже встречались, сегодня — сводка
и правило выбора.

```sql
-- 1. NOT EXISTS (сегодня)
SELECT c.id, c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1 FROM orders AS o WHERE o.customer_id = c.id
)
ORDER BY c.id;

-- 2. NOT IN (урок 1)
SELECT c.id, c.name
FROM customers AS c
WHERE c.id NOT IN (SELECT o.customer_id FROM orders AS o)
ORDER BY c.id;

-- 3. LEFT JOIN ... WHERE правый.pk IS NULL (урок 14 «Начинающего»)
SELECT c.id, c.name
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.id;
```

Все три возвращают одинаковый результат для нашей базы. Различия —
в трёх ситуациях:

- **NULL во внутреннем столбце.** `NOT IN` даёт пустой результат
  (урок 1). `NOT EXISTS` и `LEFT JOIN ... IS NULL` работают
  корректно: NULL не «отравляет» сравнение, потому что проверяется
  наличие/отсутствие строки.
- **Дубли во внутренней таблице.** `NOT EXISTS` не считает повторы:
  как только нашлась подходящая строка — ответ готов. `NOT IN` тоже
  работает с дублями (членство не зависит от числа строк). `LEFT JOIN`
  строит пары: если у покупателя несколько заказов, в промежуточном
  результате будет несколько строк. `WHERE o.id IS NULL` отсекает все
  такие пары, поэтому в итоговом результате каждый покупатель без
  заказов остаётся ровно один раз.
- **Нужны ли столбцы правой таблицы.** Если в отчёте нужны ещё и
  данные заказов — `LEFT JOIN` без `IS NULL`. Если нужна только левая
  сторона — `NOT EXISTS` короче и явно говорит «нет ни одной такой
  строки».

### Коррелированные скаляры: ещё один штрих

`EXISTS` отвечает «есть/нет». Иногда нужно **сравнить с числом**,
которое зависит от внешней строки. Здесь подзапрос тоже
коррелированный, но он возвращает одно число. В уроке 1 скалярный
подзапрос был самостоятельным — его результат был одинаковым для всех
внешних строк; здесь скалярный подзапрос зависит от `c.id`, поэтому
результат может быть разным для каждого покупателя.

```sql
SELECT name,
       (SELECT COUNT(*) FROM orders WHERE customer_id = c.id) AS orders_cnt
FROM customers AS c
ORDER BY c.id;
```

```text
+---------------+------------+
| name          | orders_cnt |
+---------------+------------+
| Анна Петрова  |          2 |
| Иван Сидоров  |          1 |
| Мария Волкова |          0 |
| Пётр Смирнов  |          0 |
+---------------+------------+
```

Для каждого покупателя внутренний `SELECT COUNT(*)` считает заказы с
его `customer_id`. Мария и Пётр дают ноль — `COUNT(*)` от нуля строк
возвращает 0, поэтому для Марии и Петра результат — 0, а не NULL.
Здесь коррелированный **скалярный** подзапрос, не `EXISTS`.

Когда что: «есть/нет» → `EXISTS` / `NOT EXISTS`; «сколько/какой
агрегат по внешней строке» → коррелированный скаляр. Обе задачи
сегодня законны.

### EXISTS и производительность: короткая ремарка

Коррелированный `EXISTS` логически связывает внутренний запрос с
текущей строкой внешнего запроса. На больших таблицах стоимость
запроса зависит от плана выполнения и доступных индексов. В нашем
примере `orders.customer_id` индексируется как внешний ключ. Подробное
сравнение `EXISTS`, `IN`, `JOIN`, индексов и `EXPLAIN` — за пределами
этого урока.

### Где живёт подзапрос сегодня

Краткая карта мест, которые сегодня законны:

- **WHERE** — `EXISTS (подзапрос)` или `NOT EXISTS (подзапрос)`. В
  этом уроке мы используем `EXISTS` и `NOT EXISTS` прежде всего в
  коррелированной форме: внутренний запрос ссылается на внешнюю
  строку. Некоррелированный `EXISTS` тоже допустим, но его результат
  не зависит от текущей строки внешнего запроса.
- **список SELECT** — коррелированный скаляр (агрегат или выражение
  по внешней строке).
- **FROM** — самостоятельная производная таблица из урока 1.
  Коррелированные производные таблицы в этом курсе пока не
  рассматриваются.

Скобки вокруг подзапроса в `EXISTS` обязательны — без них сервер не
отличит вложенный запрос от имени столбца (урок 1).

### Типичные ошибки

**`EXISTS` без корреляции.** Внутренний запрос не ссылается на
внешнюю строку — `EXISTS` для всех покупателей даёт одно и то же
значение (true или false), и результат вырождается. Корреляция —
это и есть суть инструмента.

**`SELECT список_столбцов` внутри `EXISTS`.** Семантически не
ошибка, но вводит в заблуждение: `EXISTS` интересует только факт
наличия строки. Содержимое `SELECT` не используется. Идиома — `SELECT
1` или `SELECT *`.

**`NOT EXISTS` — один оператор.** Скобки вокруг подзапроса обязательны
в любом случае.

**`NOT IN` там, где `NOT EXISTS` уместнее.** Если во внутреннем
столбце возможен NULL и анти-join — цель запроса, `NOT IN` даёт
пустой результат. Здесь правильный инструмент — `NOT EXISTS`.

### Чего в этом уроке нет

- `UNION` / `UNION ALL` — урок 3 «Среднего»: вертикальная склейка
  результатов.
- Цепочки CTE, рекурсивные CTE, календарная таблица — урок 4
  «Среднего».
- Оконные функции (`ROW_NUMBER`, `LAG`, накопительные суммы) — уроки
  5–6 «Среднего».
- `EXPLAIN`, индексы, выбор между `EXISTS` и `JOIN` по плану —
  продвинутый уровень.
- Коррелированные подзапросы в `UPDATE` и `DELETE` (например,
  «обновить товары, у которых цена ниже средней по своей категории»)
  — за границей курса MySQL, упоминается только в расширенных
  курсах.

### Резюме

- Коррелированный подзапрос ссылается на столбец внешней строки и
  пересчитывается для каждой проверки.
- `EXISTS` возвращает true/false по факту наличия хотя бы одной
  строки во внутреннем результате; содержимое `SELECT` не важно.
- `NOT EXISTS` — отрицание `EXISTS`. Это замена `NOT IN`, которая
  не «ломается» на NULL во внутреннем столбце.
- Анти-join решается тремя способами: `NOT EXISTS`, `NOT IN`,
  `LEFT JOIN ... IS NULL`. По умолчанию в современном SQL —
  `NOT EXISTS`, если не нужны столбцы правой таблицы.
- Коррелированный скаляр — для агрегатов по внешней строке
  (например, `COUNT(*)` заказов каждого покупателя).
- `EXISTS` хорош, когда связь уже поддержана индексом; без индекса
  сервер сканирует внутреннюю таблицу для каждой внешней строки.

- ❌ возвращает первую строку внутреннего запроса — error_text: `EXISTS` не возвращает строки наружу — ни первой, ни какой-либо ещё. Оператор проверяет только факт наличия хотя бы одной строки; значения столбцов во внешний контекст не уходят.
- ❌ сравнивает результат подзапроса с внешней строкой через `=` — error_text: `EXISTS` не использует сравнение значений; он проверяет количество строк. Сравнение через `=` — работа скаляра или `IN`, не `EXISTS`.
- ❌ считает количество строк внутреннего запроса — error_text: подсчёт строк — работа `COUNT(*)`, а не `EXISTS`. `EXISTS` останавливается на первой найденной строке и не считает остальные; возвращает только true/false.

### Вопрос 2: Чем `NOT EXISTS` отличается от `NOT IN` для анти-join в плане NULL?

- ✅ `NOT EXISTS` корректно работает, даже если во внутреннем столбце есть NULL; `NOT IN` в этом случае даёт пустой результат
<!-- EXISTS проверяет наличие строки, а не значение; NULL не «отравляет» ответ -->
- ❌ оба ведут себя одинаково, NULL не влияет — error_text: это ошибка. `NOT IN` ломается на NULL во внутреннем столбце: `id NOT IN (1, 2, NULL)` даёт UNKNOWN для всех обычных `id` (урок 1 «Среднего»), и строки не проходят. `NOT EXISTS` этой ловушки не имеет.
- ❌ `NOT EXISTS` возвращает NULL, а `NOT IN` — false — error_text: `NOT EXISTS` возвращает true/false, как и `NOT IN`. NULL здесь ни при чём. Различие — в том, как операторы учитывают `NULL` во внутреннем списке, а не в типе возврата.
- ❌ `NOT EXISTS` нельзя использовать с подзапросом, только с таблицей — error_text: можно и нужно. `NOT EXISTS` принимает именно подзапрос; в нашем примере это `SELECT 1 FROM orders WHERE customer_id = c.id`. Без подзапроса оператор бессмысленен.

### Вопрос 3: Запрос `SELECT id, name FROM customers AS c WHERE NOT EXISTS (SELECT 1 FROM orders AS o WHERE o.customer_id = c.id)`. Что произойдёт, если во внутреннем `orders.customer_id` появится NULL?

- ✅ результат не изменится: NULL не делает «существование» ложным и не делает его истинным; для покупателя без заказов `NOT EXISTS` остаётся true
<!-- корреляция сравнивает customer_id с c.id; для NULL-связи EXISTS даёт false, NOT EXISTS — true, остальные строки не трогаются -->
- ❌ все строки customers отфильтруются — error_text: это поведение `NOT IN`, не `NOT EXISTS`. `NOT EXISTS` сравнивает наличие строки, а не значение, и NULL в `customer_id` не превращает «есть подходящая строка» в true для всех покупателей сразу.
- ❌ появится ошибка 1242 — error_text: ошибка 1242 («Subquery returns more than 1 row») — про скалярный подзапрос с несколькими строками. `EXISTS` / `NOT EXISTS` принимают любой результат и интересуются только фактом наличия; 1242 здесь не возникает.
- ❌ NULL в `customer_id` заменит отсутствие заказа — error_text: `customer_id IS NULL` в строке заказа — это заказ без покупателя, а не заказ «для всех». У такого заказа `customer_id = NULL`, при сравнении с конкретным `c.id` строка не подходит, `EXISTS` остаётся false для текущего покупателя. Семантика «замены отсутствия» здесь не работает.

### Вопрос 4: Когда `EXISTS` уместнее, чем `LEFT JOIN ... WHERE правый.pk IS NULL`?

- ✅ когда в отчёте нужна только левая сторона и не нужны столбцы правой таблицы
<!-- EXISTS говорит «есть/нет» и не размножает строки; LEFT JOIN нужен, когда нужны данные правой -->
- ❌ всегда, потому что EXISTS короче — error_text: «короче» — не аргумент. Если в результате нужны столбцы заказов (сумма, дата, статус), `LEFT JOIN` нужен: `EXISTS` такие данные не возвращает, в списке SELECT у него пусто.
- ❌ только когда во внешней таблице меньше 100 строк — error_text: размер таблицы не критерий выбора. На малых данных оба запроса быстрые; выбор определяется семантикой результата (нужны ли правые столбцы), а не размером.
- ❌ EXISTS нельзя использовать с LEFT JOIN в одном запросе — error_text: можно. В одном запросе легко комбинировать разные конструкции: например, `SELECT ... FROM a LEFT JOIN b ON ... WHERE EXISTS (SELECT 1 FROM c WHERE ...)`. `EXISTS` живёт в `WHERE`, `LEFT JOIN` — в `FROM`, они не мешают друг другу.

### Вопрос 5: `SELECT name FROM customers AS c WHERE EXISTS (SELECT 1)`. Что вернёт этот запрос?

- ✅ всех покупателей: `SELECT 1` всегда даёт ровно одну строку, `EXISTS` для любого покупателя даёт true, фильтр не отсеивает никого
<!-- без корреляции EXISTS вырождается в константу true; запрос синтаксически валиден, но семантически бесполезен -->
- ❌ ошибку синтаксиса: подзапрос в EXISTS обязан ссылаться на внешнюю строку — error_text: это распространённое заблуждение. MySQL принимает `EXISTS (SELECT 1)` без корреляции и возвращает все строки внешней таблицы. Корреляция не синтаксическое требование, а условие полезности `EXISTS`: без неё результат не зависит от внешней строки и `EXISTS` превращается в константу.
- ❌ пустой результат — error_text: пустой результат был бы у `EXISTS (SELECT * FROM orders WHERE 1 = 0)`, где внутренний запрос заведомо пуст. `SELECT 1` без FROM возвращает ровно одну строку, поэтому `EXISTS` всегда true.
- ❌ каждого покупателя один раз, но в случайном порядке — error_text: вопрос не про порядок результата. Без `ORDER BY` SQL не гарантирует порядок строк; для проверки конкретного порядка нужна явная сортировка. Здесь же проверяется сам факт, что фильтр пропускает всех.
