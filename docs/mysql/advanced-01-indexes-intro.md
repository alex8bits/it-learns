Вопрос «а насколько быстро СУБД это выполнит» до сих пор был за кадром — на учебных наборах из десятков строк любой запрос отрабатывает мгновенно, независимо от его качества. В производственной базе интернет-магазина таблица `order_items` может содержать десятки миллионов строк, а `orders` — миллионы, и один и тот же по смыслу запрос может выполниться за миллисекунды или за минуты — в зависимости от того, знает ли СУБД быстрый путь к нужным строкам. Этот путь называется **индексом**, и его понимание — фундамент всего уровня «Продвинутый».

### Как MySQL ищет строки без индекса

Пока не сказано иное, при выполнении `WHERE customer_id = 42` MySQL обязана проверить *каждую* строку таблицы: прочитать её с диска (или из кеша в памяти), сравнить значение столбца `customer_id` с `42`, и либо включить строку в результат, либо отбросить. Такой способ поиска называется **полным сканированием таблицы** (full table scan). Для таблицы из 10 строк это не проблема — вся работа займёт микросекунды. Для таблицы `orders` с 5 000 000 строк это означает 5 000 000 сравнений при каждом обращении, даже если результату отвечает только одна строка. Полное сканирование не становится «ошибкой» — иногда это действительно единственный и по-своему правильный способ выполнить запрос (например, если условие `WHERE` отбирает половину всех строк таблицы, читать их всё равно придётся почти все, и накладные расходы на альтернативный способ поиска этого не оправдают) — но для точечных, избирательных запросов по большим таблицам полное сканирование — это именно та ситуация, которую индекс призван устранить.

### Аналогия: алфавитный указатель в книге

Представим толстую техническую книгу без предметного указателя в конце: чтобы найти все страницы, где упоминается слово «транзакция», пришлось бы пролистать книгу целиком, страницу за страницей — это прямой аналог full table scan. Предметный указатель, отсортированный по алфавиту, решает эту задачу иначе: он заранее хранит короткий список «слово → номера страниц», отсортированный так, что нужное слово находится почти мгновенно (открыв указатель, читатель сразу перескакивает в нужную область алфавита, а не читает его с первой строки). Индекс базы данных — тот же принцип: заранее подготовленная, отдельно хранимая и отсортированная структура «значение столбца → место строки в таблице», которая позволяет находить строки без перебора всех остальных.

### Устройство индекса: B-tree в двух словах

По умолчанию индексы InnoDB (основного и рекомендуемого движка хранения таблиц MySQL, используемого во всех примерах курса) реализованы через структуру данных **B-tree** (сбалансированное дерево). Не углубляясь в детали реализации (это отдельная и обширная тема computer science), для практической работы важны три следствия этого устройства:

- значения в индексе физически хранятся **в отсортированном порядке**, что делает быстрым не только точный поиск (`= значение`), но и поиск по диапазону (`BETWEEN`, `<`, `>`, `ORDER BY`);
- глубина дерева растёт **логарифмически** от числа строк — поиск по индексу в таблице из миллиона строк требует буквально нескольких шагов сравнения, а не миллиона;
- индекс — это **отдельная структура данных**, хранящаяся на диске рядом с самой таблицей, а не «настройка» существующих данных — она занимает собственное место и должна поддерживаться в согласованном состоянии при каждом изменении таблицы.

### CREATE INDEX: как создать индекс

Синтаксис создания индекса для существующей таблицы:

```sql
CREATE INDEX idx_orders_customer_id
ON orders (customer_id);
```

Здесь `idx_orders_customer_id` — имя индекса (произвольное, но по общепринятому соглашению принято включать в него имя таблицы и столбца — это заметно упрощает жизнь при чтении списка индексов таблицы через полгода), `orders` — таблица, `(customer_id)` — столбец, по которому строится индекс. После выполнения этой команды запрос `SELECT * FROM orders WHERE customer_id = 42` больше не обязан читать всю таблицу — он находит нужные строки через индекс за считаные шаги.

Индекс можно также объявить прямо при создании таблицы, внутри `CREATE TABLE` (седьмой урок уровня «Основы» уже показывал `CREATE TABLE` с ограничениями — индекс добавляется туда же):

```sql
CREATE TABLE reviews (
    id INT AUTO_INCREMENT PRIMARY KEY,
    product_id INT NOT NULL,
    customer_id INT NOT NULL,
    rating TINYINT NOT NULL,
    body TEXT,
    created_at DATETIME NOT NULL,
    INDEX idx_reviews_product_id (product_id)
);
```

Удаление индекса, если он больше не нужен, выполняется командой `DROP INDEX`, по аналогии с уже знакомым из седьмого урока уровня «Основы» `DROP`-семейством команд:

```sql
DROP INDEX idx_orders_customer_id ON orders;
```

### Важная деталь: PRIMARY KEY — это тоже индекс

Первичный ключ, объявленный ещё в шестом уроке уровня «Основы» через `PRIMARY KEY`, автоматически создаёт **уникальный индекс** по своим столбцам — отдельно вызывать `CREATE INDEX` для первичного ключа не нужно и невозможно (он уже есть). То же касается столбцов с ограничением `UNIQUE` (тот же шестой урок уровня «Основы») — уникальность в MySQL физически реализуется через уникальный индекс, который параллельно ускоряет и точечный поиск по этому столбцу. Это значит, что запрос `SELECT * FROM products WHERE id = 5` (поиск по первичному ключу) уже быстр без каких-либо дополнительных действий — а вот поиск по любому другому столбцу, не отмеченному как ключ или `UNIQUE`, по умолчанию будет полным сканированием, пока по нему не создан явный индекс.

### Цена индекса: ничего не бывает бесплатным

Если индексы настолько ускоряют чтение, почему не проиндексировать сразу все столбцы всех таблиц? Ответ — у индекса есть три вида реальной цены, которую платформа платит непрерывно, а не только в момент создания:

- **Место на диске.** Индекс — отдельная структура данных, которая хранится наряду с самой таблицей. Индекс по короткому целочисленному столбцу в таблице из миллионов строк может занимать заметную долю объёма, сравнимого с самой таблицей; несколько составных индексов на широкую таблицу способны увеличить её физический размер в разы.
- **Замедление записи.** Каждая команда `INSERT`, `UPDATE` (изменяющая проиндексированный столбец) или `DELETE` обязана не только изменить саму строку таблицы, но и обновить **каждый** индекс, затрагивающий эту строку — вставить новое значение в отсортированную структуру B-tree, удалить старое, при необходимости перестроить часть дерева. Таблица с пятью индексами платит за это ощутимо больше времени на каждую вставку, чем таблица без индексов вовсе — при высокой частоте записи (например, в `order_log`, куда пишутся события по каждому изменению заказа) это может стать заметным фактором производительности.
- **Обслуживание.** Индексы, как и сами таблицы, требуют места в буферном пуле сервера (области памяти, где MySQL кеширует часто используемые данные и структуры индексов) — лишние ненужные индексы конкурируют за эту память с действительно нужными данными, потенциально вытесняя их из кеша.

Отсюда следует практическое правило: индекс создаётся не «на будущее» и не «на всякий случай», а под конкретный, реально существующий сценарий чтения — точечный поиск, диапазонный запрос или сортировку, которые без индекса будут читать заметную долю строк большой таблицы. Столбцы, которые никогда не встречаются в `WHERE`, `ON`, `ORDER BY` или `GROUP BY`, индексировать незачем — это чистый расход места и скорости записи без единой выгоды при чтении.

### Эксперимент: поиск без индекса и с индексом

Чтобы увидеть разницу не в теории, а на практике, полезно провести небольшой эксперимент на таблице заметного размера (десятки или сотни тысяч строк — на таблице из десяти строк разница будет неразличима, потому что даже полное сканирование такой таблицы происходит мгновенно). План эксперимента:

1. Создать таблицу `orders_bench` с тем же набором столбцов, что у `orders`, и заполнить её большим числом строк — например, через `INSERT ... SELECT` (седьмой урок уровня «Средний») с генерацией случайных значений `customer_id` в цикле или через вспомогательную числовую CTE (четвёртый урок уровня «Средний» — `WITH RECURSIVE` для генерации последовательности чисел).
2. Замерить время выполнения `SELECT * FROM orders_bench WHERE customer_id = 12345;` **до** создания индекса — клиент `mysql` CLI выводит время выполнения запроса после каждой команды.
3. Выполнить `CREATE INDEX idx_orders_bench_customer_id ON orders_bench (customer_id);` и подождать её завершения — на большой таблице создание индекса требует времени, потому что серверу нужно прочитать все существующие строки и построить структуру индекса с нуля.
4. Повторить тот же самый `SELECT` и сравнить время выполнения.

На таблице из нескольких сотен тысяч строк разница обычно заметна невооружённым глазом — запрос без индекса выполняется десятки или сотни миллисекунд (пропорционально размеру таблицы), запрос с индексом — единицы миллисекунд, независимо от того, насколько выросла таблица. В следующем уроке появится инструмент `EXPLAIN`, который покажет эту разницу не через секундомер, а через явный «план выполнения» запроса — какой путь выбрала СУБД для поиска строк. Пока достаточно зафиксировать сам эффект: наличие подходящего индекса меняет характер зависимости времени поиска от размера таблицы — с линейного (чем больше строк, тем дольше) на практически постоянный.

### Резюме

- Без индекса поиск строки по условию `WHERE` требует **полного сканирования таблицы** — проверки каждой строки; на больших таблицах это дорого по времени.
- **Индекс** — заранее подготовленная, отдельно хранимая и отсортированная структура «значение → положение строки», по аналогии с алфавитным предметным указателем книги; в InnoDB реализован через B-tree.
- Благодаря отсортированности и логарифмической глубине дерева индекс ускоряет не только точный поиск (`=`), но и диапазонные условия, и сортировку.
- `PRIMARY KEY` и `UNIQUE` уже создают индекс автоматически; для остальных столбцов индекс создаётся явно командой `CREATE INDEX имя ON таблица (столбец);` и удаляется через `DROP INDEX имя ON таблица;`.
- Индекс не бесплатен: он занимает место на диске, замедляет `INSERT`/`UPDATE`/`DELETE` (каждый индекс нужно обновлять при каждой изменяющей операции) и конкурирует за память буферного пула — создавать индекс стоит под конкретный сценарий чтения, а не «про запас».
- Эффект индекса лучше всего виден на большой таблице через прямое сравнение времени выполнения одного и того же запроса до и после создания индекса — на маленьких учебных таблицах разница может быть незаметна.

## Теоретические задания

### Вопрос 1: Как MySQL выполняет условие `WHERE customer_id = 42`, если по столбцу `customer_id` нет никакого индекса?

- ✅ Полным сканированием таблицы: последовательно читает и проверяет каждую строку
<!-- full table scan — цена отсутствия индекса; на большой таблице это линейная зависимость от числа строк -->
- ❌ Отказывается выполнять запрос, пока не создан индекс — error_text: отсутствие индекса — не ошибка, а причина медленной работы. MySQL всегда может выполнить запрос полным сканированием: прочитать каждую строку и сравнить значение столбца с условием. Проблема в скорости на больших таблицах, а не в принципиальной возможности выполнить запрос.
- ❌ Читает строки в порядке первичного ключа и останавливается на первом совпадении — error_text: без индекса по `customer_id` порядок первичного ключа ничем не помогает: значения `customer_id` разбросаны по всей таблице, поэтому проверять приходится все строки до последней — первое найденное совпадение ничего не говорит о наличии остальных.
- ❌ Автоматически использует индекс первичного ключа, так как любой поиск идёт через него — error_text: индекс первичного ключа ускоряет только поиск по самому столбцу `id`: в нём строки упорядочены по `id`, а не по `customer_id`. Условие по любому другому столбцу этот порядок использовать не может.

### Вопрос 2: За счёт какого свойства индекса ускоряются не только точный поиск (`=`), но и диапазонные условия (`BETWEEN`, `>`) и сортировка (`ORDER BY`)?

- ✅ Значения в индексе физически хранятся в отсортированном порядке
<!-- B-tree отсортирован; диапазон — это непрерывный кусок этой сортировки; ORDER BY может читать уже упорядоченные значения -->
- ❌ Индекс кеширует результаты предыдущих похожих запросов — error_text: индекс — структура данных, а не кеш результатов. Он ничего не знает о том, какие запросы выполнялись и что они вернули; он хранит значения проиндексированного столбца в отсортированном порядке со ссылками на строки таблицы.
- ❌ MySQL строит отдельную уменьшенную копию таблицы в оперативной памяти — error_text: индекс — отдельная структура данных, хранящаяся на диске рядом с таблицей, а не её копия в памяти. Он содержит значения проиндексированных столбцов и ссылку на строку, но не строку целиком, и его существование не связано с кешированием.
- ❌ Дерево индекса распараллеливает сравнение значения сразу по всем строкам таблицы — error_text: сравнения в B-tree выполняются последовательно: на каждом уровне спуска по дереву одно сравнение отбрасывает целую ветвь. Ускорение даёт логарифмическая глубина дерева, а не параллелизм.

### Вопрос 3: Что верно для таблицы, в которой объявлены `PRIMARY KEY (id)` и `UNIQUE (email)`?

- ✅ Оба ограничения уже создали индексы — отдельные `CREATE INDEX` для них не нужны
<!-- PRIMARY KEY и UNIQUE физически реализованы через уникальные индексы -->
- ❌ `PRIMARY KEY` не создаёт индекс — это только логическое ограничение уникальности — error_text: первичный ключ в MySQL физически реализуется как уникальный индекс. Именно поэтому поиск по `id` быстр без каких-либо дополнительных действий — отдельный `CREATE INDEX` по первичному ключу и вовсе невозможен: он уже есть.
- ❌ `UNIQUE` создаёт индекс, только если после объявления выполнить явный `CREATE INDEX` по этому столбцу — error_text: уникальность в MySQL реализуется через уникальный индекс, который сервер создаёт автоматически при объявлении `UNIQUE`. Явный `CREATE INDEX` по тому же столбцу лишь продублировал бы уже существующую структуру.
- ❌ Ни тот ни другой не ускоряют поиск — по этим столбцам всегда полное сканирование — error_text: оба ограничения порождают индексы, и точечный поиск по ним идёт именно через эти индексы. Полным сканированием будет поиск по любому другому столбцу, для которого индекса нет.

### Вопрос 4: Чем таблица с пятью индексами платит за каждый `INSERT` по сравнению с таблицей без индексов?

- ✅ Каждая вставка обязана обновить все пять индексов — внести новое значение в каждую отсортированную структуру
<!-- цена индекса на запись: каждый индекс поддерживается в согласованном состоянии при каждой изменяющей операции -->
- ❌ Ничем: индексы влияют только на чтение — error_text: каждая изменяющая операция — `INSERT`, `UPDATE` проиндексированного столбца, `DELETE` — обязана поддерживать каждый индекс в согласованном состоянии. Чем больше индексов у таблицы, тем больше дополнительной работы выполняет сервер при записи.
- ❌ Плата вносится один раз, при `CREATE INDEX`, — дальше запись не замедляется — error_text: построение структуры при создании индекса — разовая работа по его наполнению. Но после этого каждая вставка и каждое удаление строки обязаны обновлять каждый индекс: плата непрерывная, а не разовая.
- ❌ Вставка наоборот ускоряется: индексы помогают серверу найти место для новой строки — error_text: индексы не участвуют в размещении строк — место для строки определяет движок хранения. Индексы лишь добавляют работу: в каждом из пяти отсортированных деревьев нужно зарегистрировать новое значение.

### Вопрос 5: Каков порядок числа шагов сравнения при поиске значения по индексу в таблице из 1 000 000 строк?

- ✅ Порядка нескольких шагов — глубина B-tree растёт логарифмически от числа строк
<!-- логарифмическая глубина: миллион строк — примерно 20 уровней дерева -->
- ❌ Около миллиона: даже с индексом сервер сравнивает значение с каждой строкой — error_text: это описание полного сканирования — ровно того, от чего индекс избавляет. На каждом шаге спуска по B-tree сравнение отбрасывает целую ветвь дерева, поэтому миллион строк «сжимается» до пары десятков сравнений.
- ❌ Ровно один шаг: корень дерева содержит все значения столбца — error_text: корень B-tree содержит только опорные значения для выбора следующей ветви, а не весь миллион значений. Спуск от корня к листу и составляет логарифмическое число шагов.
- ❌ Около тысячи — примерно корень из числа строк — error_text: глубина B-tree растёт не как квадратный корень, а как логарифм: при удвоении числа строк глубина увеличивается примерно на единицу. Тысяча шагов — оценка, относящаяся к совсем другой структуре данных.

### Задание 1: Первый индекс и его след в системном каталоге

`CREATE INDEX` на столбец без индекса + подтверждение структуры через
`information_schema.STATISTICS`.

<!-- Эталонное решение (для автора/бота-верификатора): CREATE INDEX idx_orders_customer ON orders (customer_id); SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE FROM information_schema.STATISTICS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'orders' ORDER BY INDEX_NAME, SEQ_IN_INDEX; -->

**statement:**

Таблица `orders` (восемь заказов) создана без единого вторичного
индекса: только первичный ключ по `id`. Частый точечный запрос
`SELECT * FROM orders WHERE customer_id = 7` сегодня выполняется
полным сканированием. Выполните два шага:

1. Создайте индекс `idx_orders_customer` по столбцу `customer_id`
   командой `CREATE INDEX`.
2. Подтвердите появление индекса запросом к системному каталогу —
   это финальная инструкция решения (промежуточные инструкции не
   должны возвращать строки):

```sql
SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'orders'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

`information_schema.STATISTICS` — системная таблица, в которой сервер
перечисляет все индексы всех таблиц: по одной строке на каждый столбец
каждого индекса.

**expected_result_text:**

Финальный SELECT возвращает две строки: созданный вами неуникальный
индекс `idx_orders_customer` по столбцу `customer_id`
(`NON_UNIQUE = 1`) и автоматически существующий уникальный `PRIMARY`
по столбцу `id` (`NON_UNIQUE = 0`). Строка `idx_orders_customer`
идёт первой: сортировка имён индексов регистронезависимая, а буква
`i` в ней стоит раньше буквы `p` из `PRIMARY`.

**seed_sql:**

```sql
CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME NOT NULL
);

INSERT INTO orders (customer_id, status, created_at) VALUES

    (2, 'paid', '2026-03-01 16:35:00'),

```

**expected_rows:**

| INDEX_NAME          | SEQ_IN_INDEX | COLUMN_NAME | NON_UNIQUE |
| ------------------- | ------------ | ----------- | ---------- |

### Задание 2: Какие индексы уже есть у таблицы

Чтение `information_schema.STATISTICS`: `PRIMARY KEY` и `UNIQUE`
порождают индексы без всякого `CREATE INDEX`.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE FROM information_schema.STATISTICS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'reviews' ORDER BY INDEX_NAME, SEQ_IN_INDEX; -->

**statement:**

Таблица `reviews` (шесть отзывов) создана со следующими
ограничениями и индексами: `PRIMARY KEY (id)`,
`UNIQUE KEY uq_reviews_product_customer (product_id, customer_id)`
и `INDEX idx_reviews_created (created_at)`. Ничего не создавая,
выведите полный список индексов этой таблицы одним запросом к
системному каталогу (финальная и единственная инструкция решения):

```sql
SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'reviews'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

Обратите внимание: `SEQ_IN_INDEX` показывает позицию столбца внутри
составного индекса, а `NON_UNIQUE` — уникальность (`0` — уникальный,
`1` — нет).

**expected_result_text:**

Финальный SELECT возвращает четыре строки: неуникальный
`idx_reviews_created` по `created_at`, уникальный `PRIMARY` по `id`
и составной уникальный `uq_reviews_product_customer` из двух строк —
`product_id` с `SEQ_IN_INDEX = 1` и `customer_id` с
`SEQ_IN_INDEX = 2`. Порядок строк — по имени индекса
(регистронезависимо: `idx...` < `PRIMARY` < `uq...`), внутри
составного индекса — по `SEQ_IN_INDEX`.

**seed_sql:**

```sql
CREATE TABLE reviews (
    id INT AUTO_INCREMENT PRIMARY KEY,
    product_id INT NOT NULL,
    customer_id INT NOT NULL,
    rating TINYINT NOT NULL,
    body TEXT,
    created_at DATETIME NOT NULL,
    UNIQUE KEY uq_reviews_product_customer (product_id, customer_id),
    INDEX idx_reviews_created (created_at)
);

INSERT INTO reviews (product_id, customer_id, rating, body, created_at) VALUES
    (3, 1, 5, 'Отличный монитор', '2026-01-18 09:20:00'),

    (3, 4, 5, 'Доволен покупкой', '2026-02-09 17:15:00'),
    (1, 5, 4, NULL, '2026-02-21 08:55:00'),
    (2, 3, 2, 'Подсветка сломалась', '2026-03-03 19:30:00');
```

**expected_rows:**

| INDEX_NAME                   | SEQ_IN_INDEX | COLUMN_NAME  | NON_UNIQUE |
| ---------------------------- | ------------ | ------------ | ---------- |
| idx_reviews_created          | 1            | created_at   | 1          |
| PRIMARY                      | 1            | id           | 0          |
