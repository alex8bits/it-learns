# IN, BETWEEN, LIKE: список, диапазон, шаблон

## Материал

### Три обещания прошлого урока

Прошлый урок закончился разделом «Чего в этом уроке нет» — и все три
пункта сегодня наши: `IN`, `BETWEEN`, `LIKE`. Если копнуть глубже,
обещание было дано ещё в «Основах», уроком 8: «диапазон одним условием
(BETWEEN), поиск по шаблону (LIKE) — тоже впереди».

Повод назрел по трём направлениям сразу. Во-первых, OR-цепочки урока 1 —
`city = 'Москва' OR city = 'Казань'` — работают, но многословны, и при
смешении с AND каждая требует скобок. Во-вторых, «от 1000 до 5000» мы
умеем только парой сравнений — работает, но один оператор лучше двух.
В-третьих — главное: «название содержит HDMI» сравнениями не выразить
вовсе, `=` требует полного совпадения. Итак: список, диапазон, шаблон.

### IN: «один из списка»

Форма — `столбец IN (список значений)`: «значение столбца — одно из
перечисленных». Это короткая запись для шаблона урока 1 «один столбец,
несколько допустимых значений»:

```sql
SELECT name, city
FROM customers
WHERE city IN ('Москва', 'Казань')
ORDER BY id;
```

```text
+-----------------------------+--------------+
| name                        | city         |
+-----------------------------+--------------+
| Анна Петрова                | Москва       |
| Иван Сидоров                | Казань       |
| Мария Волкова               | Москва       |
+-----------------------------+--------------+
```

Тот же результат, что у OR-версии урока 1: `city IN ('Москва', 'Казань')`
эквивалентен `city = 'Москва' OR city = 'Казань'`. Только короче — и без
ловушек OR: в скобках стоят значения, синтаксис не даст перепутать их с
условиями, как в `OR 'Казань'` из урока 1.

Главная практическая выгода — скобки. «Дорогие товары из периферии или
аксессуаров» в уроке 1 требовали `(category_id = 1 OR category_id = 2)
AND price > 2000`. Теперь:

```sql
SELECT name, category_id, price
FROM products
WHERE category_id IN (1, 2) AND price > 2000
ORDER BY id;
```

```text
+---------------------------+-------------+---------+
| name                      | category_id | price   |
+---------------------------+-------------+---------+
| Клавиатура механическая   |           2 | 4990.00 |
| Веб-камера                |           2 | 2450.00 |
+---------------------------+-------------+---------+
```

`IN` — единое условие, как сравнение: группировать нечего, скобки не
нужны. Список — литералы любого типа: числа без кавычек, строки и даты
в кавычках (урок 8 «Основ»); порядок значений и дубликаты в списке не важны —
это множество допустимых, а не последовательность. Отрицание — `NOT IN`:
«все, кроме перечисленных»:

```sql
SELECT name, city
FROM customers
WHERE city NOT IN ('Москва', 'Новосибирск')
ORDER BY id;
```

```text
+-----------------------------+-----------------+
| name                        | city            |
+-----------------------------+-----------------+
| Иван Сидоров                | Казань          |
| Дмитрий Козлов              | Санкт-Петербург |
+-----------------------------+-----------------+
```

А теперь NULL — тема, которую урок 1 разобрал для AND/OR и которая здесь
стреляет дважды. `IN` — это OR-цепочка сравнений на равенство, поэтому
все правила трёхзначной логики в силе.

Положительный `IN` со списком, содержащим NULL, ещё лоялен:

```sql
SELECT name, phone FROM customers WHERE phone IN ('912-345-67-89', NULL);
```

```text
+-----------------------------+---------------+
| name                        | phone         |
+-----------------------------+---------------+
| Иван Сидоров                | 912-345-67-89 |
+-----------------------------+---------------+
```

Вернулся только Иван: у него «да» на равенство номеру, а «да» OR
«неизвестно» = «да» — строка проходит. У остальных — «неизвестно» на
весь список, и они выпадают.

`NOT IN` с NULL в списке — чёрная дыра:

```sql
SELECT name FROM customers WHERE phone NOT IN ('912-345-67-89', NULL);
```

Пустой результат. У Ивана «да» OR «неизвестно» = «да», после NOT — «нет».
У каждого из остальных равенство номеру — «нет», равенство NULL —
«неизвестно», «нет» OR «неизвестно» = «неизвестно», после NOT — снова
«неизвестно». Ни одного «да» — ни одной строки. Правило: **не кладите
NULL в список `IN`/`NOT IN`** — отсутствие в списке не фильтрует, а
обнуляет результат.

Граница темы: список — всегда конкретные значения. `IN` умеет принимать
и результат подзапроса — списка из другой таблицы; это инструмент
среднего уровня, не сегодня.

Список из одного значения — тоже законно: `category_id IN (3)` — то же,
что `category_id = 3`. Вручную для одного значения пишут `=`; `IN`
оставляют спискам. Зато запросы, которые собирает программа, часто пишут
`IN` всегда — условию безразлично, одно значение пришло или десять.

### BETWEEN: диапазон одним условием

Форма — `столбец BETWEEN a AND b`, и это в точности
`столбец >= a AND столбец <= b`:

```sql
SELECT name, price
FROM products
WHERE price BETWEEN 690 AND 1290.50
ORDER BY id;
```

```text
+---------------------------+---------+
| name                      | price   |
+---------------------------+---------+
| Коврик для мыши           |  690.00 |
| Мышь беспроводная         | 1290.50 |
+---------------------------+---------+
```

Границы выбраны не случайно: коврик стоит ровно 690, мышь ровно 1290.50 —
и **обе строки в результате**. Главное свойство BETWEEN: обе границы
включены. «От 1000 до 2000» через BETWEEN — это и 1000, и 2000; вопрос
урока 8 «Основ» «что делать с границей» здесь решён по умолчанию — включать.

Зачем нужен BETWEEN, если пара сравнений даёт тот же результат?
Читаемость. `price BETWEEN 1000 AND 2000` с первого взгляда сообщает:
«диапазон, вместе с краями». Пара `price >= 1000 AND price <= 2000`
сообщает то же, но медленнее — и с шансом опечататься в одной из
половинок, например забыть `=` у границы. Одно условие вместо двух —
меньше мест для ошибки; под капотом механизм тот же.

Отрицание зеркально правилу NOT из урока 1 — нестрогие границы
переворачиваются в строгие:

```sql
SELECT name, price
FROM products
WHERE price NOT BETWEEN 690 AND 1290.50
ORDER BY id;
```

```text
+---------------------------+----------+
| name                      | price    |
+---------------------------+----------+
| Клавиатура механическая   |  4990.00 |
| Монитор 27"               | 15990.00 |
| Кабель HDMI 2 м           |   450.00 |
| Веб-камера                |  2450.00 |
+---------------------------+----------+
```

`NOT BETWEEN` = «строго меньше `a` ИЛИ строго больше `b`» — обе границы
выпали. Две мелочи напоследок. Границы перепутаны местами
(`BETWEEN 1290.50 AND 690`) дают пустой результат: условие «>= 1290.50
и <= 690» неисполнимо, сервер не станет угадывать намерение. И BETWEEN
работает для любых сравнимых значений — числа, даты, строки по алфавиту,
— но главные его роли — числа и даты. Датам отдельный разговор.

### Даты в BETWEEN: полночь на верхней границе

«Все заказы за 30 июня». Заказы хранят `DATETIME`, а урок 8 («Основы»)
уже предупреждал: литерал из одной даты в сравнении с `DATETIME` означает
полночь. Пишем наивный BETWEEN:

```sql
SELECT id, customer, created_at
FROM orders
WHERE created_at BETWEEN '2026-06-30' AND '2026-07-01'
ORDER BY id;
```

```text
+----+-----------------------------+---------------------+
| id | customer                    | created_at          |
+----+-----------------------------+---------------------+
|  2 | Иван Сидоров                | 2026-06-30 10:00:00 |
|  3 | Мария Волкова               | 2026-06-30 21:45:00 |
|  4 | Дмитрий Козлов              | 2026-07-01 00:00:00 |
+----+-----------------------------+---------------------+
```

Три строки вместо двух: верхняя граница `'2026-07-01'` — это полночь
**начала** первого июля, и она включена — границы ведь нестрогие. Заказ
Дмитрия, созданный ровно в полночь, протёк в «июнь». Профессиональный
стандарт против этой протечки — полузакрытый интервал: нижняя граница
включена, верхняя — нет:

```sql
SELECT id, customer, created_at
FROM orders
WHERE created_at >= '2026-06-30' AND created_at < '2026-07-01'
ORDER BY id;
```

```text
+----+-----------------------------+---------------------+
| id | customer                    | created_at          |
+----+-----------------------------+---------------------+
|  2 | Иван Сидоров                | 2026-06-30 10:00:00 |
|  3 | Мария Волкова               | 2026-06-30 21:45:00 |
+----+-----------------------------+---------------------+
```

`>=` дня начала, `<` следующего дня — ни одна полночь не протечёт, и не
нужно помнить, сколько дней в июне. Для столбца типа `DATE` (без времени)
ловушки полуночи нет: день — это всё значение, и `BETWEEN '2026-06-01' AND
'2026-06-30'` честно берёт весь июнь; следите только, чтобы верхней
границей был последний нужный день, а не «следующий».

### LIKE: поиск по шаблону

«Название содержит HDMI» — сравнения бессильны: `=` требует полного
совпадения. `LIKE` сравнивает строку не со значением, а с **шаблоном**, в
котором живут два метасимвола:

| Метасимвол | Что означает                                |
| ---------- | ------------------------------------------- |
| `%`        | ноль или больше любых символов              |
| `_`        | ровно один любой символ                     |

По возрастанию точности:

```sql
SELECT name FROM products WHERE name LIKE 'Мыш%';
SELECT name FROM products WHERE name LIKE '%HDMI%';
SELECT name FROM products WHERE name LIKE '_о%';
```

```text
+---------------------------+     +--------------------+     +---------------------------+
| name                      |     | name               |     | name                      |
+---------------------------+     +--------------------+     +---------------------------+
| Мышь беспроводная         |     | Кабель HDMI 2 м    |     | Коврик для мыши           |
+---------------------------+     +--------------------+     | Монитор 27"               |
                                                             +---------------------------+
```

`'Мыш%'` — начинается с «Мыш» (хвост любой длины, хоть пустой).
`'%HDMI%'` — содержит HDMI в любом месте: ведущий % разрешает символы
до, хвостовой — после; строка ровно из «HDMI» тоже подошла бы — %
матчит и пустоту. `'_о%'` — второй символ «о»: коврик и монитор
(«К**о**врик», «М**о**нитор»), а мышь и клавиатура — нет.

Метасимволы могут стоять и в середине шаблона. `'Кабель%м'` —
начинается на «Кабель» и заканчивается на «м»:

```sql
SELECT name FROM products WHERE name LIKE 'Кабель%м';
```

```text
+------------------------+
| name                   |
+------------------------+
| Кабель HDMI 2 м        |
+------------------------+
```

Фиксированный старт, любой пробег посередине, фиксированный финиш —
шаблон для случая «начало и конец известны, середина неважна».

Ровно один символ — ровно одна позиция, и это делают масками
фиксированной длины:

```sql
SELECT title, code FROM promotions WHERE code LIKE 'REG_';
SELECT title, code FROM promotions WHERE code LIKE 'REG__';
```

```text
+-----------------+------+     +-----------------+-------+
| title           | code |     | title           | code  |
+-----------------+------+     +-----------------+-------+
| Скидка 5%       | REG5 |     | Скидка 50%      | REG50 |
+-----------------+------+     +-----------------+-------+
```

`'REG_'` — ровно четыре символа: REG5 да, REG50 нет; `'REG__'` — ровно
пять. Так же маскируют телефоны: `phone LIKE '912-___-__-__'` — «код
912, дальше три-два-две цифры» — вернёт Ивана.

Детали поведения. Регистр: `name LIKE 'мыш%'` найдёт ту же «Мышь
беспроводная» — LIKE подчиняется той же настройке сравнения строк, что и
`=` (урок 8 «Основ»): в стандартной конфигурации регистр не различается. Шаблон
без метасимволов — точное совпадение: `name LIKE 'Мышь'` — то же, что
`name = 'Мышь'`. `NOT LIKE` — отрицание шаблона: «все, кроме подходящих под шаблон»:

```sql
SELECT name FROM products WHERE name NOT LIKE '%беспроводная' ORDER BY id;
```

```text
+---------------------------+
| name                      |
+---------------------------+
| Коврик для мыши           |
| Клавиатура механическая   |
| Монитор 27"               |
| Кабель HDMI 2 м           |
| Веб-камера                |
+---------------------------+
```

Пять строк — мышь, единственная «беспроводная», выпала. И последние
детали. NULL — как всегда:
`phone LIKE '9%'` вернёт только Ивана, NULL-строки ответят «неизвестно»
и выпадут (урок 11 «Основ»). Числовой столбец в LIKE MySQL приведёт к строке —
законно, но так не пишут: шаблоны — инструмент текстовых столбцов. И
напоследок границы: шаблон с **ведущим** `%` (`'%HDMI%'`) заставляет
сервер проверить каждую строку таблицы — индекс ему помочь не может;
подробно это разберём в продвинутом уровне (индексы), пока просто
знайте.

### ESCAPE: буквальные % и _

В промо-кодах подчёркивания и проценты — часть **данных**, и рано или
поздно их придётся искать. «Найти коды с подчёркиванием»:

```sql
SELECT title, code FROM promotions WHERE code LIKE '%_%' ORDER BY id;
```

```text
+--------------------+---------------+
| title              | code          |
+--------------------+---------------+
| Летняя базовая     | SUMMER_10     |
| Летняя VIP         | SUMMER_20     |
| Летняя старая      | SUMMER99      |
| Чёрная пятница     | BLACK_FRIDAY  |
| Скидка 5%          | REG5          |
| Скидка 50%         | REG50         |
+--------------------+---------------+
```

Все шесть — включая SUMMER99 без единого подчёркивания. Мы спросили не
то: `_` в шаблоне — метасимвол «ровно один символ», поэтому `'%_%'`
читается «что угодно + один любой символ + что угодно» — подходит любая
непустая строка. Чтобы метасимвол стал обычным символом, его
экранируют — ставят перед ним `\`:

```sql
SELECT title, code FROM promotions WHERE code LIKE '%\_%' ORDER BY id;
```

```text
+--------------------+---------------+
| title              | code          |
+--------------------+---------------+
| Летняя базовая     | SUMMER_10     |
| Летняя VIP         | SUMMER_20     |
| Чёрная пятница     | BLACK_FRIDAY  |
+--------------------+---------------+
```

Ровно три кода с подчёркиванием. Тот же калибр ловушки с процентом —
«акция ровно "Скидка 5%"»:

```sql
SELECT title FROM promotions WHERE title LIKE 'Скидка 5%';
SELECT title FROM promotions WHERE title LIKE 'Скидка 5\%';
```

```text
+------------+     +------------+
| title      |     | title      |
+------------+     +------------+
| Скидка 5%  |     | Скидка 5%  |
| Скидка 50% |     +------------+
+------------+
```

Без экранирования хвостовой `%` сожрал «0%» из «Скидка 50%» — лишняя
строка. С экранированием — ровно то, что спрашивали.

Экранирующий символ можно сменить параметром `ESCAPE`:

```sql
SELECT title FROM promotions WHERE title LIKE 'Скидка 5!%' ESCAPE '!';
```

Здесь `!%` — буквальный процент. Зачем менять: когда в данных много
бэкслешей — пути Windows (`C:\dir`), `домен\пользователь` — экранировать
бэкслеш бэкслешем становится пыткой: в строковом литерале он сам
экранирует, поэтому шаблон удваивает его (значение `C:\dir` записывается
в литерале как `'C:\\dir'`, а шаблон для его поиска — как `'C:\\\\dir'`:
половину съедает парсер, половину — движок LIKE). Практический совет
проще: смените ESCAPE-символ. Единственное ограничение: строка в ESCAPE
— ровно один символ; `ESCAPE '&&'` — ошибка 1210 «Incorrect arguments
to ESCAPE».

Правило раздела: буквальные `%` и `_` ищутся только экранированием;
каким символом — вопрос удобства, `\` по умолчанию или явный `ESCAPE`.

### Вместе с прошлым уроком

`IN`, `BETWEEN`, `LIKE` — такие же «кирпичики условий», как сравнения:
каждый — единое условие с приоритетом выше `AND`/`OR`, и каждый
комбинируется с чем угодно из урока 1. Скобки между `OR` и `AND` никто
не отменял:

```sql
SELECT name, price
FROM products
WHERE (name LIKE '%HDMI%' OR category_id IN (1, 3)) AND price BETWEEN 450 AND 2450
ORDER BY id;
```

```text
+---------------------------+---------+
| name                      | price   |
+---------------------------+---------+
| Коврик для мыши           |  690.00 |
| Кабель HDMI 2 м           |  450.00 |
+---------------------------+---------+
```

Читается: «содержит HDMI **или** из категорий 1 и 3» — и при этом «цена
от 450 до 2450 включительно». Монитор из категории 3 отпал по цене,
веб-камера — по условию в скобках.

### Чего в этом уроке нет

Честные границы на сегодня:

- `IN` с подзапросом — список, собранный из другой таблицы: средний
  уровень;
- индексы и скорость `LIKE` — почему ведущий `%` — анти-паттерн:
  продвинутый уровень;
- полноценный поиск по словам и релевантности (`FULLTEXT`) —
  продвинутый уровень.

### Резюме

- `IN (список)` — «один из»: эквивалент OR-цепочки равенств; единое
  условие — скобки при смешении с AND не нужны; NULL в список не
  кладите: `NOT IN` с NULL всегда пуст.
- `BETWEEN a AND b` — это `>= a AND <= b`: обе границы включены;
  `NOT BETWEEN` выкидывает границы; перепутанные границы — пустой
  результат.
- `DATETIME` и даты: литерал-дата на верхней границе — полночь начала
  дня, и она включена; надёжный диапазон дней — полузакрытый интервал
  `>= день AND < следующий день`.
- `LIKE`: `%` — ноль и больше любых символов, `_` — ровно один; регистр
  по умолчанию не различается (collation); NULL отвечает «неизвестно»;
  ведущий `%` лишает индекса — продвинутый уровень.
- `ESCAPE`: `\%` и `\_` — буквальные символы; `ESCAPE '!'` — сменить
  экранирующий (строка из ровно одного символа); бэкслеш в данных —
  повод сменить ESCAPE, а не удваивать его четыре раза.
- Всё это — кирпичики условий наряду со сравнениями: комбинируются с
  `AND`/`OR`/`NOT` урока 1, скобки между OR и AND — по-прежнему
  обязательны.

## Теоретические задания

### Вопрос 1: `SELECT name FROM products WHERE category_id IN (1, 3);` — какие строки вернёт запрос?

- ✅ товары категорий 1 и 3
<!-- три строки: категория 1 — коврик и кабель, категория 3 — монитор; периферия (2) в список не входит -->
- ❌ строки с id 1 и id 3 — error_text: IN перечисляет допустимые значения столбца слева — здесь category_id; id строк ни при чём: строки с id 1 и 3 — коврик и клавиатура, из разных категорий.
- ❌ товары категорий 1, 2 и 3 — error_text: так прочитался бы диапазон; IN берёт только перечисленные значения — периферия (2) в список не входит.
- ❌ ошибку: в списке IN должно быть ровно два значения — error_text: длина списка любая — от одного значения до любого нужного; ошибки нет, запрос вернёт три строки.

### Вопрос 2: `SELECT name FROM customers WHERE phone NOT IN ('912-345-67-89', NULL);` — что вернёт запрос?

- ✅ ни одной строки
<!-- у каждого значения, кроме ивановского номера, проверка на равенство NULL даёт «неизвестно», а NOT «неизвестно» — «неизвестно»; у Ивана «да» OR «неизвестно» = «да», после NOT — «нет» -->
- ❌ всех покупателей, кроме Ивана — error_text: так работал бы NOT IN без NULL в списке; NULL превращает каждую проверку в «неизвестно», а WHERE пропускает только «да» — результат пуст.
- ❌ только покупателей с phone IS NULL — error_text: NULL-строки выпадают вместе со всеми: их сравнение с элементами списка — «неизвестно», а NOT «неизвестно» — по-прежнему «неизвестно».
- ❌ ошибку: NULL в списке IN запрещён — error_text: синтаксически законно и выполняется без ошибок — молча и с пустым результатом; в этом и коварство.

### Вопрос 3: Товар стоит ровно 2000. Вернёт ли его запрос `WHERE price BETWEEN 1000 AND 2000`?

- ✅ да
<!-- обе границы входят: BETWEEN — это price >= 1000 AND price <= 2000, обе проверки нестрогие -->
- ❌ нет: верхняя граница не входит — error_text: границы BETWEEN нестрогие с обеих сторон; исключить верхнюю границу пришлось бы явным price < 2000.
- ❌ нет: между границами входят только значения строго внутри — error_text: «строго между» — это > и <; BETWEEN включает оба края — потому он и переводится как «между, включительно».
- ❌ это зависит от типа столбца — error_text: правило одинаково для чисел, строк и дат: обе границы включены; тип на границы не влияет.

### Вопрос 4: `SELECT name FROM products WHERE name LIKE '%HDMI%';` — какие названия найдёт запрос?

- ✅ содержащие HDMI в любом месте
<!-- например «Кабель HDMI 2 м»: % с обеих сторон разрешает любые символы до и после -->
- ❌ начинающиеся с HDMI — error_text: за это отвечает шаблон 'HDMI%' без ведущего %; ведущий % разрешает символы и до HDMI.
- ❌ только равные строке «HDMI» — error_text: точное совпадение — это шаблон без метасимволов; здесь % с обеих сторон разрешает любой контекст вокруг HDMI.
- ❌ никакие: % допустим только в конце шаблона — error_text: метасимволы могут стоять в любой позиции шаблона; '%HDMI%' — типовой поиск подстроки.

### Вопрос 5: В таблице есть коды SUMMER_10, SUMMER_20 и SUMMER99. Нужны коды, начинающиеся с «SUMMER_», где подчёркивание — часть данных. Какой шаблон правильный?

- ✅ `LIKE 'SUMMER\_%'`
<!-- \_ — буквальное подчёркивание, хвостовой % — любой конец: SUMMER_10 и SUMMER_20 найдутся, SUMMER99 — нет -->
- ❌ `LIKE 'SUMMER_%'` — error_text: без экранирования _ — метасимвол «ровно один любой символ»: шаблон поймает и SUMMER99 — девятка сойдёт за подчёркивание.
- ❌ `LIKE 'SUMMER\_%' ESCAPE '#'` — error_text: ESCAPE '#' назначает экранирующим символом # — и \ перестаёт экранировать, превращаясь в обычный символ данных: шаблон ищет строку с бэкслешем после SUMMER.
- ❌ `LIKE 'SUMMER&&_%' ESCAPE '&&'` — error_text: строка в ESCAPE должна содержать ровно один символ: '&&' даст ошибку 1210 «Incorrect arguments to ESCAPE».
