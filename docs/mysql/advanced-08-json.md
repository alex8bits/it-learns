Причина в том, что JSON — не реляционные данные в строгом смысле: это способ хранить внутри одной ячейки структуру произвольной формы (вложенные объекты, массивы), не подчиняющуюся жёсткой, одинаковой для всех строк схеме столбцов, о которой шла речь в самом первом уроке курса. ### JSON как тип столбца

MySQL, начиная с версии 5.7, поддерживает нативный тип столбца `JSON` — в отличие от простого хранения JSON-текста в `TEXT`/`VARCHAR` (что тоже возможно синтаксически, но не даёт возможностей ниже), тип `JSON`:

- **проверяет валидность** структуры при каждой записи — попытка вставить синтаксически некорректный JSON завершится ошибкой, а не будет молча сохранена как обычная строка;
- хранится во **внутреннем бинарном формате**, оптимизированном для быстрого доступа к отдельным полям без необходимости разбирать (парсить) весь текст документа заново при каждом обращении;
- поддерживается специализированными функциями (ниже) для навигации и изменения содержимого без извлечения всего документа целиком на сторону приложения.

```sql
CREATE TABLE products (
    id INT AUTO_INCREMENT PRIMARY KEY,
    category_id INT NOT NULL,
    name VARCHAR(255) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL,
    attributes JSON
);

INSERT INTO products (category_id, name, price, stock, created_at, attributes)
VALUES (3, 'Клавиатура механическая', 4500.00, 12, NOW(),
        '{"switch_type": "mechanical", "layout": "ru", "backlight": true}');
```

### Операторы -> и ->>: чтение значения по пути

Для доступа к конкретному полю внутри JSON-документа используется оператор `->`, принимающий **JSON-путь** — строку вида `$.имя_поля`, где `$` обозначает корень документа:

```sql
SELECT
    name,
    attributes->'$.switch_type' AS switch_type
FROM products
WHERE category_id = 3;
```

Результат `->` — значение типа `JSON` (даже если по смыслу это простая строка, она возвращается «в кавычках», как JSON-представление строки, например `"mechanical"`, а не `mechanical`). Для получения «развёрнутого» скалярного значения, без обёртки JSON-кавычек, используется оператор `->>` — сокращение для `->` в сочетании с функцией `JSON_UNQUOTE`:

```sql
SELECT
    name,
    attributes->>'$.switch_type' AS switch_type
FROM products
WHERE category_id = 3;
```

Разница практически значима: `attributes->'$.switch_type' = 'mechanical'` в MySQL сравнивает JSON-значение (в кавычках) со строкой и может привести к неожиданным результатам сравнения; `attributes->>'$.switch_type' = 'mechanical'` сравнивает уже развёрнутую строку со строкой — предпочтительный вариант почти во всех практических случаях фильтрации по значению.

### JSON_EXTRACT: явный аналог оператора ->

`->` — синтаксический сахар для функции `JSON_EXTRACT`, которая делает то же самое явным вызовом:

```sql
SELECT JSON_EXTRACT(attributes, '$.switch_type') FROM products;
-- эквивалентно
SELECT attributes->'$.switch_type' FROM products;
```

JSON-путь может обращаться не только к простому полю объекта, но и к элементу массива по индексу (нумерация с нуля) и к вложенным структурам произвольной глубины:

```sql
-- attributes = '{"tags": ["беспроводная", "бесшумная"], "dimensions": {"width_mm": 120}}'
SELECT
    attributes->>'$.tags[0]' AS first_tag,
    attributes->>'$.dimensions.width_mm' AS width
FROM products;
```

### Фильтрация по JSON-полю в WHERE

Ровно тот же оператор `->>`, что используется в `SELECT`, работает и в `WHERE` — JSON-поле можно использовать как условие фильтрации наравне с обычным столбцом:

```sql
SELECT name, price
FROM products
WHERE category_id = 3
  AND attributes->>'$.switch_type' = 'mechanical'
  AND attributes->>'$.backlight' = 'true';
```

Важная деталь: булево значение JSON (`true`/`false`) при развёртывании через `->>` становится строкой `'true'`/`'false'`, а не значением типа `BOOLEAN`/`TINYINT`, к которому привык шестой урок уровня «Основы» (в MySQL `BOOL` — синоним `TINYINT(1)`) — сравнение нужно вести именно со строкой, а не с числом `1`/`0`, как это было бы для обычного столбца.

Здесь стоит явно вернуться к анти-паттерну из четвёртого урока этого уровня: условие `attributes->>'$.switch_type' = 'mechanical'` — это, по сути, применение функции (`JSON_EXTRACT`/`JSON_UNQUOTE`) к каждой строке для последующего сравнения, и обычный индекс по столбцу `attributes` целиком тут не поможет ровно по той же причине, по которой не помогает индекс при вычислении `YEAR(created_at)` — сервер не может использовать отсортированный порядок значений всего JSON-документа для поиска по одному конкретному вложенному полю. Для регулярной, частой фильтрации по конкретному JSON-полю в производственной системе применяют **генерируемые столбцы** (`GENERATED ALWAYS AS ... VIRTUAL`/`STORED`), которые «вытаскивают» нужное поле в обычный, индексируемый столбец, автоматически синхронизируемый с содержимым JSON — но это отдельная, более продвинутая техника, выходящая за рамки материала этого вводного JSON-урока; на уровне этого курса достаточно понимать сам факт ограничения и знать, в какую сторону искать решение при реальной необходимости.

### JSON_SET, JSON_REMOVE: изменение документа без перезаписи целиком

Изменить одно поле JSON-документа, не переписывая всю структуру целиком на стороне приложения, позволяет `JSON_SET`:

```sql
UPDATE products
SET attributes = JSON_SET(attributes, '$.backlight', false)
WHERE id = 1;
```

Удаление поля — `JSON_REMOVE`:

```sql
UPDATE products
SET attributes = JSON_REMOVE(attributes, '$.layout')
WHERE id = 1;
```

Обе функции возвращают **новое значение** JSON (они не изменяют документ «на месте» сами по себе — как и любая функция в SQL) — поэтому их вызов оборачивается в `UPDATE ... SET столбец = функция(столбец, ...)`, ровно по той же логике, что уже применялась к обычным столбцам в десятом уроке уровня «Основы».

### JSON_ARRAY и JSON_OBJECT: собрать JSON из результата запроса

Обратная задача — не разобрать существующий JSON, а **собрать** его из реляционных данных — тоже востребована, например, при подготовке ответа API прямо на уровне SQL. `JSON_OBJECT` строит объект из пар «ключ-значение», `JSON_ARRAY` — массив из списка значений:

```sql
SELECT JSON_OBJECT(
    'id', id,
    'name', name,
    'price', price
) AS product_json
FROM products
WHERE id = 1;
```

Результат — валидный JSON-документ `{"id": 1, "name": "Клавиатура механическая", "price": 4500.00}`, который может быть напрямую отдан как ответ API-эндпоинта без дополнительной сборки в коде приложения.

### JSON_TABLE: превратить JSON-массив в обычные строки (обзорно)

Последняя, наиболее сложная функция этого урока — `JSON_TABLE` (доступна начиная с MySQL 8.0.14) — решает задачу, обратную построению JSON: **разворачивает** JSON-массив внутри документа в обычный, реляционный набор строк, к которому применимы `JOIN`, `GROUP BY` и всё остальное:

```sql
-- attributes = '{"tags": ["беспроводная", "бесшумная", "RGB"]}'
SELECT p.id, p.name, t.tag
FROM products p,
JSON_TABLE(
    p.attributes,
    '$.tags[*]' COLUMNS (tag VARCHAR(50) PATH '$')
) AS t
WHERE p.id = 1;
```

Здесь каждый элемент массива `tags` становится отдельной строкой результата — три тега превращаются в три строки с одинаковым `p.id`/`p.name`, но разным `t.tag`; по сути, `JSON_TABLE` выполняет для массива внутри JSON ту же функцию, что `order_items` выполняет для товаров одного заказа в основной схеме курса — превращает «список внутри одной ячейки» в набор нормальных строк отдельной виртуальной таблицы, к которой применимы обычные реляционные операции. Это самая сложная конструкция урока, поэтому здесь она разбирается только обзорно, как факт существования инструмента для конкретной задачи, — детальная проработка синтаксиса `COLUMNS` (в том числе вложенных `NESTED PATH` для многоуровневых массивов) выходит за рамки вводного знакомства.

### Когда действительно нужен JSON, а когда — обычные столбцы или таблица

JSON — не универсальная замена нормализованной схеме (одиннадцатый урок уровня «Средний»): решение хранить характеристику в JSON, а не в отдельном столбце или отдельной связанной таблице, стоит принимать по конкретному критерию. Если характеристика есть у **всех или почти всех** строк таблицы и по ней регулярно фильтруют/сортируют/агрегируют — это кандидат на обычный, типизированный, индексируемый столбец (снова та же логика, что рассматривалась при разговоре о плюсах и минусах денормализации). Если набор характеристик у разных строк сильно отличается по составу (одни свойства есть только у категории «электроника», другие — только у «одежды») и запросы к ним нужны редко и точечно, а не как основа для массовых аналитических отчётов, JSON-столбец — уместное и удобное решение, избегающее необходимости заранее продумывать десятки специфичных для каждой категории столбцов, большинство которых будет `NULL` для любого конкретного товара.

### Резюме

- Тип столбца **`JSON`** хранит документ произвольной вложенной структуры в проверенном на валидность бинарном формате, в отличие от обычного `TEXT`/`VARCHAR` с текстом JSON внутри.
- **`->`** возвращает значение по JSON-пути как JSON (в кавычках для строк); **`->>`** (= `JSON_UNQUOTE(->)`) возвращает развёрнутое скалярное значение — предпочтительно для сравнения в `WHERE`.
- **`JSON_EXTRACT`** — явный аналог `->`; JSON-путь может обращаться к элементам массива по индексу (`$.tags[0]`) и к вложенным объектам (`$.dimensions.width_mm`).
- Фильтрация по JSON-полю в `WHERE` — это, по сути, применение функции к каждой строке (тот же класс, что и `YEAR(created_at)` из четвёртого урока этого уровня) — обычный индекс по всему столбцу `attributes` не помогает такому условию напрямую.
- **`JSON_SET`**/**`JSON_REMOVE`** изменяют/удаляют поле документа, возвращая новое значение JSON для `UPDATE`; **`JSON_OBJECT`**/**`JSON_ARRAY`** собирают JSON из реляционных данных.
- **`JSON_TABLE`** (MySQL 8.0.14+) разворачивает JSON-массив в обычные строки, к которым применимы стандартные реляционные операции — обзорная, но не углублённая тема этого урока.
- JSON уместен для характеристик, различающихся по составу между строками и не требующих массовых аналитических запросов; регулярно фильтруемые/агрегируемые характеристики, общие для всех строк, лучше хранить как обычные типизированные столбцы.

## Теоретические задания

### Вопрос 1: В чём разница между `attributes->'$.color'` и `attributes->>'$.color'` для строкового значения поля?

- ✅ `->` возвращает значение как JSON — строка будет в кавычках (`"чёрный"`); `->>` возвращает развёрнутое значение без кавычек (`чёрный`)
<!-- ->> — сокращение для -> в сочетании с JSON_UNQUOTE; для сравнения в WHERE предпочтителен ->> -->
- ❌ Разницы нет: оба возвращают одно и то же строковое значение — error_text: Разница видна прямо в результате: `->` даёт JSON-представление строки — в кавычках, `->>` — чистый текст без них. Она практически значима: `attributes->'$.color' = 'чёрный'` сравнивает JSON-значение со строкой и может дать неожиданный результат сравнения.
- ❌ `->>` возвращает JSON с кавычками, а `->` — значение без кавычек — error_text: Истина перевёрнута: JSON-обёртку с кавычками возвращает именно одиночная стрелка `->`, а двойная `->>` (она же `->` плюс `JSON_UNQUOTE`) эту обёртку снимает.
- ❌ `->` работает только с массивами, `->>` — только с полями объектов — error_text: Оба оператора принимают один и тот же JSON-путь и читают любые структуры: поля объектов, элементы массивов по индексу, вложенные документы любой глубины. Различие между ними — только в формате возвращаемого значения.

### Вопрос 2: Что означает путь `'$.specs.weight_g'` в `JSON_EXTRACT(attributes, '$.specs.weight_g')`?

- ✅ Корень документа `$`, внутри него поле `specs`, а внутри него — поле `weight_g` вложенного объекта
<!-- путь читается по уровням вложенности слева направо -->
- ❌ Элемент массива `specs`, у которого берётся поле `weight_g` — error_text: К элементам массива обращаются по индексу в квадратных скобках, как `$.tags[0]`. Запись через точку — всегда вложенные поля объектов: `specs` здесь объект, а не массив.
- ❌ Таблица `specs`, из которой выбирается столбец `weight_g` — error_text: JSON-путь навигирует внутри одного JSON-документа, хранящегося в ячейке текущей строки, а не между таблицами базы. `$` — корень этого документа; таблицы и столбцы базы тут ни при чём.
- ❌ Шаблон регулярного выражения, где `.` означает любой символ — error_text: Точка в JSON-пути — разделитель уровней вложенности объекта, а не квантификатор из мира регулярных выражений. Путь читается буквально: корень → поле `specs` → его поле `weight_g`.

### Вопрос 3: В документе есть `"backlight": true`. Как сравнить развёрнутое через `->>` значение в `WHERE`, чтобы найти товары с подсветкой?

- ✅ Сравнить со строкой `'true'`: булево значение JSON после `->>` становится строкой, а не числом
<!-- JSON true/false разворачиваются в строки 'true'/'false', а не в 1/0 как у обычного BOOL-столбца -->
- ❌ С числом `1`, как для обычного столбца `BOOL` — error_text: Обычный `BOOL` в MySQL — синоним `TINYINT(1)`, где истина хранится как `1`. Но JSON-булево значение после `->>` разворачивается в строку `'true'`, и сравнение с числом `1` нужные строки не найдёт.
- ❌ Со значением `TRUE` без кавычек — error_text: `TRUE` без кавычек — это снова имя числа `1`, и сравнение строки `'true'` с единицей превратится в игру правил приведения типов. Нужна именно строка `'true'` в кавычках.
- ❌ Ни с чем: булевы значения JSON нельзя использовать в условиях — error_text: Можно — с учётом формата: условие `attributes->>'$.backlight' = 'true'` из материала отлично работает. Ограничения нет, есть нюанс превращения булева JSON в строку при развёртывании.

### Вопрос 4: Почему обычный индекс по столбцу `attributes` не помогает условию `attributes->>'$.switch_type' = 'mechanical'`?

- ✅ Условие — вычисление функции над столбцом для каждой строки; порядок отсортированных целых JSON-документов бесполезен для поиска по одному вложенному полю
<!-- тот же класс анти-паттернов, что YEAR(created_at) из урока 4; решение для продакшена — генерируемые столбцы -->
- ❌ Индекс не работает из-за размера: JSON-документы обычно длинные — error_text: Дело не в длине значений, а в природе условия: извлечение вложенного поля — функция над столбцом, а функции над индексированным столбцом ломают использование индекса. Это тот же анти-паттерн, что `YEAR(created_at)` из четвёртого урока этого уровня.
- ❌ JSON-столбцы в MySQL вообще нельзя индексировать — error_text: Индекс по JSON-столбцу создать можно — он просто бесполезен для поиска по конкретному вложенному полю. Для регулярной фильтрации по JSON-полю применяют генерируемые столбцы, «вытаскивающие» поле в обычный индексируемый столбец.
- ❌ Потому что `->>` всегда возвращает строку, а строки не индексируются — error_text: Строковые столбцы прекрасно индексируются — B-tree работает и для `VARCHAR`. Проблема не в строковости результата, а в том, что значение вычисляется функцией из всего документа при проверке каждой строки.

### Вопрос 5: Когда JSON-столбец — уместный выбор вместо обычных столбцов?

- ✅ Когда набор характеристик сильно различается по составу между строками, а запросы к ним нужны редко и точечно
<!-- критерий из материала: неоднородный состав характеристик + редкие точечные запросы -->
- ❌ Когда характеристика есть у всех строк и по ней постоянно фильтруют и сортируют — error_text: Это противоположный случай: массовая фильтрация и сортировка — аргумент за обычный типизированный индексируемый столбец. JSON здесь лишит запросы индексов и типизации, не дав ничего взамен.
- ❌ Когда нужно ускорить запросы по сравнению с обычными столбцами — error_text: JSON — не про скорость: доступ к вложенному полю — функция над документом, и обычный индекс на нём не работает. Выгода JSON — в гибкости схемы для неоднородных данных, а не в производительности запросов.
- ❌ Всегда: JSON универсален и заменяет нормализованную схему — error_text: JSON — не замена нормализованной схеме: реляционные связи, типизация, индексируемость и целостность остаются нужны. Это осознанный компромисс для неоднородных и редко запрашиваемых характеристик, а не универсальное решение.

### Задание 1: `->` против `->>`: кавычки JSON-представления

Чтение одного и того же строкового поля двумя операторами: с JSON-кавычками и без них.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT name, attributes->'$.color' AS color_json, attributes->>'$.color' AS color_text FROM products ORDER BY id; -->
