# Commands Playbook (it-learns)

> Справочник для агента. Фиксирует триггер-фразы, порядок и зависимости
> между `.mavis/commands/*.md`. Не дублирует содержимое команд —
> здесь только **как и когда** их запускать.
>
> Согласован с `AGENTS.md` (правила проекта), `docs/concept.md` (домен),
> `docs/platform-plan.md` (этапы). При расхождении — правила в `AGENTS.md`
> главнее, этот playbook — операционный.

## Что это вообще

`.mavis/commands/*.md` — это **playbook-файлы**. Это не зашитые в Mavis slash-команды
(автодополнение в чате их не подхватывает автоматически). Это **инструкции**,
которые агент (Mavis) читает, когда пользователь упоминает команду по имени
или триггер-фразе. Каждый файл — это протокол работы: что сказать пользователю,
как собрать контекст, какие шаги выполнить, какой результат выдать.

## Как запускается

Пользователь пишет в чате **обычной прозой**, например:

- `research-codebase auth` или `пройдись по research-codebase по аутентификации`
- `design-feature премиум-подписка` или `оформи дизайн для премиум-подписки`
- `сделай план реализации для премиум`
- `реализуй премиум-подписку` или `запусти implement-feature для премиум`
- `синхронизируй документацию маршрутов`

Ключевое слово — `research-codebase` / `design-feature` / `create-implementation-plan` /
`implement-feature` / `write-documentation` (или русский эквивалент с тем же смыслом).
Агент открывает `.mavis/commands/<имя>.md`, читает как протокол, идёт по шагам.

**Префикс `/` необязателен.** Если продукт поддерживает триггер-фразы для
пользовательских команд (Mavis-настройка профиля агента) — префикс может
работать, но это не наша ответственность, см. `AGENTS.md §5` и обсуждение
в `user.md`.

## Команды и их роль

| Команда | Файл | Что делает | Артефакт на выходе |
|---|---|---|---|
| `research-codebase` | `.mavis/commands/research-codebase.md` | Только факты: что есть в коде сейчас, с `file:line` ссылками, без предложений/критики. Параллельно 2–4 исследователя. | `.mavis/research/YYYY-MM-DD-<topic>.md` |
| `design-feature` | `.mavis/commands/design-feature.md` | Принимает решение о подходе, фиксирует границы, компоненты, data flow, риски, handoff к плану. Не пишет прод-код и не создаёт таски. | `.mavis/design/YYYY-MM-DD-<topic>.md` |
| `create-implementation-plan` | `.mavis/commands/create-implementation-plan.md` | Раскладывает фичу на 3–7 упорядоченных тасков. Не пишет прод-код. | `.mavis/tasks/YYYY-MM-DD-<topic>/<NN>-<slug>.md` |
| `implement-feature` | `.mavis/commands/implement-feature.md` | Оркестрация: парсит таски, строит волны, запускает `worker` + `code-reviewer` в нужном порядке. | прод-код + зелёные тесты |
| `write-documentation` | `.mavis/commands/write-documentation.md` | Сверяет реальные маршруты с документацией (если есть), добавляет недостающие. Не пишет API «с нуля». | дополненные файлы документации |

## Подробные триггер-фразы

Чтобы агенту было легче распознать намерение, придерживаемся канонических
фраз. Любая из них — сигнал «запусти X».

### `research-codebase`

- `research-codebase <тема или область>`
- `пройдись research-codebase по <теме>`
- `исследуй <тема>` (когда явно просишь разобрать код)
- `что у нас сейчас с <X>?` (только если явно просишь **исследование кода**, а не просто объяснение)
- **Не триггер:** общий вопрос «как у нас устроена аутентификация?» — лучше я отвечу по памяти, чем сразу запускать research-task.

Когда использовать: перед `design-feature`, если нет существующего research-документа
по теме. Если уже есть `.mavis/research/<date>-<topic>.md` по нужной области —
использовать его, а research-task не запускать.

### `design-feature`

- `design-feature <тема>`
- `оформи дизайн для <X>`
- `сделай design для <Y>`

Когда использовать: после `research-codebase` (или используя существующий research).
Перед `create-implementation-plan`. Если design-документ по теме уже есть —
переиспользовать, не плодить дубликаты.

### `create-implementation-plan`

- `create-implementation-plan <тема>` или `сделай план для <X>`
- `разбей <Y> на таски`
- `подготовь план реализации <Z>`

Когда использовать: после `design-feature`. План без дизайна — слепой; дизайн
без плана — наполовину полезен.

### `implement-feature`

- `implement-feature <тема>` или `реализуй <X>`
- `запусти реализацию <Y>`
- `выполни таски <topic>`

Когда использовать: после `create-implementation-plan`. Это entry point для
оркестрации. Без готовых тасков команда попросит research/design/plan.

### `write-documentation`

- `write-documentation` или `синхронизируй документацию маршрутов`
- `обнови API-документацию`
- `проверь, что в docs/ всё про маршруты`

Когда использовать: **отдельно** от feature-flow. Не часть обычного цикла
research → design → plan → implement. Запускается вручную, когда:
- появились/изменились маршруты;
- нужно подтянуть документацию под новые эндпоинты;
- готовим релиз.

## Зависимости между командами

```
research-codebase ──► design-feature ──► create-implementation-plan ──► implement-feature
                                                                  │
                                                                  └─► (опц.) write-documentation
```

- **research → design:** design опирается на факты. Без research получится
  дизайн «из головы», без `file:line`-цитат.
- **design → plan:** план ссылается на «Что НЕ нужно менять» и «Зависимости»
  из design-документа. Без design план не знает границ.
- **plan → implement:** implement собирает волны по плану. Без плана — нет
  явных тасков, нечего передавать `worker`.
- **implement → write-documentation (опц.):** после реализации можно прогнать
  `write-documentation`, чтобы документация маршрутов подтянулась под новые
  эндпоинты.

**Можно ли пропускать шаги?**

- `research-codebase` — иногда можно, если тебе хорошо знакома область и ты
  не хочешь тратить токены на формальный research-документ. **Не рекомендую**
  для нетривиальных фич: research ловит «а мы уже это делали в таком-то
  файле, не дублируй», что экономит больше, чем стоит.
- `design-feature` — пропускать **не рекомендую**. Без design-решения таски
  расползаются: разные `worker`'ы решают одну проблему по-разному.
- `create-implementation-plan` — пропускать **нельзя**. Без явных тасков
  `worker` не знает, где остановиться, и `code-reviewer` не знает, что
  проверять.
- `implement-feature` — это и есть реализация, не «необязательный шаг».
- `write-documentation` — действительно опционально, можно запускать
  отдельными заходами.

## Что в каждой команде фиксируется (для согласованности)

Чтобы агенты не расходились в стиле при работе с разными командами,
в каждом playbook-файле уже зафиксированы единые элементы:

- **Hard rules** — что нельзя делать (например, `research-codebase` не
  предлагает улучшения, `implement-feature` не пишет прод-код в обход
  `worker`).
- **Quality rules** — цитаты `file:line`, явные ссылки на `AGENTS.md`,
  формат вывода.
- **Frontmatter (для design и research):** `api_surface`, `api_version`,
  `affects_premium`, `affects_ai`, `affects_practice_env`.
- **Связь с `AGENTS.md`:** каждое правило качества ссылается на конкретные
  правила `AGENTS.md` (1–20), чтобы не было дрейфа.

Если нужно добавить **новую команду** (например, `prepare-release` или
`run-benchmarks`):

1. Создать `.mavis/commands/<name>.md` с тем же шаблоном: «Hard rules» /
   «Process» / «Output» / «Quality rules».
2. Добавить описание в этот playbook (таблица + триггер-фразы + место в
   feature-flow).
3. Если команда ломает какое-то правило `AGENTS.md` — сначала обновить
   `AGENTS.md`, потом команду. Никогда наоборот.

## Если триггер-фраза двусмысленная

Агент **не должен** угадывать, какую команду запускать. Если пользователь
сказал что-то вроде «разберись с авторизацией» — это может быть
`research-codebase` (если непонятно, как сейчас устроено), `design-feature`
(если нужно спроектировать), или вообще просто вопрос. В таком случае
агент уточняет одной фразой, какую команду запускать, прежде чем
открывать playbook-файл.

Исключения (когда агенту **можно** запустить самому):

- `implement-feature <тема>` — однозначно оркестрация, если уже есть
  `.mavis/tasks/.../`.
- `research-codebase <тема>` — почти однозначно, если пользователь явно
  просит «разобрать код» / «посмотреть, что у нас с X» / «пройдись по X».

В остальных случаях — короткое уточнение.

## Связь с AGENTS.md

`AGENTS.md §5` уже описывает **процесс** (фазы research → design → plan →
implement, wave-флоу, цикл на таск). Этот playbook дополняет §5
**операционной** частью: какие команды вызывать, какие у них триггер-фразы,
в каком порядке запускать. При конфликте правил — правила `AGENTS.md`
главнее, этот playbook — операционный.
