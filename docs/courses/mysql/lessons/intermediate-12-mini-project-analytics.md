## Материал

Уровень «Средний» дал курсу набор инструментов совершенно другого масштаба, чем «Начинающий»: если там мы научились сшивать таблицы по горизонтали (`JOIN`) и сворачивать строки в сводку (`GROUP BY`), то здесь появились инструменты **композиции** — подзапросы и CTE, позволяющие строить запрос как последовательность именованных, осмысленных шагов, и **оконные функции**, позволяющие получать сложную аналитику, не теряя ни одной исходной строки. Как и в двух предыдущих мини-проектах курса (двенадцатый урок уровня «Основы» и шестнадцатый урок уровня «Начинающий»), ценность этих инструментов раскрывается не по отдельности, а в сборке: реальная аналитическая задача бизнеса почти никогда укладывается в одну простую конструкцию — она требует последовательного применения нескольких приёмов сразу, оформленных так, чтобы результат можно было прочитать и объяснить.

### Постановка задачи

Руководство интернет-магазина просит подготовить дашборд с тремя связанными разделами: (1) помесячная динамика выручки с ростом к прошлому месяцу; (2) топ-3 самых продаваемых товара в каждой категории; (3) сегментация клиентов по их «расстоянию» от среднего чека магазина, оформленная как переиспользуемое представление для дальнейших отчётов. Разберём каждый раздел по шагам, показывая, как в него складываются темы всего уровня.

### Раздел 1. Динамика выручки по месяцам с ростом к прошлому месяцу

Первый шаг — собрать помесячную выручку через `GROUP BY` (уровень «Начинающий») и `DATE_FORMAT` (пятый урок уровня «Начинающий»), оформив это как CTE (четвёртый урок этого уровня), чтобы использовать результат далее без повторения агрегации:

```sql
WITH monthly_revenue AS (
    SELECT
        DATE_FORMAT(o.created_at, '%Y-%m') AS month,
        SUM(oi.quantity * oi.price) AS revenue
    FROM orders o
    INNER JOIN order_items oi ON oi.order_id = o.id
    WHERE o.status <> 'cancelled'
    GROUP BY DATE_FORMAT(o.created_at, '%Y-%m')
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
    ROUND(
        (revenue - LAG(revenue) OVER (ORDER BY month))
        / LAG(revenue) OVER (ORDER BY month) * 100,
        1
    ) AS growth_percent
FROM monthly_revenue
ORDER BY month;
```

Здесь `LAG` (шестой урок этого уровня) достаёт выручку предыдущего месяца рядом с текущей строкой без единого self-join, а вычисление процента роста использует уже знакомую из пятого урока уровня «Начинающий» функцию `ROUND`. Для самого первого месяца в наборе `LAG` вернёт `NULL` — это осмысленное поведение (нет предыдущего месяца для сравнения), а не ошибка, ровно как мы разбирали при первом знакомстве с `LAG`.

### Раздел 2. Топ-3 товара по продажам в каждой категории

Задача требует ранжирования **внутри группы** без потери отдельных строк товаров — классический случай оконной функции с `PARTITION BY` (пятый урок этого уровня). Сначала соберём количество проданных единиц каждого товара через CTE, затем пронумеруем внутри категории вторым CTE, и только затем отфильтруем:

```sql
WITH product_sales AS (
    SELECT
        p.id AS product_id,
        p.name AS product_name,
        p.category_id,
        SUM(oi.quantity) AS units_sold
    FROM products p
    INNER JOIN order_items oi ON oi.product_id = p.id
    INNER JOIN orders o ON o.id = oi.order_id
    WHERE o.status <> 'cancelled'
    GROUP BY p.id, p.name, p.category_id
),
ranked_sales AS (
    SELECT
        product_id,
        product_name,
        category_id,
        units_sold,
        ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY units_sold DESC) AS rank_in_category
    FROM product_sales
)
SELECT
    cat.name AS category_name,
    rs.product_name,
    rs.units_sold,
    rs.rank_in_category
FROM ranked_sales rs
INNER JOIN categories cat ON cat.id = rs.category_id
WHERE rs.rank_in_category <= 3
ORDER BY cat.name, rs.rank_in_category;
```

Цепочка из двух CTE здесь не случайна: `product_sales` решает одну понятную задачу («сколько продано каждого товара»), `ranked_sales` — следующую («какое место товар занимает внутри своей категории»), а финальный `SELECT` — третью («взять только топ-3 и присоединить читаемое имя категории»). Именно из-за такого разделения на шаги мы и не пытаемся отфильтровать по `rank_in_category` прямо в том же `SELECT`, где эта колонка вычисляется — как разобрано в пятом уроке, оконная функция недоступна в `WHERE` того же уровня запроса, поэтому фильтрация по её результату всегда требует отдельного, внешнего шага.

### Раздел 3. Сегментация клиентов относительно среднего чека — как VIEW

Третий раздел должен быть переиспользуемым — руководство хочет обращаться к сегментации клиентов и в других будущих отчётах, а не пересчитывать её каждый раз заново. Это прямое показание к `VIEW` (одиннадцатый урок этого уровня). Внутри самой view используем скалярный подзапрос (первый урок этого уровня) для сравнения с общим средним чеком магазина и `CASE` (уровень «Начинающий») для категоризации:

```sql
CREATE VIEW customer_spending_segments AS
WITH customer_totals AS (
    SELECT
        c.id AS customer_id,
        c.name AS customer_name,
        COUNT(DISTINCT o.id) AS orders_count,
        COALESCE(SUM(oi.quantity * oi.price), 0) AS total_spent
    FROM customers c
    LEFT JOIN orders o ON o.customer_id = c.id AND o.status <> 'cancelled'
    LEFT JOIN order_items oi ON oi.order_id = o.id
    GROUP BY c.id, c.name
)
SELECT
    customer_id,
    customer_name,
    orders_count,
    total_spent,
    (SELECT AVG(total_spent) FROM customer_totals) AS avg_spent_overall,
    CASE
        WHEN total_spent > (SELECT AVG(total_spent) FROM customer_totals) * 1.5 THEN 'выше среднего'
        WHEN total_spent < (SELECT AVG(total_spent) FROM customer_totals) * 0.5 THEN 'ниже среднего'
        ELSE 'типичный'
    END AS spending_segment
FROM customer_totals;
```

После создания view сегментация становится обычным `SELECT`, доступным кому угодно, кто не обязан разбираться во внутренней логике CTE и подзапросов:

```sql
SELECT customer_name, total_spent, spending_segment
FROM customer_spending_segments
WHERE spending_segment = 'выше среднего'
ORDER BY total_spent DESC;
```

Обратим внимание на важную деталь: `LEFT JOIN` внутри `customer_totals` вместе с `COALESCE` гарантирует, что клиенты без единого заказа тоже попадут в сегментацию (с `total_spent = 0` вместо `NULL`, как разбиралось в шестнадцатом уроке уровня «Начинающий») и корректно окажутся в сегменте «ниже среднего» — если бы вместо `LEFT JOIN` использовался `INNER JOIN`, такие клиенты вообще выпали бы из view, что противоречило бы смыслу отчёта, задуманного как полная картина по всем клиентам.

### Что объединяет три раздела дашборда

Каждый раздел использовал разный набор инструментов уровня, но общая архитектура решения одинакова во всех трёх: сначала CTE собирает «сырую» агрегацию по теме раздела (выручка по месяцам, продажи по товарам, трата по клиентам), затем, при необходимости, второй слой обработки добавляет сравнение — с соседним периодом через `LAG`, с другими товарами группы через `ROW_NUMBER`, или со средним по всему магазину через скалярный подзапрос, — и только в конце происходит финальная фильтрация или категоризация. Эта архитектура — не случайность, а прямое следствие идеи, впервые встреченной в первом уроке этого уровня: сложный запрос — это не одна большая непонятная конструкция, а последовательность простых, уже знакомых шагов, каждый из которых можно понять, проверить и объяснить по отдельности. Именно этот навык — умение разложить требование бизнеса на цепочку именованных шагов, выбрать для каждого шага подходящий инструмент (подзапрос, CTE, оконную функцию, `UNION`, `VIEW`) и собрать их в согласованный результат — является главным практическим итогом уровня «Средний», куда более важным, чем знание синтаксиса любой отдельной конструкции. На следующем уровне курса, «Продвинутый», к этому навыку добавится забота о производительности таких запросов (индексы, `EXPLAIN`) и перенос части логики на сторону самого сервера (хранимые процедуры, триггеры) — но сама идея декомпозиции сложной задачи останется той же.

### Резюме

- Реальные аналитические дашборды почти всегда состоят из нескольких разделов, каждый из которых требует своей комбинации инструментов — единого «универсального» запроса для всего дашборда обычно не существует.
- Цепочка CTE («сырая агрегация → сравнение/ранжирование → финальная фильтрация») — типовая архитектура сложного аналитического запроса; она делает намерение видимым и не требует держать в голове глубоко вложенные подзапросы.
- `LAG`/`LEAD` заменяют self-join там, где нужно сравнение с соседним по порядку периодом; `ROW_NUMBER`/`RANK` с `PARTITION BY` заменяют невозможную для `GROUP BY` задачу «топ-N внутри каждой группы, без потери исходных строк».
- Скалярный подзапрос остаётся удобным способом сравнить строку с единственным агрегированным значением (средним по всему набору), в том числе внутри `CASE`.
- `VIEW` — подходящий способ «упаковать» готовую многошаговую аналитику (включая CTE внутри неё) в простой, переиспользуемый интерфейс для тех отчётов, где сложность вычисления не должна касаться каждого нового запроса.
- `LEFT JOIN` вместо `INNER JOIN` в основании аналитической витрины принципиален, если отчёт должен включать «пустые» случаи (клиентов без заказов) — иначе такие сущности незаметно выпадут из итогового результата.
- Главный навык уровня «Средний» — декомпозиция сложной аналитической задачи на последовательность простых, проверяемых шагов с подходящим инструментом для каждого — более важен, чем синтаксис любой отдельной конструкции, и будет применяться на всех последующих уровнях курса.

## Теоретические задания

### Вопрос 1: Почему в задаче «топ-3 в каждой категории» нельзя отфильтровать строки по `rank_in_category` прямо в `WHERE` того же уровня SELECT, где вычисляется `ROW_NUMBER()`?

- ✅ Оконная функция вычисляется после этапа WHERE (логический порядок выполнения запроса), поэтому её результат доступен только внешнему запросу — например, следующему CTE
<!-- фильтрация по оконной функции всегда требует отдельного внешнего шага -->
- ❌ Потому что `ROW_NUMBER()` нельзя использовать вместе с `GROUP BY` в одном запросе — error_text: Оконные функции и `GROUP BY` сочетаются: агрегат сворачивает строки, а оконная функция работает над уже свёрнутым результатом. Запрет именно на фильтрацию по оконной функции в `WHERE` того же уровня — из-за порядка вычислений (урок 6 уровня «Начинающий»).
- ❌ Потому что `WHERE` умеет сравнивать только столбцы таблиц, а не выражения — error_text: `WHERE` принимает любые выражения уровня строк: арифметику, функции, подзапросы. Проблема не в выразительности, а в моменте вычисления — оконные функции считаются позже фильтрации.
- ❌ Ограничение снимается, если заменить `ROW_NUMBER()` на `RANK()` — его можно фильтровать в WHERE — error_text: `RANK()` — тоже оконная функция и вычисляется так же после `WHERE`; фильтровать его в `WHERE` нельзя по той же причине. Различие между ними — в нумерации при равных значениях.

### Вопрос 2: Что вернёт `LAG(revenue) OVER (ORDER BY month)` для самого первого месяца набора?

- ✅ NULL — предыдущей строки в окне нет, и это осмысленное отсутствие значения, а не ошибка
<!-- нет предыдущего месяца для сравнения -->
- ❌ 0 — предыдущего месяца не было, значит разница отсчитывается от нуля — error_text: `LAG` возвращает именно NULL, а не 0: предыдущей строки в наборе просто нет — NULL как «значения нет» разобран в уроке 11 уровня «Основы». Поэтому и процент роста первого месяца получается NULL, а не 0%.
- ❌ Ошибку выполнения: у первой строки нет предыдущей — error_text: Отсутствие предыдущей строки — не ошибка, а штатная ситуация: `LAG` честно возвращает NULL. Ошибкой было бы, например, обращение к несуществующей колонке (ошибка 1054, урок 8 уровня «Средний»).
- ❌ Значение текущей строки — для первой строки LAG возвращает её же саму — error_text: `LAG` не «залипает» на текущем значении: без предыдущей строки он возвращает NULL. Значение по умолчанию можно задать третьим аргументом `LAG(столбец, 1, значение)`, но без него это NULL.

### Вопрос 3: Почему в основе сегментации клиентов использован `LEFT JOIN` из `customers` в `orders`, а не `INNER JOIN`?

- ✅ INNER JOIN незаметно исключил бы клиентов без единого заказа, а отчёт должен охватывать всех клиентов
<!-- полный охват сущностей важнее удобства внутреннего соединения -->
- ❌ LEFT JOIN всегда быстрее INNER JOIN на больших объёмах — error_text: Скорость здесь ни при чём: `LEFT JOIN` сохраняет все строки левой таблицы и обычно не дешевле `INNER JOIN`. Выбор продиктован смыслом — клиенты без заказов должны попасть в сегментацию, а с `INNER JOIN` они бы выпали (урок 14 уровня «Начинающий»).
- ❌ INNER JOIN запрещён внутри определений VIEW — error_text: Внутри VIEW допустимы любые соединения, включая `INNER JOIN`: view — просто сохранённый `SELECT` (урок 11 уровня «Средний»), ограничений на тип JOIN в нём нет.
- ❌ LEFT JOIN нужен, чтобы сумма по клиенту без заказов автоматически стала нулём — error_text: JOIN сам по себе даёт лишь NULL-расширенные строки; ноль получается из `COALESCE(SUM(...), 0)` (урок 11 уровня «Основы»). `LEFT JOIN` лишь удерживает клиента в результате.

### Вопрос 4: Какую роль в дашборде сыграла VIEW?

- ✅ Упаковала многошаговую аналитику в переиспользуемый интерфейс: сложность спрятана внутри, а обращение выглядит как простой SELECT
<!-- переиспользуемость — про интерфейс, а не про сохранённый результат -->
- ❌ VIEW зафиксировала результат сегментации, чтобы не пересчитывать его при каждом отчёте — error_text: Представление ничего не фиксирует и не кэширует: при каждом обращении оно выполняется заново над актуальными данными (урок 11 уровня «Средний»). Выгода — в переиспользуемом интерфейсе, а не в сохранённом результате.
- ❌ VIEW заменила оконные функции, выполнив то же самое через GROUP BY — error_text: View не заменяет вычисления, а содержит их: внутри неё те же CTE и скалярные подзапросы. Задачи ранжирования внутри групп и сравнения со средним `GROUP BY` не решает.
- ❌ VIEW ускорила запросы дашборда, материализовав промежуточные таблицы — error_text: Материализации промежуточных результатов view не делает — это не копия данных. Ускорение чтения за счёт дублирования — денормализация, отдельный осознанный приём (урок 11 уровня «Средний»).

### Вопрос 5: Какова типовая архитектура сложного аналитического запроса, общая для всех трёх разделов дашборда?

- ✅ Цепочка CTE: «сырая» агрегация → сравнение или ранжирование (оконная функция / подзапрос) → финальная фильтрация или категоризация
<!-- каждый шаг прост, проверяем отдельно и читается по имени -->
- ❌ Один большой вложенный подзапрос в WHERE, отбирающий готовые строки — error_text: Глубокая вложенность — анти-паттерн читаемости, который CTE и придумали заменять: цепочка именованных шагов читается, проверяется и объясняется по отдельности.
- ❌ UNION ALL всех промежуточных результатов в один отчёт — error_text: `UNION ALL` склеивает результаты по вертикали (урок 3 уровня «Средний»), а здесь шаги не склеиваются, а продолжают друг друга: каждый следующий потребляет результат предыдущего.
- ❌ Создание копий исходных таблиц под каждый раздел отчёта — error_text: Копирование данных — не аналитический приём, а источник рассинхронизации. Все разделы работают над одними и теми же таблицами через временные именованные результаты — CTE и VIEW.

### Задание 3: VIEW: сегментация клиентов по средним тратам
