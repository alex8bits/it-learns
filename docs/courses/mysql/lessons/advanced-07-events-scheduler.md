## Материал

Прошлый урок разобрал триггеры — код, срабатывающий автоматически в ответ на изменение конкретной строки конкретной таблицы. Но есть класс задач, у которых нет «строки-повода»: они должны выполняться просто по расписанию, независимо от того, происходили ли в это время какие-либо изменения данных — «раз в сутки помечать просроченные неоплаченные заказы как отменённые», «раз в час пересчитывать агрегированную статистику», «раз в месяц архивировать старые записи `order_log`». Для таких задач в MySQL существует **планировщик событий** (Event Scheduler) и объекты **EVENT**.

### Планировщик событий: включение и проверка состояния

Планировщик событий — отдельный фоновый процесс внутри сервера MySQL, который не работает по умолчанию — прежде чем создавать события, нужно убедиться, что он включён:

```sql
SHOW VARIABLES LIKE 'event_scheduler';
```

Если переменная показывает `OFF`, планировщик включается на время сессии (или до перезапуска сервера) командой:

```sql
SET GLOBAL event_scheduler = ON;
```

Постоянное включение (сохраняющееся после перезапуска сервера) требует правки конфигурационного файла сервера (`my.cnf`/`my.ini`) — эта тема относится к администрированию сервера и будет затронута в двенадцатом уроке этого уровня; на уровне отдельной сессии `SET GLOBAL` достаточно для экспериментов и понимания механики.

### CREATE EVENT: минимальный пример

Событие создаётся командой `CREATE EVENT` и обязательно указывает, **когда** и **как часто** выполнять указанное действие:

```sql
DELIMITER //

CREATE EVENT cancel_stale_pending_orders
ON SCHEDULE EVERY 1 DAY
STARTS CURRENT_TIMESTAMP
DO
BEGIN
    UPDATE orders
    SET status = 'cancelled'
    WHERE status = 'pending'
      AND created_at < NOW() - INTERVAL 7 DAY;
END //

DELIMITER ;
```

Тело события (после `DO`) — это произвольный SQL-блок, использующий тот же процедурный синтаксис, что и хранимые процедуры из пятого урока этого уровня (переменные, условия, циклы доступны и здесь) — событие, по сути, можно рассматривать как процедуру, у которой вместо явного вызова `CALL` есть встроенное расписание запуска.

### ON SCHEDULE: одноразовые и повторяющиеся события

Конструкция `ON SCHEDULE` бывает двух видов. Одноразовое событие выполняется единожды в указанный момент и затем автоматически удаляется (если не указано иное):

```sql
CREATE EVENT one_time_cleanup
ON SCHEDULE AT '2026-12-31 23:59:00'
DO
    DELETE FROM order_log WHERE changed_at < '2020-01-01';
```

Повторяющееся событие использует `EVERY интервал`, с необязательными уточнениями `STARTS`/`ENDS`, задающими окно, в течение которого повторение действует:

```sql
CREATE EVENT recalculate_daily_revenue
ON SCHEDULE EVERY 1 DAY
STARTS '2026-01-01 03:00:00'
DO
    -- пересчёт агрегированной таблицы отчётности
    ...;
```

Единица интервала (`DAY`, `HOUR`, `MINUTE`, `WEEK`, `MONTH` и другие) синтаксически использует то же семейство `INTERVAL`-выражений, что уже встречалось в пятом уроке уровня «Начинающий» при работе с `DATE_ADD`.

### Управление событием: пауза, включение, изменение, удаление

Событие можно временно отключить без удаления его определения — `ALTER EVENT имя DISABLE;` — и включить обратно `ALTER EVENT имя ENABLE;`. Изменение расписания или тела существующего события — тоже через `ALTER EVENT`, без необходимости пересоздавать объект с нуля (в отличие от процедур из пятого урока, где изменение тела требует `DROP` + `CREATE`):

```sql
ALTER EVENT cancel_stale_pending_orders
ON SCHEDULE EVERY 12 HOUR;
```

Удаление — `DROP EVENT имя;`, список существующих событий текущей базы — `SHOW EVENTS;`.

### ON COMPLETION: что происходит после одноразового события

Для одноразовых событий по умолчанию действует поведение `ON COMPLETION NOT PRESERVE` — после единственного выполнения определение события автоматически удаляется сервером, как если бы никто не вызывал `DROP EVENT` вручную. Если требуется, чтобы определение осталось видимым (например, для аудита истории «что и когда должно было сработать») даже после того, как событие сработало и больше не будет выполняться, используется `ON COMPLETION PRESERVE`:

```sql
CREATE EVENT one_time_migration
ON SCHEDULE AT '2026-06-01 00:00:00'
ON COMPLETION PRESERVE
DO
    ...;
```

Для повторяющихся событий (`EVERY`) это уточнение не имеет практического значения — они продолжают существовать до явного `DROP EVENT` или до истечения `ENDS`, независимо от того, сколько раз уже сработали.

### Почему EVENT — не универсальная замена внешнего планировщика задач

На первый взгляд `EVENT` решает ту же задачу, что и внешние системы планирования задач операционной системы (`cron` в Linux, Планировщик заданий в Windows) или очереди задач приложения — выполнить что-то по расписанию. Но у `EVENT` есть принципиальные ограничения, важные для осознанного выбора инструмента:

- **Он может выполнять только SQL** — если задача требует обращения к внешнему API, отправки email, работы с файловой системой или любого другого действия за пределами самой базы данных, `EVENT` для неё не подходит вообще; это чисто SQL-инструмент, работающий строго внутри сервера MySQL.
- **Он зависит от того, что сервер MySQL запущен и планировщик включён** — если сервер перезапускается, а конфигурация не включает планировщик автоматически при старте (`event_scheduler = ON` в `my.cnf`, а не только временный `SET GLOBAL`), запланированные события просто не будут выполняться, без явного уведомления об этом на уровне приложения.
- **Наблюдаемость ограничена** — у `EVENT` нет встроенного журналирования ошибок выполнения, удобного для типичного мониторинга приложений (email/Slack-уведомление при сбое, метрики длительности, retry-политики) — эти возможности нужно либо реализовывать вручную внутри тела события (например, оборачивая логику в обработчик ошибок, записывающий факт сбоя в отдельную таблицу), либо перекладывать задачу целиком на внешний планировщик уровня приложения.

Практический ориентир: `EVENT` разумен для узкого класса задач, которые (а) целиком выражаются в SQL, (б) не требуют сложной логики повторных попыток и внешних уведомлений о сбое, и (в) естественно живут рядом с самими данными (архивация, пересчёт агрегатов, точечная очистка). Для регулярных задач, которые взаимодействуют с внешним миром или требуют надёжного мониторинга исполнения, стандартная практика — планировщик на уровне приложения или операционной системы, который вызывает обычный SQL-код (в том числе, возможно, ту же хранимую процедуру из пятого урока) по собственному расписанию, с собственным журналированием и повторными попытками при сбое.

### Почему у этого урока нет практики в изолированной среде

Эффект `EVENT` по своей природе проявляется во времени — событие срабатывает только по достижении назначенного момента, а не в момент выполнения `CREATE EVENT`. Изолированная среда практики курса (описанная в правилах составления уроков) поднимается с нуля под каждую попытку и проверяет единственный итоговый результат сразу после выполнения решения — она не рассчитана на ожидание реального времени, необходимое, чтобы увидеть первое срабатывание `EVERY 1 DAY` или даже `EVERY 1 MINUTE`. Проверить материал этого урока на практике можно самостоятельно, вне ограничений песочницы курса: создать событие с коротким интервалом (`EVERY 1 MINUTE`) на реальном сервере с включённым планировщиком, подождать пару минут в открытой сессии `mysql` CLI и убедиться, что целевая таблица действительно изменилась — это ровно тот же принцип «два открытых окна для наблюдения эффекта во времени», что уже встречался в десятом уроке уровня «Средний» для наблюдения эффекта блокировок, только здесь фактором служит не второе соединение, а прошедшее время.

### Резюме

- **Планировщик событий** (Event Scheduler) — фоновый процесс сервера, по умолчанию выключенный; включается через `SET GLOBAL event_scheduler = ON` (постоянно — через конфигурацию сервера).
- **`CREATE EVENT`** задаёт SQL-блок (синтаксис тела — как у хранимой процедуры, пятый урок этого уровня) и расписание через `ON SCHEDULE`: одноразовое (`AT момент`) или повторяющееся (`EVERY интервал`, с необязательными `STARTS`/`ENDS`).
- Событие управляется через `ALTER EVENT` (пауза `DISABLE`/`ENABLE`, изменение расписания или тела без пересоздания), удаляется через `DROP EVENT`, список — `SHOW EVENTS`.
- `ON COMPLETION NOT PRESERVE` (по умолчанию) удаляет определение одноразового события после единственного срабатывания; `ON COMPLETION PRESERVE` сохраняет его для истории.
- `EVENT` умеет выполнять только SQL внутри самого сервера, зависит от того, что планировщик включён при каждом запуске сервера, и не имеет встроенных средств уведомления о сбоях — для задач, выходящих за пределы SQL или требующих надёжного мониторинга, разумнее внешний планировщик уровня приложения/ОС.
- Материал урока не проверяется в изолированной среде курса, поскольку эффект `EVENT` проявляется во времени, а песочница проверяет единственный результат сразу после выполнения решения — проверка предполагает самостоятельный эксперимент на реальном сервере с включённым планировщиком.

### Вопрос 1: Как включить планировщик событий для текущего запуска сервера?

- ✅ `SET GLOBAL event_scheduler = ON;` — до перезапуска; постоянное включение требует настройки в конфигурационном файле сервера
<!-- планировщик по умолчанию выключен; проверка состояния — SHOW VARIABLES LIKE 'event_scheduler' -->
- ❌ Просто создать событие `CREATE EVENT` — планировщик включится автоматически — error_text: Создание события не включает планировщик: событие будет существовать, но не исполнится, пока `event_scheduler` выключен. Проверить состояние можно запросом `SHOW VARIABLES LIKE 'event_scheduler'`.
- ❌ Выполнить `ALTER EVENT имя ENABLE;` — error_text: `ENABLE` и `DISABLE` управляют конкретным событием — пауза и возврат в строй одного события. Планировщик — отдельный фоновый процесс всего сервера, и включается он командой `SET GLOBAL event_scheduler = ON`.
- ❌ Ничего не нужно: планировщик событий работает по умолчанию — error_text: По умолчанию планировщик выключен — событие без включённого планировщика молча не исполняется. Именно поэтому проверка `event_scheduler` — первый шаг перед любой работой с событиями.

### Вопрос 2: Что происходит с определением одноразового события (`ON SCHEDULE AT ...`) после его единственного выполнения, если не указано иное?

- ✅ Определение автоматически удаляется сервером — это поведение `ON COMPLETION NOT PRESERVE` по умолчанию
<!-- PRESERVE сохраняет определение для истории «что и когда должно было сработать» -->
- ❌ Событие остаётся и начинает повторяться каждые сутки — error_text: Повторение задаётся только расписанием `EVERY интервал`; событие `AT момент` на второе выполнение не переходит в принципе. После срабатывания его определение по умолчанию удаляется сервером автоматически.
- ❌ Событие автоматически переводится в `DISABLE` и ждёт ручного включения — error_text: Перевод в `DISABLE` — ручная операция `ALTER EVENT имя DISABLE` для паузы события. Автоматического «паркования» одноразовых событий не существует: по умолчанию они просто удаляются после срабатывания.
- ❌ Ничего: определение хранится до явного `DROP EVENT` — error_text: Так ведут себя повторяющиеся события (`EVERY`) и одноразовые с `ON COMPLETION PRESERVE`. По умолчанию же (`NOT PRESERVE`) определение одноразового события после единственного срабатывания удаляется самим сервером.

### Вопрос 3: Как изменить расписание уже существующего события?

- ✅ `ALTER EVENT имя ON SCHEDULE ...` — расписание и тело меняются у существующего события без пересоздания
<!-- отличие от процедур: тем для смены тела нужен DROP + CREATE -->
- ❌ Только удалить событие и создать заново через `DROP EVENT` + `CREATE EVENT` — error_text: Пересоздание обязательно для хранимых процедур — их тело иначе не изменить. События устроены иначе: `ALTER EVENT` меняет и расписание, и тело существующего события, что разобрано в материале как явное преимущество.
- ❌ `MODIFY EVENT имя ON SCHEDULE ...` — error_text: Команды `MODIFY EVENT` в MySQL нет — это перенос синтаксиса `ALTER TABLE ... MODIFY COLUMN` из мира таблиц. Для событий используется `ALTER EVENT`.
- ❌ Никак: расписание фиксируется при создании события — error_text: Расписание — изменяемый атрибут события: `ALTER EVENT имя ON SCHEDULE EVERY 12 HOUR` из материала меняет его у уже созданного события. «Фиксируется навсегда» прямо противоречит назначению команды `ALTER EVENT`.

### Вопрос 4: Какую задачу в принципе невозможно решить событием `EVENT`?

- ✅ Отправить email-уведомление администратору при сбое выполнения
<!-- EVENT выполняет только SQL внутри самого сервера -->
- ❌ Раз в сутки помечать просроченные неоплаченные заказы как отменённые — error_text: Это чисто SQL-задача (`UPDATE ... WHERE status = 'pending' AND created_at < ...`), целиком живущая внутри базы, — типичный пример из материала, для которого `EVENT` и предназначен.
- ❌ Раз в час пересчитывать агрегированную таблицу статистики — error_text: Пересчёт агрегатов — операция только над данными самой БД: никаких выходов за пределы сервера, внешних сервисов и уведомлений. Идеальный кандидат на повторяющееся событие `EVERY 1 HOUR`.
- ❌ Раз в месяц архивировать старые записи журнала `order_log` — error_text: Архивация старых записей по дате — снова задача над данными самой БД, удовлетворяющая всем критериям уместности `EVENT` из материала: выражается в SQL, не требует внешних уведомлений и повторных попыток при сбое.

### Вопрос 5: Чем событие `EVENT` принципиально отличается от триггера?

- ✅ Событие срабатывает по расписанию — по наступлению времени, без всякой связи с изменениями данных; триггер — в ответ на изменение строки конкретной таблицы
<!-- событию нужен момент времени; триггеру — строка-повод -->
- ❌ Событие срабатывает при вставке строк, триггер — при их удалении — error_text: Оба механизма не привязаны к конкретному типу операции над строками: триггер настраивается на любое из `INSERT`/`UPDATE`/`DELETE`, а событие к строкам вообще не привязано. Разница не в типе операции, а в самом поводе срабатывания.
- ❌ Событие вызывается командой `CALL`, триггер срабатывает сам — error_text: `CALL` вызывает хранимые процедуры; события не вызываются вручную вовсе — их запускает планировщик по расписанию. Триггер действительно срабатывает сам, но его повод — изменение данных, а не время.
- ❌ Ничем: это два названия одного механизма автоматического выполнения кода — error_text: Механизмы разные и закрывают разные классы задач: триггер — реакция на изменение строки в таблице, событие — действие по времени, не требующее никакого повода в данных. У них разные команды создания, управления и условия срабатывания.
