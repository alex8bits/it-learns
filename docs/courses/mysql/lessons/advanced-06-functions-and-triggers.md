## Материал

Прошлый урок показал, как оформить многошаговую логику в вызываемый по требованию блок — хранимую процедуру, которая выполняется, только когда её явно вызвали командой `CALL`. Но у многих правил есть другая природа: они должны срабатывать не по явному запросу, а **автоматически**, каждый раз, когда происходит определённое изменение данных — независимо от того, какое именно приложение или какой именно пользователь это изменение вызвал. Для этого в MySQL существуют **хранимые функции** (короткое дополнение к процедурам прошлого урока) и, что более важно для реальной практики, **триггеры** — код, который сервер запускает сам, в ответ на `INSERT`/`UPDATE`/`DELETE`.

### Хранимые функции: как процедура, но с возвращаемым значением

**Хранимая функция** синтаксически похожа на процедуру из прошлого урока, но имеет принципиальное отличие: она обязана вернуть **одно** значение через `RETURN` и, в отличие от процедуры, может использоваться **прямо внутри обычного SQL-выражения** — в `SELECT`, `WHERE`, `ORDER BY` — там, где уместно любое скалярное значение, а не только через отдельный вызов `CALL`:

```sql
DELIMITER //

CREATE FUNCTION order_total(p_order_id INT)
RETURNS DECIMAL(10, 2)
DETERMINISTIC
READS SQL DATA
BEGIN
    DECLARE v_total DECIMAL(10, 2);

    SELECT COALESCE(SUM(quantity * price), 0)
    INTO v_total
    FROM order_items
    WHERE order_id = p_order_id;

    RETURN v_total;
END //

DELIMITER ;
```

Использование — как у встроенных функций (`SUM`, `COALESCE`, знакомых с восьмого урока уровня «Начинающий»):

```sql
SELECT id, order_total(id) AS total
FROM orders
WHERE customer_id = 42;
```

Обратим внимание на две обязательные характеристики после `RETURNS`, которых не было у процедур: `DETERMINISTIC` (или `NOT DETERMINISTIC`) сообщает серверу, всегда ли функция возвращает одинаковый результат для одинаковых входных параметров (сама `order_total` — детерминирована в рамках одного и того же состояния данных, но, строго говоря, недетерминирована во времени, поскольку зависит от содержимого `order_items`, которое меняется; в учебных и большинстве практических целей для функций, читающих таблицы, достаточно понимать, что этот атрибут — декларация для оптимизатора и для механизма логирования репликации, а не гарантия математической чистоты функции), а `READS SQL DATA` явно объявляет, что тело функции обращается к данным таблиц (в отличие от чисто вычислительной функции без обращения к БД, для которой было бы уместно `NO SQL`). MySQL требует такие декларации явно — без них создание функции, читающей данные, будет отклонено при включённых строгих режимах логирования.

Важная практическая оговорка: вызов пользовательской функции внутри `WHERE` для столбца, который иначе был бы проиндексирован, создаёт ровно тот же анти-паттерн, что был разобран в четвёртом уроке этого уровня («функция над индексированным столбцом ломает использование индекса») — если функция читает данные из других таблиц (как `order_total`) и вызывается для каждой строки большого результата, это может стать заметно медленнее, чем эквивалентный `JOIN` с агрегацией. Хранимая функция удобна для читаемости точечных запросов и переиспользования формулы в разных местах, но не является бесплатной заменой обычного SQL там, где обычный `JOIN`/подзапрос справится не хуже и быстрее.

### Триггер: код, который срабатывает сам

**Триггер** — это блок кода, прикреплённый к конкретной таблице и конкретному событию изменения данных (`INSERT`, `UPDATE` или `DELETE`), который сервер выполняет автоматически, без явного вызова, каждый раз, когда это событие происходит. У триггера два измерения, задающих момент и повод его срабатывания:

- **момент** относительно самого изменения — `BEFORE` (до того, как изменение фактически применено к таблице) или `AFTER` (сразу после того, как изменение применено);
- **событие** — `INSERT`, `UPDATE` или `DELETE`.

Комбинации этих измерений дают шесть типов триггеров на одну таблицу: `BEFORE INSERT`, `AFTER INSERT`, `BEFORE UPDATE`, `AFTER UPDATE`, `BEFORE DELETE`, `AFTER DELETE`.

### BEFORE-триггер: изменить или проверить данные до записи

`BEFORE`-триггеры типично используются для **валидации** или **автоматической корректировки** значений до того, как строка попадёт в таблицу — внутри такого триггера доступна псевдотаблица `NEW`, представляющая новую версию строки, которую можно изменить прямо в теле триггера:

```sql
DELIMITER //

CREATE TRIGGER trg_products_before_insert
BEFORE INSERT ON products
FOR EACH ROW
BEGIN
    IF NEW.price < 0 THEN
        SET NEW.price = 0;
    END IF;
END //

DELIMITER ;
```

Здесь `NEW.price` — цена товара, который сейчас пытаются вставить; изменение `NEW.price` внутри `BEFORE INSERT` реально повлияет на то, что окажется сохранено в таблице (в отличие от `AFTER`-триггеров, где строка уже сохранена и правки `NEW` не имели бы смысла для этой же операции). Такая проверка — не замена ограничению `CHECK` (шестой урок уровня «Основы»): `CHECK` — декларативное ограничение, которое просто **отклонит** всю операцию с ошибкой при нарушении, а `BEFORE`-триггер способен **скорректировать** значение и позволить операции пройти — выбор между ними зависит от того, должна ли невалидная попытка провалиться целиком или быть незаметно исправлена.

### AFTER-триггер: побочные действия после изменения

`AFTER`-триггеры используются, когда изменение данных должно повлечь **дополнительное** действие — типичный пример — ведение журнала аудита. Сквозной датасет курса уже включает таблицу `order_log(id, order_id, changed_at, old_status, new_status)`, спроектированную именно для этой цели:

```sql
DELIMITER //

CREATE TRIGGER trg_orders_after_update
AFTER UPDATE ON orders
FOR EACH ROW
BEGIN
    IF OLD.status <> NEW.status THEN
        INSERT INTO order_log (order_id, changed_at, old_status, new_status)
        VALUES (NEW.id, NOW(), OLD.status, NEW.status);
    END IF;
END //

DELIMITER ;
```

Здесь появляется вторая псевдотаблица — `OLD`, представляющая версию строки **до** изменения; для `UPDATE`-триггеров доступны сразу обе — `OLD` (что было) и `NEW` (что стало), что делает возможным условие `OLD.status <> NEW.status` — записывать в журнал только те обновления, которые действительно изменили статус заказа, а не любое обновление любого столбца этой строки. Для `INSERT`-триггеров доступна только `NEW` (строки не существовало до вставки — «старой» версии нет), для `DELETE`-триггеров — только `OLD` (после удаления новой версии не будет).

После создания этого триггера **любое** обновление статуса заказа — сделанное через приложение, через `mysql` CLI администратором, через ещё не написанную будущую интеграцию — гарантированно попадёт в `order_log`, без необходимости помнить о вызове дополнительной команды логирования в каждом месте кода, где может произойти такое обновление. Это ключевое отличие подхода «триггер» от подхода «хранимая процедура» из прошлого урока: процедуру нужно **явно вызвать**, чтобы её логика сработала, а триггер срабатывает **сам**, при самом факте изменения, независимо от способа, которым это изменение было сделано.

### Множественные триггеры и порядок их выполнения

На одну таблицу и одно событие может быть создано несколько триггеров одного типа (например, два разных `AFTER INSERT` триггера на `products` — один для аудита, другой для пересчёта агрегированной статистики). По умолчанию порядок их выполнения — в порядке создания; начиная с MySQL 5.7.2 можно управлять этим порядком явно через `FOLLOWS`/`PRECEDES` в определении триггера. Для учебных и большинства практических целей достаточно избегать самой ситуации нескольких равнозначных триггеров на одно событие там, где порядок между ними принципиален — читаемость и предсказуемость важнее компактности, и часто разумнее объединить логику в один триггер, чем полагаться на порядок нескольких.

### Удаление и просмотр триггеров

Триггер удаляется командой `DROP TRIGGER имя;`. Список существующих триггеров текущей базы данных можно посмотреть через `SHOW TRIGGERS;` — команда, аналогичная по духу уже знакомому `SHOW`-семейству (упомянутому вскользь во втором уроке уровня «Основы» применительно к клиентам и базам данных).

### Скрытая логика: главный риск триггеров

У силы триггеров есть прямая обратная сторона — **невидимость**. Разработчик, читающий код приложения, видит явный вызов `UPDATE orders SET status = 'paid' WHERE id = ...` и по этому коду не может напрямую понять, что где-то в базе данных на это событие автоматически сработает триггер, который дополнительно что-то запишет, изменит или проверит — если только он не знает заранее о существовании этого триггера или не догадается посмотреть `SHOW TRIGGERS`. Эта невидимость создаёт вполне реальные практические проблемы: неожиданное падение производительности `UPDATE`, если триггер незаметно выполняет тяжёлую работу; сложность отладки, когда результат в базе не совпадает с тем, что «видимый» код должен был произвести; риск каскада триггеров, если один триггер сам меняет данные, вызывающие срабатывание другого триггера на другой таблице, и итоговую цепочку событий сложно удержать в голове целиком.

### Когда логика должна жить в БД, а когда — в приложении

Пятый урок этого уровня уже поднимал этот вопрос применительно к хранимым процедурам; для триггеров он даже острее, именно из-за их неявного, автоматического характера. Разумный практический ориентир:

- **В БД (триггер)** — стоит помещать инвариант, который **должен** соблюдаться независимо от того, какое приложение и какой путь кода изменил данные: аудит критичных изменений (как `order_log`), поддержание согласованности денормализованных значений (одиннадцатый урок уровня «Средний» вводил денормализацию — например, пересчёт `order_total` при изменении `order_items`), базовая защита целостности, которую не покрывают декларативные ограничения (`CHECK`, `FOREIGN KEY`).
- **В приложении** — стоит оставлять любую логику, которая зависит от контекста конкретного пользовательского действия (например, «отправить письмо клиенту при смене статуса заказа» — это явно не задача БД, потому что вовлекает внешний сервис, а не только данные), любую логику, которую полезно явно видеть при чтении кода бизнес-процесса, и любую логику, часто меняющуюся по бизнес-причинам (частые изменения кода триггера на продуктивной базе — источник риска, требующий отдельной дисциплины миграций, не более лёгкой, чем для схемы таблиц).

Итоговое правило простое: триггер — инструмент для *инвариантов данных*, а не для *бизнес-процессов*; если сформулировать логику можно фразой «эти данные всегда должны быть согласованы вот так», это кандидат на триггер, а если фразой «когда происходит X, система также должна сделать Y» (где Y выходит за пределы самой базы данных или зависит от того, кто и почему инициировал X) — это задача для кода приложения.

### Резюме

- **Хранимая функция** — как процедура, но обязана вернуть значение через `RETURN` и может использоваться прямо внутри `SELECT`/`WHERE`/`ORDER BY`; требует явных атрибутов `DETERMINISTIC`/`NOT DETERMINISTIC` и `READS SQL DATA`/`NO SQL`. Вызов внутри `WHERE` для каждой строки большого результата подвержен тому же анти-паттерну «функция над столбцом», что и обычные функции (четвёртый урок этого уровня).
- **Триггер** — код, прикреплённый к таблице и событию (`INSERT`/`UPDATE`/`DELETE`), срабатывающий автоматически на любое изменение, независимо от того, как оно было сделано; задаётся моментом (`BEFORE`/`AFTER`) и событием.
- `BEFORE`-триггеры могут изменять данные до записи через псевдотаблицу `NEW` (валидация, автокоррекция); `AFTER`-триггеры выполняют побочные действия после записи (типично — аудит через `INSERT` в отдельный журнал, например `order_log`), используя `OLD` (только для `UPDATE`/`DELETE`) и `NEW` (только для `INSERT`/`UPDATE`).
- Главный риск триггеров — неявность: код, вызывающий обычный `UPDATE`, не показывает, что срабатывает дополнительная автоматическая логика; это усложняет отладку и создаёт риск неожиданных цепочек триггеров.
- Практический ориентир: триггер — для инвариантов, которые должны соблюдаться независимо от источника изменения (аудит, согласованность денормализованных значений); бизнес-процессы, зависящие от контекста и выходящие за пределы самой базы данных (уведомления, интеграции), — задача приложения, а не БД.

## Теоретические задания

### Вопрос 1: Чем хранимая функция принципиально отличается от хранимой процедуры?

- ✅ Функция обязана вернуть одно значение через `RETURN` и может использоваться прямо внутри `SELECT`/`WHERE`/`ORDER BY`; процедуру вызывают отдельно командой `CALL`
<!-- функция встраивается в SQL-выражение как встроенные SUM/COALESCE; процедура — отдельный вызов -->
- ❌ Функция вызывается командой `CALL`, а процедура используется внутри `SELECT` — error_text: Роли перепутаны местами: `CALL` — способ явного вызова процедуры, а именно функция встраивается внутрь SQL-выражений как скалярное значение. Это зеркальная ловушка на различие двух типов хранимых объектов.
- ❌ Функция срабатывает автоматически при изменении данных в таблице — error_text: Автоматически в ответ на изменение данных срабатывает триггер — это его определение. Функция исполняется только там, где её явно упомянули в выражении, как встроенные `SUM` или `COALESCE`.
- ❌ Функция не может читать данные из таблиц — error_text: Может: атрибут `READS SQL DATA` как раз объявляет, что тело функции обращается к данным таблиц. Такова функция `order_total` из материала — она читает `order_items`, чтобы вернуть сумму заказа.

### Вопрос 2: В каком триггере инструкция `SET NEW.price = 0` реально изменит значение, которое будет сохранено в таблице?

- ✅ В `BEFORE INSERT` или `BEFORE UPDATE`: строка ещё не применена к таблице, и правка `NEW` попадает в сохраняемое значение
<!-- пример с отрицательной ценой из материала: корректировка значения до записи -->
- ❌ В `AFTER INSERT` — строка уже сохранена, но триггер может тут же её исправить — error_text: К моменту `AFTER`-срабатывания строка уже фактически записана в таблицу, поэтому присваивание `NEW.price` уже не повлияет на результат этой операции. Исправить значение до записи может только `BEFORE`-триггер.
- ❌ В любом: триггер выполняется внутри той же операции записи, момент не важен — error_text: Момент — суть различия: `BEFORE` выполняется до применения изменения (правки `NEW` сохраняются), `AFTER` — после (менять уже поздно). Смешение этих моментов — классическая ошибка при выборе типа триггера.
- ❌ Ни в каком: `NEW` доступна только для чтения — error_text: В `BEFORE`-триггерах `NEW` специально изменяема — это штатный механизм валидации и автокоррекции значений до записи (пример `SET NEW.price = 0` при отрицательной цене из материала). «Только чтение» — поведение, к которому приводит лишь неправильный выбор `AFTER`.

### Вопрос 3: Какие псевдотаблицы доступны внутри триггера на событие `UPDATE`?

- ✅ Обе: `OLD` (версия строки до изменения) и `NEW` (версия после)
<!-- UPDATE — единственное событие, где есть и «было», и «стало»: условие OLD.status <> NEW.status -->
- ❌ Только `NEW` — строка после изменения — error_text: Только `NEW` доступна в `INSERT`-триггерах: до вставки старой версии строки не существовало. У `UPDATE` есть обе версии — «было» и «стало», поэтому в аудит-триггере и возможно сравнение `OLD.status <> NEW.status`.
- ❌ Только `OLD` — строка до изменения — error_text: Только `OLD` доступна в `DELETE`-триггерах: после удаления новой версии строки не будет. `UPDATE` же изменяет существующую строку, и сервер видит обе её версии одновременно.
- ❌ Ни одной: триггер не видит изменяемую строку — error_text: Доступ к изменяемой строке через `OLD`/`NEW` — основной механизм триггера: условие аудита, копирование значений в журнал, корректировка перед записью. Без псевдотаблиц триггер вообще не мог бы видеть, что именно изменилось.

### Вопрос 4: Сколько триггеров одного типа (например, `AFTER UPDATE`) можно создать на одну таблицу в MySQL 8?

- ✅ Несколько: по умолчанию они выполняются в порядке создания, а с MySQL 5.7.2 порядок можно задать явно через `FOLLOWS`/`PRECEDES`
<!-- несколько триггеров на событие допустимы; где порядок важен — лучше объединить логику в один триггер -->
- ❌ Ровно один: вторая попытка завершится ошибкой — error_text: Лимит «один триггер на событие и таблицу» — история старых версий MySQL (до 5.7.2); в MySQL 8 несколько `AFTER UPDATE`-триггеров на одной таблице допустимы. Впрочем, если порядок их работы принципиален, разумнее объединить логику в один триггер — так предсказуемее.
- ❌ Несколько, но порядок их выполнения не гарантирован и не управляется — error_text: Порядок по умолчанию определён — это порядок создания, — и с 5.7.2 его можно закрепить явно через `FOLLOWS`/`PRECEDES`. «Полный хаос» — преувеличение, хотя полагаться на неявный порядок нескольких триггеров действительно плохая практика.
- ❌ Шесть — по одному на каждую комбинацию момента и события — error_text: Шесть — это число возможных типов триггеров на таблицу (`BEFORE`/`AFTER` × `INSERT`/`UPDATE`/`DELETE`), а не лимит на каждый тип. Внутри одного типа в MySQL 8 допустимы несколько триггеров.

### Вопрос 5: Какая из этих задач — плохой кандидат на реализацию триггером?

- ✅ Отправить письмо клиенту при смене статуса его заказа
<!-- выход за пределы БД и зависимость от контекста действия — задача приложения -->
- ❌ Записывать в `order_log` каждую смену статуса заказа — error_text: Это образцовый триггер: инвариант «любая смена статуса протоколируется» должен соблюдаться независимо от того, какой код выполнил `UPDATE`. Триггер — единственный механизм, гарантирующий это для всех путей изменения.
- ❌ Пересчитывать денормализованную сумму заказа при изменении его позиций — error_text: Поддержание согласованности денормализованных значений — формулировка вида «эти данные всегда согласованы вот так», то есть инвариант данных. Именно такие инварианты материал рекомендует держать в БД, чтобы ни одно приложение не смогло их обойти.
- ❌ Отклонять изменение, нарушающее правило целостности, которое не выражается через `CHECK` и `FOREIGN KEY` — error_text: Базовая защита целостности сверх декларативных ограничений — легитимная зона `BEFORE`-триггеров: правило обязано работать для любого источника изменения. «Данные всегда валидны» — это инвариант, а не бизнес-процесс.

`deleted_at = 2026-08-20 09:30:00` из значения по умолчанию. Товары
с ненулевым остатком (мышь и монитор) не удаляются и в архив не
попадают.

**seed_sql:**

```sql
CREATE TABLE products (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL
);

INSERT INTO products (name, price, stock) VALUES
    ('Мышь беспроводная', 1290.50, 14),
    ('Коврик войлочный', 450.00, 0),
    ('Клавиатура механическая', 4990.00, 0),
    ('Монитор 27"', 15990.00, 5),
    ('Кабель HDMI', 320.00, 0);

CREATE TABLE product_archive (
    id INT AUTO_INCREMENT PRIMARY KEY,
    product_id INT NOT NULL,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    deleted_at DATETIME NOT NULL DEFAULT '2026-08-20 09:30:00'
);
```
