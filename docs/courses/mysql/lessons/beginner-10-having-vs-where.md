## Материал

В шестом уроке мы уже забегали вперёд, объясняя, почему в SQL существуют два разных инструмента фильтрации — `WHERE` и `HAVING` — и что это следствие логического порядка выполнения запроса. Теперь, когда мы прошли и `GROUP BY`, и агрегатные функции, у нас есть все инструменты, чтобы разобрать `HAVING` не абстрактно, а на конкретных, практических примерах: он фильтрует не отдельные строки, а уже сформированные **группы**, оставляя только те, которые удовлетворяют условию, обычно построенному на агрегатной функции.

### Зачем нужен отдельный оператор для фильтрации групп

Представим задачу: найти категории, в которых **больше 5** товаров. Попробуем интуитивно применить `WHERE`, как мы делали для отдельных строк:

```sql
-- ОШИБКА: агрегатные функции недопустимы в WHERE
SELECT category, COUNT(*) AS products_count
FROM products
GROUP BY category
WHERE COUNT(*) > 5;
```

Такой запрос завершится ошибкой синтаксиса. Причина точно та же, что мы разбирали в шестом уроке: `WHERE` (шаг 2 логического порядка) обрабатывается **до** формирования групп (`GROUP BY` — шаг 3), а условие `COUNT(*) > 5` имеет смысл только после того, как строки уже собраны в группы и агрегат уже посчитан. На момент выполнения `WHERE` вообще нет никаких «пяти товаров в группе» — есть только отдельные, ещё не сгруппированные строки исходной таблицы, и спрашивать про количество строк «в группе» пока рано.

Именно для таких условий — тех, что можно проверить только **после** того, как группы сформированы и агрегаты вычислены, — в SQL предусмотрен отдельный оператор `HAVING`, который располагается в тексте запроса сразу после `GROUP BY` (это единственно допустимое синтаксическое место) и по логическому порядку выполняется на шаге 4, уже после группировки:

```sql
SELECT category, COUNT(*) AS products_count
FROM products
GROUP BY category
HAVING COUNT(*) > 5;
```

Этот запрос работает корректно: сначала строки группируются по `category` (шаг 3), для каждой группы считается `COUNT(*)` (тоже часть подготовки к шагу 4), а затем `HAVING` отбирает только те группы, где это число больше 5 — остальные группы целиком исключаются из результата, как если бы их не существовало.

### HAVING с разными агрегатными функциями

`HAVING` работает с любой агрегатной функцией из восьмого урока, не только с `COUNT`. Найдём категории, средняя цена товаров в которых превышает 3000 рублей:

```sql
SELECT category, ROUND(AVG(price), 2) AS avg_price
FROM products
GROUP BY category
HAVING AVG(price) > 3000;
```

Обратите внимание на важную деталь: в `HAVING` мы написали `AVG(price)`, а не псевдоним `avg_price`, хотя в некоторых СУБД (включая MySQL) обращение к псевдониму из `SELECT` в `HAVING` тоже допустимо — MySQL здесь менее строг, чем в случае `WHERE` и псевдонимов, и позволяет использовать псевдонимы `SELECT` в `HAVING`, потому что `HAVING` выполняется **после** `SELECT` по логическому порядку из шестого урока. Тем не менее многие практикующие разработчики предпочитают писать в `HAVING` полное выражение агрегата, а не псевдоним — это делает запрос переносимым между разными СУБД (не все из них разрешают псевдонимы в `HAVING`) и явным независимо от контекста.

Найдём категории, в которых суммарный остаток на складе меньше 20 единиц — потенциальный сигнал для менеджера о необходимости пополнения запасов:

```sql
SELECT category, SUM(stock) AS total_stock
FROM products
GROUP BY category
HAVING SUM(stock) < 20;
```

### HAVING можно комбинировать с логическими операторами

`HAVING`, как и `WHERE`, принимает произвольное логическое условие, включая составные условия с `AND`/`OR`/`NOT` и скобками из первого урока этого уровня. Найдём категории с более чем 3 товарами **и** средней ценой выше 2000:

```sql
SELECT category, COUNT(*) AS products_count, ROUND(AVG(price), 2) AS avg_price
FROM products
GROUP BY category
HAVING COUNT(*) > 3 AND AVG(price) > 2000;
```

### WHERE и HAVING в одном запросе: разные задачи, разные моменты

Самое важное практическое умение этого урока — понимать, что `WHERE` и `HAVING` **не заменяют**, а **дополняют** друг друга и решают принципиально разные задачи в одном запросе: `WHERE` отбрасывает отдельные строки исходных данных до того, как они попадут в группы, а `HAVING` отбрасывает уже сформированные группы после того, как по ним посчитана статистика. Рассмотрим составную задачу: найти категории, в которых **больше 2 товаров, имеющихся на складе** (`stock > 0`), при этом смотрим только на товары дешевле 10000 рублей:

```sql
SELECT category, COUNT(*) AS in_stock_products_count
FROM products
WHERE stock > 0 AND price < 10000
GROUP BY category
HAVING COUNT(*) > 2;
```

Разберём это построчно по логическому порядку из шестого урока:

1. `WHERE stock > 0 AND price < 10000` — из всей таблицы `products` сразу выбрасываются дорогие товары и товары не в наличии; эти строки не участвуют в дальнейших шагах вообще, даже в подсчёте.
2. `GROUP BY category` — оставшиеся строки группируются по категориям.
3. `COUNT(*)` — для каждой группы считается, сколько строк в ней осталось (то есть только подходящих под условие `WHERE` товаров).
4. `HAVING COUNT(*) > 2` — из получившихся групп остаются только те, где таких товаров больше двух.

Если в этом примере условие `stock > 0` ошибочно переместить в `HAVING` вместо `WHERE`, задача не решится корректно даже синтаксически: `stock` — это отдельный столбец конкретной строки, а не агрегат группы, поэтому условие `HAVING stock > 0` было бы синтаксически некорректным без агрегатной функции вокруг `stock`, и в любом случае концептуально неверным — фильтрация по свойству отдельной строки должна происходить в `WHERE`, а не в `HAVING`, даже если технически можно придумать обходной путь через агрегат (например, `HAVING MAX(stock) > 0`, что решает совсем другую задачу — «в группе есть хотя бы один товар в наличии», а не «считать только товары в наличии»).

### Практическое правило выбора между WHERE и HAVING

Чтобы не путаться, полезно задавать себе один простой вопрос: **условие касается одной конкретной строки (до группировки) или свойства целой группы (после группировки)?** Если условие можно проверить, глядя на одну единственную строку исходной таблицы, не зная ничего про остальные строки её группы — это `WHERE`. Если условие описывает совокупное, агрегированное свойство целой группы, которое невозможно узнать по одной строке в отдельности (сколько всего строк в группе, какая у них сумма, среднее, максимум) — это `HAVING`. Практическое следствие: `WHERE` почти никогда не содержит агрегатных функций (это технически возможно только в подзапросах — тема будущего уровня курса, здесь не рассматриваем), а `HAVING`, наоборот, почти всегда содержит хотя бы одну агрегатную функцию, иначе условие проще и эффективнее было бы перенести в `WHERE`, отфильтровав строки раньше и избежав группировки лишних данных.

### Резюме

- `HAVING` фильтрует уже сформированные **группы** (после `GROUP BY`), а не отдельные строки — в отличие от `WHERE`, который работает до группировки.
- Условие в `HAVING`, как правило, построено на агрегатной функции (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) — именно такие условия физически невозможно проверить в `WHERE`, потому что на момент его выполнения групп ещё не существует.
- `HAVING` располагается в запросе сразу после `GROUP BY`; в MySQL допустимо ссылаться и на псевдоним агрегата из `SELECT`, и на полное выражение агрегата — но полное выражение более переносимо между СУБД.
- `HAVING` поддерживает составные условия с `AND`/`OR`/`NOT`, как и `WHERE`.
- `WHERE` и `HAVING` дополняют друг друга в одном запросе: `WHERE` убирает ненужные строки до группировки (и делает саму группировку эффективнее — меньше строк нужно обрабатывать), `HAVING` убирает ненужные группы после того, как по ним посчитана статистика.
- Практическое правило выбора: если условие проверяется по одной строке — `WHERE`; если условие описывает свойство целой группы через агрегат — `HAVING`.

## Теоретические задания

### Вопрос 1: Почему условие `COUNT(*) > 5` нельзя написать в WHERE запроса с GROUP BY?

- ✅ WHERE выполняется до группировки — на этом шаге групп ещё не существует и агрегат считать не по чему
<!-- WHERE — шаг 2 конвейера, GROUP BY — шаг 3: условие по агрегату невозможно проверить раньше группировки -->
- ❌ можно — если расположить WHERE до GROUP BY в тексте запроса — error_text: место в тексте не спасает: агрегатные функции в WHERE недопустимы в принципе, сервер откажет с ошибкой «invalid use of group function». Для условий по агрегатам существует HAVING.
- ❌ COUNT(*) вообще нельзя использовать вместе с GROUP BY — error_text: сочетание штатное: `GROUP BY category` плюс `COUNT(*)` — типовой отчёт «сколько товаров в категории». Запрещено только условие по агрегату внутри WHERE.
- ❌ потому что COUNT возвращает целое число, а WHERE принимает только логические значения — error_text: WHERE принимает любое логическое условие, включая сравнение чисел — `stock > 0` работает с урока 8 «Основ». Дело не в типе, а в моменте выполнения: WHERE работает до того, как группы и агрегаты возникнут.

### Вопрос 2: В отчёте по категориям нужно учесть только товары дешевле 10000. Где писать условие `price < 10000`?

- ✅ в WHERE — свойство одной строки, проверяемое без знания о группе
<!-- практическое правило урока: условие по одной строке — WHERE, свойство группы — HAVING -->
- ❌ в HAVING — error_text: HAVING предназначен для условий на свойства целой группы — количество, сумму, среднее. Условие `price < 10000` проверяется по одному товару, поэтому его место в WHERE: так строки отсекаются до группировки.
- ❌ куда угодно — результат одинаков — error_text: результаты разные. WHERE отсекает дешёвые строки до группировки; вариант с HAVING потребовал бы агрегата вроде `HAVING MAX(price) < 10000` и решал бы другую задачу — «в категории нет ни одного дорогого товара», выкидывая категорию целиком.
- ❌ ни там ни там — фильтрация делается в SELECT через CASE — error_text: CASE в SELECT меняет отображение значений, а не состав строк (урок 7 «Начинающего»). Инструментов фильтрации два: WHERE — для строк, HAVING — для групп.

### Вопрос 3: В каком порядке логически выполняются WHERE и HAVING?

- ✅ WHERE — до формирования групп, HAVING — после
<!-- конвейер урока 6: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY -->
- ❌ оба до группировки — error_text: до группировки работает только WHERE (шаг 2 конвейера). HAVING — шаг 4, после GROUP BY: он и существует потому, что условия на агрегаты проверяемы только по готовым группам.
- ❌ HAVING раньше WHERE — error_text: это нарушает конвейер урока 6 «Начинающего»: FROM → WHERE → GROUP BY → HAVING. Синтаксически HAVING раньше тоже не написать — он стоит сразу после GROUP BY.
- ❌ порядок зависит от расположения условий в тексте запроса — error_text: логический порядок выполнения фиксирован и от текста не зависит. Текст запроса и конвейер обработки — разные вещи: WHERE в тексте всегда до GROUP BY, а HAVING — после.

### Вопрос 4: Можно ли в MySQL написать `HAVING avg_price > 3000` вместо `HAVING AVG(price) > 3000`, если avg_price — псевдоним из SELECT?

- ✅ можно — MySQL допускает псевдонимы SELECT в HAVING, но полная запись переносимее между СУБД
<!-- HAVING выполняется после SELECT, поэтому алиас доступен; не все СУБД так умеют -->
- ❌ нельзя — псевдонимы в HAVING запрещены стандартом SQL во всех СУБД — error_text: MySQL допускает обращение к псевдониму в HAVING, потому что HAVING выполняется после SELECT (конвейер урока 6). Запрещены псевдонимы в WHERE — он выполняется раньше SELECT.
- ❌ можно, но только если убрать GROUP BY — error_text: GROUP BY здесь ни при чём: доступность псевдонима в HAVING не зависит от группировки. А без GROUP BY агрегат сворачивал бы всю таблицу в одну строку — это другая задача.
- ❌ псевдоним доступен в WHERE, но не в HAVING — error_text: ровно наоборот: WHERE выполняется до SELECT, поэтому алиасы там недоступны (урок 6 «Начинающего»), а HAVING — после SELECT, и MySQL разрешает в нём алиасы.

### Вопрос 5: Какие категории попадут в результат запроса `SELECT category, SUM(stock) FROM products GROUP BY category HAVING SUM(stock) < 20;`?

- ✅ только те, у которых суммарный остаток всех товаров категории меньше 20
<!-- HAVING оценивает агрегат по группе целиком -->
- ❌ те, в которых есть хотя бы один товар с остатком меньше 20 — error_text: условие «есть товар с остатком меньше 20» — построчное, его место в WHERE (`WHERE stock < 20`), и решало бы оно другую задачу. HAVING оценивает SUM по всем строкам группы сразу.
- ❌ те, в которых товаров меньше 20 — error_text: количество товаров в группе — это COUNT(*), а не SUM(stock). Условие `HAVING COUNT(*) < 20` отбирало бы категории по числу позиций, а не по суммарному остатку.
- ❌ ни одной — SUM в HAVING недопустим — error_text: HAVING как раз создан для условий по агрегатным функциям — COUNT, SUM, AVG, MIN, MAX. Агрегат в HAVING — типовой паттерн этого урока.

### Задание 1: Категории с достаточным ассортиментом

HAVING: отбор категорий по количеству товаров в группе.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT category, COUNT(*) AS products FROM products GROUP BY category HAVING COUNT(*) >= 2 ORDER BY category; -->

**statement:**

Таблица `products` содержит десять товаров четырёх категорий. Выведите
только те категории, в которых не меньше двух товаров: категория
`category`, число товаров `products`. Строки отсортируйте по алфавиту
категорий.

**expected_result_text:**

Финальный SELECT возвращает три строки: мониторы (2), ноутбуки (2) и
периферия (5). Аксессуары с единственным товаром не проходят фильтр
HAVING и в результат не попадают.

**seed_sql:**

```sql
CREATE TABLE products (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0
);

INSERT INTO products (name, category, price, stock) VALUES
```
