## Материал

В прошлом уроке эффект индекса был показан «на секундомер» — сравнением времени выполнения запроса до и после `CREATE INDEX`. Такой способ работает для учебного эксперимента, но никуда не годится в реальной работе: секундомер не говорит, *почему* запрос быстрый или медленный, не показывает, какой именно индекс (если их несколько) СУБД выбрала, и не помогает, если после изменения запроса он внезапно замедлился без видимой причины. Для ответа на вопрос «как именно MySQL собирается выполнить этот запрос» существует команда `EXPLAIN` — она не выполняет запрос, а показывает **план** его выполнения, составленный оптимизатором.

### Что делает EXPLAIN

`EXPLAIN` ставится перед любым `SELECT` (а также перед `UPDATE`/`DELETE`/`INSERT ... SELECT` в современных версиях MySQL) и вместо результата запроса возвращает таблицу, описывающую, каким способом сервер планирует его выполнить:

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 42;
```

Важно зафиксировать сразу: `EXPLAIN` **не выполняет** сам запрос и не возвращает данные, которые бы вернул обычный `SELECT` — он показывает только план, составленный оптимизатором запросов (компонентом MySQL, который решает, в каком порядке соединять таблицы и какие индексы использовать, ещё до фактического чтения данных). У этого плана есть важное следствие: показанный план — это *намерение* оптимизатора на основе накопленной статистики о таблицах, а не гарантированно точное описание того, что произошло бы при полном исполнении на всех данных, — но на практике план оптимизатора почти всегда совпадает с реальным поведением сервера, и именно поэтому `EXPLAIN` — базовый рабочий инструмент, а не приближённая догадка.

### Столбцы плана: разбираем главное

Вывод `EXPLAIN` содержит по одной строке на каждую таблицу, участвующую в запросе (для запроса с несколькими `JOIN` строк будет несколько — план описывает порядок обращения к каждой из них). Разберём столбцы, важные для повседневной диагностики:

**`table`** — имя таблицы (или её алиас), к которой относится эта строка плана. В запросе с несколькими `JOIN` порядок строк в выводе показывает порядок, в котором сервер планирует обращаться к таблицам — это не обязательно тот порядок, в котором таблицы записаны в запросе: оптимизатор может решить, что эффективнее начать с другой таблицы.

**`type`** — тип доступа к таблице, самый важный столбец плана: он показывает, *каким способом* сервер собирается найти нужные строки. От лучшего к худшему для точечного поиска:

- `const` / `system` — таблица содержит не более одной подходящей строки (обычно поиск по первичному или уникальному ключу с константой) — быстрее не бывает;
- `eq_ref` — для каждой строки внешней таблицы находится ровно одна строка по уникальному индексу — типичный случай `JOIN` по первичному ключу;
- `ref` — поиск по неуникальному индексу, может найти несколько строк, но использует индекс, а не полное сканирование;
- `range` — поиск диапазона значений по индексу (`BETWEEN`, `<`, `>`, `IN` с несколькими значениями);
- `index` — сканируется **весь** индекс целиком (а не таблица), это дешевле полного сканирования таблицы, но всё же требует прохода по всем его записям;
- `ALL` — **полное сканирование таблицы** без единого индекса — ровно то, что было продемонстрировано в прошлом уроке как медленный вариант.

Увидеть `type = ALL` для большой таблицы в запросе, который выполняется часто, — почти всегда сигнал «здесь не хватает подходящего индекса» (если только запрос сознательно не должен читать почти все строки, о чём — четвёртый урок этого уровня).

**`key`** — имя индекса, который сервер фактически выбрал для этой таблицы (или `NULL`, если ни один индекс не подошёл — обычно вместе с `type = ALL`). Полезно сравнить `key` со столбцом `possible_keys`, который показывает все индексы, которые *теоретически подходили* по условию `WHERE`/`ON` — если `possible_keys` не пуст, а `key` показывает `NULL` или другой, не самый подходящий индекс, это повод разобраться, почему оптимизатор отклонил ожидаемый вариант (об этом — в третьем уроке этого уровня, где разбираются причины, по которым индекс может не сработать).

**`rows`** — оценка количества строк, которые сервер планирует прочитать для этой таблицы (не точное число, а статистическая оценка на основе накопленной информации о распределении данных). Резкое несоответствие между `rows` и реальным ожидаемым результатом запроса (например, план обещает прочитать миллион строк, а результат запроса — три строки) — характерный симптом отсутствия подходящего индекса: сервер вынужден проверить намного больше строк, чем в итоге попадёт в ответ.

**`Extra`** — дополнительные примечания о плане, среди которых особенно важны два:

- `Using filesort` — сервер не смог отсортировать результат «бесплатно» через порядок индекса и выполняет отдельную, дополнительную сортировку уже отобранных строк в памяти (или на диске, если строк слишком много). Для небольших результатов это не проблема, но для больших — заметный источник замедления, устранимый подходящим индексом (третий урок этого уровня разберёт, при каких условиях индекс избавляет от `filesort`);
- `Using temporary` — сервер создаёт временную таблицу для промежуточного хранения результатов (типично для некоторых сочетаний `GROUP BY`/`DISTINCT`/`UNION` без подходящего индекса) — тоже источник дополнительной работы, которого в ряде случаев можно избежать.

Ни `Using filesort`, ни `Using temporary` не являются сами по себе признаком ошибки в запросе — на маленьком результате они безвредны; тревожный сигнал — это их появление в сочетании с большим `rows` в плане того же запроса.

### Сквозной пример: читаем план целиком

Рассмотрим план запроса, соединяющего заказы с позициями:

```sql
EXPLAIN
SELECT o.id, oi.product_id, oi.quantity
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 42
ORDER BY o.created_at;
```

Без индекса по `orders.customer_id` типичный (упрощённый) план показал бы для таблицы `o` строку с `type = ALL`, `key = NULL` и большим значением `rows`, приблизительно равным общему числу строк в `orders` — сервер обязан проверить каждый заказ, чтобы найти те, что принадлежат клиенту 42. После создания `CREATE INDEX idx_orders_customer_id ON orders (customer_id);` (первый урок этого уровня) тот же план для таблицы `o` показал бы `type = ref`, `key = idx_orders_customer_id` и `rows`, приблизительно равное числу заказов именно этого клиента — на несколько порядков меньше. Для таблицы `oi` ожидаем `type = ref` по индексу внешнего ключа `order_id` (такой индекс MySQL создаёт автоматически для столбцов, участвующих в `FOREIGN KEY`, — двенадцатый урок уровня «Начинающий» вводил внешние ключи, но не упоминал явно, что они порождают индекс: это ровно тот механический эффект, который делает `JOIN` по внешнему ключу изначально дешёвым без специальных дополнительных действий).

### EXPLAIN ANALYZE: план и реальность одновременно

Начиная с MySQL 8.0.18 доступна расширенная форма — `EXPLAIN ANALYZE` — которая, в отличие от обычного `EXPLAIN`, **фактически выполняет** запрос и показывает не только предполагаемый оптимизатором план, но и реальное измеренное время выполнения каждого шага:

```sql
EXPLAIN ANALYZE
SELECT o.id, oi.product_id
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 42;
```

Вывод `EXPLAIN ANALYZE` организован как дерево вложенных шагов (в отличие от табличного `EXPLAIN`) и для каждого шага показывает предполагаемое и фактическое число строк, а также реальное время выполнения — это ценно именно тогда, когда обычный `EXPLAIN` показывает план, который *выглядит* правильным (использует нужный индекс), но запрос всё равно медленный: `EXPLAIN ANALYZE` помогает увидеть, на каком именно шаге в дереве уходит основное время. Поскольку `EXPLAIN ANALYZE` реально выполняет запрос, его не стоит использовать для тяжёлых пишущих операций или на продуктивной базе без осторожности — ровно так же, как не стоит бездумно гонять на проде любой дорогой аналитический `SELECT`.

### EXPLAIN — инструмент диагностики, а не генератор индексов

Важно с самого начала избежать ошибочного вывода «раз `EXPLAIN` показывает `type = ALL`, надо создать индекс». `EXPLAIN` только *показывает* текущий способ выполнения — решение, что с этим делать, требует понимания контекста: возможно, здесь действительно не хватает индекса (тема следующих уроков), а возможно, запрос отбирает такую большую долю таблицы, что полное сканирование — уже самый эффективный вариант, и никакой индекс здесь не поможет (сервер в такой ситуации сам, скорее всего, откажется от использования индекса, даже если он есть, — это разбирается в третьем уроке этого уровня). `EXPLAIN` даёт факты о плане; интерпретация этих фактов и выбор действия — отдельный навык, который курс будет развивать до самого капстоуна пятнадцатого урока этого уровня.

### Резюме

- `EXPLAIN` перед `SELECT` (и рядом других команд) показывает **план** выполнения запроса, составленный оптимизатором, не выполняя сам запрос.
- Ключевые столбцы плана: `table` (какая таблица), `type` (способ доступа: от лучшего `const`/`eq_ref`/`ref`/`range` до худшего `ALL` — полное сканирование), `key` (фактически выбранный индекс, в сравнении с `possible_keys`), `rows` (оценка числа читаемых строк), `Extra` (примечания, среди которых важны `Using filesort` и `Using temporary`).
- `type = ALL` на большой таблице в частом запросе — типичный сигнал недостающего индекса; резкое расхождение `rows` с ожидаемым размером результата — тоже.
- `EXPLAIN ANALYZE` (MySQL 8.0.18+) реально выполняет запрос и добавляет к плану фактическое измеренное время и число строк на каждом шаге — полезен, когда обычный `EXPLAIN` не объясняет реальную медлительность.
- `EXPLAIN` — инструмент диагностики: он показывает текущий способ выполнения, но не подсказывает автоматически правильное решение — интерпретация плана и выбор действия (индекс, переписывание запроса или ничего не менять) остаются за разработчиком.

- ✅ Показывает план выполнения запроса, составленный оптимизатором, не выполняя сам запрос

- ❌ Выполняет запрос и выводит время его выполнения — error_text: это способ «на секундомер» из прошлого урока, а не `EXPLAIN`. Замер времени не объясняет, почему запрос медленный и какой индекс выбрала СУБД. `EXPLAIN` сам запрос не выполняет и время не измеряет.
- ❌ Автоматически создаёт недостающие индексы для запроса — error_text: `EXPLAIN` — инструмент диагностики, а не генератор индексов. Он лишь показывает текущий способ выполнения; решение — создать индекс, переписать запрос или ничего не менять — принимает разработчик на основе чтения плана.
- ❌ Возвращает данные запроса вместе со строками статистики — error_text: `EXPLAIN` не возвращает данные запроса вообще. Вместо строк результата он возвращает строки плана — по одной на каждую таблицу запроса с описанием способа доступа к ней.

### Вопрос 2: В плане `EXPLAIN` для таблицы стоит `type = ALL`. Что это означает?

- ✅ Полное сканирование таблицы: строки ищутся без использования индексов
<!-- ALL — худший тип доступа; на большой таблице в частом запросе — сигнал недостающего индекса -->
- ❌ Сервер использует все индексы таблицы по очереди — error_text: `ALL` — наоборот, худший тип доступа: индексы не используются вовсе, сервер читает таблицу целиком. Использование индекса отражается другими значениями `type` — `ref`, `range`, `const` и так далее.
- ❌ «Все условия WHERE выполнены» — лучший из возможных типов — error_text: `type` описывает способ поиска строк, а не выполнение условий. В порядке качества типы идут от `const`/`eq_ref`/`ref`/`range`/`index` к `ALL` — то есть `ALL` находится в самом конце списка как наихудший.
- ❌ Запрос вернёт все строки таблицы, и это всегда ошибка проектирования — error_text: `type` показывает способ доступа, а не размер результата. Полное сканирование иногда — осознанно самое дешёвое решение, например когда запрос и должен вернуть большую долю строк таблицы; `ALL` — не всегда ошибка.

### Вопрос 3: Что показывает столбец `rows` в плане `EXPLAIN`?

- ✅ Оценку числа строк, которые сервер планирует прочитать для этой таблицы
<!-- rows — статистическая оценка чтения; резкое расхождение с размером результата — симптом -->
- ❌ Точное число строк в результате запроса — error_text: `rows` — оценка числа читаемых строк, причём до применения всех условий, а не размер конечного результата. Характерный симптом проблем как раз в обратном: план обещает прочитать миллион строк, а результат запроса — три строки.
- ❌ Общее число строк в таблице на момент выполнения `EXPLAIN` — error_text: такой оценкой `rows` был бы только для `type = ALL`. При доступе через индекс `rows` оценивает лишь строки, которые сервер собирается прочитать по этому индексу, — обычно многократно меньше размера таблицы.
- ❌ Число обращений к диску при выполнении запроса — error_text: `rows` — оценка объёма чтения строк, а не счётчик дисковых операций. Ввод-вывод в плане не отчётывается; фактические затраты каждого шага измеряет `EXPLAIN ANALYZE`.

### Вопрос 4: Что означает пометка `Using filesort` в столбце `Extra`?

- ✅ Сервер не смог использовать порядок индекса и выполняет отдельный шаг сортировки отобранных строк
<!-- filesort — дополнительная сортировка; опасна в сочетании с большим rows -->
- ❌ Файлы таблицы фрагментированы, требуется `OPTIMIZE TABLE` — error_text: `filesort` не имеет отношения к фрагментации файлов. Это внутренняя сортировка результата в памяти (или во временных файлах при её нехватке), выполняемая тогда, когда использовать готовый порядок индекса не удалось.
- ❌ Сервер отсортировал строки через индекс — это лучший случай — error_text: сортировка через порядок индекса не порождает `Using filesort` вовсе: строки читаются уже упорядоченными, отдельного шага сортировки нет. Пометка появляется именно когда такого «бесплатного» порядка не нашлось.
- ❌ Запрос завершится ошибкой: результат слишком велик для памяти — error_text: `Using filesort` — примечание к плану, а не ошибка. На небольших результатах дополнительная сортировка безвредна; тревожный сигнал — её сочетание с большой оценкой `rows` в том же плане.

### Вопрос 5: Чем `EXPLAIN ANALYZE` отличается от обычного `EXPLAIN`?

- ✅ Он фактически выполняет запрос и добавляет к плану реальное время и фактическое число строк каждого шага
<!-- ANALYZE выполняет запрос: дерево шагов + измерения; осторожно на проде -->
- ❌ Ничем, кроме более удобного табличного формата вывода — error_text: различие принципиальное: `EXPLAIN ANALYZE` выполняет запрос и измеряет фактические затраты каждого шага. Его вывод к тому же организован деревом вложенных шагов, а не таблицей, как у обычного `EXPLAIN`.
- ❌ Он показывает план после автоматического переписывания запроса оптимизатором — error_text: план оптимизатор составляет в обоих случаях. `ANALYZE` добавляет к плану фактические измерения — какое время и сколько строк дало реальное выполнение каждого шага, — а не «улучшенную версию» запроса.
- ❌ Он безопаснее для продуктивной базы, потому что не выполняет запрос — error_text: ровно наоборот: именно `EXPLAIN ANALYZE` выполняет запрос по-настоящему, поэтому для тяжёлых операций и на продуктивной базе его применяют с осторожностью. Обычный `EXPLAIN` запрос не выполняет.

## Практические задания

Каждое задание исполняется в собственной изолированной среде: сид-скрипт
задания создаёт таблицы с нуля, и наборы данных у заданий свои. Состав
может отличаться и от демо-таблиц материала, и от соседних заданий —
опирайтесь на таблицы, описанные в формулировке самого задания.

Во всех трёх заданиях план `EXPLAIN` уже прочитан за вас и приведён в
формулировке: ваша задача — устранить найденное узкое место созданием
нужного индекса. Так как оценки плана (`rows`, `filtered`) нестабильны
между прогонами, зачётным подтверждением служит детерминированный запрос
к системному каталогу `information_schema.STATISTICS` — таблице, в
которой сервер перечисляет все индексы: по одной строке на каждый
столбец каждого индекса (`SEQ_IN_INDEX` — позиция столбца в индексе,
`NON_UNIQUE` — `0` для уникального, `1` для неуникального).

### Задание 1: Узкое место в JOIN

Диагноз `type = ALL` на соединяемой таблице и его устранение индексом
по столбцу соединения.

<!-- Эталонное решение (для автора/бота-верификатора): CREATE INDEX idx_orders_customer_id ON orders (customer_id); SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE FROM information_schema.STATISTICS WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'orders' ORDER BY INDEX_NAME, SEQ_IN_INDEX; -->

**statement:**

Таблицы `customers` (четыре покупателя) и `orders` (восемь заказов).
Внешний ключ на `orders (customer_id)` **не** объявлен, поэтому
InnoDB не создал индекс по столбцу соединения. Частый отчёт:

```sql
SELECT c.name, o.id, o.total
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id
WHERE c.id = 3;
```

даёт в `EXPLAIN` для таблицы `o` строку с `type = ALL`, `key = NULL`
и `rows`, близким к полному размеру таблицы, — на каждый заказ
покупателя сервер перечитывает все строки `orders`. Устраните узкое
место:

1. Создайте индекс `idx_orders_customer_id` по столбцу
   `orders.customer_id`.
2. Финальной инструкцией (промежуточные не должны возвращать строки)
   подтвердите структуру индексов таблицы `orders` запросом к
   системному каталогу:

```sql
SELECT INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'orders'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

**expected_result_text:**

Финальный SELECT возвращает две строки: созданный неуникальный индекс
`idx_orders_customer_id` по столбцу `customer_id` (`NON_UNIQUE = 1`)
и уникальный первичный ключ `PRIMARY` по `id` (`NON_UNIQUE = 0`).
Строка `idx_orders_customer_id` первая: сортировка имён индексов
регистронезависимая (`i` раньше `p`).

**seed_sql:**

```sql

    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    city VARCHAR(50) NOT NULL
);

INSERT INTO customers (name, city) VALUES
    ('Ольга Кузнецова', 'Казань'),
    ('Дмитрий Романов', 'Москва'),
    ('Светлана Орлова', 'Новосибирск'),
    ('Артём Богданов', 'Самара');

CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    total DECIMAL(10,2) NOT NULL
);

INSERT INTO orders (customer_id, status, total) VALUES
    (3, 'paid', 12450.00),
    (1, 'pending', 3200.00),
    (3, 'shipped', 8700.50),

    (3, 'paid', 5400.25),
    (2, 'cancelled', 980.00),
    (3, 'pending', 22100.75),
    (1, 'paid', 7600.00);
```

**expected_rows:**

| INDEX_NAME            | SEQ_IN_INDEX | COLUMN_NAME  | NON_UNIQUE |
| --------------------- | ------------ | ------------ | ---------- |
