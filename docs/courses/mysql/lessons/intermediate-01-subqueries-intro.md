## Материал

На уровне «Начинающий» мы научились получать данные сразу из нескольких таблиц с помощью `JOIN`: он «сшивает» строки двух таблиц в одну широкую строку по условию `ON`. Но не любая задача укладывается в форму «взять строки одной таблицы и приклеить к ним подходящие строки другой». Иногда результат одного запроса нужен не как самостоятельный ответ, а как **промежуточный материал** для другого запроса: «список id клиентов, у которых средний чек выше, чем средний чек по всему магазину», «товары дороже, чем средняя цена в их категории», «заказы клиента, который живёт в том же городе, что клиент с id = 1». Здесь один запрос естественно распадается на два вложенных друг в друга: внутренний вычисляет некое значение или набор значений, а внешний использует их как условие. Такая вложенная конструкция называется **подзапросом** (subquery), и это тема данного урока.

### Что такое подзапрос

**Подзапрос** — это `SELECT`-запрос, размещённый внутри другого SQL-запроса: в `WHERE`, в `SELECT`, в `FROM` или даже внутри другого подзапроса. Внешний запрос называют **основным** (outer query), внутренний — **подзапросом** (subquery, inner query). MySQL сначала (концептуально) вычисляет подзапрос, получает его результат, а затем подставляет этот результат в основной запрос — как если бы вы сначала выполнили внутренний `SELECT` вручную, скопировали результат и вставили его в текст внешнего запроса.

Подзапросы классифицируют по тому, **что** они возвращают:

- **скалярный подзапрос** (scalar subquery) — ровно одно значение: одна строка, один столбец;
- **подзапрос-список** (multi-row, single column) — один столбец, несколько строк, обычно используется с `IN`, `ANY`, `ALL`;
- **табличный подзапрос** (table subquery, derived table) — несколько столбцов и несколько строк, используется в `FROM` как временная «виртуальная таблица».

Ниже разберём все три вида по порядку, от самого простого к самому мощному.

### Скалярный подзапрос: сравнение с одним вычисленным значением

Представим задачу: найти товары, чья цена выше средней цены по всему каталогу. Средняя цена — это одно число, которое само нужно вычислить агрегатной функцией `AVG` (восьмой урок уровня «Начинающий»). Раньше нам не хватало инструмента, чтобы одним запросом и вычислить среднее, и сразу же сравнить с ним каждую строку — пришлось бы выполнить два отдельных запроса и подставить число вручную. Скалярный подзапрос решает это одним запросом:

```sql
SELECT id, name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);
```

Внутренний запрос `(SELECT AVG(price) FROM products)` возвращает ровно одно число — среднюю цену по всем товарам. MySQL вычисляет его один раз и подставляет в условие `WHERE price > <число>`, как если бы вы написали конкретное значение, например `WHERE price > 8450.30`. Разница лишь в том, что число не захардкожено, а вычисляется динамически при каждом выполнении запроса — если в каталог добавят новые товары, среднее пересчитается автоматически.

Скалярный подзапрос можно использовать везде, где ожидается одно значение: не только после операторов сравнения (`=`, `>`, `<`, `>=`, `<=`, `<>`), но и в самом списке `SELECT`:

```sql
SELECT
    id,
    name,
    price,
    (SELECT AVG(price) FROM products) AS avg_price,
    price - (SELECT AVG(price) FROM products) AS price_diff
FROM products;
```

Здесь для каждой строки товара мы дополнительно выводим среднюю цену по каталогу и разницу конкретной цены со средней. Важная деталь: MySQL не обязан заново пересчитывать одинаковый подзапрос для каждой строки — оптимизатор способен вычислить его один раз, если подзапрос не зависит от текущей строки внешнего запроса (о зависимых, «коррелированных» подзапросах — в следующем уроке). Главное правило скалярного подзапроса: **если он возвращает больше одной строки, MySQL вернёт ошибку** (`Subquery returns more than 1 row`) — с точки зрения синтаксиса скалярный подзапрос обязан быть именно скалярным, и ответственность за это лежит на авторе запроса: если результат потенциально не единственен, нужно либо добавить агрегатную функцию, либо `LIMIT 1` с осмысленным `ORDER BY`, либо использовать другую форму подзапроса.

### Подзапрос-список: оператор IN с подзапросом

Второй уровня «Начинающий» показал `IN` со статическим списком значений: `WHERE city IN ('Москва', 'Казань')`. Гораздо чаще список, по которому фильтруют, сам является результатом другого запроса, а не набором значений, которые программист заранее знает и вписывает руками. Классический пример — найти клиентов, у которых **есть хотя бы один заказ**:

```sql
SELECT id, name, email
FROM customers
WHERE id IN (SELECT customer_id FROM orders);
```

Внутренний запрос `SELECT customer_id FROM orders` возвращает столбец из множества значений — идентификаторы клиентов, у которых есть хотя бы один заказ (одно и то же значение может повторяться, если у клиента несколько заказов, но для `IN` это не важно — важна лишь принадлежность множеству). Внешний запрос отбирает из `customers` только те строки, чей `id` встречается среди этих значений.

Обратная задача — клиенты **без единого заказа** — решается оператором `NOT IN`:

```sql
SELECT id, name, email
FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);
```

Здесь стоит сделать важную оговорку про `NULL`, которая часто ловит новичков. Если хотя бы одна строка результата подзапроса содержит `NULL` (например, `customer_id` в какой-то строке `orders` оказался `NULL`), то `NOT IN` начинает вести себя неожиданно: сравнение любого значения с `NULL` даёт `NULL` (а не `TRUE`/`FALSE`, как мы разбирали в одиннадцатом уроке уровня «Основы»), и если хотя бы один элемент множества — `NULL`, весь результат `NOT IN` для **всех** строк превращается в `NULL`, то есть ни одна строка не пройдёт фильтр — запрос молча вернёт пустой результат, хотя по смыслу должен был вернуть клиентов без заказов. `IN` от той же проблемы страдает меньше (если искомое значение находится среди «нормальных» элементов списка, `NULL` в списке не мешает получить `TRUE`), но при использовании `NOT IN` с подзапросом всегда стоит убедиться, что столбец подзапроса гарантированно не содержит `NULL` — либо добавить в подзапрос условие `WHERE customer_id IS NOT NULL`, либо (что мы разберём в следующем уроке) заменить `NOT IN` на `NOT EXISTS`, которая с `NULL` ведёт себя предсказуемо.

Помимо `IN`/`NOT IN`, для подзапросов-списков существуют операторы `ANY` и `ALL`: `price > ALL (SELECT price FROM products WHERE category_id = 3)` означает «цена больше, чем **любая** цена в категории 3» (то есть больше максимальной), а `price > ANY (...)` — «цена больше, чем **хотя бы одна** цена в категории» (то есть больше минимальной). Эти операторы встречаются реже, чем `IN`, потому что почти всегда их можно заменить более явной и читаемой конструкцией через `MAX`/`MIN` в скалярном подзапросе, но знать о их существовании полезно — вы можете встретить их в чужом коде.

### Табличный подзапрос: производная таблица в FROM

Третья форма — подзапрос, который возвращает не одно значение и не один столбец, а полноценный набор строк с несколькими столбцами, и используется не в `WHERE`, а прямо в `FROM`, как если бы это была обычная таблица. Такую конструкцию называют **производной таблицей** (derived table).

Представим, что нам нужны только те категории, где больше пяти товаров, а из них — вывести название категории и количество товаров, отсортировав по количеству. Можно решить это через `GROUP BY`/`HAVING` (девятый-десятый уроки уровня «Начинающий») — и в простом случае так и стоит делать. Но если после подсчёта нужна дополнительная обработка результата — например, соединить эти агрегированные данные с другой таблицей, — удобно сначала оформить агрегацию как отдельную производную таблицу:

```sql
SELECT cat.name AS category_name, stats.products_count
FROM (
    SELECT category_id, COUNT(*) AS products_count
    FROM products
    GROUP BY category_id
    HAVING COUNT(*) > 5
) AS stats
INNER JOIN categories cat ON cat.id = stats.category_id
ORDER BY stats.products_count DESC;
```

Здесь внутренний запрос в скобках — обычный `SELECT ... GROUP BY ... HAVING ...`, который мы уже умели писать. Разница в том, что он не выполняется отдельно и не возвращает результат пользователю — он встроен прямо в `FROM` и **обязан иметь псевдоним** (`AS stats`), потому что MySQL должен как-то называть эту временную таблицу, чтобы к ней можно было обращаться дальше в запросе (например, в `INNER JOIN ... ON` и в `ORDER BY`). Без псевдонима MySQL вернёт синтаксическую ошибку — это единственное синтаксическое требование, которое отличает производную таблицу от «просто скобок вокруг запроса».

Мысленная модель здесь простая: производная таблица — это именно то, чем кажется по названию, — обычная таблица, только не сохранённая физически на диске, а вычисленная «на лету» непосредственно перед выполнением внешнего запроса и существующая ровно на время его выполнения. Всё, что мы умеем делать с обычной таблицей после `FROM` — `JOIN` к ней, `WHERE` по её столбцам, обращение по алиасу, — работает и с производной таблицей одинаково.

### Подзапрос или JOIN: как выбирать

У опытного взгляда часто возникает вопрос: то, что мы сделали через `IN (SELECT ...)`, можно было получить и через `JOIN` с `DISTINCT`. Это правда — многие задачи решаются обоими способами, и в них есть смысловая разница:

- `JOIN` **соединяет** строки двух таблиц горизонтально: если у клиента три заказа, `INNER JOIN` даст три строки клиента (по одной на каждый заказ) — что уместно, когда данные заказа тоже нужны в результате.
- Подзапрос с `IN`/`EXISTS` только **проверяет принадлежность или существование**, не добавляя данных из второй таблицы в результат: клиент с тремя заказами всё равно останется одной строкой в результате, потому что нас интересует только сам факт наличия заказов, а не их детали.

Отсюда практическое правило: если из второй таблицы в итоге не нужны никакие столбцы, а нужен только факт «есть/нет» или сравнение с агрегатом — используйте подзапрос, он точнее выражает намерение и не создаёт риска случайного размножения строк, о котором мы говорили в шестнадцатом уроке уровня «Начинающий» (там размножение строк после `JOIN` с `order_items` потребовало `COUNT(DISTINCT ...)` — с подзапросом эта проблема просто не возникает). Если же данные из второй таблицы нужны в результате — используйте `JOIN`.

### Резюме

- **Подзапрос** — `SELECT`, вложенный в другой запрос: в `WHERE`, в список `SELECT` или в `FROM`; выполняется как самостоятельный шаг, результат которого подставляется в основной запрос.
- **Скалярный подзапрос** возвращает ровно одно значение и используется везде, где ожидается одно число или строка (после `=`, `>` и других операторов сравнения, в списке `SELECT`); возврат более одной строки — ошибка выполнения.
- **Подзапрос-список** (один столбец, много строк) используется с `IN`/`NOT IN`; при `NOT IN` нужно следить за `NULL` в результате подзапроса — он может незаметно «обнулить» весь результат фильтрации.
- **Производная таблица** — подзапрос с несколькими столбцами и строками, используемый прямо в `FROM`; обязательно требует псевдонима и далее ведёт себя как обычная таблица — к ней применимы `JOIN`, `WHERE`, обращение по алиасу.
- Подзапрос уместен, когда из второй таблицы нужен только факт принадлежности/существования или агрегированное значение, а не сами данные; когда нужны конкретные столбцы второй таблицы — предпочтительнее `JOIN`.
- Подзапросы — не отдельная «экзотическая» тема, а способ **композиции**: сложный запрос собирается из более простых, уже знакомых `SELECT`-ов, вложенных друг в друга. Эта идея композиции будет развиваться на протяжении всего уровня «Средний» — в следующем уроке подзапросы научатся «заглядывать» в каждую строку внешнего запроса (коррелированные подзапросы), а позже похожую роль возьмут на себя более читаемые CTE.

## Теоретические задания

### Вопрос 1: Скалярный подзапрос, использованный в `WHERE` после оператора сравнения, вернул две строки. Что сделает MySQL?

- ✅ Завершит запрос ошибкой «Subquery returns more than 1 row» (ошибка 1242)
<!-- скалярный подзапрос обязан возвращать ровно одно значение; две строки — ошибка выполнения -->
- ❌ Возьмёт первую из двух строк и продолжит выполнение — error_text: скалярный подзапрос обязан возвращать ровно одно значение, и MySQL не выбирает «какую-нибудь» строку из нескольких — запрос прерывается ошибкой 1242. Если результат потенциально не единственен, добавьте агрегат (`MAX`, `MIN`) или `LIMIT 1` с осмысленным `ORDER BY`.
- ❌ Возьмёт минимальное из двух значений — error_text: «тихого» агрегирования не происходит: выбор минимума — это работа явного `MIN` внутри подзапроса, который сам делает результат скалярным. Без него две строки — та же ошибка 1242.
- ❌ Вернёт пустой результат — error_text: пустой результат дал бы внешний запрос, если бы условие `WHERE` не выполнилось ни для одной строки. Но до фильтра дело не дойдёт: MySQL прервёт выполнение ошибкой 1242 сразу, как подзапрос вернёт две строки.

### Вопрос 2: Запрос `SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders)`. Среди строк `orders` есть строка с `customer_id = NULL`. Что вернёт запрос?

- ✅ Пустой результат: сравнение со списком, содержащим NULL, даёт NULL, и ни одна строка не проходит фильтр
<!-- ловушка NOT IN: один NULL в списке «обнуляет» весь результат фильтрации -->
- ❌ Клиентов, у которых нет ни одного заказа — error_text: именно этого ждут от запроса по смыслу, но NULL в списке «обнуляет» фильтр: `NOT IN` для каждой строки даёт NULL, а NULL не проходит `WHERE` (NULL-семантика — урок 11 уровня «Основы»). Лечение — `WHERE customer_id IS NOT NULL` внутри подзапроса или `NOT EXISTS` из следующего урока.
- ❌ Ошибку выполнения — error_text: NULL в списке значений синтаксически допустим, ошибки не будет. Запрос «молча» вернёт ноль строк — в этом и коварство ловушки: программа выглядит правильной, но ничего не находит.
- ❌ Все строки таблицы `customers` — error_text: NULL в трёхзначной логике — не TRUE и не FALSE (урок 11 уровня «Основы»), поэтому вариант «условие всегда истинно» неверен: строки, для которых `NOT IN` дал NULL, отбрасываются фильтром, как и строки с FALSE.

### Вопрос 3: Что MySQL требует от подзапроса в `FROM` (производной таблицы)?

- ✅ Обязательный псевдоним: без имени MySQL не сможет обращаться к временному результату в остальной части запроса
<!-- единственное синтаксическое требование, отличающее производную таблицу от «просто скобок вокруг SELECT» -->
- ❌ Ничего: скобок вокруг SELECT достаточно — error_text: без псевдонима MySQL отклоняет запрос синтаксической ошибкой («Every derived table must have its own alias»). Псевдоним — то единственное, что отличает производную таблицу от «просто скобок»: серверу нужно имя, по которому обращаться к вычисленному набору строк в `JOIN`, `WHERE` и `ORDER BY`.
- ❌ Внутри производной таблицы обязателен `GROUP BY` или агрегатная функция — error_text: содержимым производной таблицы может быть любой `SELECT`: с `GROUP BY`, без него, с `JOIN`, с `WHERE`. Обязателен только псевдоним, а не агрегация.
- ❌ Псевдоним нужен, только если к производной таблице будет `JOIN` — error_text: псевдоним обязателен всегда, даже в простейшем `SELECT ... FROM (SELECT ...) AS t` без единого соединения. Требование — про имя таблицы, а не про способы её дальнейшего использования.

### Вопрос 4: У клиента Анны три заказа. Чем отличается вывод списка «клиенты с заказами» через `IN (SELECT customer_id FROM orders)` от `INNER JOIN orders`?

- ✅ `IN` вернёт одну строку Анны (важен факт принадлежности), `INNER JOIN` — три строки (по одной на каждую пару клиент–заказ)
<!-- IN проверяет принадлежность и не размножает строки; JOIN соединяет по парам -->
- ❌ Оба вернут по одной строке — error_text: `JOIN` соединяет строки по парам: три заказа Анны дают три строки результата с повторением столбцов клиента. Одна строка при любом числе заказов — свойство `IN`, который проверяет только принадлежность множеству.
- ❌ Оба вернут по три строки — error_text: размножение строк — эффект `JOIN`. Подзапрос с `IN` не добавляет столбцов `orders` в результат, поэтому Анна остаётся одной строкой; три строки дал бы только `JOIN`.
- ❌ `IN` вернёт три строки, а `INNER JOIN` — одну — error_text: ровно наоборот: `JOIN` «ширеет» по парам клиент–заказ и даёт строку на каждый заказ, а `IN` отвечает только на вопрос «есть заказы или нет» — одна строка на клиента.

### Вопрос 5: Что означает условие `price > ALL (SELECT price FROM products WHERE category_id = 3)`?

- ✅ Цена больше каждой цены категории 3, то есть строго больше максимальной цены этой категории
<!-- ALL: сравнение со всеми элементами списка; > ALL эквивалентен «больше максимума» -->
- ❌ Цена больше хотя бы одной цены категории 3 — error_text: «хотя бы одна» — это `ANY`: `> ANY` истинен, когда значение больше минимальной цены категории. `ALL` строже: значение должно превышать каждый элемент списка, включая максимальный.
- ❌ Цена равна максимальной цене категории 3 — error_text: сравнение строгое (`>`), равенство не проходит. «Больше всех цен» означает строго больше максимума; сам максимум условию не удовлетворяет — для равенства нужен был бы `>= ALL`.
- ❌ Цена больше средней цены категории 3 — error_text: сравнение со средней — это скалярный подзапрос `> (SELECT AVG(price) ...)`. `ALL` сравнивает значение со всеми элементами списка по отдельности, а не со сводной величиной по ним.

### Задание 3: Крупные заказы через производную таблицу

Производная таблица в `FROM` с агрегатом, обязательным псевдонимом и

<!-- Эталонное решение (для автора/бота-верификатора): SELECT t.order_id, c.name AS customer_name, t.order_total FROM (SELECT o.id AS order_id, o.customer_id, SUM(oi.quantity * oi.price) AS order_total FROM orders o INNER JOIN order_items oi ON oi.order_id = o.id GROUP BY o.id, o.customer_id) AS t INNER JOIN customers c ON c.id = t.customer_id WHERE t.order_total > 10000 ORDER BY t.order_total DESC; -->

`customer_name`, `order_total`. Отсортируйте по убыванию `order_total`.
