## Материал

В конце прошлого урока мы упёрлись в ограничение `INNER JOIN`: он показывает только те строки, для которых нашлось совпадение **в обеих** таблицах, — клиент без единого заказа полностью исчезал из результата. Но часто ровно противоположная задача бывает не менее важной: «показать всех клиентов, включая тех, у кого пока нет заказов» или «найти товары, которые ещё никогда не заказывали». Для таких задач нужен другой вид соединения — **внешнее** (outer) соединение, конкретно `LEFT JOIN` и `RIGHT JOIN`.

### LEFT JOIN: сохраняем все строки левой таблицы

`LEFT JOIN` (полное название — `LEFT OUTER JOIN`, слово `OUTER` в MySQL можно не писать явно, оно подразумевается) соединяет две таблицы так же, как `INNER JOIN` — по условию `ON`, — но с одним принципиальным отличием: **все** строки левой таблицы (то есть указанной в `FROM`, до слова `JOIN`) попадают в результат **независимо** от того, нашлось ли для них совпадение в правой таблице. Если совпадение находится — столбцы правой таблицы заполняются реальными значениями, как в `INNER JOIN`. Если совпадения **нет** — строка левой таблицы всё равно попадает в результат, а все столбцы правой таблицы получают значение `NULL`.

Возьмём задачу «показать всех клиентов вместе с количеством их заказов, включая клиентов без единого заказа»:

```sql
SELECT c.name, o.id AS order_id, o.created_at
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;
```

Для клиента, у которого есть, скажем, три заказа, в результате появятся три строки — по одной на каждый заказ, с реальными `order_id` и `created_at`, в точности как в `INNER JOIN`. Но для клиента без единого заказа появится **одна** строка, где `c.name` — реальное имя клиента, а `o.id` и `o.created_at` — оба `NULL`, потому что для этой строки левой таблицы не нашлось ни одной подходящей строки в правой. Именно это и требовалось: клиент не пропал из результата только из-за отсутствия заказов.

### Классическая задача LEFT JOIN: анти-джойн — найти строки без пары

Одно из самых частых и практически ценных применений `LEFT JOIN` — найти строки одной таблицы, для которых **нет вообще ни одного** совпадения в другой таблице, — эту технику часто называют **анти-джойном** (anti-join), хотя формального отдельного оператора с таким названием в SQL нет — это просто прием на основе `LEFT JOIN`. Ключевая идея: раз при отсутствии совпадения все столбцы правой таблицы становятся `NULL`, значит, чтобы отобрать именно строки без пары, достаточно после `LEFT JOIN` добавить условие `WHERE правая_таблица.любой_столбец IS NULL` (обычно для этого удобно брать столбец первичного ключа правой таблицы, потому что он никогда не бывает `NULL` для реально совпавших строк):

```sql
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

Этот запрос найдёт именно тех клиентов, у которых **нет ни одного** заказа: для них `o.id` не может быть ничем иным, кроме `NULL`, — ведь если хотя бы одно совпадение нашлось бы, `o.id` содержал бы реальный, не-`NULL` идентификатор существующего заказа. Аналогично можно найти товары, которые ещё никогда не заказывали:

```sql
SELECT p.id, p.name
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.id
WHERE oi.id IS NULL;
```

Такая техника — прямая практическая альтернатива более явной по смыслу, но пока не изученной конструкции `NOT EXISTS` (её мы разберём на уровне «Средний»); на уровне «Начинающий» именно `LEFT JOIN ... WHERE ... IS NULL` — стандартный, широко используемый способ решить задачу «найти строки без связанной пары».

### RIGHT JOIN: то же самое, но с приоритетом у правой таблицы

`RIGHT JOIN` (полностью — `RIGHT OUTER JOIN`) работает симметрично `LEFT JOIN`, но сохраняет все строки **правой** таблицы (указанной после `JOIN`), а не левой:

```sql
SELECT c.name, o.id AS order_id
FROM orders o
RIGHT JOIN customers c ON o.customer_id = c.id;
```

Этот запрос эквивалентен предыдущему примеру с `LEFT JOIN customers c ... FROM orders o`, только сами таблицы в `FROM`/`JOIN` переставлены местами. На практике `RIGHT JOIN` используется заметно **реже**, чем `LEFT JOIN` — почти любой запрос с `RIGHT JOIN` можно переписать через `LEFT JOIN`, просто поменяв порядок таблиц в `FROM` и после `JOIN`, и большинство разработчиков предпочитают именно этот, единый стиль (всегда `LEFT JOIN`, никогда `RIGHT JOIN`) для единообразия и предсказуемости чтения кода: при взгляде на длинную цепочку из нескольких `LEFT JOIN` подряд сразу ясно, что «главная», отправная таблица — первая после `FROM`, а все присоединённые таблицы — дополнительные и могут не иметь совпадений. Знать `RIGHT JOIN` полезно для чтения чужого кода, но при написании нового кода рекомендуется по умолчанию выбирать `LEFT JOIN`.

### Критически важный нюанс: условие в ON и условие в WHERE — не одно и то же

При использовании `LEFT JOIN` разница между условием, помещённым в `ON`, и условием, помещённым в `WHERE`, становится не просто стилистической, а **меняющей результат запроса**. Рассмотрим задачу: показать всех клиентов вместе с их заказами, но только теми заказами, что оформлены в статусе `'delivered'` — при этом клиенты без единого доставленного заказа всё равно должны остаться в результате (просто без строк заказов).

Первый вариант — условие о статусе внутри `ON`:

```sql
SELECT c.name, o.id AS order_id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'delivered';
```

Здесь условие `o.status = 'delivered'` — часть самого условия соединения. Логика получается такая: строка `orders` присоединяется к строке `customers` только если совпадает `customer_id` **и** статус — `'delivered'`. Если у клиента есть заказы, но ни один из них не в статусе `'delivered'`, ни один из них не «подходит» под условие `ON` — и, поскольку это `LEFT JOIN`, клиент всё равно останется в результате одной строкой, но с `o.id = NULL` и `o.status = NULL` (условие соединения не нашло пары, и сработало базовое поведение `LEFT JOIN` — сохранить левую строку с `NULL` вместо правой).

Второй, внешне похожий, но принципиально другой вариант — то же условие о статусе, но в `WHERE`:

```sql
SELECT c.name, o.id AS order_id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'delivered';
```

Здесь `LEFT JOIN` сначала полностью выполняется без учёта статуса — присоединяются **все** заказы каждого клиента, независимо от статуса, а клиенты без заказов получают строку с `NULL`. И только **после** этого, уже по готовому расширенному набору строк, применяется `WHERE o.status = 'delivered'`. Но у клиента без заказов `o.status` — это `NULL`, а условие `NULL = 'delivered'` (мы помним это из одиннадцатого урока «Основ») даёт «неизвестно», а не `TRUE`, и такая строка отбрасывается `WHERE`. В результате **все** клиенты без единого доставленного заказа (включая тех, у кого заказы есть, но не в статусе `'delivered'`, и тех, у кого заказов вовсе нет) полностью пропадают из результата — то есть `WHERE` фактически «превращает» `LEFT JOIN` обратно в поведение, эквивалентное `INNER JOIN`, полностью убивая смысл, ради которого мы выбрали именно `LEFT JOIN`.

Это одна из самых частых и самых незаметных ошибок при работе с `LEFT JOIN`: разработчик хочет «отфильтровать» результат по столбцу присоединённой таблицы, интуитивно пишет условие в привычное место — `WHERE`, — и неожиданно для себя вообще теряет все строки без совпадения, которые он специально хотел сохранить, выбрав `LEFT JOIN` вместо `INNER JOIN`. Практическое правило, которое стоит запомнить твёрдо: **условия, описывающие, какие строки правой таблицы должны участвовать в самом соединении** (не отбрасывая при этом строки левой таблицы без пары), помещаются в `ON`; **условия, отбрасывающие уже готовые, полностью собранные строки результата** (включая те случаи, где такое отбрасывание намеренно уберёт и строки с `NULL`, полученные из-за отсутствия пары), помещаются в `WHERE`.

### Резюме

- `LEFT JOIN` сохраняет **все** строки левой (первой по порядку в запросе) таблицы, даже если для них не нашлось совпадения в правой таблице — недостающие столбцы правой таблицы заполняются `NULL`.
- `RIGHT JOIN` — то же самое, но приоритет отдаётся правой таблице; на практике используется реже, обычно предпочитают `LEFT JOIN` с таблицами, переставленными местами, для единообразия стиля.
- Классическая техника анти-джойна: `LEFT JOIN ... WHERE правая.столбец IS NULL` находит строки левой таблицы, для которых в правой таблице нет вообще ни одной пары.
- Условие, помещённое в `ON` вместе с условием соединения, ограничивает, **какие** строки правой таблицы участвуют в соединении, но не убирает строки левой таблицы без пары.
- То же условие, помещённое в `WHERE`, применяется уже **после** формирования соединения и может непреднамеренно отбросить строки левой таблицы, для которых правая часть оказалась `NULL` из-за отсутствия пары — эффективно превращая `LEFT JOIN` обратно в поведение `INNER JOIN`.
- Практическое правило: условие о том, каким должно быть совпадение — в `ON`; условие о том, что должно остаться в итоговом результате после соединения — в `WHERE`; смешивать их местами — частый источник трудноуловимых ошибок.

## Теоретические задания

### Вопрос 1: Чем `LEFT JOIN` в `FROM customers c LEFT JOIN orders o ON o.customer_id = c.id` отличается от `INNER JOIN`?

- ✅ Все строки `customers` попадают в результат; если заказов у клиента нет — столбцы `orders` заполняются `NULL`
<!-- внешнее соединение: левая таблица сохраняется целиком, правая — по ON -->
- ❌ Все строки `orders` попадают в результат, даже без совпадения в `customers` — error_text: это описание `RIGHT JOIN` — сохраняется таблица, стоящая после `JOIN`. В `LEFT JOIN` сохраняется левая таблица из `FROM` — здесь `customers`.
- ❌ Ничем: оба оставляют только совпавшие пары строк — error_text: «только совпавшие» — формула `INNER JOIN` урока 13. Весь смысл `LEFT JOIN` — сохранить и непарные строки левой таблицы, дополнив их `NULL`.
- ❌ Строки `customers` без заказов удаляются из таблицы физически — error_text: `JOIN` — операция чтения: он собирает временный результат и не меняет данные в таблицах. И «удалять» тут нечего — `LEFT JOIN` как раз сохраняет такие строки в результате.

### Вопрос 2: Какой запрос найдёт клиентов, у которых нет ни одного заказа?

- ✅ `FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.id IS NULL`
<!-- анти-джойн: NULL в правой части после LEFT JOIN означает «пары не нашлось» -->
- ❌ `FROM customers c INNER JOIN orders o ON o.customer_id = c.id` — error_text: `INNER` оставляет только тех, у кого заказы есть, — мы получим противоположность искомого. Клиенты без заказов в результат не попадают в принципе.
- ❌ `FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.id = NULL` — error_text: сравнение `= NULL` всегда даёт «неизвестно», а не «истина» — это ключевая тема урока 11 уровня «Основы». Для проверки отсутствия значения существует только `IS NULL`.
- ❌ `FROM customers c LEFT JOIN orders o ON o.customer_id = c.id` без `WHERE` — error_text: без фильтра вернутся все клиенты — и с заказами, и без. Нужен второй шаг анти-джойна: отобрать строки, где правая часть — `NULL`, то есть `WHERE o.id IS NULL`.

### Вопрос 3: В `FROM customers c LEFT JOIN orders o ON o.customer_id = c.id` добавили `WHERE o.status = 'delivered'`. Что произойдёт с клиентом, у которого нет ни одного заказа?

- ✅ Он исчезнет из результата: `NULL = 'delivered'` даёт «неизвестно», и `WHERE` отбросит эту строку
<!-- фильтр по правой таблице в WHERE превращает LEFT JOIN в INNER по эффекту -->
- ❌ Он останется в результате со значением `NULL` в `o.status` — error_text: так было бы, будь условие в `ON`: там оно решает, какие заказы присоединяются, и строка без пары сохраняется. Но `WHERE` выполняется после соединения и отбрасывает строки с «неизвестно» — эффект `LEFT JOIN` уничтожен.
- ❌ Запрос завершится ошибкой сравнения `NULL` со строкой — error_text: сравнение с `NULL` — не ошибка, а «неизвестно» в трёхзначной логике урока 1 уровня «Начинающий». Строка просто не пройдёт фильтр, без всяких ошибок.
- ❌ Ничего не изменится: `WHERE` выполняется до соединения, и `LEFT JOIN` потом вернёт клиента — error_text: порядок обратный: сначала `FROM` вместе с соединением собирает строки, затем `WHERE` фильтрует готовые строки — урок 6 уровня «Начинающий». Поэтому «пустая» пара с `NULL` в `o.status` отбрасывается.

### Вопрос 4: Чем отличается условие `o.status = 'delivered'` в `ON` от того же условия в `WHERE` при `LEFT JOIN`?

- ✅ В `ON` оно решает, какие заказы участвуют в соединении, — клиент без подходящих заказов остаётся с `NULL`; в `WHERE` оно отбрасывает готовые строки, включая «пустые» пары
<!-- ON ограничивает участников соединения, WHERE — итоговые строки результата -->
- ❌ Разницы нет: `ON` и `WHERE` в MySQL взаимозаменяемы — error_text: на `INNER JOIN` результат часто совпадает, но на `LEFT JOIN` это два разных запроса: условие по правой таблице в `WHERE` непреднамеренно превращает внешнее соединение во внутреннее — главная тема этого урока.
- ❌ Условие в `ON` выполняется быстрее, потому что до `WHERE` дело не доходит — error_text: разница не в скорости, а в результате: `WHERE` выполняется в любом случае — уже над собранными строками. Вопрос урока — какие строки доживут до финального результата.
- ❌ В `ON` условие можно писать только по столбцам правой таблицы, а в `WHERE` — только по левой — error_text: ограничений нет: и в `ON`, и в `WHERE` допустимы условия по любым таблицам. Выбор места — про смысл: кто участвует в соединении или что остаётся в результате.

### Вопрос 5: Что гарантирует `FROM orders o RIGHT JOIN customers c ON o.customer_id = c.id`?

- ✅ В результат попадут все строки `customers`, даже те, у которых нет заказов
<!-- правое внешнее соединение: сохраняется таблица после JOIN -->
- ❌ В результат попадут все строки `orders`, даже без совпадения в `customers` — error_text: сохраняется правая таблица — та, что после `JOIN`, то есть `customers`. Строки `orders` без пары здесь не сохраняются: это была бы формула `LEFT JOIN`.
- ❌ В результат попадут строки обеих таблиц, включая непарные с обеих сторон — error_text: это `FULL OUTER JOIN`, которого в MySQL нет. `RIGHT JOIN` сохраняет только правую таблицу; непарные строки левой теряются.
- ❌ Запрос эквивалентен `INNER JOIN`, потому что `orders` записана в `FROM` первой — error_text: порядок в `FROM` не превращает внешнее соединение во внутреннее. `RIGHT JOIN` читается по положению таблицы после `JOIN` — сохраняется `customers` с NULL-подстановкой слева.
