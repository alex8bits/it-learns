## Материал

В первом уроке мы уже написали свой первый запрос `SELECT name, price FROM products;`, но не разбирали, почему он выглядит именно так, что можно менять, а что — нет. Пора закрыть эти пробелы: разберём правила синтаксиса SQL, поговорим о том, как правильно оформлять запросы, и расширим `SELECT` командой `LIMIT`, которая ограничивает количество возвращаемых строк.

### SQL — не язык программирования в привычном смысле

Прежде чем разбирать конкретные правила, стоит понять природу SQL. В отличие от языков программирования типа Python или JavaScript, где вы описываете последовательность действий (цикл, условие, изменение переменной), SQL — **декларативный** язык: вы описываете *результат*, который хотите получить, а не алгоритм его получения. Фраза `SELECT name, price FROM products` читается почти как обычное предложение: «выбери [name, price] из [products]» — и это не случайность, SQL был спроектирован в 1970-х годах так, чтобы быть максимально близким к естественному языку и понятным даже без специального образования в программировании.

Эта особенность объясняет, почему в SQL много «слов», а не скобок и операторов, как в других языках, и почему структура запроса напоминает структуру предложения с более-менее фиксированным порядком частей.

### Анатомия запроса SELECT

Базовая форма запроса на чтение данных выглядит так:

```sql
SELECT столбец1, столбец2
FROM таблица;
```

У этой конструкции есть несколько обязательных частей:

- **`SELECT`** — ключевое слово, указывающее, что мы хотим *получить* данные (в противоположность, например, `INSERT`, который данные *добавляет* — с этой командой мы познакомимся в следующем уроке).
- **Список столбцов** — что именно нужно вернуть. Столбцы перечисляются через запятую, в том порядке, в котором они должны появиться в результате. Порядок столбцов в запросе не обязан совпадать с порядком столбцов в самой таблице — вы вольны выбирать и переставлять их как угодно.
- **`FROM`** — ключевое слово, после которого указывается имя таблицы — источник данных.
- **Точка с запятой `;`** — символ конца команды. Формально в консольном клиенте `mysql` именно точка с запятой сигнализирует «команда завершена, можно выполнять»; без неё клиент будет ждать продолжения ввода. В некоторых графических клиентах точка с запятой не обязательна для одной команды, но её всегда стоит ставить — это часть стандарта SQL и делает код переносимым между разными способами выполнения.

Если нужно получить **все столбцы** таблицы, а не перечислять их по одному, используется символ звёздочки `*`:

```sql
SELECT *
FROM products;
```

Это работает, но у такого подхода есть недостаток, который стоит осознавать с самого начала: `SELECT *` возвращает все столбцы таблицы, включая те, что вам сейчас не нужны, — это увеличивает объём передаваемых данных и делает код менее явным (человек, который читает запрос, не понимает, какие именно столбцы использует приложение дальше). Кроме того, если позже в таблицу добавят новый столбец, `SELECT *` начнёт возвращать и его — это может неожиданно повлиять на код, который обрабатывает результат. Поэтому на практике, особенно в реальных приложениях, принято явно перечислять нужные столбцы, а `SELECT *` использовать только для быстрого, разового просмотра данных «что там вообще есть в таблице».

### Регистр ключевых слов

Один из первых вопросов новичка: обязательно ли писать `SELECT` заглавными буквами? Технически — нет. MySQL нечувствителен к регистру ключевых слов: `SELECT`, `select` и `SeLeCt` будут работать абсолютно одинаково. То же касается `FROM`, `WHERE`, `LIMIT` и всех остальных ключевых слов SQL.

Тем не менее в профессиональной практике сложилось устойчивое соглашение: **ключевые слова пишут заглавными буквами**, а имена таблиц и столбцов — обычным регистром (как они были созданы):

```sql
SELECT name, price
FROM products;
```

Это не требование языка, а вопрос читаемости кода: заглавные ключевые слова визуально выделяются на фоне названий таблиц и столбцов, и глазу проще отличить «структуру запроса» от «данных, с которыми он работает», особенно когда запрос становится длиннее и сложнее. В этом курсе мы будем придерживаться именно такого стиля, и рекомендуем перенять его — он принят практически везде, где пишут SQL, и его использование сделает ваш код понятным для других разработчиков.

Важная оговорка: **регистр имён таблиц и столбцов** — совсем другая история, и здесь единого правила по умолчанию нет. На системах Linux имена таблиц по умолчанию чувствительны к регистру (то есть `Products` и `products` — разные таблицы), а на Windows и macOS — обычно нет; это зависит от настройки сервера (`lower_case_table_names`), а не от самого SQL. Чтобы не зависеть от таких особенностей, хорошая практика — всегда называть таблицы и столбцы в одном регистре (например, только маленькими буквами) и обращаться к ним именно так, как они были созданы.

### Форматирование запроса: пробелы, отступы, перенос строк

SQL не чувствителен к «лишним» пробелам, табуляциям и переносам строк между словами запроса (кроме случаев, когда пробел разделяет два токена, которые иначе слились бы в одно слово). Это значит, что следующие два запроса абсолютно эквивалентны для сервера:

```sql
SELECT name, price FROM products;
```

```sql
SELECT
    name,
    price
FROM
    products;
```

Пока запрос короткий, разница не важна. Но по мере роста сложности запроса (когда появятся условия фильтрации, сортировка, соединения нескольких таблиц) читаемость начинает иметь значение. Общепринятое соглашение — переносить основные части запроса (`SELECT`, `FROM`, `WHERE` и другие ключевые слова верхнего уровня) на новую строку и выравнивать их друг под другом, а перечисление столбцов — каждый на отдельной строке с небольшим отступом, если их много:

```sql
SELECT
    name,
    price,
    stock
FROM
    products;
```

Для короткого запроса из одной-двух строк такое форматирование избыточно — писать `SELECT name FROM products;` в одну строку совершенно нормально. Правило простое: чем длиннее и сложнее запрос, тем важнее его структурировать переносами строк, чтобы не превращать его в нечитаемую «стену текста».

### Комментарии в SQL

Иногда в запросе полезно оставить пояснение, которое сервер должен просто игнорировать. Для этого в SQL, как и в большинстве языков, есть комментарии:

```sql
-- однострочный комментарий: всё после -- до конца строки игнорируется
SELECT name, price
FROM products; -- получаем только название и цену
```

```sql
/* многострочный комментарий,
   может занимать несколько строк */
SELECT name FROM products;
```

Комментарии не влияют на выполнение запроса и полезны, когда нужно объяснить неочевидное решение или временно «выключить» часть запроса при отладке.

### Ограничение количества строк: LIMIT

До сих пор запрос `SELECT ... FROM ...` без дополнительных условий возвращал *все* строки таблицы. Но что, если таблица содержит миллион товаров, а нам сейчас нужно только взглянуть на несколько первых строк, чтобы понять структуру данных? Возвращать весь миллион строк ради этого — расточительно и медленно. Именно для таких случаев существует ключевое слово `LIMIT`.

```sql
SELECT name, price
FROM products
LIMIT 2;
```

Этот запрос вернёт **не более двух строк** результата — даже если в таблице `products` их сотни. Обратите внимание на порядок частей запроса: `LIMIT` пишется *после* `FROM` (и, как мы увидим в следующих уроках, после `WHERE`, `GROUP BY`, `ORDER BY`, если они присутствуют) — это часть строго определённого порядка секций запроса, который SQL требует соблюдать. Написать `LIMIT` перед `FROM` — синтаксическая ошибка.

Важный нюанс, который стоит осознать сразу: если в запросе нет явной сортировки (`ORDER BY` — о нём будет отдельный урок), то *какие именно* строки попадут в результат при `LIMIT 2` — не гарантировано и может зависеть от внутренней реализации сервера, порядка физического хранения данных или даже от версии MySQL. `LIMIT` без `ORDER BY` хорош для быстрого просмотра «покажи мне немного данных, чтобы понять, что там вообще есть», но не подходит, когда важно предсказуемо получить, например, «три самых дорогих товара» — для такой задачи нужна сортировка, и мы разберём её позже.

`LIMIT` можно комбинировать с указанием смещения — сколько строк пропустить перед началом отбора. Такая форма (`LIMIT смещение, количество` или `LIMIT количество OFFSET смещение`) нужна для постраничного вывода данных и подробно рассматривается в отдельном уроке про сортировку и страницы; пока достаточно запомнить самый простой вариант `LIMIT N` — «верни не более N первых найденных строк».

### Итоговый вид запроса и общий порядок частей SQL

Собирая всё вместе, законченный запрос с ограничением на количество строк выглядит так:

```sql
SELECT name, price
FROM products
LIMIT 3;
```

Уже на этом простом примере видно, что у SQL-запроса есть **фиксированный порядок секций** — сначала указывается, что вернуть (`SELECT`), затем откуда (`FROM`), затем дополнительные ограничения и модификаторы (`LIMIT` и другие, с которыми мы познакомимся дальше: `WHERE`, `ORDER BY`). Этот порядок нельзя менять произвольно — он определён синтаксисом языка, и в следующих уроках мы будем добавлять новые секции строго на предписанные им места.

### Резюме

- SQL — декларативный язык: запрос описывает *что* нужно получить, а не пошаговый алгоритм получения данных.
- Базовый запрос состоит из `SELECT список_столбцов FROM имя_таблицы;`; символ `*` вместо списка столбцов означает «все столбцы», но в реальном коде обычно перечисляют нужные столбцы явно.
- MySQL нечувствителен к регистру ключевых слов, но общепринятое соглашение — писать ключевые слова заглавными буквами, а имена таблиц и столбцов — как они были созданы; регистр имён таблиц зависит от настроек сервера и операционной системы.
- Пробелы и переносы строк между частями запроса не влияют на его выполнение; форматирование запроса переносами строк — вопрос читаемости, важный для длинных запросов.
- Комментарии (`-- текст` для однострочных, `/* текст */` для многострочных) позволяют оставлять пояснения, которые сервер игнорирует при выполнении.
- `LIMIT N` ограничивает результат не более чем N строками; без `ORDER BY` конкретный набор возвращённых строк не гарантирован и годится только для беглого просмотра данных.
- Части SQL-запроса подчиняются фиксированному порядку секций (`SELECT` → `FROM` → `LIMIT` и другие в дальнейшем) — их нельзя менять местами.

## Теоретические задания

### Вопрос 1: Обязательно ли писать ключевые слова SQL (`SELECT`, `FROM`, `LIMIT`) заглавными буквами?

- ✅ нет: регистр ключевых слов серверу безразличен, а заглавные буквы — общепринятое соглашение для читаемости
- ❌ да, запрос со строчными `select` и `from` завершится ошибкой — error_text: MySQL нечувствителен к регистру ключевых слов: `SELECT`, `select` и даже `SeLeCt` работают одинаково. Заглавные буквы — правило стиля, а не синтаксиса.
- ❌ регистр безразличен для любых слов запроса, включая имена таблиц и столбцов — error_text: регистр ключевых слов действительно безразличен, но с именами таблиц всё сложнее: их чувствительность к регистру зависит от операционной системы и настройки сервера, поэтому надёжнее обращаться к ним так, как они были созданы.

### Вопрос 2: Почему `SELECT *` в рабочем коде приложения — плохая практика?

- ✅ он возвращает лишние столбцы и делает набор столбцов результата зависимым от структуры таблицы
- ❌ звёздочка допустима только в паре с `LIMIT` — error_text: `*` никак не связана с `LIMIT` и может использоваться в любом запросе на чтение. Претензия к звёздочке не в допустимости, а в том, что неявный список столбцов делает код менее надёжным и понятным.
- ❌ `SELECT *` в MySQL 8 запрещён и вызывает ошибку — error_text: запрос полностью законен и выполняется. Недостаток у него практический: лишние данные в результате и неожиданное изменение результата при добавлении столбца в таблицу.

### Вопрос 3: Где в запросе должно стоять ключевое слово `LIMIT`?

- ✅ после `FROM` — у секций запроса фиксированный порядок: `SELECT` → `FROM` → `LIMIT`
- ❌ перед `FROM` — так сервер раньше узнает размер результата — error_text: порядок секций определён синтаксисом языка и не выбирается из соображений «удобства сервера»: `LIMIT` перед `FROM` — синтаксическая ошибка.
- ❌ сразу после `SELECT`, перед списком столбцов — error_text: секции запроса нельзя менять местами; `LIMIT` стоит в конце запроса — после `FROM` (а в будущем — и после других секций, у которых в запросе своё место).

### Вопрос 4: Запрос `SELECT name FROM products LIMIT 2;` выполняется без `ORDER BY`. Какие две строки вернёт сервер?

- ✅ какие именно две строки — не гарантировано: без сортировки LIMIT годится только для беглого просмотра данных
- ❌ обязательно две строки, вставленные в таблицу первыми — error_text: без явной сортировки сервер не обещает вернуть строки в порядке вставки: как он прочтёт данные — внутреннее дело реализации. Рассчитывать на «первые вставленные» нельзя.
- ❌ две строки с названиями, которые идут первыми по алфавиту — error_text: LIMIT не сортирует данные — он лишь ограничивает число строк результата. Отбор «первых по порядку» требует сортировки — это тема отдельного урока о порядке строк.

### Вопрос 5: Один запрос записан в одну строку, другой — такой же по смыслу, но с переносами строк и отступами. Различаются ли они для сервера?

- ✅ нет: пробелы, табуляции и переносы строк между словами запроса не влияют на выполнение
- ❌ многострочный запрос выполняется медленнее — error_text: форматирование — это удобство чтения для человека; серверу безразлично, как запрос разбит на строки, скорость одна и та же.
- ❌ в многострочном запросе точку с запятой нужно ставить после каждой строки — error_text: точка с запятой завершает всю команду целиком, а не её строки; перенос строки — обычный пробельный символ, команду он не заканчивает.

### Задание 2: Быстрый просмотр каталога

Звёздочка и `LIMIT`: беглый взгляд на первые строки таблицы.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT * FROM products LIMIT 3; -->

**statement:**

Чтобы быстро оценить новый каталог, выведите первые три строки таблицы
`products` — все столбцы, не перечисляя их по именам (звёздочкой).

Четыре столбца — `id`, `name`, `price`, `stock` — и три строки: чайник,

```sql
CREATE TABLE products (
    id INT NOT NULL,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
```
