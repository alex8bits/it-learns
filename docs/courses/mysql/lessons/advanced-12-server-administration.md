## Материал

Второй урок уровня «Основы» бегло представил MySQL как клиент-серверную архитектуру и упомянул `USE`, системные схемы и обзор клиентов — этого было достаточно, чтобы начать писать запросы, но недостаточно, чтобы управлять самим сервером как эксплуатируемой системой. Этот урок возвращается к тому же второму уроку курса с намного более глубоким взглядом: как сервер настраивается, как посмотреть его текущее состояние и что происходит на нём в реальном времени, и что скрывается в системных схемах, названия которых до сих пор мелькали в курсе без объяснения (`information_schema`, `performance_schema`).

### Конфигурация сервера: my.cnf и переменные

Поведение сервера MySQL управляется большим числом параметров — от размера буферного пула (упомянутого в первом уроке этого уровня как область памяти для кеширования данных и индексов) до включённости планировщика событий (седьмой урок этого уровня) и режима строгости проверки данных. Часть этих параметров задаётся в конфигурационном файле сервера, традиционно называемом `my.cnf` (Linux/macOS) или `my.ini` (Windows), который читается **один раз при старте** процесса `mysqld`:

```ini
[mysqld]
max_connections = 200
innodb_buffer_pool_size = 4G
event_scheduler = ON
sql_mode = STRICT_TRANS_TABLES,NO_ZERO_DATE,NO_ENGINE_SUBSTITUTION
```

Изменение значения в этом файле требует **перезапуска сервера**, чтобы вступить в силу — это существенно отличает такие параметры от переменных сессии, о которых пойдёт речь ниже.

### SHOW VARIABLES: посмотреть текущие настройки

Не открывая файл конфигурации напрямую (который может быть недоступен клиенту, подключающемуся удалённо, или который администратор изменил, но ещё не перезапустил сервер), текущие значения параметров сервера можно посмотреть прямо через SQL:

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE '%charset%';
```

Седьмой урок этого уровня уже использовал `SHOW VARIABLES LIKE 'event_scheduler'` именно в этом качестве — проверить текущее состояние переменной перед тем, как что-то менять.

### SET SESSION и SET GLOBAL: два разных уровня действия изменений

Некоторые переменные сервера можно менять прямо во время его работы, без перезапуска, через команду `SET` — но у неё есть два принципиально разных уровня действия:

- **`SET SESSION имя = значение`** (или без явного `SESSION` — это область действия по умолчанию для большинства переменных) — изменение действует **только для текущего соединения** и исчезает, как только это соединение закрывается. Пример — временное изменение `sql_mode` для одной сессии отладки, не влияющее на других подключённых клиентов.
- **`SET GLOBAL имя = значение`** — изменение действует для **всех новых соединений**, устанавливаемых после этой команды (уже открытые соединения его не увидят автоматически, пока не переподключатся), но **не сохраняется** после перезапуска сервера — при следующем старте сервер снова читает значение из `my.cnf`. Именно так в седьмом уроке этого уровня включался планировщик событий (`SET GLOBAL event_scheduler = ON`) — временно, до перезапуска, в отличие от постоянного включения через файл конфигурации.

Практическое правило: `SET SESSION` — для точечной, временной настройки поведения собственного клиента; `SET GLOBAL` — для временного изменения поведения сервера в целом (например, для диагностики без перезапуска); постоянные изменения, переживающие перезапуск, — только через `my.cnf`/`my.ini`.

### SHOW PROCESSLIST: что сервер делает прямо сейчас

**`SHOW PROCESSLIST`** — один из самых практически полезных инструментов администрирования: он показывает список всех активных соединений к серверу и то, что каждое из них делает в данный момент:

```sql
SHOW PROCESSLIST;
```

Типичный вывод содержит для каждого соединения: `Id` (идентификатор потока, используемый для последующего управления им), `User` и `Host` (кто подключился и откуда), `db` (к какой базе данных подключено соединение), `Command` (тип текущей операции — `Query`, `Sleep`, `Binlog Dump` и другие), `Time` (сколько секунд длится текущее состояние) и `Info` (сам выполняемый в данный момент SQL-запрос, если есть). Это первый инструмент для ответа на вопрос «а что вообще происходит на сервере прямо сейчас, и не завис ли там долгий запрос» — соединение, у которого `Command = Query` и очень большое `Time`, — прямой кандидат на дальнейшую диагностику (например, через `EXPLAIN` из второго урока этого уровня, применённый к тому же запросу, или через изучение блокировок из десятого урока уровня «Средний», если подозревается, что запрос не выполняется, а именно заблокирован другой сессией).

Соединение можно принудительно завершить командой `KILL идентификатор;`, где идентификатор — значение столбца `Id` из `SHOW PROCESSLIST` — крайняя мера, применяемая когда конкретный запрос или сессия мешает нормальной работе сервера (например, случайно запущенный без `WHERE` тяжёлый `UPDATE`, который ещё не успел закоммититься, — девятый урок уровня «Средний» напоминает, что `ROLLBACK` в такой ситуации отменит уже частично сделанные изменения, но сама долгая операция должна быть прервана явно).

### Системные схемы: mysql, information_schema, performance_schema

Помимо пользовательских баз данных (в терминах курса — `shop` или аналогичной, где живут `products`, `orders` и остальные таблицы сквозного датасета), MySQL при установке создаёт несколько служебных схем, видимых через `SHOW DATABASES` наравне с пользовательскими, но выполняющих разные системные роли:

- **`mysql`** — служебная схема самого сервера: здесь хранятся учётные записи пользователей, их привилегии, а также некоторые внутренние таблицы (например, для реализации отложенных событий и часовых зон). Тема пользователей и привилегий, хранящихся здесь, — предмет следующего, тринадцатого урока этого уровня.
- **`information_schema`** — стандартизированное (часть стандарта SQL, поддерживаемая и другими СУБД, не только MySQL) представление метаданных обо всех объектах сервера: какие таблицы существуют, какие у них столбцы и типы, какие индексы созданы, какие ограничения (`CHECK`, `FOREIGN KEY`) действуют. Это не обычные таблицы с данными приложения, а *представления* (концептуально близкие к `VIEW` из одиннадцатого урока уровня «Средний»), вычисляемые сервером по факту описания реальных объектов базы. Пример практического запроса — узнать все столбцы таблицы `orders` программным способом, не открывая `DESCRIBE`:

```sql
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'shop' AND table_name = 'orders';
```

- **`performance_schema`** — низкоуровневая инфраструктура наблюдения за производительностью самого сервера: время выполнения отдельных операций, статистика по ожиданиям на блокировках, использование памяти внутренними структурами. Это существенно более детальный и «дорогой» с точки зрения накладных расходов инструмент диагностики, чем `EXPLAIN` или `SHOW PROCESSLIST` — предназначенный для глубокого профилирования конкретных проблем производительности сервера в целом, а не отдельного запроса; для большинства повседневных задач разработчика приложения `EXPLAIN` и `SHOW PROCESSLIST` покрывают практическую потребность, а `performance_schema` становится нужен на следующем уровне детализации, когда этих двух инструментов уже не хватает.

### Batch-режим CLI: выполнение SQL-скрипта без интерактивной сессии

Второй урок уровня «Основы» показал `mysql` CLI как интерактивный инструмент — клиент запускается, и пользователь вводит команды одну за другой. Но `mysql` CLI поддерживает и неинтерактивный, **batch**-режим — выполнение целого файла с SQL-командами одним вызовом из командной строки операционной системы (не из самого клиента `mysql`):

```bash
lessons -u root -p shop < migration.sql
```

Здесь `migration.sql` — обычный текстовый файл с последовательностью SQL-команд (например, набор `CREATE TABLE`/`ALTER TABLE` для разворачивания схемы на новом сервере, или большой `INSERT`-скрипт для сидирования тестовых данных); знак `<` перенаправляет содержимое файла на стандартный ввод клиента `mysql`, который выполняет их последовательно и завершается после последней команды, не переходя в интерактивный режим ожидания ввода. Именно такой batch-режим используется в реальной эксплуатации для автоматизации: развёртывания схемы через CI/CD-пайплайн, регулярных обслуживающих скриптов, восстановления из бэкапа (тема четырнадцатого урока этого уровня, где `mysqldump` создаёт файл ровно такого вида, который затем воспроизводится обратно через тот же batch-режим `mysql`).

### Резюме

- **Конфигурационный файл** (`my.cnf`/`my.ini`) задаёт параметры сервера, применяемые при старте процесса `mysqld`; изменение требует перезапуска.
- **`SHOW VARIABLES LIKE 'шаблон'`** показывает текущие значения параметров сервера без обращения к самому файлу конфигурации.
- **`SET SESSION`** меняет переменную только для текущего соединения; **`SET GLOBAL`** — для новых соединений сервера, но не сохраняется после перезапуска (в отличие от изменения в файле конфигурации).
- **`SHOW PROCESSLIST`** показывает все активные соединения сервера и что каждое из них выполняет прямо сейчас; **`KILL идентификатор`** принудительно завершает конкретное соединение.
- **`mysql`** (служебная схема) — учётные записи и привилегии (тема тринадцатого урока); **`information_schema`** — стандартизированные метаданные обо всех объектах сервера (таблицы, столбцы, индексы, ограничения), доступные обычным `SELECT`; **`performance_schema`** — низкоуровневая, более «дорогая» инфраструктура детального профилирования производительности сервера.
- **Batch-режим** `mysql` CLI (`mysql -u ... -p база < файл.sql`) выполняет целый SQL-файл неинтерактивно из командной строки ОС — основа автоматизации развёртывания схемы, сидирования и восстановления из бэкапа.

## Теоретические задания

### Вопрос 1: Чем `SET SESSION sql_mode = ...` отличается от `SET GLOBAL sql_mode = ...`?

- ✅ `SESSION` действует только для текущего соединения и исчезает при его закрытии; `GLOBAL` — для новых соединений сервера
<!-- SET без ключевого слова действует как SET SESSION -->
- ❌ `SESSION` действует до перезапуска сервера, а `GLOBAL` меняет файл конфигурации `my.cnf` — error_text: уровни перепутаны: `SET GLOBAL` не трогает файл конфигурации и теряется при перезапуске — при старте сервер заново читает `my.cnf`. А `SESSION` живёт только до закрытия текущего соединения; переживает перезапуск лишь значение, прописанное в самом файле конфигурации.
- ❌ `GLOBAL` применяется ко всем соединениям немедленно, включая уже открытые — error_text: `SET GLOBAL` действует на соединения, устанавливаемые после команды. Уже открытые соединения продолжают работать со значением, полученным при подключении, и увидят новое только после переподключения.
- ❌ разницы нет: без слов `SESSION`/`GLOBAL` команда действует одинаково на весь сервер — error_text: `SET` без ключевого слова действует как `SET SESSION` — только на текущее соединение. Если нужно временно повлиять на сервер целиком без перезапуска, уровень указывают явно: `SET GLOBAL`.

### Вопрос 2: Как сделать изменение переменной сервера (например, `max_connections`) постоянным — переживающим перезапуск `mysqld`?

- ✅ прописать значение в конфигурационный файл `my.cnf` (`my.ini`) и перезапустить сервер
<!-- my.cnf читается один раз при старте — это единственное «постоянное» место для значения -->
- ❌ выполнить `SET GLOBAL max_connections = 200` — значение сохранится в конфигурации — error_text: `SET GLOBAL` действует только до перезапуска: при следующем старте сервер читает значение из `my.cnf`, и изменение молча пропадает. Постоянное значение живёт именно в конфигурационном файле.
- ❌ выполнить `SET SESSION` от имени администратора: root-сессия управляет всем сервером — error_text: `SET SESSION`, кем бы он ни выполнялся, меняет поведение ровно одного соединения — того, в котором выполнен. Права администратора не расширяют область действия уровня `SESSION`.
- ❌ прочитать текущее значение через `SHOW VARIABLES` и перезапустить сервер — error_text: `SHOW VARIABLES` — команда чтения: она показывает текущее значение переменной и ничего не меняет. Изменение — это `SET` (временно) или файл конфигурации (постоянно, после перезапуска).

### Вопрос 3: Что показывает `SHOW PROCESSLIST`?

- ✅ все активные соединения с сервером и то, что каждое делает сейчас: Id, User, Host, db, Command, Time, Info
<!-- соединение с Command = Query и большим Time — кандидат на KILL или диагностику -->
- ❌ план выполнения запроса: типы доступа, индексы, оценку строк — error_text: план запроса показывает `EXPLAIN` (второй урок этого уровня). `SHOW PROCESSLIST` — про соединения и их текущую активность, а не про то, как оптимизатор собирается выполнять конкретный запрос.
- ❌ список всех переменных сервера и их текущих значений — error_text: переменные сервера перечисляет `SHOW VARIABLES`. `SHOW PROCESSLIST` показывает соединения: кто и откуда подключился, к какой базе, какая команда выполняется и сколько секунд она длится.
- ❌ содержимое системных схем `mysql` и `information_schema` — error_text: содержимое системных схем смотрят обычными `SELECT` по их таблицам и представлениям. `SHOW PROCESSLIST` — отдельная команда про активные соединения сервера и выполняемые в них запросы.

### Вопрос 4: Где сервер MySQL хранит учётные записи пользователей и их привилегии?

- ✅ в служебной схеме `mysql`
<!-- тема следующего урока; information_schema — метаданные объектов, performance_schema — производительность -->
- ❌ в `information_schema` — error_text: `information_schema` — стандартизированные метаданные об объектах баз: таблицы, столбцы, индексы, ограничения. Учётные записи и привилегии — данные самого сервера, они хранятся в схеме `mysql`.
- ❌ в `performance_schema` — error_text: `performance_schema` — инфраструктура наблюдения за производительностью: тайминги операций, статистика ожиданий, память внутренних структур. К учётным записям она отношения не имеет.
- ❌ в конфигурационном файле `my.cnf` — error_text: `my.cnf` хранит параметры работы сервера — размеры буферов, лимиты, режимы, — читаемые при старте. Учётные записи и привилегии — данные, они живут в служебной схеме `mysql`.

### Вопрос 5: Каким одним запросом программно получить список столбцов таблицы `orders` базы `shop` (имя, тип, NULL-допустимость), не открывая `DESCRIBE`?

- ✅ `SELECT column_name, data_type, is_nullable FROM information_schema.columns WHERE table_schema = 'shop' AND table_name = 'orders';`
<!-- information_schema — представления метаданных, доступные обычным SELECT -->
- ❌ `SELECT ... FROM performance_schema.columns WHERE ...` — error_text: `performance_schema` не хранит метаданные пользовательских таблиц: это инструменты профилирования производительности сервера. Описания таблиц и столбцов находятся в `information_schema`.
- ❌ `SHOW PROCESSLIST` с фильтром по таблице `orders` — error_text: `SHOW PROCESSLIST` показывает активные соединения и выполняемые ими команды, а не структуру таблиц. Структуру смотрят `DESCRIBE`, а программно — запросом к `information_schema.columns`.
- ❌ `SHOW VARIABLES LIKE 'orders%'` — error_text: `SHOW VARIABLES` показывает параметры сервера — настройки вроде `max_connections`, — а не структуру пользовательских таблиц. Метаданные столбцов — это `information_schema.columns`.
