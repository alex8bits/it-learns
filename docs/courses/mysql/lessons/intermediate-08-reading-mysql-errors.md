## Материал

За все предыдущие уроки курса вы наверняка уже видели десятки сообщений об ошибках — от простой опечатки в имени столбца до отказа вставить дублирующееся значение. До сих пор мы, встречая ошибку, чаще всего интуитивно понимали, что пошло не так, потому что задачи были сравнительно простыми, а ошибка — рядом с местом её причины. Но по мере роста сложности запросов (JOIN нескольких таблиц, подзапросы, upsert-конструкции) сообщение об ошибке нередко указывает не совсем туда, где на самом деле кроется причина, а сам текст ошибки становится менее очевидным. Этот урок — не про новую SQL-конструкцию, а про навык, который экономит время на каждом последующем уроке и в любой реальной работе с базой: научиться быстро и точно читать сообщение об ошибке MySQL, а не воспринимать его как непонятный текст, который остаётся только скопировать в поисковик.

### Анатомия сообщения об ошибке

Типичное сообщение об ошибке MySQL состоит из нескольких частей, каждая из которых несёт свою порцию информации:

```
ERROR 1054 (42S22): Unknown column 'pric' in 'field list'
```

- **Числовой код ошибки** (`1054`) — это код, специфичный именно для MySQL; он однозначно определяет **тип** проблемы и одинаков независимо от языка сообщения или версии клиента.
- **SQLSTATE-код** (`42S22`) — стандартизованный код, общий для многих СУБД (не только MySQL), группирующий ошибки по более широким категориям (например, коды, начинающиеся на `42`, относятся к синтаксическим и семантическим нарушениям запроса).
- **Текст сообщения** (`Unknown column 'pric' in 'field list'`) — человекочитаемое описание, которое почти всегда указывает конкретное имя объекта (столбца, таблицы, ограничения), из-за которого возникла проблема, и место, где MySQL это обнаружил (`field list` — список столбцов после `SELECT`).

Алгоритм чтения любой ошибки MySQL можно свести к четырём шагам: **код → текст → конкретное имя (строка/таблица/колонка) → какое правило нарушено**. Разберём по этому алгоритму несколько самых частых кодов, с которыми вы точно столкнётесь в практике курса и за его пределами.

### 1054 — Unknown column: опечатка или неверная область видимости

```
ERROR 1054 (42S22): Unknown column 'c.nmae' in 'field list'
```

Самая частая причина — банальная опечатка в имени столбца (`nmae` вместо `name`). Но есть и менее очевидная причина, прямо связанная с материалом этого уровня: попытка использовать псевдоним `SELECT` или оконную функцию в `WHERE`, что мы разбирали в пятом уроке этого уровня — MySQL на этапе `WHERE` действительно «не знает» такого столбца, потому что он физически ещё не вычислен. Разбор: `field list` в тексте ошибки подсказывает, что проблема — в списке столбцов после `SELECT` или в аналогичном месте; если имя написано верно, следующий шаг — проверить, не ссылается ли запрос на псевдоним раньше, чем тот успел вычислиться по логическому порядку выполнения (шестой урок уровня «Начинающий»).

### 1064 — синтаксическая ошибка: где именно споткнулся парсер

```
ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'FORM products' at line 1
```

Код `1064` — общая синтаксическая ошибка: сам текст запроса не соответствует грамматике SQL (пропущенная запятая, лишняя скобка, опечатка в ключевом слове — здесь `FORM` вместо `FROM`). Ключевая часть сообщения — `near '...'`: MySQL указывает фрагмент текста, **на котором** разбор запроса впервые не смог продолжиться. Важная тонкость: место, указанное в `near`, — это место, где парсер **обнаружил** проблему, а не обязательно место, где реальная причина ошибки расположена в тексте — например, если не закрыта открывающая скобка на 50 символов раньше, ошибка может показать `near` в конце строки, где парсер окончательно «потерял» структуру запроса. Разбор: смотреть на текст возле `near`, но если там всё выглядит правильно — проверять по всему запросу выше баланс скобок, кавычек и точек с запятой.

### 1062 — Duplicate entry: нарушение уникальности

```
ERROR 1062 (23000): Duplicate entry 'client@example.com' for key 'customers.email'
```

Этот код мы уже видели в шестом уроке уровня «Основы»: попытка вставить или обновить строку так, что значение конфликтует с `PRIMARY KEY` или `UNIQUE` ограничением. Сообщение здесь особенно информативно: оно прямо называет **конфликтующее значение** (`'client@example.com'`) и **имя ограничения**, которое оно нарушило (`customers.email` — конкретный `UNIQUE`-индекс на столбце `email` таблицы `customers`). Разбор в контексте этого уровня — прямая связь с седьмым уроком: если ошибка 1062 возникает при регулярной, повторяющейся загрузке данных, это сигнал, что обычный `INSERT` нужно заменить на `INSERT IGNORE`, `REPLACE` или, что предпочтительнее, на `INSERT ... ON DUPLICATE KEY UPDATE`.

### 1451 и 1452 — нарушение внешнего ключа

```
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`shop`.`orders`, CONSTRAINT `orders_ibfk_1` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`))
```

```
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`shop`.`orders`, CONSTRAINT `orders_ibfk_1` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`))
```

Оба кода относятся к `FOREIGN KEY` (двенадцатый урок уровня «Начинающий»), но с разных сторон связи: **1451** возникает при попытке удалить или изменить строку в **родительской** таблице (`customers`), на которую всё ещё ссылаются строки в дочерней таблице (`orders`) — если для внешнего ключа не настроен подходящий `ON DELETE CASCADE`/`SET NULL`, MySQL защищает целостность данных, отказываясь «осиротить» дочерние строки. **1452**, напротив, возникает при попытке вставить или изменить строку в **дочерней** таблице (`orders`) со значением `customer_id`, которого не существует в родительской таблице `customers` — сама ссылка некорректна с самого начала. Разбор: сообщение всегда называет обе участвующие таблицы и имя `CONSTRAINT` — по имени родительской и дочерней таблицы в тексте сразу понятно, с какой стороны связи возникла проблема, даже если в самом запросе явно фигурирует только одна из двух таблиц.

### 1048 — Column cannot be null

```
ERROR 1048 (23000): Column 'customer_id' cannot be null
```

Прямое нарушение ограничения `NOT NULL` (шестой урок уровня «Основы»): попытка вставить или обновить строку так, что для столбца, объявленного `NOT NULL` без `DEFAULT`, значение отсутствует или явно передан `NULL`. Разбор здесь самый прямой из всех: сообщение прямо называет столбец-нарушитель, остаётся только проверить, откуда в конкретном запросе (буквальном `VALUES`, результате `SELECT` при `INSERT ... SELECT`, или отсутствующем значении в исходных данных) взялось отсутствующее значение для этого столбца.

### Общий алгоритм разбора любой ошибки MySQL

Собирая разобранные примеры в единый метод:

1. **Код** — по числовому коду (или его первым цифрам, сгруппированным по смыслу: 1054/1064 — проблемы самого текста запроса, 1048/1062/1451/1452 — нарушения ограничений целостности данных) сразу понятна общая категория проблемы, даже не читая текст.
2. **Текст** — прочитать сообщение целиком, не бросая взгляд только на код; MySQL почти всегда указывает конкретное имя (столбца, таблицы, ограничения, значения), а не абстрактную формулировку.
3. **Место** (строка/таблица/колонка) — сопоставить названное в сообщении имя с реальным текстом запроса: где именно оно встречается, и что там происходит.
4. **Нарушенное правило** — вспомнить, какое ограничение или синтаксическое требование стоит за этим кодом (`NOT NULL`, `UNIQUE`, `FOREIGN KEY`, порядок выполнения `SELECT`, синтаксис `INSERT`), и исправить именно причину, а не симптом (например, при 1062 — не удалять существующую строку вручную «чтобы влезла новая», а разобраться, нужен ли здесь upsert).

Этот алгоритм работает не только для пяти кодов, разобранных в этом уроке, но и для любого другого сообщения MySQL, с которым вы столкнётесь дальше в курсе или в реальной практике: код почти всегда документирован (официальная документация MySQL перечисляет все коды с объяснениями), а текст сообщения почти всегда указывает конкретный объект — значит, задача чтения ошибки сводится к внимательному, а не паническому взгляду на уже присутствующую в сообщении информацию.

### Резюме

- Сообщение об ошибке MySQL состоит из числового кода (специфичен для MySQL), SQLSTATE-кода (общий для разных СУБД) и текста с конкретным указанием объекта и места проблемы.
- **1054** (Unknown column) — опечатка в имени столбца либо обращение к псевдониму/оконной функции раньше их вычисления по логическому порядку выполнения `SELECT`.
- **1064** (синтаксис) — `near '...'` показывает, где парсер обнаружил проблему; реальная причина (незакрытая скобка, пропущенная запятая) может быть немного раньше по тексту.
- **1062** (Duplicate entry) — нарушение `UNIQUE`/`PRIMARY KEY`; сообщение прямо называет конфликтующее значение и имя ограничения; при регулярной повторной загрузке — сигнал использовать upsert-конструкции.
- **1451**/**1452** — нарушение `FOREIGN KEY`: 1451 — попытка удалить/изменить родительскую строку, на которую ссылаются дочерние; 1452 — попытка вставить дочернюю строку со ссылкой на несуществующую родительскую.
- **1048** (Column cannot be null) — прямое нарушение `NOT NULL`; сообщение называет конкретный столбец-нарушитель.
- Универсальный алгоритм разбора: код → текст → конкретное имя объекта → какое правило нарушено — применим к любому сообщению об ошибке MySQL, не только к разобранным в этом уроке кодам.

## Теоретические задания

### Вопрос 1: Запрос с оконной функцией упал с `ERROR 1054 (42S22): Unknown column 'rank_in_category' in 'where clause'`, хотя алиас `rank_in_category` объявлен в списке SELECT. В чём причина?

- ✅ `WHERE` выполняется раньше вычисления столбцов `SELECT`, поэтому алиаса (и самой оконной функции) на этом шаге ещё не существует — вычисление нужно вынести в CTE или производную таблицу
<!-- тот же порядок выполнения, что в пятом уроке уровня «Средний» и шестом уроке уровня «Начинающий» -->
- ❌ в таблице нет столбца `rank_in_category` — нужно добавить его через `ALTER TABLE` — error_text: речь об алиасе из списка `SELECT`, а не о столбце схемы: менять структуру таблицы не нужно. Проблема в порядке выполнения запроса — `WHERE` отрабатывает до шага `SELECT`, где алиас только вычисляется.
- ❌ SQLSTATE 42S22 запрещает оконные функции в WHERE — error_text: SQLSTATE — лишь стандартизованная категория ошибки (коды на `42` — нарушения текста запроса), а не правило про оконные функции. Запрет связан с логическим порядком выполнения, а не с кодом состояния.
- ❌ версия сервера не поддерживает оконные функции — error_text: оконные функции поддерживаются с MySQL 8.0, и сообщение при этом было бы другим. Здесь сервер просто не знает столбца на этапе `WHERE` — та же история, что с псевдонимами агрегатов из шестого урока уровня «Начинающий».

### Вопрос 2: `ERROR 1064 (42000): You have an error in your SQL syntax; ... near 'FORM products' at line 1`. Что означает фрагмент `near 'FORM products'`?

- ✅ место, на котором парсер впервые не смог продолжить разбор; реальная причина (здесь — опечатка `FORM` вместо `FROM`) может располагаться и раньше по тексту запроса
<!-- near — точка обнаружения проблемы, а не гарантированное место её причины -->
- ❌ точное место ошибки: опечатка всегда строго внутри фрагмента near — error_text: `near` показывает, где разбор споткнулся, а не где причина. При незакрытой скобке много раньше по тексту парсер «теряет структуру» только в конце — и `near` укажет именно туда. Если возле `near` всё выглядит верным, проверяйте запрос выше: скобки, кавычки, точки с запятой.
- ❌ версию MySQL, для которой написан запрос — error_text: упоминание версии в тексте ошибки лишь рекомендует свериться с документацией соответствующего релиза. Конкретное место проблемы показывает фрагмент после `near`.
- ❌ имя таблицы, вызвавшей ошибку — error_text: текст после `near` — фрагмент вашего запроса, а не имя объекта БД. Здесь это опечатка `FORM`, из-за которой нарушена грамматика SQL (код 1064 — синтаксическая ошибка).

### Вопрос 3: Регулярный импорт упал с ошибкой `ERROR 1062 (23000): Duplicate entry 'client@example.com' for key 'customers.email'`. Что произошло и в какую сторону лечить?

- ✅ нарушен `UNIQUE`-ключ на `customers.email`; при повторяющейся загрузке обычный `INSERT` стоит заменить на upsert-конструкцию — `INSERT ... ON DUPLICATE KEY UPDATE`, `INSERT IGNORE` или `REPLACE`
<!-- сообщение прямо называет конфликтующее значение и имя ограничения -->
- ❌ в таблицу пытаются вставить NULL в NOT NULL-столбец — error_text: это код 1048 Column cannot be null, и сообщение называло бы столбец-нарушитель. Здесь 1062 — нарушение уникальности: прямо названы конфликтующее значение `'client@example.com'` и ключ `customers.email`, который оно дублирует.
- ❌ customer_id ссылается на несуществующего клиента — error_text: это нарушение внешнего ключа — код 1452 (Cannot add or update a child row), и в тексте назывался бы `CONSTRAINT`. 1062 связан с `UNIQUE`/`PRIMARY KEY`, а не со ссылочной целостностью.
- ❌ опечатка в имени столбца email — error_text: опечатка в имени столбца — это 1054 Unknown column, и запрос не дошёл бы до вставки. Здесь запрос синтаксически верен: сервер отказался вставлять значение, которое уже есть в `UNIQUE`-индексе `customers.email`.

### Вопрос 4: Чем ошибка 1452 отличается от ошибки 1451?

- ✅ 1452 возникает при вставке или обновлении дочерней строки со ссылкой на несуществующую родительскую, 1451 — при удалении или изменении родительской строки, на которую ещё ссылаются дочерние
<!-- обе — нарушения FOREIGN KEY, но с разных сторон связи -->
- ❌ 1452 — нарушение NOT NULL, 1451 — нарушение UNIQUE — error_text: оба кода относятся к внешним ключам. `NOT NULL` — это 1048, `UNIQUE`/`PRIMARY KEY` — 1062; их не нужно смешивать с 1451/1452, у которых в тексте ошибки всегда названы `CONSTRAINT` и обе таблицы связи.
- ❌ 1452 возникает при операции над родительской таблицей, 1451 — над дочерней — error_text: ровно наоборот: 1451 срабатывает при операции над родителем (удаляют или меняют строку, на которую ссылаются дети), 1452 — при операции над дочерней таблицей (вставляют строку с несуществующей ссылкой). Мнемоника — из самих текстов: «Cannot delete or update a **parent** row» против «Cannot add or update a **child** row».
- ❌ различие только в SQLSTATE-коде — error_text: у обоих кодов SQLSTATE одинаковый — `23000`, категория «нарушение целостности». Числовые коды MySQL различают их содержательно: по стороне связи, на которой произошла попытка нарушить внешний ключ.

### Вопрос 5: При выполнении `INSERT INTO orders (...) SELECT ...` получено `ERROR 1048 (23000): Column 'customer_id' cannot be null`. С чего начинать разбор?

- ✅ сообщение называет столбец с ограничением `NOT NULL`, получивший `NULL`; проверять нужно источник значения — буквальный список `VALUES`, результат `SELECT` или отсутствующие значения в исходных данных
<!-- самый прямой из кодов: столбец-нарушитель назван в тексте -->
- ❌ с проверки синтаксиса запроса возле фрагмента near — error_text: `near` появляется у синтаксических ошибок с кодом 1064. Здесь запрос уже разобран и исполнение дошло до вставки: нарушено ограничение `NOT NULL`, и текст называет столбец-нарушитель — `customer_id`.
- ❌ с удаления дубликатов из orders — error_text: дубликаты — это 1062 Duplicate entry, к `NOT NULL` они отношения не имеют. Здесь вставляемое значение отсутствует (`NULL`), а не повторяется — это разные нарушения ограничений.
- ❌ с проверки внешнего ключа на customer_id — error_text: нарушение внешнего ключа — код 1452 (Cannot add or update a child row), и текст ошибки назвал бы `CONSTRAINT` и обе таблицы. Здесь ограничение проще: столбец объявлен `NOT NULL`, а вставляется `NULL` — проверять надо источник значения, а не ссылочную целостность.
