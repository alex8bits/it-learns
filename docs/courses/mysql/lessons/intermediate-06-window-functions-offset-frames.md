## Материал

В прошлом уроке оконные функции решали задачи, в которых важен был **относительный порядок** строки внутри окна — её номер или ранг. Но у окна есть ещё одна форма пользы: заглянуть в **соседнюю** строку того же окна (предыдущую или следующую по порядку) или посчитать агрегат не по всему окну целиком, а по его **части**, ограниченной относительно текущей строки — например, «нарастающим итогом от начала окна до текущей строки». Это тема второго урока про оконные функции.

### LAG и LEAD: значение соседней строки

`LAG()` возвращает значение указанного столбца из строки, которая находится **на N позиций раньше** текущей (по порядку, заданному `ORDER BY` внутри `OVER`); `LEAD()` — симметрично, значение из строки **на N позиций позже**. Классическая задача, для которой они созданы — сравнение текущего периода с предыдущим, например, помесячная выручка магазина и её изменение относительно прошлого месяца:

```sql
WITH monthly_revenue AS (
    SELECT
        DATE_FORMAT(o.created_at, '%Y-%m') AS month,
        SUM(oi.quantity * oi.price) AS revenue
    FROM orders o
    INNER JOIN order_items oi ON oi.order_id = o.id
    GROUP BY DATE_FORMAT(o.created_at, '%Y-%m')
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue) OVER (ORDER BY month) AS revenue_change
FROM monthly_revenue
ORDER BY month;
```

Для каждой строки (месяца) `LAG(revenue) OVER (ORDER BY month)` подставляет `revenue` **предыдущей** по порядку строки — то есть выручку прошлого месяца, оказавшуюся рядом с текущей без единого самостоятельного `JOIN` таблицы на саму себя. Задача «сравнить строку с предыдущей» ранее в курсе требовала бы self-join (пятнадцатый урок уровня «Начинающий») с искусственным условием соответствия по номеру месяца — заметно более громоздкой конструкции, чем `LAG`.

Для самой первой строки окна (у которой просто не существует предыдущей) `LAG()` возвращает `NULL` — предсказуемое, ожидаемое поведение (аналогично `SUM`/`MAX` по пустому множеству из восьмого урока уровня «Начинающий»): значения для сравнения физически не существует, и `NULL` корректно отражает это «отсутствие». `LAG()` и `LEAD()` принимают необязательный второй аргумент — смещение (по умолчанию 1) и необязательный третий — значение по умолчанию вместо `NULL`, например, `LAG(revenue, 1, 0) OVER (ORDER BY month)` вернёт `0` для первой строки вместо `NULL`, если по смыслу задачи это уместнее.

### FIRST_VALUE и LAST_VALUE: значение из края окна

`FIRST_VALUE()` возвращает значение из **первой** строки окна, `LAST_VALUE()` — из **последней**, независимо от того, на какой по счёту строке эта функция вычисляется. Например, для каждого заказа клиента показать сумму его самого первого заказа (чтобы видеть, выросли клиент в тратах или нет с момента первого обращения):

```sql
SELECT
    o.id AS order_id,
    o.customer_id,
    o.created_at,
    SUM(oi.quantity * oi.price) AS order_total,
    FIRST_VALUE(SUM(oi.quantity * oi.price)) OVER (
        PARTITION BY o.customer_id ORDER BY o.created_at
    ) AS first_order_total
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, o.customer_id, o.created_at;
```

Здесь `PARTITION BY o.customer_id` делит окно по клиентам (как в прошлом уроке), а `FIRST_VALUE(...)` внутри каждого такого окна берёт сумму самой первой по дате строки — то есть сумму первого заказа этого клиента — и повторяет её рядом с каждым последующим заказом того же клиента. `LAST_VALUE()` в применении требует особой осторожности: по умолчанию граница окна («до какой строки считается „последняя“») устроена не так, как интуитивно ожидается — это подробно объясняется в следующем разделе про `ROWS BETWEEN`.

### Рамка окна: ROWS BETWEEN

До сих пор `PARTITION BY`/`ORDER BY` определяли *раздел* и *порядок* строк в окне, но не то, какая именно **часть** этого раздела участвует в вычислении для конкретной строки. Эта часть называется **рамкой** (frame) и задаётся дополнительно конструкцией `ROWS BETWEEN ... AND ...`. Когда `ORDER BY` присутствует, а рамка не указана явно, MySQL по умолчанию использует рамку `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — «от начала раздела до текущей строки включительно». Именно из-за этого умолчания оконный `SUM` с `ORDER BY` без явной рамки превращается в **накопительную сумму** (running total), а не в сумму всего раздела:

```sql
SELECT
    o.id AS order_id,
    o.customer_id,
    o.created_at,
    SUM(oi.quantity * oi.price) AS order_total,
    SUM(SUM(oi.quantity * oi.price)) OVER (
        PARTITION BY o.customer_id ORDER BY o.created_at
    ) AS running_total
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, o.customer_id, o.created_at
ORDER BY o.customer_id, o.created_at;
```

Для каждого заказа клиента `running_total` показывает сумму **всех его заказов до текущего и включая текущий**, а не сумму всех заказов клиента вообще — именно этот эффект и создаёт умолчание «от начала раздела до текущей строки». Как только следующий по дате заказ того же клиента обрабатывается, окно «сдвигается» — включает ещё одну строку, и накопительная сумма увеличивается. Это ровно то поведение, которое нужно для отчёта «рост выручки клиента со временем» — каждая строка показывает, сколько клиент потратил *к этому моменту*.

Рамку можно указать и явно, что делает намерение видимым в самом тексте запроса, а не зависящим от неочевидного умолчания:

```sql
SUM(SUM(oi.quantity * oi.price)) OVER (
    PARTITION BY o.customer_id
    ORDER BY o.created_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
) AS running_total
```

`UNBOUNDED PRECEDING` означает «без ограничения назад — от самого начала раздела», `CURRENT ROW` — «до текущей строки включительно». Явная запись рамки рекомендуется именно потому, что умолчание совпадает с ней лишь при наличии `ORDER BY` — для новичка это легко забыть и получить не накопительную, а, например, полную сумму раздела там, где она была не нужна, либо наоборот.

Другой частый вид рамки — **скользящее окно фиксированного размера**, например, среднее за последние три месяца:

```sql
SELECT
    month,
    revenue,
    AVG(revenue) OVER (
        ORDER BY month
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS moving_avg_3m
FROM monthly_revenue
ORDER BY month;
```

`2 PRECEDING AND CURRENT ROW` — рамка из трёх строк: две предыдущие плюс текущая. Для первых двух месяцев, у которых физически нет двух предыдущих строк, MySQL просто использует столько строк, сколько реально доступно (одну или две) — рамка не «дополняется» несуществующими строками и не выдаёт ошибку, а корректно сокращается у самого края раздела.

Наконец, чтобы получить **сумму по всему разделу целиком** для каждой строки (в отличие от накопительной суммы), рамку нужно расширить в обе стороны:

```sql
SUM(SUM(oi.quantity * oi.price)) OVER (
    PARTITION BY o.customer_id
    ORDER BY o.created_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
) AS customer_total_all_orders
```

`UNBOUNDED FOLLOWING` — «без ограничения вперёд, до самого конца раздела» — в сочетании с `UNBOUNDED PRECEDING` даёт весь раздел целиком, независимо от позиции текущей строки; именно такая рамка нужна и для корректной работы `LAST_VALUE()`, если вы хотите получить действительно последнюю строку раздела, а не «последнюю среди строк до текущей включительно», которая при умолчании совпадает с самой текущей строкой.

### Резюме

- **`LAG(col, N)`** / **`LEAD(col, N)`** возвращают значение столбца из строки, смещённой на `N` позиций назад/вперёд относительно текущей в пределах окна; для строк у края окна, где соседа не существует, результат — `NULL` (или значение по умолчанию, заданное третьим аргументом).
- **`FIRST_VALUE()`** / **`LAST_VALUE()`** возвращают значение из первой/последней строки текущей **рамки** окна — не всего раздела, если рамка не расширена явно.
- **Рамка окна** (`ROWS BETWEEN ... AND ...`) определяет, какая часть раздела участвует в вычислении для текущей строки; при наличии `ORDER BY` без явной рамки MySQL по умолчанию берёт `UNBOUNDED PRECEDING AND CURRENT ROW` — отсюда эффект «накопительной суммы» у обычного оконного `SUM`/`AVG` с `ORDER BY`.
- Явное указание рамки (`ROWS BETWEEN N PRECEDING AND CURRENT ROW` для скользящего окна, `UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` для всего раздела) делает намерение запроса видимым и не зависящим от неочевидного умолчания.
- У краёв раздела рамка корректно сокращается до реально доступных строк, не вызывая ошибок и не «доливая» несуществующие данные.
- Оконные функции этого и прошлого урока вместе закрывают класс задач «вычислить что-то по группе строк, не теряя ни одной исходной строки» — от простой нумерации до накопительных итогов и сравнения с соседними периодами.

## Теоретические задания

### Вопрос 1: В отчёте помесячной выручки добавлен столбец `LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue`. Что вернёт этот столбец для самого первого месяца?

- ✅ `NULL` — предыдущей строки в окне физически не существует
<!-- NULL на краю окна — ожидаемое поведение LAG, как пустое множество у агрегатов (восьмой урок уровня «Начинающий») -->
- ❌ `0` — error_text: `LAG` не «додумывает» нулевое значение: строки раньше первой нет, и `NULL` корректно отражает это отсутствие — как `SUM` или `MAX` по пустому множеству. Если по смыслу нужен именно 0, его задают третьим аргументом: `LAG(revenue, 1, 0)`.
- ❌ ошибку выполнения — error_text: отсутствие соседа у края окна — штатная ситуация, а не ошибка: смещение просто выходит за пределы раздела, и MySQL возвращает `NULL`. Ошибкой было бы только некорректное смещение — например, отрицательное.
- ❌ выручку этого же первого месяца — error_text: `LAG` возвращает значение предыдущей строки, а не текущей; подстановка текущего значения означала бы «изменение всегда ноль». Для первой строки предыдущей нет — возвращается `NULL` (или значение по умолчанию третьим аргументом).

### Вопрос 2: Почему `SUM(amount) OVER (PARTITION BY customer_id ORDER BY created_at)` возвращает накопительную сумму, а не сумму всех заказов клиента?

- ✅ при наличии `ORDER BY` без явной рамки MySQL использует рамку по умолчанию — от начала раздела до текущей строки включительно, поэтому в сумму попадают только заказы до текущего
<!-- умолчание RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW -->
- ❌ `SUM` в окне всегда считает только пройденные строки — error_text: рамка — не свойство `SUM`, а свойство конструкции `OVER`: без `ORDER BY` или с рамкой `UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` в сумму попадёт весь раздел. Накопительность создаёт именно умолчание рамки при наличии `ORDER BY`.
- ❌ потому что `PARTITION BY` обрезает раздел по текущей строке — error_text: `PARTITION BY` лишь делит окно на части по `customer_id` и не «двигается» вместе с текущей строкой (это разбирали в пятом уроке уровня «Средний»). Движущейся границей управляет рамка, а не разбиение.
- ❌ потому что `ORDER BY` сортирует строки по возрастанию даты — error_text: `ORDER BY` задаёт порядок строк внутри раздела, но сам по себе никакой набор строк в вычислении не ограничивает. Ограничивает рамка — и её умолчание при `ORDER BY` как раз «от начала раздела до текущей строки включительно».

### Вопрос 3: Вычисляется `AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` — скользящее среднее по трём строкам. Что получится для самой первой строки раздела?

- ✅ среднее по одной доступной строке — самой первой: рамка у края раздела сокращается до реально существующих строк
<!-- рамка не дополняется несуществующими строками и не вызывает ошибку -->
- ❌ `NULL` — среднее по пустому множеству — error_text: множество не пусто: текущая строка всегда входит в рамку (`CURRENT ROW`), поэтому у первой строки в рамке одна строка — она сама. `NULL` получился бы, только если бы рамка не включала текущую строку.
- ❌ ошибку: для первой строки не хватает двух предыдущих — error_text: у края раздела рамка корректно сокращается до доступных строк — это штатное поведение. Ошибки нет ни для первой строки (рамка из одной строки), ни для второй (из двух).
- ❌ среднее по трём строкам соседнего раздела — error_text: рамка никогда не выходит за границу раздела, заданного `PARTITION BY` (а без него — за начало таблицы). Строки чужого раздела в скользящее окно не попадают — окно обрезается краем.

### Вопрос 4: `LAST_VALUE(amount) OVER (PARTITION BY customer_id ORDER BY created_at)` вернул для каждого заказа сумму самого этого заказа, а не сумму последнего заказа клиента. Почему?

- ✅ при рамке по умолчанию (до текущей строки включительно) «последняя» строка рамки — сама текущая; чтобы увидеть последнюю строку раздела, рамку нужно расширить до `UNBOUNDED FOLLOWING`
<!-- ловушка LAST_VALUE: значение берётся из рамки, а не из всего раздела -->
- ❌ `LAST_VALUE` всегда возвращает значение текущей строки — error_text: `LAST_VALUE` берёт последнюю строку текущей рамки. Если рамка расширена до `UNBOUNDED FOLLOWING`, функция честно вернёт последнюю строку раздела. Проблема не в функции, а в умолчании рамки при наличии `ORDER BY`.
- ❌ нужно было написать `LAST_VALUE(amount, 1)` — error_text: у `LAST_VALUE`, в отличие от `LAG`/`LEAD`, нет аргумента смещения. Управлять тем, какая строка считается «последней», можно только рамкой — например `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.
- ❌ нужно убрать `ORDER BY` из `OVER` — error_text: без `ORDER BY` рамка по умолчанию действительно станет «весь раздел», и `LAST_VALUE` вернёт последнюю строку — но «последнюю» в неопределённом порядке, потому что порядок строк в окне не задан. Корректное решение — сохранить `ORDER BY` и явно расширить рамку до `UNBOUNDED FOLLOWING`.

### Вопрос 5: Что делает третий аргумент в `LAG(revenue, 1, 0)`?

- ✅ подставляет `0` вместо `NULL` у строки, у которой нет предыдущей — например, у первой строки окна
<!-- значение по умолчанию вместо NULL на краю окна -->
- ❌ прибавляет 0 к значению предыдущей строки — error_text: третий аргумент не участвует в арифметике — это значение по умолчанию, которое возвращается вместо `NULL`, когда смещение выходит за край раздела. Прибавление нуля писалось бы снаружи функции: `LAG(revenue) + 0`.
- ❌ ограничивает смещение одной строкой максимум — error_text: число строк смещения — это второй аргумент (по умолчанию 1). Третий — значение по умолчанию вместо `NULL`: например, `LAG(revenue, 3, 0)` сместится на три строки и вернёт 0, если их не нашлось.
- ❌ заменяет `NULL` на `0` во всём столбце `revenue` — error_text: аргумент влияет только на результат самой функции, когда соседней строки не существует. Если в предыдущей строке столбец `revenue` сам содержит `NULL`, `LAG` вернёт именно этот `NULL` — значение по умолчанию его не заменяет.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT DATE_FORMAT(month, '%Y-%m') AS month, revenue, LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue, revenue - LAG(revenue) OVER (ORDER BY month) AS revenue_change FROM monthly_revenue ORDER BY month; -->

### Задание 3: Накопительные траты клиента

Накопительная сумма заказов каждого клиента через оконный `SUM` с `PARTITION BY` и `ORDER BY`.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT customer_id, id AS order_id, created_at, amount, SUM(amount) OVER (PARTITION BY customer_id ORDER BY created_at, id) AS running_total FROM orders ORDER BY customer_id, created_at, order_id; -->

**statement:**

Таблица `orders` (`id`, `customer_id`, `created_at DATE`, `amount`)
содержит заказы трёх клиентов за 2026 год; у клиента 2 два заказа
с одинаковой датой. Для каждого заказа выведите `running_total` —
сумму всех заказов его клиента от первого по дате до текущего
включительно: `SUM(amount) OVER (PARTITION BY customer_id ORDER BY
created_at, id)` (при равной дате меньший `id` считается раньше).
Накопительность здесь создаёт рамка по умолчанию при наличии
`ORDER BY`; явная запись — `ROWS BETWEEN UNBOUNDED PRECEDING AND
CURRENT ROW` — даёт тот же результат. Столбцы: `customer_id`,
`order_id` (это `id` заказа), `created_at`, `amount`, `running_total`.
Сортировка по `customer_id`, затем `created_at`, затем `order_id`.

**expected_result_text:**
