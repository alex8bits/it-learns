## Материал

Первые два урока показали индекс как «переключатель»: либо он есть и запрос быстрый, либо его нет и запрос читает всю таблицу. В реальной схеме почти все интересные запросы фильтруют или сортируют не по одному столбцу, а по нескольким сразу — «заказы клиента 42 со статусом paid, отсортированные по дате» — и здесь простого индекса по одному столбцу уже не хватает: нужны составные индексы и понимание того, как именно СУБД их использует, потому что интуитивные ожидания («индекс есть — значит, поможет») здесь регулярно расходятся с действительностью.

### Составной индекс: порядок столбцов имеет значение

**Составной индекс** (composite index) строится не по одному, а по нескольким столбцам сразу, в заданном порядке:

```sql
CREATE INDEX idx_orders_customer_status
ON orders (customer_id, status, created_at);
```

Физически такой индекс — это всё та же отсортированная B-tree структура (первый урок этого уровня), но ключом сортировки в ней служит **комбинация** значений трёх столбцов: сначала строки сортируются по `customer_id`, затем внутри одинакового `customer_id` — по `status`, и затем внутри одинаковой пары `(customer_id, status)` — по `created_at`. Это устройство прямо аналогично тому, как в бумажном телефонном справочнике записи сортируются сначала по фамилии, затем внутри одной фамилии — по имени: справочник, отсортированный так, отлично подходит для поиска «все Ивановы», но совершенно не подходит для поиска «все, у кого имя Пётр», если не листать его целиком — потому что имена без фамилии в такой сортировке разбросаны по всему справочнику.

### Leftmost prefix: правило «слева без пропусков»

Из физической структуры составного индекса следует ключевое правило, которое определяет, когда MySQL может его использовать — правило **leftmost prefix** («самый левый префикс»): индекс `(customer_id, status, created_at)` эффективно применяется для условий `WHERE`, которые ограничивают столбцы **последовательно слева, без пропусков**:

- `WHERE customer_id = 42` — использует индекс (задействует только первый столбец, но это допустимо: `ref` по префиксу индекса);
- `WHERE customer_id = 42 AND status = 'paid'` — использует индекс по первым двум столбцам;
- `WHERE customer_id = 42 AND status = 'paid' AND created_at > '2026-01-01'` — использует индекс по всем трём столбцам, максимально эффективно;
- `WHERE status = 'paid'` (без `customer_id`) — индекс **не может** быть использован для поиска по этому условию: в отсортированном по `customer_id` списке строки со `status = 'paid'` разбросаны по всей структуре, как имена без фамилий в примере со справочником — здесь понадобился бы полный проход по всему индексу (или таблице);
- `WHERE customer_id = 42 AND created_at > '2026-01-01'` (без `status`) — индекс используется только по первому столбцу `customer_id`; для условия по `created_at` он не поможет непосредственно, поскольку между `customer_id` и `created_at` в порядке индекса «встроен» пропущенный `status`.

Отсюда прямое практическое следствие: **порядок столбцов при создании составного индекса нужно выбирать исходя из того, как реально устроены запросы** — самый частый и самый избирательный столбец точечного равенства обычно ставится первым (или столбцы, всегда присутствующие в `WHERE` вместе), а столбец, участвующий в диапазонном условии (`>`, `<`, `BETWEEN`) или в `ORDER BY`, — как правило, последним, поскольку диапазонное условие «обрывает» полезность порядка для всех столбцов правее него в самом индексе.

### Покрывающий индекс: когда таблица вообще не нужна

Индекс хранит не только значения проиндексированных столбцов, но и (для не-первичных индексов InnoDB) значение первичного ключа строки — через него сервер, если нужно, обращается к самой таблице за остальными столбцами. Но если **все** столбцы, упомянутые в запросе (и в `SELECT`, и в `WHERE`), уже присутствуют в самом индексе, серверу не требуется вообще заглядывать в таблицу — достаточно данных из самого индекса. Такой индекс называется **покрывающим** (covering index) для конкретного запроса, а в плане `EXPLAIN` (второй урок этого уровня) это видно по пометке `Using index` в столбце `Extra`:

```sql
CREATE INDEX idx_orders_customer_status_covering
ON orders (customer_id, status, created_at);

EXPLAIN
SELECT customer_id, status, created_at
FROM orders
WHERE customer_id = 42 AND status = 'paid';
```

Если бы запрос запрашивал `SELECT *` (а не только три проиндексированных столбца), индекс перестал бы быть покрывающим для этого запроса — сервер использовал бы его для *поиска* нужных строк (это всё ещё быстрее полного сканирования), но для каждой найденной строки дополнительно обратился бы к самой таблице за оставшимися столбцами. Разница между «индекс просто нашёл строки» и «индекс полностью покрыл запрос» — заметный источник ускорения на таблицах с частыми, узкими, повторяющимися отчётными запросами, и одна из причин, по которой `SELECT *` — не просто вопрос стиля, а потенциальная потеря производительности (эта тема продолжится в следующем уроке об анти-паттернах).

### Селективность: почему не любой индекс одинаково полезен

**Селективность** столбца — это доля уникальных значений среди всех строк таблицы. Столбец `orders.id` (первичный ключ) обладает максимальной селективностью — каждое значение уникально. Столбец `orders.status`, если в системе всего пять-шесть возможных статусов заказа на миллионы строк, обладает *низкой* селективностью — каждое значение соответствует огромной доле всей таблицы. Индекс по низкоселективному столбцу приносит мало пользы: условие `WHERE status = 'paid'` может отобрать, например, 40% всех строк таблицы — и в этом случае для сервера **дешевле** прочитать таблицу полностью (`type = ALL`), чем скакать по индексу, находя каждую подходящую строку и затем отдельно обращаясь к таблице за остальными столбцами (это как раз тот случай, упомянутый в конце второго урока: `EXPLAIN`, показывающий `type = ALL`, — не всегда сигнал отсутствующего индекса, иногда это осознанное и правильное решение оптимизатора). Оптимизатор MySQL принимает решение об использовании индекса именно на основе оценки селективности (статистики распределения значений, которую сервер поддерживает автоматически) — поэтому один и тот же индекс может быть проигнорирован для одного значения `status` (например, `'pending'`, если таких заказов почти все) и активно использован для другого (`'refunded'`, если таких заказов исключительно мало).

### Индекс и ORDER BY / GROUP BY: сортировка «бесплатно»

Поскольку значения в индексе физически хранятся в отсортированном порядке, тот же составной индекс `(customer_id, status, created_at)` способен удовлетворить не только `WHERE`, но и `ORDER BY created_at` **для строк одного и того же клиента и статуса** — сервер читает уже отсортированный кусок индекса и не выполняет отдельного шага сортировки (тот самый `Using filesort` из второго урока этого уровня, которого таким образом удаётся избежать):

```sql
EXPLAIN
SELECT id, created_at
FROM orders
WHERE customer_id = 42 AND status = 'paid'
ORDER BY created_at;
```

Это работает ровно потому, что порядок `ORDER BY` совпадает с «оставшимся» порядком индекса после применения условий равенства к его ведущим столбцам — принцип leftmost prefix действует одинаково и для условий `WHERE`, и для `ORDER BY`/`GROUP BY`: если бы запрос сортировался, например, по `status` (второй столбец индекса) при отсутствии условия равенства по `customer_id`, индекс не смог бы обеспечить нужный порядок бесплатно, и `Using filesort` появился бы снова.

### Когда индекс не работает: явные и неявные причины

Итог урока — сводный список ситуаций, в которых индекс, даже существующий и синтаксически подходящий, не приносит ожидаемой пользы:

- **Низкая селективность условия** — индекс по столбцу, где искомое значение занимает большую долю таблицы; оптимизатор осознанно выбирает полное сканирование как более дешёвый вариант (разобрано выше).
- **Нарушение leftmost prefix** — условие обращается не к самому левому столбцу составного индекса, или пропускает столбец в середине (разобрано выше).
- **Несовпадающий тип данных или неявное приведение типов** — сравнение `VARCHAR`-столбца с числом или условия, требующие скрытого преобразования типа для каждой строки, могут заставить сервер отказаться от индекса — сервер физически не может использовать отсортированный порядок исходных значений, если ему нужно сначала преобразовать каждое из них для сравнения.
- **Функция или выражение над индексированным столбцом в условии** — например, `WHERE YEAR(created_at) = 2026` требует вычислить `YEAR()` для *каждой* строки перед сравнением, что делает исходный порядок индекса по `created_at` бесполезным (эта проблема и её решение — тема следующего урока: анти-паттерны и их починка).

Разбор этих причин не самоцель — то, что индекс не сработал, ещё не значит, что «что-то пошло не так»: иногда это правильное решение оптимизатора при низкой селективности, а иногда — сигнал переписать сам запрос, а не просто добавить очередной индекс. Разграничение этих двух случаев — центральная тема капстоуна пятнадцатого урока этого уровня, а конкретные анти-паттерны и их починка — тема следующего, четвёртого урока.

### Резюме

- **Составной индекс** сортирует строки последовательно по нескольким столбцам сразу, в порядке их объявления в `CREATE INDEX` — этот порядок определяет, для каких запросов индекс полезен.
- **Leftmost prefix** — индекс эффективно используется для условий, ограничивающих его столбцы слева без пропусков; пропуск столбца в середине «отрезает» полезность индекса для столбцов правее пропуска.
- **Покрывающий индекс** содержит все столбцы, нужные запросу (и в `WHERE`, и в `SELECT`) — тогда сервер вообще не обращается к самой таблице, что видно в `EXPLAIN` по пометке `Using index`.
- **Селективность** — доля уникальных значений столбца; индекс по низкоселективному столбцу оптимизатор часто и справедливо игнорирует в пользу полного сканирования.
- Составной индекс может «бесплатно» удовлетворить `ORDER BY`/`GROUP BY`, избегая `Using filesort`, если порядок сортировки совпадает с оставшимся порядком индекса после условий равенства по его ведущим столбцам.
- Индекс не срабатывает при низкой селективности условия, нарушении leftmost prefix, несовпадении типов данных при сравнении и при применении функции к индексированному столбцу непосредственно в условии `WHERE`.

## Теоретические задания

### Вопрос 1: В таблице есть составной индекс `(customer_id, status, created_at)`. Какое условие сможет использовать его для поиска?

- ✅ `WHERE customer_id = 42 AND status = 'paid' AND created_at > '2026-01-01'`
<!-- столбцы ограничены слева без пропусков — все три столбца индекса работают -->
- ❌ `WHERE status = 'paid'` — error_text: условие не затрагивает самый левый столбец `customer_id` — нарушено правило leftmost prefix. В структуре, отсортированной сначала по `customer_id`, строки со `status = 'paid'` разбросаны по всему индексу, и точечный вход в него невозможен.
- ❌ `WHERE created_at > '2026-01-01'` — error_text: условие обращается к третьему столбцу, пропуская оба ведущих. Порядок индекса определяется в первую очередь `customer_id`, затем `status` — значения `created_at` в нём «переплетены», искать по ним напрямую нельзя.
- ❌ `WHERE status = 'paid' AND created_at > '2026-01-01'` — error_text: условие начинается со второго столбца: между началом индекса и `created_at` «встроен» пропущенный `customer_id`. Без равенства по самому левому столбцу индекс для поиска применён быть не может.

### Вопрос 2: В каком порядке расставить столбцы составного индекса под запрос `WHERE customer_id = 42 AND status = 'paid' ORDER BY created_at`?

- ✅ `(customer_id, status, created_at)`: условия равенства — первыми, столбец диапазона и сортировки — последним
<!-- equality → range: диапазонное условие обрывает полезность порядка для столбцов правее -->
- ❌ `(created_at, status, customer_id)`: столбец сортировки первым — error_text: по ведущему столбцу `created_at` в запросе нет условия равенства — точечного входа в индекс не будет, а условия по `customer_id` и `status` окажутся «разбросаны» по всей структуре. Диапазон и сортировку ставят в конец индекса, а не в начало.
- ❌ `(status, customer_id, created_at)`: статус первым, ведь значений статуса меньше — error_text: малое число уникальных значений — это низкая селективность: первым ставят более селективный столбец точечного равенства. Индекс, начинающийся с `status`, сначала отделяет огромную долю строк и лишь потом фильтрует по `customer_id`.
- ❌ Порядок не важен: MySQL переставит столбцы под конкретный запрос — error_text: порядок столбцов фиксируется в `CREATE INDEX` и определяет физическую сортировку структуры B-tree. Перестроить порядок «на лету» под запрос сервер не может — для другого порядка нужен другой индекс.

### Вопрос 3: Что означает пометка `Using index` в столбце `Extra` плана `EXPLAIN`?

- ✅ Индекс покрывающий: все столбцы запроса есть в самом индексе, и таблица не читается вовсе
<!-- покрывающий индекс: SELECT и WHERE полностью удовлетворены индексом -->
- ❌ Запрос использует индекс первичного ключа — error_text: `Using index` — про покрывающий индекс, а не про первичный ключ. Какой именно индекс задействован, видно в столбце `key`; пометка в `Extra` означает, что обращения к самой таблице не было.
- ❌ В таблице есть индекс по всем её столбцам — error_text: покрывающим индекс делает не «индекс по всем столбцам таблицы», а совпадение столбцов конкретного запроса — и в `SELECT`, и в `WHERE` — со столбцами индекса. Один и тот же индекс покрывает один запрос и не покрывает другой, берущий из таблицы дополнительный столбец.
- ❌ Сервер не смог применить индекс и читает таблицу целиком — error_text: это описание `type = ALL`. `Using index` — противоположная ситуация: чтение идёт только из индекса, без дообращений к строкам таблицы за остальными столбцами.

### Вопрос 4: Столбец `status` принимает четыре значения на пяти миллионах строк, индекс по нему есть. Почему при `WHERE status = 'paid'` оптимизатор может выбрать полное сканирование?

- ✅ Низкая селективность: условие отбирает большую долю таблицы, и один линейный проход дешевле прыжков по индексу
<!-- осознанное решение оптимизатора, а не сбой; оценка по статистике распределения -->
- ❌ Индекс по строковому столбцу в MySQL не работает — error_text: работает: и точечный поиск, и сортировку. Дело не в типе столбца, а в доле отбираемых строк: когда значению отвечает огромная часть таблицы, проход по индексу с дообращением к таблице за каждой строкой дороже одного полного прохода.
- ❌ Оптимизатор всегда игнорирует неуникальные индексы — error_text: неуникальные индексы — нормальный рабочий случай (тип доступа `ref`). Игнорируется не индекс, а конкретное условие — когда его селективность низка и полное сканирование объективно дешевле.
- ❌ Статистика по таблице не обновляется автоматически, поэтому решение ошибочно — error_text: сервер поддерживает статистику распределения значений автоматически, и решение о полном сканировании в этой ситуации — осознанная оценка стоимости, а не сбой из-за устаревшей статистики.

### Вопрос 5: Индекс `(customer_id, status, created_at)`, условие `WHERE customer_id = 42`. Какой `ORDER BY` будет выполнен без `Using filesort`?

- ✅ `ORDER BY status, created_at`
<!-- порядок сортировки совпадает с оставшимся порядком индекса после равенства по ведущему столбцу -->
- ❌ `ORDER BY created_at` — error_text: между `customer_id` и `created_at` в порядке индекса стоит пропущенный `status`: внутри одного клиента строки идут в порядке `(status, created_at)`, а не `created_at`. Порядок «через столбец» индекс не даёт — появится filesort.
- ❌ `ORDER BY created_at, status` — error_text: порядок столбцов сортировки обратен порядку столбцов индекса. Бесплатная сортировка возможна, только когда столбцы `ORDER BY` идут в том же порядке, что и «оставшиеся» столбцы индекса, — здесь это `(status, created_at)`.
- ❌ `ORDER BY id` — error_text: хотя значение первичного ключа и хранится в составе вторичного индекса, порядок строк внутри одного `customer_id` определяется парой `(status, created_at)`. Сортировка по `id` этому порядку не соответствует — серверу понадобится отдельный шаг сортировки.

```sql
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```
