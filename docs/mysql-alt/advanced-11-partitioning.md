### Что такое партиционирование

**Партиционирование** — это разбиение данных одной таблицы на несколько физически отдельных частей (**партиций**) по правилу, зависящему от значения одного или нескольких столбцов, при этом с точки зрения любого SQL-запроса таблица остаётся **единой** — партиционирование не меняет ни синтаксис `SELECT`/`INSERT`/`UPDATE`/`DELETE`, ни видимую структуру таблицы для клиента. Это ключевое отличие от «шардирования» (упомянутого лишь обзорно в пятнадцатом уроке этого уровня) — там данные физически распределяются между разными серверами, а партиционирование происходит внутри одного и того же сервера и одной и той же таблицы, оставаясь полностью прозрачным для запросов.

### RANGE-партиционирование: диапазоны значений

Самый частый на практике вид — **RANGE**-партиционирование, разбивающее строки по диапазонам значений столбца, чаще всего даты:

```sql
CREATE TABLE order_log (
    id INT AUTO_INCREMENT,
    order_id INT NOT NULL,
    changed_at DATETIME NOT NULL,
    old_status VARCHAR(20),
    new_status VARCHAR(20) NOT NULL,
    PRIMARY KEY (id, changed_at)
)
PARTITION BY RANGE (YEAR(changed_at)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN (2027),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

Каждая строка при вставке автоматически попадает ровно в одну партицию — ту, чей диапазон соответствует значению `YEAR(changed_at)` для этой строки. Партиция `p_future` с границей `MAXVALUE` — распространённый приём «партиции-приёмника», гарантирующий, что вставка строки с датой за пределами явно перечисленных диапазонов не завершится ошибкой, а попадёт в эту последнюю, catch-all партицию.

Обратим внимание на важное синтаксическое требование: первичный ключ (или любой уникальный индекс) партиционированной таблицы **обязан включать** столбец, по которому идёт партиционирование (в примере — `changed_at` добавлен в составной первичный ключ `(id, changed_at)`), — это требование MySQL, гарантирующее, что сервер способен определить принадлежность строки конкретной партиции, не обращаясь ко всем партициям сразу при проверке уникальности.

### LIST-партиционирование: явные списки значений

**LIST**-партиционирование разбивает строки по явно перечисленным дискретным значениям, а не по диапазону — уместно для столбцов с небольшим, заранее известным набором категориальных значений:

```sql
CREATE TABLE orders_by_status (
    id INT NOT NULL,
    customer_id INT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (id, status)
)
PARTITION BY LIST COLUMNS (status) (
    PARTITION p_active VALUES IN ('pending', 'paid', 'shipped'),
    PARTITION p_closed VALUES IN ('delivered', 'cancelled', 'refunded')
);
```

Здесь каждая партиция соответствует не диапазону, а явно перечисленному конечному множеству значений `status` — строка со статусом, не упомянутым ни в одном списке, не попадёт ни в одну партицию, и попытка её вставить завершится ошибкой (в отличие от RANGE с партицией-приёмником `MAXVALUE`, у LIST-партиционирования нет встроенного аналога «партиции по умолчанию» для непредусмотренных значений).

### HASH-партиционирование: равномерное распределение

**HASH**-партиционирование не пытается сгруппировать строки по смысловому диапазону или категории — оно вычисляет хеш-функцию от значения указанного столбца (или выражения) и по остатку от деления на число партиций равномерно распределяет строки между ними:

```sql
CREATE TABLE customers_hashed (
    id INT NOT NULL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    city VARCHAR(100),
    registered_at DATETIME NOT NULL
)
PARTITION BY HASH (id)
PARTITIONS 4;
```

Цель HASH-партиционирования — не оптимизация запросов по конкретному диапазону или категории (в отличие от RANGE и LIST), а равномерное распределение операций записи и чтения между несколькими физическими частями таблицы, что может снизить конкуренцию за внутренние ресурсы сервера при очень высокой интенсивности параллельных операций. Для большинства учебных и умеренно нагруженных практических сценариев RANGE и LIST приносят больше очевидной пользы, чем HASH, — HASH-партиционирование релевантно в первую очередь для узкоспециализированных сценариев с экстремальной параллельной нагрузкой.

### Partition pruning: как партиционирование ускоряет запросы

Главный практический эффект партиционирования для чтения — **partition pruning** («обрезка партиций»): если условие `WHERE` запроса позволяет оптимизатору однозначно определить, что искомые строки могут находиться только в одной или нескольких конкретных партициях, сервер **физически не обращается** к остальным партициям вообще — они полностью пропускаются, как если бы их не существовало для этого конкретного запроса:

```sql
EXPLAIN
SELECT * FROM order_log
WHERE changed_at >= '2026-01-01' AND changed_at < '2026-02-01';
```

Вывод `EXPLAIN` (второй урок этого уровня) для партиционированной таблицы содержит дополнительный столбец `partitions`, показывающий, какие именно партиции сервер собирается читать — для запроса выше это будет только `p2026`, независимо от того, сколько всего строк накопилось в `p2024` и `p2025`. Partition pruning работает **независимо** от обычных индексов и дополняет их: даже без единого дополнительного индекса на `changed_at`, сам факт того, что запрос читает одну партицию из четырёх, а не все данные таблицы сразу, — это уже кратное сокращение объёма данных, который нужно просмотреть. Комбинация правильного партиционирования и подходящего обычного индекса *внутри* каждой партиции (второй и третий уроки этого уровня) даёт наибольший эффект: сначала pruning отбрасывает ненужные партиции целиком, а затем индекс ускоряет поиск внутри оставшихся.

### Практическая ценность для журналов и больших исторических таблиц

Помимо ускорения чтения, партиционирование по дате даёт особенно ценный практический эффект для таблиц вроде `order_log` — **дешёвое удаление устаревших данных**. Вместо `DELETE FROM order_log WHERE changed_at < '2024-01-01';` (операция, которая на партиции с миллионами строк потребует построчного удаления и записи в журнал транзакций для каждой удаляемой строки — девятый урок уровня «Средний» напоминает, что любое изменение данных обёрнуто в транзакционные гарантии, и это не бесплатно для большого объёма строк), партиционированную по годам таблицу можно «очистить» от целого устаревшего года почти мгновенно:

```sql
ALTER TABLE order_log DROP PARTITION p2024;
```

`DROP PARTITION` физически удаляет партицию целиком — это операция уровня файловой системы (удаление файла или сегмента файла, в котором физически хранилась партиция), а не построчное `DELETE`, поэтому она выполняется за доли секунды независимо от того, сколько миллионов строк было в удаляемой партиции. Ровно такой сценарий — периодическое добавление новой партиции под новый период (`ALTER TABLE ... ADD PARTITION`) и удаление самой старой — типичное «скользящее окно» для журналов и временных рядов, и естественный кандидат на автоматизацию через `EVENT` из седьмого урока этого уровня.

### Ограничения партиционирования

Партиционирование — не универсальный инструмент «на все случаи больших таблиц», и у него есть значимые ограничения, которые нужно учитывать перед проектированием:

- **Первичный и любой уникальный ключ обязаны включать столбец партиционирования** (показано выше) — это может потребовать пересмотра структуры ключа существующей таблицы, если партиционирование добавляется к уже спроектированной схеме.
- **`FOREIGN KEY` не поддерживаются партиционированными таблицами InnoDB напрямую** — партиционированная таблица не может ссылаться на другую через внешний ключ и не может быть целью ссылки от другой таблицы. Для сквозного датасета курса это означает, что партиционировать, например, саму таблицу `orders` (на которую ссылается `order_items` через `order_id`) без пересмотра всей схемы связей было бы невозможно — партиционирование `order_log`, у которой в датасете курса нет исходящих/входящих `FOREIGN KEY`, подобной проблемы не создаёт.
- **Запрос без условия на столбец партиционирования** не получает выгоды от pruning вообще — сервер обязан просмотреть все партиции, как если бы таблица не была партиционирована; в этом случае партиционирование не ухудшает производительность запроса, но и не улучшает её.
- **Слишком мелкое или слишком крупное партиционирование** снижает пользу: сотни крошечных партиций создают накладные расходы на управление метаданными каждой из них, а несколько огромных партиций не дают достаточной granularity ни для pruning, ни для дешёвого удаления устаревших данных. Выбор границ партиций (по годам, месяцам, неделям) — инженерное решение, зависящее от реального объёма данных за период и от того, каким периодом обычно ограничены запросы к таблице.

### Резюме

- **Партиционирование** физически разбивает одну логическую таблицу на несколько отдельно хранимых частей по правилу, зависящему от значения столбца, оставаясь полностью прозрачным для синтаксиса SQL-запросов.
- **RANGE** — партиции по диапазонам значений (типично — по дате, с партицией-приёмником `VALUES LESS THAN MAXVALUE` для значений за пределами явных диапазонов).
- **LIST** — партиции по явно перечисленным дискретным значениям категориального столбца, без встроенной партиции по умолчанию для непредусмотренных значений.
- **HASH** — равномерное распределение строк между партициями по значению хеш-функции; не оптимизирует конкретные диапазонные запросы, а снижает конкуренцию за ресурсы при высокой параллельной нагрузке.
- **Partition pruning** — сервер физически пропускает партиции, не подходящие условию `WHERE`, что видно в `EXPLAIN` по столбцу `partitions`; работает независимо от обычных индексов и дополняет их.
- **`ALTER TABLE ... DROP PARTITION`** удаляет партицию целиком почти мгновенно (в отличие от построчного `DELETE`) — ключевая практическая ценность RANGE-партиционирования по дате для журналов и временных рядов, типа `order_log`.
- Ограничения: первичный/уникальный ключ обязан включать столбец партиционирования; партиционированные таблицы InnoDB не поддерживают `FOREIGN KEY`; запрос без условия на столбец партиционирования не получает выгоды pruning; выбор granularity партиций — инженерный компромисс между накладными расходами на метаданные и полезной детализацией.
