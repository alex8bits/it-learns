В первом уроке этого уровня мы познакомились с производной таблицей — подзапросом в `FROM`, который ведёт себя как временная таблица. У производных таблиц есть неудобство, которое становится заметным, когда запрос усложняется: если один и тот же промежуточный результат нужен несколько раз в разных частях основного запроса, производную таблицу пришлось бы **дублировать текстуально** — писать один и тот же вложенный `SELECT` заново в каждом месте, где он нужен. А если такой запрос вложен глубоко — скобки внутри скобок внутри скобок — читать его становится тяжело. **Common Table Expression** (CTE, «обобщённое табличное выражение») решает обе проблемы: даёт промежуточному результату имя один раз и позволяет ссылаться на него по этому имени сколько угодно раз в основном запросе, при этом текст запроса читается сверху вниз, а не разворачивается «изнутри наружу», как вложенные подзапросы.

### Синтаксис WITH: именование производной таблицы

CTE объявляется ключевым словом `WITH` перед основным запросом:

```sql
WITH expensive_products AS (
    SELECT id, name, price, category_id
    FROM products
    WHERE price > 10000
)
SELECT category_id, COUNT(*) AS expensive_count
FROM expensive_products
GROUP BY category_id;
```

Смысл конструкции: `expensive_products` — это имя, под которым временно, только на время выполнения этого запроса, доступен результат вложенного `SELECT`. Основной запрос после `WITH ... AS (...)` использует `expensive_products` в `FROM` совершенно так же, как использовал бы обычную таблицу. По сравнению с производной таблицей из первого урока разница чисто структурная: там временный результат был написан прямо внутри `FROM` основного запроса (`FROM (SELECT ...) AS stats`), а здесь он вынесен и назван **перед** основным запросом — но лежащая в основе идея («вычислить набор строк один раз, дать ему имя, использовать как таблицу») та же самая.

Разница становится практически значимой, когда одно и то же CTE нужно использовать **несколько раз**. Например, посчитать не только количество дорогих товаров по категориям, но и сравнить со средней ценой среди них:

```sql
WITH expensive_products AS (
    SELECT id, name, price, category_id
    FROM products
    WHERE price > 10000
)
SELECT
    category_id,
    COUNT(*) AS expensive_count,
    AVG(price) AS avg_expensive_price,
    (SELECT COUNT(*) FROM expensive_products) AS total_expensive_overall
FROM expensive_products
GROUP BY category_id;
```

Здесь `expensive_products` использована и в основном `FROM`, и внутри дополнительного скалярного подзапроса — с производной таблицей пришлось бы дважды выписывать один и тот же `WHERE price > 10000`, рискуя случайно изменить условие в одном месте и забыть в другом.

### Цепочки CTE: несколько именованных шагов подряд

`WITH` допускает несколько CTE через запятую — каждое следующее может использовать результаты предыдущих, что превращает сложный запрос в последовательность понятных, именованных шагов:

```sql
WITH order_totals AS (
    SELECT
        o.id AS order_id,
        o.customer_id,
        SUM(oi.quantity * oi.price) AS order_total
    FROM orders o
    INNER JOIN order_items oi ON oi.order_id = o.id
    GROUP BY o.id, o.customer_id
),
customer_totals AS (
    SELECT
        customer_id,
        COUNT(*) AS orders_count,
        SUM(order_total) AS total_spent
    FROM order_totals
    GROUP BY customer_id
)
SELECT
    c.name,
    ct.orders_count,
    ct.total_spent
FROM customer_totals ct
INNER JOIN customers c ON c.id = ct.customer_id
ORDER BY ct.total_spent DESC;
```

Каждый шаг решает одну понятную задачу: `order_totals` считает сумму каждого заказа (используя `SUM`/`GROUP BY` из восьмого-девятого уроков уровня «Начинающий»), `customer_totals` агрегирует эти суммы уже по клиенту, а финальный `SELECT` просто присоединяет имя клиента и сортирует результат. По сравнению с эквивалентной записью через вложенные друг в друга подзапросы в `FROM` (`FROM (SELECT ... FROM (SELECT ...) AS x GROUP BY ...) AS y`), цепочка CTE читается **сверху вниз, в порядке размышления**, а не «изнутри наружу» — это не даёт новых возможностей по сравнению с подзапросами, но заметно облегчает чтение и сопровождение сложных запросов, что для запросов из нескольких агрегаций подряд оказывается решающим на практике.

### Рекурсивные CTE: обход иерархий

Обычное CTE выполняется один раз и не может ссылаться само на себя. Но у MySQL (начиная с версии 8.0) есть особая форма — **рекурсивное CTE** (`WITH RECURSIVE`), которая умеет ссылаться сама на себя и повторять вычисление, пока не иссякнут новые строки. Это единственный инструмент курса, способный элегантно решить задачу, которая не давалась предыдущим средствам: обойти **дерево произвольной глубины**, например, дерево категорий товаров (`categories` с `parent_id`, знакомое по пятнадцатому уроку уровня «Начинающий», где self-join находил только одно поколение — прямых потомков или прямого родителя, а не всё дерево целиком).

Рекурсивное CTE состоит из двух частей, соединённых `UNION ALL` (третий урок этого уровня):

```sql
WITH RECURSIVE category_tree AS (
    -- Якорная часть: стартовая точка рекурсии
    SELECT id, name, parent_id, 0 AS depth
    FROM categories
    WHERE id = 1

    UNION ALL

    -- Рекурсивная часть: находит "детей" уже найденных строк
    SELECT c.id, c.name, c.parent_id, ct.depth + 1
    FROM categories c
    INNER JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT id, name, depth
FROM category_tree
ORDER BY depth, id;
```

Механика выполнения устроена так:

1. **Якорная часть** (anchor member) — выполняется один раз и даёт начальный набор строк: в примере это одна категория с `id = 1` и глубиной `depth = 0`.
2. **Рекурсивная часть** (recursive member) — соединяет `categories` с **уже накопленным** результатом `category_tree` (это и есть ссылка CTE на само себя) и находит прямых потомков строк, найденных на предыдущем шаге, увеличивая `depth` на единицу.
3. MySQL повторяет шаг 2 снова и снова, каждый раз используя результат **предыдущей** итерации как вход для следующей, пока рекурсивная часть не перестанет находить новые строки (то есть пока у самых глубоких найденных категорий не окажется больше непроверенных детей).
4. Итоговый результат `category_tree` — объединение (`UNION ALL`) якорной строки и всех строк, найденных на каждой итерации.

Результат такого запроса — вся ветвь дерева категорий, начиная с категории 1 и вниз до самых глубоких вложенных подкатегорий, с явным указанием глубины каждой найденной категории — задача, которую self-join из пятнадцатого урока решить не мог в принципе, потому что заранее неизвестно, сколько уровней вложенности потребуется соединить.

### Практическая опасность рекурсии: бесконечный цикл

У рекурсивного CTE есть риск, которого не было ни у одной конструкции курса до сих пор: если данные организованы так, что рекурсивная часть **никогда** не перестаёт находить новые строки (например, из-за ошибочно зациклённых `parent_id`, где категория A указывает на B, а B — обратно на A), выполнение теоретически может продолжаться бесконечно. MySQL защищается от этого системной переменной `cte_max_recursion_depth` (по умолчанию 1000): если число итераций превысит это значение, сервер прервёт выполнение с ошибкой, а не зависнет навечно. Тем не менее закладываться на этот предохранитель как на «нормальное» поведение не стоит — он существует для аварийной остановки, а не как способ намеренно ограничить глубину дерева; для реального ограничения глубины лучше добавлять явное условие (`WHERE depth < N`) в рекурсивную часть.

### Ещё один пример: календарная таблица

Рекурсивные CTE полезны не только для деревьев — их часто используют, чтобы сгенерировать последовательность значений, которой нет ни в одной таблице базы, например, список всех дат месяца (это нужно, чтобы в отчёте по датам не пропадали дни без единого заказа — проблема, с которой чистый `GROUP BY` без данных за конкретный день справиться не может, ведь группировать нечего, если строк с этой датой не существует):

```sql
WITH RECURSIVE calendar AS (
    SELECT DATE('2025-01-01') AS day

    UNION ALL

    SELECT day + INTERVAL 1 DAY
    FROM calendar
    WHERE day < '2025-01-31'
)
SELECT day FROM calendar;
```

Якорная часть даёт первый день месяца, а рекурсивная — на каждой итерации добавляет один день к последнему найденному, пока не дойдёт до условия останова (`day < '2025-01-31'`, то есть последняя добавленная дата — 31 января). Условие останова здесь не отдельная «защита от бесконечного цикла», а прямая часть бизнес-логики: без него рекурсия остановилась бы только при достижении `cte_max_recursion_depth`, что и не совпадает с нужным результатом, и опирается на неявный предохранитель там, где должно быть явное условие.

### CTE против производной таблицы: когда какую форму выбрать

Обе конструкции взаимозаменяемы для нерекурсивных случаев — движок MySQL в большинстве случаев обрабатывает их одинаково эффективно. Разница — в удобстве для человека, читающего запрос:

- **CTE** предпочтительно, когда промежуточный результат используется несколько раз, когда есть несколько последовательных шагов вычисления (цепочка), или когда конструкция сама себе не помещается в одну строку и выигрывает от именования, — то есть почти всегда в сложных аналитических запросах.
- **Производная таблица** остаётся уместной для одноразового, короткого, самоочевидного вложения, где заводить отдельное имя было бы избыточно.
- **Рекурсивное CTE** — единственный вариант, когда нужен обход иерархии произвольной глубины или генерация последовательности значений, не хранящейся в таблице.

### Резюме

- **CTE** (`WITH имя AS (SELECT ...)`) даёт подзапросу имя, под которым он доступен в основном запросе как обычная таблица — по смыслу то же самое, что производная таблица, но читается сверху вниз и позволяет использовать один и тот же промежуточный результат несколько раз без дублирования текста.
- **Цепочка CTE** (`WITH a AS (...), b AS (...) SELECT ...`) превращает сложный многошаговый запрос в последовательность именованных, понятных шагов; каждый следующий CTE может использовать предыдущие.
- **`WITH RECURSIVE`** состоит из якорной части (стартовые строки) и рекурсивной части (находит следующий «слой» на основе уже накопленного результата), объединённых `UNION ALL`; выполняется, пока рекурсивная часть находит новые строки.
- Рекурсивные CTE решают задачи, недоступные self-join: обход дерева произвольной глубины (иерархия категорий), генерация последовательности значений, не хранящейся ни в одной таблице (календарная таблица).
- Без явного условия останова рекурсия может уйти в бесконечный цикл; системный предохранитель `cte_max_recursion_depth` прерывает такие случаи аварийно, но не заменяет осмысленное условие останова в самом запросе.
- Для нерекурсивных случаев CTE и производная таблица эквивалентны по возможностям — выбор определяется читаемостью: одноразовое короткое вложение — производная таблица, многошаговое или повторно используемое вычисление — CTE.
