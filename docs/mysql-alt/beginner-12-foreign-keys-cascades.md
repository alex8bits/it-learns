Но пока эта идея существовала только «по договорённости» — ничто не мешало вставить в `orders.customer_id` значение `9999`, даже если клиента с `id = 9999` не существует вовсе, или удалить клиента, у которого остались активные заказы, оставив их «висящими в воздухе», ссылающимися на несуществующую строку. Чтобы такие нарушения целостности данных были невозможны на уровне самой СУБД, а не только на уровне дисциплины программиста, MySQL предоставляет формальное ограничение `FOREIGN KEY` — тема этого урока.

### FOREIGN KEY: формальное объявление связи

Ограничение `FOREIGN KEY` объявляется при создании таблицы (`CREATE TABLE`, знакомая нам с шестого урока «Основ») и указывает, что значения одного столбца обязаны либо совпадать со значением первичного ключа в указанной связанной таблице, либо быть `NULL` (если сам столбец допускает `NULL`). Создадим таблицу `orders`, у которой `customer_id` формально ссылается на `customers.id`:

```sql
CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'new',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id) REFERENCES customers(id)
);
```

Строка `FOREIGN KEY (customer_id) REFERENCES customers(id)` — само объявление ограничения: она сообщает СУБД, что значение `customer_id` в каждой строке `orders` должно соответствовать реально существующему значению `id` в таблице `customers`. С этого момента любая попытка нарушить это правило будет отклонена самой базой данных — независимо от того, откуда пришёл запрос и насколько внимателен был программист, писавший его.

Проверим это на практике. Попытка вставить заказ с несуществующим `customer_id`:

```sql
INSERT INTO orders (customer_id, status) VALUES (9999, 'new');
-- Ошибка: Cannot add or update a child row: a foreign key constraint fails
```

MySQL немедленно отклоняет такую вставку с ошибкой — потому что клиента с `id = 9999` не существует в `customers`, а ограничение `FOREIGN KEY` требует обязательного совпадения. Это ровно та защита целостности данных, о которой мы говорили ещё в первом уроке «Основ», обсуждая проблемы хранения данных в обычном файле — теперь мы видим её конкретную, работающую реализацию.

### Именование внешнего ключа

Синтаксис выше создаёт ограничение с автоматически сгенерированным именем. Чтобы иметь возможность впоследствии удобно ссылаться на конкретное ограничение (например, для его удаления через `ALTER TABLE`, знакомый нам с седьмого урока «Основ»), полезно назначать имя явно через `CONSTRAINT`:

```sql
CREATE TABLE order_items (
    id INT AUTO_INCREMENT PRIMARY KEY,
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL DEFAULT 1,
    price DECIMAL(10, 2) NOT NULL,
    CONSTRAINT fk_order_items_order FOREIGN KEY (order_id) REFERENCES orders(id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products(id)
);
```

Здесь наглядно видна связующая таблица M:N из предыдущего урока: `order_items` объявляет **два** внешних ключа — на `orders` и на `products` — и именно эта пара ссылок реализует связь «многие ко многим» между заказами и товарами.

### Проблема удаления связанной строки

Формальное ограничение `FOREIGN KEY` защищает не только от вставки «висящих» ссылок, но и от удаления строки, на которую всё ещё есть ссылки. Представим, что мы попытались удалить клиента, у которого есть хотя бы один заказ:

```sql
DELETE FROM customers WHERE id = 42;
-- Ошибка: Cannot delete or update a parent row: a foreign key constraint fails
```

По умолчанию (это поведение называется `RESTRICT`, о нём чуть ниже подробнее) MySQL **запрещает** такое удаление — потому что если бы клиент удалился, у оставшихся заказов `customer_id = 42` стал бы ссылкой на несуществующую строку, что нарушило бы целостность данных, ту самую, которую всё ограничение и призвано защищать. Возникает практический вопрос: а что, если удаление клиента вместе со всей его историей заказов — это ровно то, что нужно сделать (например, по требованию клиента о полном удалении его данных)? Для описания того, что должно происходить со связанными строками при удалении (или изменении) «родительской» строки, в `FOREIGN KEY` предусмотрены специальные модификаторы `ON DELETE` и `ON UPDATE`.

### ON DELETE RESTRICT (и NO ACTION) — поведение по умолчанию

`RESTRICT` — поведение, которое мы только что наблюдали: удаление родительской строки **запрещается**, если на неё есть хотя бы одна ссылка из связанной таблицы. Явно это записывается так (хотя, поскольку это поведение и без явного указания подразумевается по умолчанию, такую запись часто не пишут вовсе):

```sql
FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT
```

`NO ACTION` в MySQL ведёт себя фактически идентично `RESTRICT` — оба варианта блокируют операцию, нарушающую целостность; различие между ними в стандарте SQL касается момента проверки внутри транзакции (тема, которую подробно разберём на уровне «Средний», обсуждая транзакции), и на уровне «Начинающий» их можно считать взаимозаменяемыми.

### ON DELETE CASCADE — удаление «по цепочке»

`CASCADE` означает, что при удалении родительской строки все связанные строки-«потомки» **удаляются автоматически**, вместе с ней:

```sql
CREATE TABLE order_items (
    id INT AUTO_INCREMENT PRIMARY KEY,
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL DEFAULT 1,
    price DECIMAL(10, 2) NOT NULL,
    FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT
);
```

С таким объявлением удаление заказа автоматически удалит **все** его позиции из `order_items` — их отдельно удалять вручную не нужно, СУБД сделает это сама, обеспечив, что после удаления заказа не останется «осиротевших» строк `order_items`, ссылающихся на несуществующий `order_id`:

```sql
DELETE FROM orders WHERE id = 15;
-- вместе с заказом автоматически удалятся все его строки в order_items
```

При этом мы намеренно оставили `ON DELETE RESTRICT` для связи с `products` — потому что удаление товара, который упоминается в истории уже совершённых заказов, **не** должно приводить к автоматической, «тихой» потере исторических данных о том, что было продано; такое удаление должно быть либо вообще запрещено, либо (что чаще встречается в реальных системах) заменено не физическим `DELETE`, а установкой отдельного признака «товар снят с продажи» — это уже вопрос дизайна приложения, а не самого `FOREIGN KEY`. `CASCADE` — мощный, но и по-настоящему опасный инструмент: он способен незаметно удалить огромный объём данных одной операцией `DELETE` над «верхней» строкой, поэтому применять его стоит осознанно, только там, где связанные строки-потомки действительно не имеют смысла без родительской записи (как позиции заказа без самого заказа), а не по умолчанию «на всякий случай».

### ON DELETE SET NULL — обрыв связи без удаления

`SET NULL` при удалении родительской строки не удаляет связанные строки, а **устанавливает** внешний ключ в `NULL` — связь обрывается, но сама «дочерняя» строка остаётся в таблице. Этот вариант применим **только** если столбец внешнего ключа допускает `NULL` (то есть не объявлен `NOT NULL`) — иначе `SET NULL` вошёл бы в противоречие с ограничением `NOT NULL`, и MySQL просто не даст создать такую комбинацию ограничений. Представим, что у товаров есть необязательная ссылка на «рекомендованного поставщика» — отдельную таблицу `suppliers`, которую поставщик может удалить из системы, но сами товары при этом не должны исчезать:

```sql
CREATE TABLE products (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    preferred_supplier_id INT NULL,
    FOREIGN KEY (preferred_supplier_id) REFERENCES suppliers(id) ON DELETE SET NULL
);
```

При удалении строки из `suppliers` все товары, у которых `preferred_supplier_id` указывал на неё, автоматически получат `preferred_supplier_id = NULL` — товар останется в каталоге, просто информация о «рекомендованном поставщике» пропадёт, что вполне соответствует смыслу данных: поставщика больше нет, но это не причина удалять сам товар.

### ON UPDATE: та же логика для изменения первичного ключа

Модификатор `ON UPDATE` описывает точно такую же логику (`RESTRICT`, `CASCADE`, `SET NULL`), но применительно к ситуации, когда изменяется значение первичного ключа родительской строки (а не сама строка удаляется):

```sql
FOREIGN KEY (customer_id) REFERENCES customers(id)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
```

`ON UPDATE CASCADE` означает: если значение `customers.id` для какой-то строки изменится (на практике это происходит крайне редко, если первичный ключ — автоинкрементный `AUTO_INCREMENT` из шестого урока «Основ», значения которого обычно вообще не изменяются вручную после создания строки), все ссылки на него из `orders.customer_id` автоматически обновятся на новое значение, синхронно с родительской строкой.

### Резюме

- `FOREIGN KEY (столбец) REFERENCES таблица(столбец)` — формальное ограничение, требующее, чтобы значение столбца совпадало с существующим значением первичного ключа связанной таблицы (или было `NULL`, если столбец это допускает); нарушающие вставки/обновления отклоняются самой СУБД.
- Именование через `CONSTRAINT имя FOREIGN KEY ...` облегчает последующее управление ограничением (например, его удаление через `ALTER TABLE`).
- Связующая таблица для связи M:N (например, `order_items`) объявляет сразу два внешних ключа — по одному на каждую из связанных «главных» таблиц.
- `ON DELETE RESTRICT` (поведение по умолчанию, `NO ACTION` — практически то же самое) — запрещает удаление родительской строки, если на неё есть ссылки.
- `ON DELETE CASCADE` — автоматически удаляет все связанные строки-потомки вместе с родительской; мощный, но потенциально опасный инструмент — годится для данных, не имеющих смысла без родителя (позиции заказа без заказа), но не для случаев, где нужно сохранить историю.
- `ON DELETE SET NULL` — обрывает ссылку, устанавливая внешний ключ в `NULL`, без удаления самой дочерней строки; требует, чтобы столбец допускал `NULL`.
- `ON UPDATE` описывает ту же логику (`RESTRICT`/`CASCADE`/`SET NULL`) для случая изменения значения первичного ключа родительской строки, а не её удаления.
