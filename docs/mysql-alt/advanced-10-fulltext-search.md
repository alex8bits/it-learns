Четвёртый урок этого уровня уже дал прямой ответ на вопрос «что делать, если нужно искать подстроку где угодно внутри текста»: `LIKE '%слово%'` с ведущим `%` не может использовать обычный B-tree индекс ни при каких условиях, и для по-настоящему массового поиска по содержимому текста нужен принципиально другой инструмент. Этот урок вводит его — **полнотекстовый поиск** (full-text search), встроенный в MySQL механизм, спроектированный именно для задачи «найти документы, релевантные набору слов», а не для точного совпадения значения или его префикса.

### Зачем полнотекстовый поиск, если есть LIKE

Разница между `LIKE '%слово%'` и полнотекстовым поиском — не только в скорости (хотя и в ней тоже: `LIKE` с ведущим `%` всегда требует полного просмотра). Она в самой природе задачи. `LIKE` ищет точное вхождение подстроки байт-в-байт, без какого-либо понимания структуры текста: запрос `WHERE body LIKE '%клавиатур%'` не найдёт отзыв со словом «клавиатуры» (с другим окончанием, если искать точное `'%клавиатура%'`), не отличит совпадение внутри значимого слова от случайного совпадения внутри другого слова, и не умеет ранжировать найденные строки по тому, насколько хорошо они соответствуют запросу — либо строка совпала, либо нет. Полнотекстовый поиск, напротив, разбивает текст на отдельные слова заранее (при индексации), понимает границы слов, умеет искать по нескольким словам сразу с учётом их совместного появления в тексте и возвращает числовую **релевантность** — оценку того, насколько хорошо конкретная строка соответствует запросу, по которой результаты естественно сортируются от наиболее подходящих к наименее.

### Создание FULLTEXT-индекса

`FULLTEXT`-индекс создаётся так же, как и обычный, но с ключевым словом `FULLTEXT`, и, в отличие от обычного B-tree индекса, поддерживается только для столбцов типа `CHAR`/`VARCHAR`/`TEXT`:

```sql
CREATE FULLTEXT INDEX idx_reviews_body_fulltext
ON reviews (body);
```

Или прямо при создании таблицы (седьмой урок уровня «Основы»):

```sql
CREATE TABLE reviews (
    id INT AUTO_INCREMENT PRIMARY KEY,
    product_id INT NOT NULL,
    customer_id INT NOT NULL,
    rating TINYINT NOT NULL,
    body TEXT,
    created_at DATETIME NOT NULL,
    FULLTEXT INDEX idx_reviews_body_fulltext (body)
);
```

`FULLTEXT`-индекс можно создать сразу по нескольким текстовым столбцам одновременно (например, по `name` товара и его текстовому описанию вместе) — в этом случае поиск учитывает совпадения в любом из индексированных столбцов как часть общей релевантности одной и той же строки.

### MATCH ... AGAINST: базовый синтаксис

Поиск по `FULLTEXT`-индексу выполняется не через `LIKE`, а через специальную конструкцию `MATCH(столбцы) AGAINST(поисковая_строка)`:

```sql
SELECT id, body,
       MATCH(body) AGAINST('клавиатура удобная') AS relevance
FROM reviews
WHERE MATCH(body) AGAINST('клавиатура удобная')
ORDER BY relevance DESC;
```

Конструкция `MATCH(body) AGAINST(...)` возвращает числовое значение релевантности (тем больше, чем лучше строка соответствует запросу) и используется одновременно двумя способами: в `WHERE` — как условие отбора (строки с релевантностью `0` считаются не соответствующими запросу и не проходят фильтр), и в `SELECT`/`ORDER BY` — как непосредственное значение для показа или сортировки. Оба использования в одном запросе (как в примере выше) — стандартный, наиболее частый паттерн: MySQL достаточно умён, чтобы вычислить релевантность один раз и не пересчитывать её отдельно для `WHERE` и для `SELECT`.

### Режим Natural Language (по умолчанию)

Показанный выше пример работает в режиме **Natural Language** — режиме по умолчанию, если явно не указано иное. В этом режиме поисковая строка интерпретируется как «естественный», человеческий текст: MySQL сам разбивает её на слова, ищет строки, содержащие эти слова (не обязательно все сразу и не обязательно подряд), и рассчитывает релевантность на основе того, сколько раз и насколько «редко» (по всей таблице) встречается каждое из искомых слов — принцип, отдалённо похожий на то, как работают поисковые системы в интернете: чем реже слово встречается в целом по коллекции документов, тем больше вес несёт его совпадение в конкретном документе.

### Режим Boolean: явные операторы поиска

Режим **Boolean** включается явным указанием `IN BOOLEAN MODE` и позволяет управлять поиском через явные операторы прямо в поисковой строке, а не полагаться на автоматическую интерпретацию естественного языка:

```sql
SELECT id, body
FROM reviews
WHERE MATCH(body) AGAINST('+клавиатура -неудобная' IN BOOLEAN MODE);
```

Основные операторы Boolean-режима:

- `+слово` — слово **обязательно** должно присутствовать (в Natural Language режиме слова не обязательны, только желательны для повышения релевантности);
- `-слово` — слово **обязательно должно отсутствовать** — строки, содержащие его, исключаются из результата целиком;
- `слово*` — поиск по **префиксу**: `клавиатур*` найдёт «клавиатура», «клавиатуры», «клавиатурный» — это единственная встроенная возможность полнотекстового поиска, отдалённо напоминающая функциональность `LIKE 'префикс%'`, но применённая к отдельным словам внутри более крупного текста;
- `"точная фраза"` — поиск точной последовательности слов рядом друг с другом, а не разрозненных совпадений слов где угодно в тексте.

Boolean-режим уместен, когда пользователь интерфейса поиска (или логика приложения) должен явно контролировать, какие слова обязательны, какие запрещены, — например, поиск отзывов, где обязательно упоминается конкретная деталь товара, но не упоминаются жалобы: `MATCH(body) AGAINST('+доставка -задержк*' IN BOOLEAN MODE)`.

### Минимальная длина слова и стоп-слова

Полнотекстовый поиск в MySQL по умолчанию игнорирует слова короче определённой минимальной длины (управляется системной переменной `innodb_ft_min_token_size`, по умолчанию 3 символа для таблиц InnoDB) — слово «за» или «и» не попадёт в индекс и не будет найдено через `MATCH ... AGAINST`, даже если оно явно присутствует в тексте. Кроме того, существует встроенный список **стоп-слов** — часто встречающихся, малоинформативных слов (артиклей, союзов, местоимений для английского языка; для русского языка встроенный список стоп-слов существенно менее развит и часто требует ручной настройки под конкретный проект), которые исключаются из индексации, поскольку их наличие почти не помогает отличить релевантный документ от нерелевантного — они встречаются почти во всех документах примерно одинаково часто. Обе особенности — не ошибка, а осознанное проектное решение полнотекстового поиска: индексировать и учитывать при ранжировании только те слова, которые реально помогают отличить один документ от другого по смыслу.

### Режим Query Expansion (обзорно)

Третий, менее часто используемый режим — `WITH QUERY EXPANSION` — выполняет поиск в два прохода: сначала находит наиболее релевантные документы по обычному запросу, затем расширяет исходный запрос словами, часто встречающимися именно в этих найденных документах, и повторяет поиск уже с расширенным набором слов. Идея — найти документы, которые содержательно связаны с темой запроса, даже если они не содержат буквально те же слова, что ввёл пользователь. Этот режим упоминается здесь обзорно, как факт существования более сложной альтернативы для специфичных сценариев (например, поисковых систем с претензией на «умный» подбор синонимичных по смыслу результатов) — детальная проработка выходит за рамки материала этого урока.

### FULLTEXT — не замена индексу по обычному столбцу

Важно чётко зафиксировать границу применимости: `FULLTEXT`-индекс решает задачу поиска по *содержанию* достаточно длинного, «естественного» текста (отзывы, описания, статьи). Он не заменяет обычный индекс (первый урок этого уровня) для точечного поиска по короткому, структурированному значению — искать товар по точному `id` или заказ по точному `customer_id` полнотекстовым индексом не только избыточно, но и синтаксически неестественно (`MATCH ... AGAINST` не предназначен для точных числовых сравнений). Выбор инструмента определяется природой самого поиска: точное совпадение или диапазон по структурированному значению — обычный индекс; «найти документы, где упоминается вот это» по неструктурированному тексту — `FULLTEXT`.

### Резюме

- **Полнотекстовый поиск** решает задачу «найти документы, релевантные набору слов» — в отличие от `LIKE '%слово%'`, который ищет точное байтовое вхождение подстроки без понимания слов и без ранжирования по релевантности.
- **`FULLTEXT INDEX`** создаётся для `CHAR`/`VARCHAR`/`TEXT`-столбцов, может охватывать сразу несколько столбцов одной таблицы.
- **`MATCH(столбцы) AGAINST(строка)`** возвращает числовую релевантность; типовой паттерн — использовать её одновременно в `WHERE` (как фильтр: релевантность `0` = не найдено) и в `ORDER BY`/`SELECT` (для сортировки и показа).
- Режим **Natural Language** (по умолчанию) — автоматическая интерпретация поисковой строки как «человеческого» текста, без явных операторов.
- Режим **Boolean** (`IN BOOLEAN MODE`) — явные операторы: `+слово` (обязательно), `-слово` (запрещено), `слово*` (поиск по префиксу слова), `"точная фраза"`.
- Слова короче минимальной длины и стоп-слова из встроенного списка не индексируются и не участвуют в поиске — осознанное ограничение, повышающее качество ранжирования по смыслу.
- Режим **Query Expansion** (обзорно) — двухпроходный поиск с автоматическим расширением исходного запроса словами из наиболее релевантных найденных документов.
- `FULLTEXT` дополняет, а не заменяет обычные индексы — область его применения — содержательный поиск по неструктурированному тексту, а не точечный поиск по коротким структурированным значениям.

## Теоретические задания

### Вопрос 1: Почему `LIKE '%слово%'` хуже полнотекстового поиска для массового поиска по содержимому отзывов?

- ✅ `LIKE` ищет точное байтовое вхождение подстроки: не знает границ слов, не ранжирует находки, а ведущий `%` исключает использование обычного индекса
<!-- разница в природе задачи, а не только в скорости -->
- ❌ `LIKE` не умеет искать кириллицу — error_text: Умеет: `LIKE` работает с любыми символами кодировки столбца, включая кириллицу. Его слабость не в алфавите, а в механике — побайтовое вхождение подстроки без понимания слов и без ранжирования.
- ❌ `LIKE` использует FULLTEXT-индекс, если он создан — error_text: `LIKE` и FULLTEXT-индекс никак не связаны: индекс этого типа обслуживает только конструкцию `MATCH ... AGAINST`. `LIKE '%...%'` остаётся полным перебором строк, сколько бы FULLTEXT-индексов ни существовало.
- ❌ Разница только в скорости, результат одинаков — error_text: Результат принципиально разный: `LIKE` не отличит совпадение внутри чужого слова, не найдёт документы по набору слов с учётом их совместного появления и не отсортирует находки по релевантности. Полнотекстовый поиск решает другую задачу — «найти документы, релевантные словам запроса».

### Вопрос 2: Что делает оператор `+` перед словом в `AGAINST('+клавиатура -шумная' IN BOOLEAN MODE)`?

- ✅ Требует обязательного присутствия слова: документ без него исключается из результата целиком
<!-- жёсткое требование — в отличие от Natural Language, где слова лишь повышают релевантность -->
- ❌ Добавляет единицу к релевантности документа — error_text: `+` — не арифметический бонус к релевантности, а жёсткое условие: нет слова — нет строки в результате, сколько бы других совпадений ни было. Мягкое повышение веса — поведение Natural Language режима для обычных слов.
- ❌ Ищет слова, начинающиеся с этого префикса — error_text: Префиксный поиск — оператор `*` после слова (`клавиатур*`). `+` перед словом означает обязательность его точного присутствия, а не совпадение по началу слова.
- ❌ Работает в любом режиме, включая Natural Language — error_text: Операторы `+`, `-`, `*` и кавычки — синтаксис именно Boolean-режима, включаемого `IN BOOLEAN MODE`. В Natural Language поисковая строка трактуется как естественный текст без выделения операторов.

### Вопрос 3: Что найдёт запрос `AGAINST('клавиатур*' IN BOOLEAN MODE)`?

- ✅ Документы со словами, начинающимися с «клавиатур»: «клавиатура», «клавиатуры», «клавиатурный»
<!-- единственная встроенная возможность полнотекстового поиска, похожая на LIKE 'префикс%' -->
- ❌ Только документы с точным словом «клавиатур» — error_text: Точное слово ищется написанием `'клавиатура'` без операторов. Звёздочка после слова — именно префиксный поиск: совпадают любые слова с этим началом, что и позволяет одним запросом поймать разные формы слова.
- ❌ Документы, не содержащие слов на «клавиатур» — error_text: Исключение слова из поиска — оператор `-` перед ним. Звёздочка после слова наоборот расширяет поиск, включая все слова с этим началом, а не запрещая их.
- ❌ Документы, где «клавиатур» встречается как подстрока внутри других слов — error_text: Префиксный оператор привязан к началу слова, а не к произвольной позиции внутри чужого слова. Подстрока в любом месте — поведение `LIKE '%клавиатур%'`, и именно этого полнотекстовый поиск не делает.

### Вопрос 4: Почему слово «и» в поисковой строке `AGAINST('мышь и провод')` не участвует в поиске, даже если оно есть в текстах?

- ✅ Слова короче минимальной длины (`innodb_ft_min_token_size`, по умолчанию 3 символа для InnoDB) не индексируются и не ищутся
<!-- то же относится к стоп-словам; осознанное ограничение для качества ранжирования -->
- ❌ Сервер завершает запрос ошибкой на слишком коротком слове — error_text: Короткое слово не вызывает ошибку: оно молча игнорируется — не попадает в индекс и не участвует в поиске и ранжировании. Ошибки тут не предусмотрено, это осознанное поведение.
- ❌ Короткие слова ищутся, но с нулевым весом в релевантности — error_text: Дело не в нулевом весе: короткие слова вообще не попадают в полнотекстовый индекс, поэтому искать их через `MATCH ... AGAINST` бесполезно — совпадений не будет даже при их физическом наличии в тексте.
- ❌ Русские союзы ищутся только в Boolean-режиме — error_text: Режим не расширяет словарь индекса: что не проиндексировано, то не ищется ни в Natural Language, ни в Boolean. Короткое «и» недоступно обоим режимам одинаково.

### Вопрос 5: Что возвращает конструкция `MATCH(body) AGAINST('доставка')` и как она типово используется?

- ✅ Числовую релевантность строки запросу; типовой паттерн — одно и то же выражение в `WHERE` (0 = не найдено) и в `SELECT`/`ORDER BY`
<!-- сервер вычисляет релевантность один раз и не пересчитывает для WHERE и SELECT отдельно -->
- ❌ Булево значение «найдено / не найдено» — error_text: Результат — число: релевантность, растущая с качеством соответствия строки запросу. Ноль действительно означает «не соответствует», поэтому выражение работает как фильтр в `WHERE`, но это именно число, которое можно сортировать и показывать.
- ❌ Список совпавших слов документа — error_text: Конструкция возвращает одно число на строку — оценку соответствия, а не перечень совпавших слов. Какие слова учтены, сервер использует внутри расчёта релевантности; наружу список не отдаётся.
- ❌ Работает и без FULLTEXT-индекса, просто медленнее — error_text: `MATCH ... AGAINST` требует существующего FULLTEXT-индекса по указанным столбцам: без него запрос завершится ошибкой, а не «просто медленно». В этом принципиальное отличие от `LIKE`, которому индекс не нужен вовсе.
