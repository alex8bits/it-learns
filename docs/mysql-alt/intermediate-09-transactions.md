Но в реальных сценариях изменение данных часто требует **нескольких** взаимосвязанных шагов, которые должны либо выполниться **все вместе**, либо не выполниться **вовсе** — оформление заказа, например, требует создать сам заказ, добавить его позиции, уменьшить остаток товара на складе и зарегистрировать платёж. Если после успешного создания заказа и уменьшения остатка регистрация платежа неожиданно завершится ошибкой (сервер платежей недоступен, соединение с БД прервалось), а все предыдущие шаги уже физически сохранены в таблицах — база окажется в противоречивом состоянии: заказ существует, товар списан со склада, а денег никто не получил. Механизм, который защищает от такого «наполовину выполненного» изменения данных, называется **транзакцией**, и это тема данного урока.

### Транзакция: группа операций с единой судьбой

**Транзакция** — это последовательность из одной или нескольких SQL-команд, изменяющих данные, которая обрабатывается СУБД как единое целое: либо все её команды успешно применяются к базе данных, либо (в случае любой ошибки на любом шаге) не применяется ни одна из них, и база остаётся точно в том состоянии, в котором была до начала транзакции. Это свойство называют **атомарностью** — от греческого «неделимый»: с точки зрения любого, кто смотрит на базу данных снаружи, транзакция выглядит как единое, неразрывное действие, у которого нет промежуточных, «частично готовых» состояний.

### ACID: четыре свойства надёжной транзакции

Атомарность — лишь одно из четырёх фундаментальных свойств, которые описывают надёжную транзакцию; вместе они образуют акроним **ACID**:

- **Atomicity (атомарность)** — уже описанное свойство «всё или ничего»: набор изменений применяется целиком или полностью откатывается.
- **Consistency (согласованность)** — транзакция переводит базу данных из одного согласованного состояния в другое: все ограничения целостности (`NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK` — уровень «Основы» и «Начинающий») остаются выполненными и до, и после транзакции; если по пути какое-то ограничение оказалось бы нарушено, транзакция не должна завершиться успешно.
- **Isolation (изолированность)** — незавершённые изменения одной транзакции не видны другим транзакциям, выполняющимся параллельно, до тех пор, пока первая транзакция не завершится; это свойство подробно разбирается в следующем уроке уровня.
- **Durability (долговечность)** — после того как транзакция объявлена успешно завершённой, её результат гарантированно сохранён и переживёт даже сбой питания или перезапуск сервера сразу после завершения — СУБД физически записывает изменения в журнал так, чтобы их можно было восстановить.

MySQL с движком хранения **InnoDB** (используемым по умолчанию для всех таблиц, которые мы создавали на протяжении курса) полностью поддерживает ACID-транзакции «из коробки» — это одна из главных причин, почему InnoDB стал таким широко используемым движком: без него ни одна из гарантий этого урока не была бы доступна.

### START TRANSACTION, COMMIT, ROLLBACK: базовый синтаксис

По умолчанию MySQL-клиент работает в режиме **автокоммита** (autocommit): каждая отдельная команда (`INSERT`, `UPDATE`, `DELETE`) автоматически оборачивается в собственную, мгновенно завершающуюся транзакцию — именно поэтому до сих пор в курсе каждая команда сразу и безусловно применялась к данным. Чтобы объединить несколько команд в одну транзакцию, нужно явно её начать:

```sql
START TRANSACTION;

UPDATE products SET stock = stock - 2 WHERE id = 5;

INSERT INTO orders (customer_id, status, created_at)
VALUES (10, 'new', NOW());

INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (LAST_INSERT_ID(), 5, 2, 4500.00);

COMMIT;
```

`START TRANSACTION` явно сообщает MySQL: «дальнейшие команды до особого распоряжения не должны применяться по отдельности — держи их как единую группу». `COMMIT` — это распоряжение «зафиксировать все изменения этой группы окончательно»: только после успешного `COMMIT` изменения становятся постоянными (durable в терминах ACID) и видимыми для других соединений к базе данных.

Если на любом шаге до `COMMIT` происходит ошибка или обнаруживается, что продолжать не нужно, транзакцию можно **отменить** командой `ROLLBACK` — она отбрасывает **все** изменения, сделанные с момента `START TRANSACTION`, возвращая данные в исходное состояние, как если бы ни одна из команд транзакции никогда не выполнялась:

```sql
START TRANSACTION;

UPDATE products SET stock = stock - 2 WHERE id = 5;

-- Обнаружили, что на складе недостаточно товара для этого заказа
ROLLBACK;
```

После `ROLLBACK` строка `products` с `id = 5` вернётся к тому значению `stock`, которое было до `UPDATE` — как если бы команда `UPDATE` вообще не выполнялась.

### Сценарий «заказ → позиции → склад → платёж» с намеренной ошибкой

Рассмотрим полный сценарий, ради которого этот урок и появился в программе — оформление заказа как единую транзакцию, включающую все четыре связанные таблицы, с проверкой на каждом шаге:

```sql
START TRANSACTION;

-- Шаг 1: создать заказ
INSERT INTO orders (customer_id, status, created_at)
VALUES (10, 'new', NOW());

SET @order_id = LAST_INSERT_ID();

-- Шаг 2: добавить позицию заказа
INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (@order_id, 5, 2, 4500.00);

-- Шаг 3: списать товар со склада
UPDATE products SET stock = stock - 2 WHERE id = 5 AND stock >= 2;

-- Проверка: если строк не затронуто — товара не хватило, откатываем всё
-- (в реальном приложении здесь код на стороне клиента читает ROW_COUNT()
-- и решает, вызывать ROLLBACK или продолжать)

-- Шаг 4: зарегистрировать платёж
INSERT INTO payments (order_id, amount, method)
VALUES (@order_id, 9000.00, 'card');

COMMIT;
```

Если на шаге 3 условие `stock >= 2` не выполнилось (товара недостаточно), `UPDATE` затронет 0 строк, но **сам по себе не вызовет ошибку и не остановит транзакцию** — MySQL не «знает», что 0 затронутых строк здесь означает провал бизнес-сценария, а не штатный результат (в отличие, например, от нарушения `FOREIGN KEY`, которое MySQL действительно распознаёт как ошибку и прерывает транзакцию сам). Поэтому проверка «действительно ли шаг сработал так, как должен был» — ответственность приложения, а не автоматическое поведение сервера: код, выполняющий эту транзакцию, обязан после шага 3 проверить количество затронутых строк и, если товара не хватило, самостоятельно вызвать `ROLLBACK`, не переходя к шагу 4. Если бы вместо ручной проверки в схеме стоял `CHECK (stock >= 0)` (шестой урок уровня «Основы»), попытка через `UPDATE` списать больше, чем есть на складе, привела бы к настоящей ошибке ограничения — и тогда транзакция была бы прервана сервером автоматически. Этот пример показывает важный практический вывод: транзакция защищает от **частичного** применения группы операций, но не заменяет проверку бизнес-логики внутри самого приложения — она гарантирует лишь то, что *если* решение об откате принято (явно или из-за реальной ошибки ограничения), *все* изменения группы будут отменены согласованно, без исключений.

### SAVEPOINT: частичный откат внутри транзакции

Иногда транзакция состоит из нескольких логических блоков, и при ошибке в одном из последних блоков хотелось бы откатить только его, а не всю транзакцию с самого начала. Для этого существуют **точки сохранения** — `SAVEPOINT`:

```sql
START TRANSACTION;

INSERT INTO orders (customer_id, status, created_at) VALUES (10, 'new', NOW());
SET @order_id = LAST_INSERT_ID();

SAVEPOINT before_items;

INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (@order_id, 5, 2, 4500.00);

-- Обнаружили проблему именно с позициями заказа (например, неверную цену)
ROLLBACK TO SAVEPOINT before_items;

-- Заказ (шаг с orders) остался, позиция откатилась - можно попробовать вставить её снова
INSERT INTO order_items (order_id, product_id, quantity, price)
VALUES (@order_id, 5, 2, 4200.00);

COMMIT;
```

`SAVEPOINT before_items` отмечает промежуточную точку внутри уже начатой транзакции. `ROLLBACK TO SAVEPOINT before_items` откатывает только те изменения, что были сделаны **после** этой точки (здесь — неудачную вставку `order_items`), но сохраняет всё, что было сделано **до** неё (созданный заказ), — и после этого транзакция продолжается: можно выполнить новые команды и в конце вызвать обычный `COMMIT`, который зафиксирует и созданный заказ, и вторую, исправленную попытку вставить позицию. Важно, что `SAVEPOINT` — это точка внутри **одной** незавершённой транзакции, а не альтернатива `COMMIT`: пока не будет вызван итоговый `COMMIT` или `ROLLBACK` (без указания конкретной точки, что откатывает всю транзакцию целиком), никакие изменения, даже до самой первой `SAVEPOINT`, не становятся постоянными.

### Резюме

- **Транзакция** — группа команд изменения данных, которая применяется к базе данных как единое целое: либо все команды успешны, либо ни одна.
- **ACID** — четыре гарантии надёжной транзакции: атомарность («всё или ничего»), согласованность (ограничения целостности выполнены до и после), изолированность (незавершённые изменения не видны другим до завершения — тема следующего урока), долговечность (после `COMMIT` результат переживёт сбой).
- **`START TRANSACTION`** явно начинает группу команд, до этого момента MySQL применяет каждую команду отдельно и мгновенно (режим автокоммита).
- **`COMMIT`** окончательно фиксирует все изменения транзакции; **`ROLLBACK`** отбрасывает все изменения, сделанные с момента `START TRANSACTION`, возвращая данные к исходному состоянию.
- Транзакция автоматически прерывается сервером только при настоящей ошибке (нарушение `UNIQUE`/`FOREIGN KEY`/`CHECK` и т. п.); ситуации, не являющиеся ошибкой с точки зрения SQL (например, `UPDATE`, затронувший 0 строк из-за недостатка товара на складе), должны проверяться и обрабатываться самим приложением, которое при необходимости вызывает `ROLLBACK` явно.
- **`SAVEPOINT`** создаёт промежуточную точку внутри незавершённой транзакции; **`ROLLBACK TO SAVEPOINT имя`** откатывает только изменения после этой точки, сохраняя более ранние изменения той же транзакции и позволяя продолжить работу с последующим `COMMIT`.
