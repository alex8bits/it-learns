В прошлом уроке все подзапросы были **независимыми**: внутренний `SELECT` можно было выполнить сам по себе, отдельно от внешнего запроса, и получить осмысленный результат — среднюю цену, список идентификаторов клиентов с заказами и так далее. Но существует другой, более гибкий вид подзапроса — тот, который «заглядывает» в текущую строку внешнего запроса и для каждой строки вычисляется заново, с другим результатом. Такой подзапрос называется **коррелированным** (correlated subquery), и именно с ним чаще всего работает пара операторов `EXISTS`/`NOT EXISTS` — тема этого урока.

### Коррелированный подзапрос: подзапрос, зависящий от внешней строки

Рассмотрим задачу: найти клиентов, у которых есть хотя бы один заказ на сумму дороже 10000. В прошлом уроке мы находили клиентов с заказами вообще — теперь добавилось условие на конкретную сумму конкретного заказа. Попробуем написать это через `IN`, как в прошлом уроке:

```sql
SELECT id, name
FROM customers
WHERE id IN (
    SELECT customer_id
    FROM orders
    WHERE status <> 'cancelled'
    -- где здесь учесть сумму заказа? Она не хранится в orders напрямую
);
```

Проблема: сумма заказа собирается из `order_items` (мы считали её в шестнадцатом уроке уровня «Начинающий» через `SUM(quantity * price)` с `GROUP BY`), и просто дописать условие на сумму в этот подзапрос неудобно — придётся добавлять `JOIN` и `GROUP BY`/`HAVING` внутрь подзапроса, что усложняет конструкцию. Здесь удобнее сформулировать вопрос иначе: «для этого конкретного клиента (id которого мы уже знаем из внешнего запроса) — существует ли хотя бы один его заказ дороже 10000?» Такая формулировка — «для *этой* строки — существует ли...» — прямой признак коррелированного подзапроса:

```sql
SELECT id, name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    INNER JOIN order_items oi ON oi.order_id = o.id
    WHERE o.customer_id = c.id
    GROUP BY o.id
    HAVING SUM(oi.quantity * oi.price) > 10000
);
```

Ключевое отличие от прошлого урока — строка `WHERE o.customer_id = c.id`. Здесь `c` — это алиас **внешней** таблицы `customers`, а `c.id` — это `id` **текущей строки**, которую в данный момент проверяет внешний запрос. Подзапрос ссылается на переменную из внешнего запроса — отсюда и название «коррелированный»: он коррелирует (связывает) себя с конкретной строкой снаружи. Из-за этой связи MySQL концептуально выполняет подзапрос **отдельно для каждой строки** таблицы `customers`: для клиента с `id = 1` подзапрос проверяет заказы клиента 1, для клиента с `id = 2` — заказы клиента 2, и так далее. (На практике оптимизатор MySQL умеет исполнять это эффективнее буквального повторного запроса на каждую строку, но с точки зрения смысла запроса удобно и корректно думать именно так.)

### EXISTS: проверка «есть хотя бы одна строка»

Оператор `EXISTS` возвращает `TRUE`, если подзапрос вернул **хотя бы одну строку**, и `FALSE`, если не вернул ни одной — вне зависимости от того, сколько столбцов и что именно выбрано внутри. По этой причине внутри `EXISTS` принято писать `SELECT 1` или `SELECT *` — конкретные значения роли не играют, важен только факт существования строки. Это принципиально отличает `EXISTS` от скалярного подзапроса и от `IN`: там имело значение само *значение*, здесь — только *факт наличия строки*.

Разберём ещё один характерный пример — товары, у которых есть хотя бы один отзыв с рейтингом 5:

```sql
SELECT p.id, p.name
FROM products p
WHERE EXISTS (
    SELECT 1
    FROM reviews r
    WHERE r.product_id = p.id AND r.rating = 5
);
```

Для каждого товара `p` подзапрос проверяет: существует ли строка в `reviews`, у которой `product_id` совпадает с `id` текущего товара и рейтинг равен 5. Если хотя бы одна такая строка есть — `EXISTS` даёт `TRUE`, и товар попадает в результат.

### NOT EXISTS: надёжная альтернатива NOT IN

В прошлом уроке мы разобрали ловушку `NOT IN` с `NULL` в результате подзапроса: если хотя бы одно значение внутри подзапроса — `NULL`, весь `NOT IN` может неожиданно перестать находить что-либо. `NOT EXISTS` этой проблемы не имеет вообще, потому что она проверяет не конкретные значения, а сам факт существования подходящей строки — а существование не зависит от того, есть ли `NULL` где-то ещё:

```sql
-- Клиенты без единого заказа: надёжная версия через NOT EXISTS
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

Этот запрос корректно найдёт клиентов без заказов независимо от того, есть ли где-то в `orders` строка с `customer_id IS NULL` — потому что подзапрос проверяет конкретное условие `o.customer_id = c.id` для каждого `c.id` отдельно, а не строит общий список значений заранее. Именно поэтому в профессиональной практике `NOT EXISTS` считается более безопасным и предсказуемым выбором, чем `NOT IN`, когда есть хоть малейшая вероятность `NULL` в столбце, участвующем в подзапросе.

### EXISTS против анти-JOIN: два способа увидеть одну и ту же идею

В четырнадцатом уроке уровня «Начинающий» мы решали похожую задачу — «товары без заказов» — через `LEFT JOIN` с последующим `WHERE ... IS NULL` (анти-джойн). Та же задача через `NOT EXISTS`:

```sql
-- Анти-джойн (уровень «Начинающий», урок 14)
SELECT p.id, p.name
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.id
WHERE oi.id IS NULL;

-- То же через NOT EXISTS
SELECT p.id, p.name
FROM products p
WHERE NOT EXISTS (
    SELECT 1 FROM order_items oi WHERE oi.product_id = p.id
);
```

Оба запроса возвращают один и тот же результат, но выражают идею по-разному. Анти-джойн физически соединяет таблицы и затем откидывает совпавшие строки — при соединении с таблицей, где на одну строку `products` может приходиться несколько строк `order_items`, легко забыть про размножение строк (как мы видели в шестнадцатом уроке уровня «Начинающий») и получить неверный результат, если добавить в такой запрос агрегаты без `DISTINCT`. `NOT EXISTS` изначально устроена так, что размножения строк не происходит: она лишь спрашивает «да/нет» и никогда не тиражирует строку `products`, сколько бы совпадений ни было у неё в `order_items`. Из-за этого при работе с таблицами, где связь «один ко многим» может создать путаницу, `EXISTS`/`NOT EXISTS` часто читается яснее и меньше подвержена ошибкам, чем эквивалентный `JOIN`.

### Когда какой инструмент выбрать

К этому моменту у нас есть три близких по смыслу, но разных инструмента:

- **`JOIN`** — когда из второй таблицы нужны конкретные данные в результате (например, вывести не просто «есть заказ», а сам номер заказа и его сумму).
- **`IN (SELECT ...)`** — когда нужно сравнить столбец с множеством значений без ссылки на текущую строку внешнего запроса; подзапрос независим и может быть вычислен один раз.
- **`EXISTS`/`NOT EXISTS`** — когда важен только факт существования (или отсутствия) связанной строки, удовлетворяющей произвольно сложному условию, включая условия, зависящие от текущей строки внешнего запроса (например, «заказ этого же клиента»).

Практическое правило выбора между `IN` и `EXISTS`, когда оба применимы: если условие внутри подзапроса не зависит от внешней строки — обычно естественнее и привычнее выглядит `IN`; если условие обязательно ссылается на столбец внешней строки (как `o.customer_id = c.id` выше) — это, по определению, коррелированный подзапрос, и синтаксически естественнее оформить его как `EXISTS`.

### Резюме

- **Коррелированный подзапрос** ссылается на столбец (алиас) внешнего запроса внутри своего `WHERE` и логически вычисляется заново для каждой строки внешнего запроса — в отличие от независимого подзапроса из прошлого урока.
- **`EXISTS`** проверяет только факт наличия хотя бы одной строки в результате подзапроса; конкретные выбранные значения (`SELECT 1` или `SELECT *`) не имеют значения.
- **`NOT EXISTS`** — надёжная альтернатива `NOT IN`: не подвержена ловушке с `NULL` в результате подзапроса, потому что проверяет существование строки, а не сравнивает значения со списком.
- Задачи вида «товары/клиенты без связанных записей» можно решить и анти-джойном (`LEFT JOIN ... WHERE ... IS NULL`), и `NOT EXISTS` — но `NOT EXISTS` не тиражирует строки внешней таблицы при связи «один ко многим», что делает её более предсказуемой в сложных случаях.
- Выбор инструмента зависит от того, что на самом деле нужно: данные второй таблицы — `JOIN`; сравнение со множеством значений — `IN`; факт существования, возможно зависящий от текущей строки — `EXISTS`.
