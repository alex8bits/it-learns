# Типы данных MySQL: INT/DECIMAL, VARCHAR/TEXT, DATE/DATETIME, BOOL; кодировки — обзорно (utf8mb4)

## Материал

### Ранее в курсе

- Урок 1 уровня «Основы» «Что такое БД и СУБД» — узнали про таблицы, строки и столбцы, познакомились с `SELECT`.
- Урок 2 уровня «Основы» «MySQL сервер и клиент» — разобрались с клиент-серверной архитектурой и базами данных на сервере.
- Урок 3 уровня «Основы» «Синтаксис SQL и SELECT» — освоили синтаксис запросов, регистр ключевых слов, `LIMIT`.
- Урок 4 уровня «Основы» «Добавление данных» — научились добавлять строки командой `INSERT INTO ... VALUES ...`, в том числе несколько строк за раз.

В прошлом уроке мы записывали в таблицу и текст, и числа, но не задерживались на вопросе: а почему одно значение пишется в кавычках, а другое — нет? Откуда сервер знает, что можно положить в конкретный столбец, а что — нельзя? Ответ — в понятии **типа данных**. В этом уроке разберём основные типы, которые встретятся вам в подавляющем большинстве таблиц: числа, текст, дату и время, логические значения, а также кратко коснёмся кодировок текста.

### Зачем столбцу нужен тип данных

Мы уже говорили в первом уроке, что схема таблицы фиксирует набор столбцов, общий для всех строк. Но одного только имени столбца недостаточно — сервер должен знать, *какого рода* значения в нём допустимы, чтобы:

- **проверять корректность** — не дать записать текст в столбец, предназначенный для чисел, или недопустимую дату;
- **экономить место на диске** — маленькое целое число можно хранить компактнее, чем длинный текст, и сервер выделяет ровно столько места, сколько нужно конкретному типу;
- **правильно сравнивать и сортировать значения** — числа сравниваются по величине, даты — по хронологии, а строки — по алфавитному порядку (с нюансами, о которых пойдёт речь в продвинутых темах курса); без явного типа сервер не знал бы, какое правило сравнения применить;
- **выполнять операции, специфичные для типа** — например, складывать числа, вычислять разницу между датами или переводить текст в верхний регистр. Такие операции имеют смысл только для «своего» типа данных.

Тип данных указывается один раз — при создании столбца (с этим мы познакомимся в следующем уроке, про `CREATE TABLE`) — и действует для всех значений этого столбца во всех строках таблицы.

### Целые числа: INT и его семейство

Для хранения целых чисел (без дробной части) в MySQL служит тип `INT` (сокращение от *integer* — «целое»):

```sql
-- пример объявления столбца (полностью разберём CREATE TABLE в следующем уроке)
stock INT
```

`INT` занимает 4 байта и может хранить числа примерно от −2 147 483 648 до 2 147 483 647 — для подавляющего большинства практических задач (количество товара на складе, число заказов, возраст пользователя) этого более чем достаточно. У MySQL есть и другие целочисленные типы разного размера — `TINYINT`, `SMALLINT`, `MEDIUMINT`, `BIGINT`, отличающиеся диапазоном допустимых значений и объёмом занимаемой памяти; с ними вы столкнётесь по мере усложнения задач (например, `BIGINT` нужен, когда числа могут превысить диапазон `INT`, — так часто делают для идентификаторов в очень крупных таблицах). На уровне «Основы» вам достаточно уверенно пользоваться `INT` — это самый частый и универсальный выбор для целых чисел.

Целочисленные значения при вставке пишутся без кавычек: `INSERT INTO products (stock) VALUES (12);` — кавычки здесь не нужны, а если их поставить (`'12'`), MySQL в большинстве случаев всё равно преобразует строку в число автоматически, но такая запись противоречит смыслу типа и не рекомендуется — лучше всегда писать числа как числа.

### Точные дробные числа: DECIMAL

Для денег, цен и любых значений, где важна абсолютная точность вычислений (никаких «плывущих» копеек), в MySQL используется тип `DECIMAL(precision, scale)`, где `precision` — общее количество значащих цифр, а `scale` — количество цифр после запятой:

```sql
price DECIMAL(10, 2)
```

Такое объявление означает: до 10 значащих цифр всего, из них 2 — после десятичной точки. Например, `4500.00` или `99999999.99` — допустимые значения для `DECIMAL(10, 2)`, а число с тремя цифрами после точки (`4500.005`) MySQL при вставке округлит до двух цифр по стандартным правилам округления.

Почему для денег нельзя просто использовать привычные во многих языках программирования типы «числа с плавающей точкой» (`FLOAT`, `DOUBLE`)? Дело в том, что числа с плавающей точкой представляют дробные значения в двоичной системе счисления, и многие «обычные» десятичные дробные числа (например, 0.1) физически невозможно представить в двоичном виде абсолютно точно — возникает крошечная погрешность. Для научных расчётов эта погрешность обычно не важна, но при работе с деньгами накопление таких мелких неточностей в тысячах операций может привести к ощутимым и трудно диагностируемым расхождениям в отчётах. `DECIMAL` хранит число как точную последовательность цифр, а не как приближение, поэтому именно этот тип — стандартный выбор для денежных сумм, тарифов, любых значений, где нужна арифметическая точность до последней копейки.

`FLOAT` и `DOUBLE` в MySQL всё же существуют и уместны там, где точность до последнего знака не критична (например, для координат на карте или результатов физических измерений), но для интернет-магазина, с которым мы работаем на протяжении курса, `price` — это всегда `DECIMAL`.

### Текст: VARCHAR и TEXT

Для хранения текстовых данных MySQL предоставляет два основных семейства типов.

**`VARCHAR(N)`** (variable character — «символы переменной длины») хранит текст длиной **не более N символов**; при этом реально занимаемое место на диске зависит от фактической длины конкретного значения, а не всегда равно N. Например:

```sql
name VARCHAR(255)
```

означает: в этот столбец можно записать текст длиной от 0 до 255 символов; попытка вставить более длинную строку приведёт либо к ошибке, либо (в зависимости от настроек режима строгости сервера) к автоматическому обрезанию текста — в любом случае это нежелательная ситуация, поэтому длину `VARCHAR` стоит выбирать с запасом под реальные данные (для названия товара, имени клиента, адреса email — 255 символов обычно более чем достаточно).

**`TEXT`** предназначен для длинных текстов — вплоть до 65 535 байт (это, в свою очередь, накладывает ограничения на индексирование такого столбца, о которых мы поговорим на уровне «Продвинутый»). `TEXT` не принимает параметр максимальной длины в скобках и используется, когда текст заведомо может быть длинным и непредсказуемым по размеру — например, отзыв покупателя о товаре или описание статьи.

Как выбрать между `VARCHAR` и `TEXT`? Практическое правило: если у текста есть разумный и предсказуемый предел длины (имя, email, короткий заголовок) — используйте `VARCHAR` с подходящим числом; если текст потенциально длинный и без явного предела (описание, комментарий, статья) — используйте `TEXT`. И `VARCHAR`, и `TEXT` при вставке значений требуют одинарных кавычек: `'Клавиатура механическая'`.

### Дата и время: DATE и DATETIME

Для хранения календарной даты без времени суток используется тип `DATE`:

```sql
registered_at DATE
```

Значение записывается в стандартном формате `'ГГГГ-ММ-ДД'`, например `'2024-03-15'`. Такой формат — не случайность и не прихоть MySQL: он совпадает со стандартом ISO 8601, который однозначно упорядочивает даты и не зависит от локальных традиций записи (в отличие от, например, американского формата «месяц/день/год», который легко спутать с европейским «день/месяц/год»).

Когда важно хранить не только дату, но и точный момент времени (час, минуту, секунду), используется `DATETIME`:

```sql
created_at DATETIME
```

Значение записывается в формате `'ГГГГ-ММ-ДД ЧЧ:МИ:СС'`, например `'2024-03-15 14:30:00'`. `DATETIME` пригождается, когда важен не просто «в какой день», а «в какой именно момент» произошло событие — например, момент создания заказа, чтобы можно было впоследствии выстроить точную хронологию событий, а не только сгруппировать их по дням.

Оба типа значений при вставке записываются как текст в одинарных кавычках, а не как числа — хотя по смыслу это не обычный текст: сервер понимает содержимое такой строки именно как дату или дату-время и умеет применять к ней специальные операции — сравнивать хронологически, вычислять разницу между двумя датами, извлекать год или месяц. С этими возможностями мы подробно познакомимся на уровне «Начинающий», в уроке про функции для работы с числами и датами; пока важно просто научиться правильно записывать значения даты и даты-времени при `INSERT`.

### Логические значения: BOOL / BOOLEAN

Для значений вида «да/нет», «включено/выключено» в MySQL есть тип `BOOL` (или его синоним `BOOLEAN` — оба имени обозначают одно и то же). Особенность MySQL в том, что под капотом `BOOL` — это на самом деле alias (синоним) для `TINYINT(1)`, то есть самого маленького целочисленного типа: значение `TRUE` физически хранится как `1`, а `FALSE` — как `0`.

```sql
is_active BOOL
```

При вставке можно использовать как ключевые слова `TRUE` / `FALSE`, так и напрямую числа `1` / `0` — для MySQL это полностью равнозначные записи:

```sql
INSERT INTO products (name, is_active) VALUES ('Клавиатура', TRUE);
INSERT INTO products (name, is_active) VALUES ('Мышь', 1);
```

Оба варианта дадут одинаковый результат. Полезно знать эту особенность, чтобы не удивляться, увидев `1` и `0` вместо `TRUE`/`FALSE`, если результат запроса выводится, например, консольным клиентом или программной библиотекой без специальной интерпретации логического типа.

### Кодировки: почему важен utf8mb4

Последний важный аспект типов данных, особенно текстовых, — это **кодировка** (character set): правило, по которому символы (буквы, цифры, знаки пунктуации, эмодзи) преобразуются в последовательность байт для хранения на диске.

Исторически распространённой кодировкой была `latin1`, покрывающая только латинский алфавит и ограниченный набор символов — её недостаточно даже для полноценной работы с кириллицей, не говоря уже о смешанных текстах на разных языках или эмодзи. Более широкая кодировка `utf8`, которая долгое время была «стандартом» в MySQL, на самом деле исторически поддерживала не весь Юникод, а только символы, кодируемые не более чем тремя байтами — этого достаточно для большинства алфавитов, включая кириллицу, но недостаточно для некоторых редких символов и, что особенно заметно на практике, для эмодзи (которые требуют четырёх байт).

Поэтому в современных проектах на MySQL рекомендуется использовать кодировку **`utf8mb4`** («UTF-8, до 4 байт на символ») — она покрывает весь актуальный диапазон Юникода без исключений, включая эмодзи, и является кодировкой по умолчанию в MySQL 8, начиная с которой ведётся этот курс. Указывается кодировка при создании базы данных или таблицы (мы увидим это в следующем уроке, при разборе `CREATE TABLE`) и в подавляющем большинстве современных проектов её просто выставляют единообразно на весь проект, не задумываясь об этом в каждом отдельном запросе.

Для практики на уровне «Основы» вам не нужно указывать кодировку самостоятельно — среда, в которой вы работаете, уже настроена на `utf8mb4` по умолчанию. Достаточно знать сам термин и понимать, почему он важен: без правильной кодировки текст на кириллице, эмодзи в отзывах покупателей или названия товаров на разных языках могут отображаться некорректно или вовсе не сохраниться так, как ожидалось.

### Что произойдёт при попытке записать «невозможное» значение

Раз у каждого столбца есть тип, логично спросить: что случится, если попытаться вставить значение, которое этому типу не соответствует? Например, записать текст в числовой столбец, или дату в неправильном формате?

MySQL в этом отношении может вести себя по-разному в зависимости от режима работы сервера (`sql_mode`). В строгом режиме (который включён по умолчанию в MySQL 8 и используется в этом курсе) сервер **откажется выполнять** такую вставку и вернёт ошибку, объясняющую, что значение не подходит по типу — например, «Incorrect integer value» для попытки записать нечисловой текст в `INT`, или «Incorrect date value» для некорректно оформленной даты. Строка при этом не будет добавлена в таблицу вовсе.

Такое поведение — снова прямое следствие идеи, с которой начинался этот курс: СУБД защищает целостность данных на уровне сервера, не позволяя приложению (или человеку, вводящему команды вручную) записать заведомо некорректные значения. Умение читать и понимать такие ошибки — важный практический навык, к которому мы вернёмся отдельно на уровне «Средний», когда разберём типичные коды ошибок MySQL системно; на уровне «Основы» достаточно не пугаться при виде такой ошибки и понимать её общий смысл: «то, что вы попытались записать, не соответствует объявленному типу столбца».

### Резюме

- Каждый столбец таблицы имеет **тип данных**, определяющий, какие значения в нём допустимы, сколько места они занимают и какие операции к ним применимы.
- `INT` — целые числа без дробной части; для денежных сумм и других значений, где важна точность до последнего знака, используется `DECIMAL(precision, scale)`, а не `FLOAT`/`DOUBLE` (у которых возможны погрешности представления).
- `VARCHAR(N)` — текст ограниченной длины (до N символов), подходит для имён, заголовков, email; `TEXT` — для потенциально длинного текста без чёткого предела (описания, отзывы, статьи).
- `DATE` хранит календарную дату в формате `'ГГГГ-ММ-ДД'`, `DATETIME` — дату и время в формате `'ГГГГ-ММ-ДД ЧЧ:МИ:СС'`; оба записываются как текст в кавычках, но интерпретируются сервером как хронологические значения.
- `BOOL`/`BOOLEAN` в MySQL — синоним `TINYINT(1)`: логические значения физически хранятся как `1` (истина) и `0` (ложь), а `TRUE`/`FALSE` — равнозначные им ключевые слова при записи.
- Кодировка `utf8mb4` — рекомендуемый стандарт для текстовых данных в MySQL 8, покрывающий весь Юникод, включая эмодзи; более старые кодировки (`latin1`, ограниченный `utf8`) не гарантируют корректного хранения всех символов.
- При попытке вставить значение, не соответствующее типу столбца, сервер в строгом режиме отклоняет всю строку с ошибкой — это защищает целостность данных на уровне СУБД.
