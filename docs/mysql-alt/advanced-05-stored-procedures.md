Но не любая бизнес-задача укладывается в единственный запрос: сценарий «начислить скидку каждому клиенту в зависимости от суммы его покупок за прошлый месяц» требует последовательности шагов с условной логикой, переменными для промежуточных значений и, возможно, цикла по строкам. SQL как язык запросов не создан для описания такой процедурной логики напрямую — для этого в MySQL существуют **хранимые процедуры**, программируемые объекты, живущие внутри самого сервера.

### Что такое хранимая процедура

**Хранимая процедура** — это именованный блок кода на процедурном расширении SQL (в MySQL это диалект, близкий к стандарту SQL/PSM), сохранённый на сервере и вызываемый по имени командой `CALL`. В отличие от обычного `SELECT`, который декларативно описывает *что* нужно получить, тело процедуры может содержать несколько последовательных инструкций, переменные, условия и циклы — то есть описывать *как*, шаг за шагом, выполнить сложную операцию.

Минимальный пример — процедура, которая по идентификатору клиента возвращает список его заказов:

```sql
DELIMITER //

CREATE PROCEDURE get_customer_orders(IN p_customer_id INT)
BEGIN
    SELECT id, status, created_at
    FROM orders
    WHERE customer_id = p_customer_id
    ORDER BY created_at DESC;
END //

DELIMITER ;
```

Вызов:

```sql
CALL get_customer_orders(42);
```

### DELIMITER: зачем менять разделитель команд

Первое, что бросается в глаза в примере выше — конструкция `DELIMITER //`. По умолчанию клиент `mysql` CLI (второй урок уровня «Основы») считает точку с запятой `;` концом команды и отправляет всё, что до неё написано, на сервер. Но тело процедуры само состоит из нескольких инструкций, разделённых точкой с запятой (`SELECT ...;` внутри `BEGIN ... END`) — если оставить стандартный разделитель, клиент оборвал бы отправку команды на первой же внутренней точке с запятой, до того как дойдёт до `END`. `DELIMITER //` временно говорит клиенту: «теперь концом команды считается `//`, а не `;`» — это позволяет клиенту отправить весь текст `CREATE PROCEDURE ... END` как единую команду, несмотря на точки с запятой внутри. После завершения объявления процедуры `DELIMITER ;` возвращает стандартный разделитель обратно. Важная деталь: `DELIMITER` — это команда самого клиента (`mysql` CLI), а не часть языка SQL — она не сохраняется на сервере и не имеет отношения к тому, как процедура выполняется; в графических клиентах (DBeaver, Workbench) это обычно решается иначе (например, отдельной кнопкой «выполнить блок»), но принцип тот же: нужно как-то обозначить границу целого блока кода, отличную от точки с запятой внутри него.

### Параметры процедуры: IN, OUT, INOUT

Параметры процедуры объявляются с одним из трёх режимов:

- **`IN`** (по умолчанию, если режим не указан явно) — параметр передаётся в процедуру, но изменения его значения внутри тела процедуры не возвращаются вызывающему коду. Это самый частый случай — входные данные для вычислений.
- **`OUT`** — параметр не принимает значение при вызове, но процедура записывает в него результат, который становится доступен вызывающему коду после `CALL`.
- **`INOUT`** — комбинация: параметр принимает входное значение и может быть изменён внутри процедуры, а изменение возвращается наружу.

Пример с `OUT`-параметром — процедура, вычисляющая общую сумму заказов клиента:

```sql
DELIMITER //

CREATE PROCEDURE get_customer_total_spent(
    IN p_customer_id INT,
    OUT p_total DECIMAL(10, 2)
)
BEGIN
    SELECT COALESCE(SUM(oi.quantity * oi.price), 0)
    INTO p_total
    FROM orders o
    INNER JOIN order_items oi ON oi.order_id = o.id
    WHERE o.customer_id = p_customer_id
      AND o.status <> 'cancelled';
END //

DELIMITER ;
```

Вызов и чтение результата из `OUT`-параметра происходит через пользовательскую переменную сессии (переменную вида `@имя`, которая существует, пока не завершится соединение):

```sql
CALL get_customer_total_spent(42, @total);
SELECT @total;
```

Конструкция `SELECT ... INTO переменная` внутри тела процедуры — стандартный способ сохранить единственное скалярное значение результата запроса в переменную вместо того, чтобы вернуть его как обычный результирующий набор строк.

### Переменные внутри тела процедуры

Помимо параметров, внутри тела процедуры можно объявлять локальные переменные командой `DECLARE` (обязательно в самом начале блока `BEGIN ... END`, до любых других инструкций — это требование синтаксиса процедурного расширения MySQL) и присваивать им значения через `SET`:

```sql
DELIMITER //

CREATE PROCEDURE classify_customer(IN p_customer_id INT, OUT p_segment VARCHAR(20))
BEGIN
    DECLARE v_total DECIMAL(10, 2);

    SELECT COALESCE(SUM(oi.quantity * oi.price), 0)
    INTO v_total
    FROM orders o
    INNER JOIN order_items oi ON oi.order_id = o.id
    WHERE o.customer_id = p_customer_id
      AND o.status <> 'cancelled';

    IF v_total > 100000 THEN
        SET p_segment = 'VIP';
    ELSEIF v_total > 20000 THEN
        SET p_segment = 'постоянный';
    ELSE
        SET p_segment = 'новый';
    END IF;
END //

DELIMITER ;
```

Здесь `v_total` — локальная переменная (принятое соглашение — приставка `v_` для локальных переменных и `p_` для параметров, чтобы визуально не путать их в теле процедуры), а `IF ... ELSEIF ... ELSE ... END IF` — управляющая конструкция условной логики, отдалённо напоминающая `CASE WHEN` (седьмой урок уровня «Начинающий»), но принципиально другая по назначению: `CASE` — выражение внутри `SELECT`, вычисляющее значение для каждой строки результата, а `IF` в процедуре — оператор ветвления самого потока выполнения кода, определяющий, какие инструкции будут выполнены вообще.

### Циклы: LOOP, WHILE, REPEAT

Для повторяющихся действий процедурное расширение MySQL предлагает несколько форм циклов. `WHILE` выполняет тело, пока условие истинно (проверка перед итерацией):

```sql
DELIMITER //

CREATE PROCEDURE seed_demo_numbers(IN p_count INT)
BEGIN
    DECLARE v_counter INT DEFAULT 1;

    WHILE v_counter <= p_count DO
        INSERT INTO demo_numbers (value) VALUES (v_counter);
        SET v_counter = v_counter + 1;
    END WHILE;
END //

DELIMITER ;
```

`LOOP` — цикл без встроенного условия, требующий явного выхода через `LEAVE` с меткой:

```sql
DELIMITER //

CREATE PROCEDURE seed_demo_numbers_loop(IN p_count INT)
BEGIN
    DECLARE v_counter INT DEFAULT 1;

    counting_loop: LOOP
        IF v_counter > p_count THEN
            LEAVE counting_loop;
        END IF;
        INSERT INTO demo_numbers (value) VALUES (v_counter);
        SET v_counter = v_counter + 1;
    END LOOP;
END //

DELIMITER ;
```

На практике стоит явно оговорить: почти любую задачу вида «пронумеровать последовательность» или «сгенерировать N строк» четвёртый урок уровня «Средний» уже решал через `WITH RECURSIVE` — множественную, декларативную, часто более эффективную альтернативу процедурному циклу. Циклы в процедурах нужны не для замены множественных SQL-операций, а там, где на каждой итерации требуется нетривиальная процедурная логика (условия, вызовы других процедур, накопление состояния, не выражаемого одним агрегатом) — то есть именно там, где чисто декларативный SQL-запрос описать решение не может.

### Курсоры: построчная обработка результата запроса

**Курсор** — механизм, позволяющий процедуре обойти результат `SELECT` строка за строкой, а не получить его целиком как единый набор (как это происходит при обычном обращении к результату из приложения). Курсор объявляется, открывается, из него читается по одной строке через `FETCH`, и в конце явно закрывается:

```sql
DELIMITER //

CREATE PROCEDURE apply_loyalty_discounts()
BEGIN
    DECLARE v_customer_id INT;
    DECLARE v_total DECIMAL(10, 2);
    DECLARE v_done INT DEFAULT 0;

    DECLARE cur CURSOR FOR
        SELECT c.id, COALESCE(SUM(oi.quantity * oi.price), 0) AS total_spent
        FROM customers c
        LEFT JOIN orders o ON o.customer_id = c.id AND o.status <> 'cancelled'
        LEFT JOIN order_items oi ON oi.order_id = o.id
        GROUP BY c.id;

    DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = 1;

    OPEN cur;

    read_loop: LOOP
        FETCH cur INTO v_customer_id, v_total;
        IF v_done = 1 THEN
            LEAVE read_loop;
        END IF;

        IF v_total > 100000 THEN
            UPDATE customers SET loyalty_discount = 0.10 WHERE id = v_customer_id;
        ELSEIF v_total > 20000 THEN
            UPDATE customers SET loyalty_discount = 0.05 WHERE id = v_customer_id;
        END IF;
    END LOOP;

    CLOSE cur;
END //

DELIMITER ;
```

Здесь `DECLARE CONTINUE HANDLER FOR NOT FOUND` — обработчик особого условия «строки в курсоре закончились»: без него `FETCH` из пустого курсора привёл бы к ошибке, обрывающей выполнение процедуры; `CONTINUE HANDLER` перехватывает это условие и, вместо ошибки, просто устанавливает флаг `v_done`, который цикл читает для аккуратного завершения. Курсоры — это самый «дорогой» по стоимости выполнения инструмент из показанных в этом уроке: построчная обработка внутри процедуры почти всегда медленнее, чем эквивалентная операция, выраженная через один-два обычных `SET`-based запроса (`UPDATE` с `JOIN`, `INSERT ... SELECT`), поэтому их применение оправдано только тогда, когда логику для каждой строки действительно невозможно свести к единому декларативному запросу.

### Изменение и удаление процедуры

Процедура удаляется командой `DROP PROCEDURE имя;` — по аналогии с `DROP TABLE`/`DROP INDEX`, уже знакомыми из седьмого урока уровня «Основы» и первого урока этого уровня. MySQL не поддерживает прямое «изменение» тела существующей процедуры одной командой — стандартный подход: `DROP PROCEDURE IF EXISTS имя;`, затем заново `CREATE PROCEDURE` с новым телом.

### Когда хранимая процедура — правильный инструмент, а когда — нет

Хранимая процедура переносит часть бизнес-логики с уровня приложения на уровень сервера базы данных. У этого решения есть ситуативные плюсы (логика гарантированно выполняется одинаково для любого клиента, обращающегося к базе — не только для одного конкретного приложения; сложная многошаговая операция выполняется одним вызовом `CALL`, без обмена промежуточными результатами по сети) и не менее весомые минусы (логика на процедурном SQL сложнее тестировать и версионировать, чем код приложения; она не видна инструментам статического анализа и системам контроля версий приложения так же прозрачно, как обычный код; она привязывает бизнес-правила к конкретной СУБД, усложняя потенциальный переход на другую). Общепринятая практика — использовать хранимые процедуры point-wise, для конкретных, явно обоснованных случаев (пакетные, регулярно повторяющиеся операции над большими объёмами данных, где накладные расходы на сетевой обмен между приложением и сервером были бы неприемлемы), а не как основной способ реализации бизнес-логики приложения по умолчанию. Тот же вопрос — «где должна жить эта логика: на сервере БД или в приложении» — станет ещё более выраженным в следующем уроке, посвящённом триггерам.

### Резюме

- **Хранимая процедура** — сохранённый на сервере блок процедурного кода, вызываемый по имени через `CALL`; в отличие от `SELECT`, может содержать последовательность инструкций, условия и циклы.
- `DELIMITER` временно меняет разделитель команд для клиента, чтобы отправить на сервер весь текст `CREATE PROCEDURE ... END` целиком, несмотря на точки с запятой внутри тела.
- Параметры процедуры бывают трёх видов: `IN` (входной, по умолчанию), `OUT` (выходной, читается из пользовательской переменной `@имя` после `CALL`), `INOUT` (оба направления).
- Локальные переменные объявляются `DECLARE` в начале блока, изменяются через `SET`, единственное скалярное значение результата запроса сохраняется через `SELECT ... INTO переменная`.
- `IF/ELSEIF/ELSE`, `WHILE`, `LOOP`/`LEAVE` — управляющие конструкции ветвления и повторения; для генерации последовательностей и агрегации по множеству строк декларативные средства (`WITH RECURSIVE`, `GROUP BY`) почти всегда предпочтительнее процедурного цикла.
- **Курсор** обходит результат `SELECT` построчно (`DECLARE ... CURSOR FOR`, `OPEN`, `FETCH ... INTO`, `CLOSE`); обработчик `DECLARE CONTINUE HANDLER FOR NOT FOUND` нужен для аккуратного завершения цикла по исчерпании строк. Курсоры — самый дорогой инструмент урока, оправданный только когда логику для строки невозможно выразить одним декларативным запросом.
- Процедура удаляется через `DROP PROCEDURE`; изменение тела — через пересоздание (`DROP` + `CREATE`).
- Перенос логики в хранимые процедуры — осознанный компромисс: удобство единого вызова и гарантированной консистентности против сложности тестирования, версионирования и привязки к конкретной СУБД.
