`GROUP BY`, изученный на уровне «Начинающий», умеет ровно одну вещь: сворачивать несколько строк в одну, теряя доступ к отдельным строкам внутри группы — после группировки видна только итоговая сумма, среднее или количество, а какие конкретно строки в неё вошли, из результата уже не восстановить. Но частая практическая задача требует **обратного**: сохранить все исходные строки как есть, но при этом снабдить каждую дополнительной информацией, вычисленной по группе, к которой она принадлежит — например, «номер товара по убыванию цены **внутри своей категории**», не теряя ни сам товар, ни его категорию, ни остальные столбцы. Именно эту задачу решают **оконные функции** (window functions) — тема этого и следующего урока.

### Идея окна: агрегат без потери строк

Ключевая идея оконной функции: она вычисляется **для каждой строки отдельно**, но использует при этом не только эту строку, а некоторый набор «соседних» строк — то самое **окно** (window), — определяемый явно указанным правилом. В отличие от `GROUP BY`, где строки группы физически объединяются в одну, оконная функция оставляет каждую исходную строку на месте и просто добавляет к ней новый столбец с результатом вычисления по окну.

Синтаксически оконная функция отличается от обычной наличием конструкции `OVER (...)` сразу после названия функции:

```sql
SELECT
    name,
    category_id,
    price,
    ROW_NUMBER() OVER (ORDER BY price DESC) AS price_rank
FROM products;
```

Здесь `ROW_NUMBER() OVER (ORDER BY price DESC)` пронумеровала все товары по убыванию цены: самому дорогому — номер 1, следующему — 2, и так далее, **не убирая ни одной строки и не группируя их** — результат содержит ровно столько строк, сколько было в `products`, просто с дополнительным столбцом-номером.

### PARTITION BY: окно по группам, без склейки строк

Пока окно было общим на всю таблицу. Чтобы получить нумерацию **внутри каждой категории отдельно** (что и была настоящая исходная задача — «топ товаров по цене в каждой категории»), окно делится на части конструкцией `PARTITION BY` — прямой аналог `GROUP BY` по смыслу разбиения на группы, но без сворачивания строк:

```sql
SELECT
    name,
    category_id,
    price,
    ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC) AS rank_in_category
FROM products;
```

Теперь нумерация начинается заново (с 1) для каждого значения `category_id`: самый дорогой товар в категории 1 получит `rank_in_category = 1`, самый дорогой товар в категории 2 — тоже `rank_in_category = 1`, и так для каждой категории отдельно. `PARTITION BY category_id` определяет границы окна («в пределах какой группы считать»), `ORDER BY price DESC` определяет порядок внутри этого окна («в каком порядке нумеровать») — эти две части `OVER (...)` независимы и могут комбинироваться свободно: можно иметь `PARTITION BY` без `ORDER BY` (для функций, которым порядок не важен), `ORDER BY` без `PARTITION BY` (окно на всю таблицу, но с заданным порядком), или оба вместе, как в примере.

Практическая ценность становится очевидной сразу: получить «топ-3 самых дорогих товара в каждой категории» с обычным `GROUP BY` невозможно в принципе — `GROUP BY` даёт одну итоговую строку на группу, а не три конкретные строки-товара. С оконной функцией это делается естественно: сначала пронумеровать, а затем отфильтровать по номеру.

### Фильтрация по результату оконной функции: почему не WHERE

Логичная на первый взгляд попытка сразу ограничить топ-3 через `WHERE`:

```sql
-- Не работает:
SELECT name, category_id, price, ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC) AS rank_in_category
FROM products
WHERE rank_in_category <= 3;
```

наталкивается на то же самое препятствие, что и попытка использовать псевдоним агрегата в `WHERE` из шестого урока уровня «Начинающий»: `WHERE` выполняется **раньше**, чем вычисляются столбцы `SELECT`, включая оконные функции — на момент `WHERE` столбца `rank_in_category` просто ещё не существует, и MySQL вернёт ошибку `Unknown column`. Более того, оконные функции вообще нельзя использовать в `WHERE` напрямую, даже полностью выписав функцию заново (`WHERE ROW_NUMBER() OVER (...) <= 3`) — это запрещено синтаксисом MySQL: оконные функции относятся к тому же логическому шагу выполнения запроса, что и обычный `SELECT`, то есть выполняются **после** `WHERE`.

Правильное решение — вычислить оконную функцию в производной таблице или CTE (третий и четвёртый уроки этого уровня), а затем отфильтровать уже готовый столбец во внешнем `WHERE`:

```sql
WITH ranked_products AS (
    SELECT
        name,
        category_id,
        price,
        ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC) AS rank_in_category
    FROM products
)
SELECT name, category_id, price, rank_in_category
FROM ranked_products
WHERE rank_in_category <= 3
ORDER BY category_id, rank_in_category;
```

Здесь CTE `ranked_products` вычисляет нумерацию один раз, а внешний `SELECT` фильтрует уже по готовому, полностью вычисленному столбцу — на этом уровне `WHERE` работает с обычным столбцом производной таблицы, а не с «недовычисленной» оконной функцией, и никакого конфликта порядка выполнения не возникает.

### ROW_NUMBER, RANK и DENSE_RANK: три способа нумеровать при совпадениях

`ROW_NUMBER()` всегда даёт **уникальные, последовательные** номера без пропусков — даже если у двух строк совпадает значение, по которому идёт сортировка (например, у двух товаров одна и та же цена), одна из них произвольно (в рамках порядка, гарантированного явным `ORDER BY`) получит меньший номер, другая — больший, но никогда одинаковый.

`RANK()` и `DENSE_RANK()`, напротив, специально предназначены для ситуаций, где одинаковый ранг **должен** отражать одинаковое значение — как в спортивном рейтинге, где два спортсмена с одинаковым результатом делят одно и то же место. Разница между ними — в том, что происходит с номером **после** совпадения:

```sql
SELECT
    name,
    price,
    ROW_NUMBER() OVER (ORDER BY price DESC) AS row_num,
    RANK() OVER (ORDER BY price DESC) AS rnk,
    DENSE_RANK() OVER (ORDER BY price DESC) AS dense_rnk
FROM products
ORDER BY price DESC;
```

Представим три товара с ценами 5000, 5000, 4000 (два товара стоят одинаково, третий дешевле):

| price | row_num | rnk | dense_rnk |
|-------|---------|-----|-----------|
| 5000 | 1 | 1 | 1 |
| 5000 | 2 | 1 | 1 |
| 4000 | 3 | 3 | 2 |

- `row_num` — как и раньше, три уникальных последовательных номера 1, 2, 3, независимо от совпадения цен.
- `rnk` (`RANK`) — оба товара с ценой 5000 получают ранг 1 (делят первое место), но следующий товар (4000) получает ранг **3**, а не 2 — `RANK` «пропускает» номера, зарезервированные для количества строк, разделивших предыдущее место (здесь — две строки делили место 1, значит следующее свободное число — 3).
- `dense_rnk` (`DENSE_RANK`) — тоже даёт ранг 1 обоим товарам с ценой 5000, но следующий товар получает ранг **2**, без пропуска — `DENSE_RANK` считает только количество *различных* значений, встреченных до текущей строки, а не количество строк.

Выбор между тремя функциями определяется смыслом задачи: нужен ли гарантированно уникальный порядковый номер безо всякого смысла у совпадений (`ROW_NUMBER`, например, для отбора «ровно N строк», как в примере с топ-3 выше — там нам не нужно было, чтобы товары с одинаковой ценой оба попали в тройку, разрушив её размер до четырёх), или содержательный ранг, где одинаковое значение обязано давать одинаковое место, с последующим вопросом — пропускать ли места конкурентов (`RANK`) или нет (`DENSE_RANK`).

### Оконные функции и агрегаты: SUM/COUNT/AVG в качестве оконных

Любая уже знакомая агрегатная функция — `SUM`, `COUNT`, `AVG`, `MIN`, `MAX` — тоже может использоваться с `OVER (...)`, превращаясь из «сворачивающего» агрегата в оконный, который снова не теряет строк:

```sql
SELECT
    name,
    category_id,
    price,
    AVG(price) OVER (PARTITION BY category_id) AS avg_price_in_category,
    price - AVG(price) OVER (PARTITION BY category_id) AS diff_from_avg
FROM products;
```

Это прямое развитие скалярного подзапроса из первого урока (`price - (SELECT AVG(price) FROM products)`), но теперь среднее считается не по всему каталогу, а **отдельно для каждой категории**, и не требует ни подзапроса, ни `GROUP BY`/`JOIN` для «возврата» информации по категории к каждой строке. Без оконных функций эквивалент пришлось бы собирать через `JOIN` товара с производной таблицей, содержащей средние цены по категориям (как мы делали в первом уроке с производной таблицей `stats`) — оконная функция даёт тот же результат одним столбцом в одном `SELECT`, без дополнительного соединения.

### Резюме

- **Оконная функция** вычисляется для каждой строки отдельно, используя набор «соседних» строк (окно), но не сворачивает и не удаляет исходные строки — в отличие от `GROUP BY`.
- Синтаксис: `<функция>(...) OVER (PARTITION BY ... ORDER BY ...)`; `PARTITION BY` определяет границы окна (аналог группы), `ORDER BY` — порядок внутри окна; оба необязательны и независимы друг от друга.
- **`ROW_NUMBER()`** — уникальные последовательные номера без пропусков, даже при совпадающих значениях сортировки.
- **`RANK()`** — одинаковый ранг у совпадений, с пропуском последующих номеров пропорционально числу совпавших строк.
- **`DENSE_RANK()`** — одинаковый ранг у совпадений, без пропуска номеров — считает количество различных значений.
- Оконную функцию нельзя использовать напрямую в `WHERE` (она вычисляется позже, на этапе `SELECT`, как и псевдонимы из шестого урока уровня «Начинающий»); для фильтрации по её результату нужно вынести вычисление в CTE или производную таблицу и фильтровать уже готовый столбец снаружи.
- Обычные агрегатные функции (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`) можно использовать с `OVER (...)` как оконные — это даёт «агрегат по группе рядом с каждой строкой» без `GROUP BY` и без дополнительного `JOIN`.

## Теоретические задания

### Вопрос 1: Три товара имеют цены 5000, 5000 и 4000 рублей и отсортированы по убыванию цены. Какие номера даст `RANK() OVER (ORDER BY price DESC)`?

- ✅ 1, 1, 3
<!-- RANK даёт совпадающим значениям одинаковый ранг и пропускает номера пропорционально числу строк, разделивших предыдущее место -->
- ❌ 1, 2, 3 — error_text: так нумерует `ROW_NUMBER` — всегда уникальные последовательные номера, даже при совпадении цен. `RANK` специально присваивает одинаковое значение одинаковым: оба товара по 5000 делят место 1, а следующий получает не 2, а 3 — место 2 «израсходовано» поделившими первое.
- ❌ 1, 1, 2 — error_text: так нумерует `DENSE_RANK` — без пропусков, по числу различных значений. `RANK` после двух строк на месте 1 пропускает один номер и отдаёт товару за 4000 ранг 3.
- ❌ 1, 1, 1 — error_text: одинаковый ранг получают только строки с одинаковым значением сортировки. Товар за 4000 дешевле двух товаров за 5000, поэтому его ранг обязан отличаться — «догонять» его до места 1 `RANK` не станет.

### Вопрос 2: В каждой категории нужно отобрать ровно три товара — не больше и не меньше, даже если у нескольких товаров совпадает цена. Какую функцию использовать?

- ✅ `ROW_NUMBER` с `ORDER BY`, дополненным тай-брейком (например, по `id`), и фильтрацией «номер <= 3» через CTE или производную таблицу
<!-- ROW_NUMBER гарантирует уникальные номера, поэтому «топ-3» — это всегда ровно три строки; тай-брейк делает выбор детерминированным -->
- ❌ `RANK` — одинаковым ценам и так должно достаться одинаковое место — error_text: именно поэтому `RANK` здесь не подходит: при совпадении цен в тройку попадёт больше трёх строк, и «ровно три» превратится в четыре-пять. `RANK` нужен, когда ничьи важно сохранить, а не ограничить размер выборки.
- ❌ `DENSE_RANK` — error_text: `DENSE_RANK` страдает тем же: одинаковые значения получают одинаковый ранг, и фильтр «<= 3» оставит все строки с ценой третьего места, включая поделившие его. Только `ROW_NUMBER` даёт гарантированно уникальные номера — ровно N строк на раздел.
- ❌ `GROUP BY` по категории с `LIMIT 3` — error_text: `GROUP BY` сворачивает строки в одну на группу и в принципе не умеет «три конкретных товара категории» (девятый урок уровня «Начинающий»). Голый `LIMIT` без нумерации внутри категорий ограничил бы весь результат, а не каждую категорию.

### Вопрос 3: Почему `WHERE rank_in_category <= 3` не работает в том же SELECT, где вычисляется `ROW_NUMBER() OVER (...) AS rank_in_category`?

- ✅ `WHERE` выполняется до вычисления столбцов `SELECT`, поэтому столбца `rank_in_category` на этом шаге ещё не существует; вычисление нужно вынести в CTE или производную таблицу и фильтровать снаружи
<!-- тот же конфликт логического порядка выполнения, что и с псевдонимами агрегатов в WHERE (шестой урок уровня «Начинающий») -->
- ❌ MySQL запрещает сравнивать целые числа с результатом оконных функций — error_text: сравнение ни при чём: после вынесения нумерации в CTE тот же самый столбец спокойно сравнивается с числом во внешнем `WHERE`. Ограничение — на саму оконную функцию на шаге `WHERE`, а не на операции сравнения.
- ❌ потому что алиас объявлен после `FROM`, а не до него — error_text: место объявления алиаса в тексте запроса не важно — важен логический порядок выполнения: `FROM → WHERE → ... → SELECT`. Столбцы и алиасы списка `SELECT` вычисляются позже `WHERE`, поэтому в `WHERE` их нет (шестой урок уровня «Начинающий»).
- ❌ нужно повторить `ROW_NUMBER() OVER (...)` прямо в `WHERE`, без алиаса — error_text: оконные функции в `WHERE` запрещены синтаксисом MySQL полностью — они вычисляются на том же шаге, что и `SELECT`, то есть после `WHERE`. Повторение функции не обходит порядок выполнения; правильное решение — CTE или производная таблица.

### Вопрос 4: Чем результат запроса с `AVG(price) OVER (PARTITION BY category_id)` отличается от `GROUP BY category_id` с `AVG(price)`?

- ✅ оконный вариант возвращает столько же строк, сколько было в таблице, повторяя среднее категории в каждой её строке; `GROUP BY` сворачивает каждую категорию в одну строку
<!-- окно добавляет агрегат к строкам, не теряя их; GROUP BY теряет отдельные строки -->
- ❌ ничем, это два синтаксиса одного и того же — error_text: результаты принципиально разные по форме: `GROUP BY` теряет отдельные строки, оставляя одну на группу, а оконная функция сохраняет все исходные строки и лишь добавляет к каждой столбец со средним по её категории.
- ❌ оконный вариант тоже возвращает одну строку на категорию, но быстрее — error_text: одну строку на категорию возвращает именно `GROUP BY`. Оконная функция с `PARTITION BY` вычисляется для каждой исходной строки — столько строк на выходе, сколько было на входе, и сама по себе она не про скорость.
- ❌ `PARTITION BY` работает только с `SUM` и `COUNT`, но не с `AVG` — error_text: `AVG` — одна из агрегатных функций (`SUM`, `COUNT`, `AVG`, `MIN`, `MAX`), и любая из них может использоваться с `OVER (PARTITION BY ...)`, превращаясь из сворачивающего агрегата в оконный.

### Вопрос 5: Что можно сказать о нумерации `ROW_NUMBER() OVER (PARTITION BY category_id)` — без `ORDER BY` внутри `OVER`?

- ✅ номера останутся уникальными в пределах каждой категории, но их привязка к конкретным строкам не определена — для детерминированного результата нужен `ORDER BY` внутри `OVER`
<!-- PARTITION BY задаёт границы окна, ORDER BY — порядок внутри него; без ORDER BY порядок строк в окне не гарантирован -->
- ❌ запрос упадёт с синтаксической ошибкой — error_text: `ORDER BY` внутри `OVER (...)` необязателен, как и `PARTITION BY` — эти части независимы. Запрос валиден, но для функций, чувствительных к порядку (`ROW_NUMBER`, `RANK`, `DENSE_RANK`), результат непредсказуем.
- ❌ строки автоматически пронумеруются в порядке вставки — error_text: «порядок вставки» не гарантируется ничем — на это же указывает и обычный `ORDER BY` из девятого урока уровня «Основы». Пока порядок не задан явно, сервер вправе нумеровать строки раздела в любом порядке.
- ❌ категории получат сквозную нумерацию от 1 до конца таблицы — error_text: сквозную нумерацию на всю таблицу даёт отсутствие `PARTITION BY`. Здесь разбиение на части остаётся: нумерация начинается заново с 1 в каждой категории — не задан только порядок строк внутри каждой части.

### Задание 3: ROW_NUMBER, RANK и DENSE_RANK рядом

<!-- Эталонное решение (для автора/бота-верификатора): SELECT name, salary, ROW_NUMBER() OVER (ORDER BY salary DESC, id ASC) AS row_num, RANK() OVER (ORDER BY salary DESC) AS rnk, DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rnk FROM employees ORDER BY salary DESC, id ASC; -->
