Анти-паттерн — распространённый, интуитивно понятный, но вредный для производительности способ написать запрос; его опасность в том, что синтаксически такой запрос абсолютно корректен и возвращает правильный результат — проблема всплывает только на реальном объёме данных, и часто далеко не сразу после того, как код был написан и одобрен на код-ревью.

### Анти-паттерн 1: SELECT * вместо явного списка столбцов

`SELECT *` — соблазнительно короткая запись, которая уже была вскользь показана как проблема для покрывающих индексов в третьем уроке этого уровня, но её вред не ограничивается только этим случаем:

```sql
-- Анти-паттерн
SELECT * FROM orders WHERE customer_id = 42;

-- Починка
SELECT id, status, created_at, paid_at
FROM orders
WHERE customer_id = 42;
```

Проблемы `SELECT *`:

- **Разрушает покрывающие индексы** — как показано в третьем уроке этого уровня, если запросу реально нужны только два-три столбца, а составлен покрывающий их индекс, `SELECT *` заставит сервер всё равно обращаться к самой таблице за остальными столбцами (включая, например, `TEXT`-поля вроде `body` в `reviews`, которые могут быть заметно тяжелее по объёму, чем нужные числовые столбцы).
- **Передаёт по сети больше данных, чем нужно приложению** — если из десяти столбцов таблицы приложению реально нужны три, оставшиеся семь всё равно вычитываются с диска, упаковываются в протокол и передаются по сети клиенту, где немедленно отбрасываются.
- **Делает код хрупким к изменению схемы** — если позже в таблицу добавят новый столбец (`ALTER TABLE ... ADD COLUMN`, седьмой урок уровня «Основы»), `SELECT *` в уже написанном коде приложения начнёт возвращать дополнительный столбец, на который код не рассчитывал, — это может привести к неочевидным ошибкам далеко от места самого изменения схемы.

Явный список столбцов после `SELECT` — не педантизм, а осознанная защита от всех трёх проблем сразу; он ничего не стоит с точки зрения читаемости (наоборот, явно показывает, какие данные запросу действительно нужны) и всегда безопаснее в развивающемся проекте.

### Анти-паттерн 2: функция над индексированным столбцом

Третий урок этого уровня уже показал пример `WHERE YEAR(created_at) = 2026` как условие, ломающее использование индекса по `created_at`. Причина этого — фундаментальная: индекс хранит **исходные** значения столбца в отсортированном порядке; если запрос требует сравнивать не сами значения, а результат функции от них, сервер не может воспользоваться готовым порядком — ему пришлось бы вычислить `YEAR(created_at)` для каждой строки таблицы, что эквивалентно полному сканированию. Тот же эффект дают любые вычисления над столбцом внутри условия:

```sql
-- Анти-паттерн: индекс по created_at не используется
SELECT * FROM orders WHERE YEAR(created_at) = 2026;

-- Анти-паттерн: индекс по price не используется
SELECT * FROM products WHERE price * 1.2 > 1000;
```

Починка — «развернуть» условие так, чтобы **сам столбец** остался без изменений, а вычисление ушло на константу (которая вычисляется один раз, а не для каждой строки):

```sql
-- Индекс по created_at используется как диапазон
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- Индекс по price используется
SELECT * FROM products WHERE price > 1000 / 1.2;
```

Общий принцип: **левая часть условия сравнения должна оставлять индексированный столбец «голым»** — любое преобразование должно переехать на правую часть, в константу или в подзапрос, вычисляемый один раз, а не в функцию, применяемую к каждой строке таблицы.

### Анти-паттерн 3: leading-wildcard LIKE

Второй урок уровня «Начинающий» ввёл `LIKE` с шаблонами `%`/`_`, но не сказал явно о разной стоимости разных позиций `%`. Условие `LIKE 'значение%'` (шаблон в конце) индекс использовать может — префикс `значение` задаёт точное начало отсортированного диапазона, и сервер может искать по нему почти так же, как по обычному диапазонному условию. А вот условие с **ведущим** `%` — `LIKE '%значение'` или `LIKE '%значение%'` — индекс использовать не может **в принципе**, независимо от его наличия:

```sql
-- Индекс по name может помочь: ищем точное начало строки
SELECT * FROM products WHERE name LIKE 'Клавиатура%';

-- Индекс по name не поможет: искомая подстрока может быть где угодно внутри значения
SELECT * FROM products WHERE name LIKE '%клавиатура%';
```

Причина та же, что в предыдущих анти-паттернах: индекс отсортирован по **началу** строкового значения, а «подстрока где угодно внутри» не связана с этим порядком никак — поиск товара, чьё название *содержит* слово в произвольном месте, требует либо полного сканирования, либо специализированного инструмента — полнотекстового индекса (`FULLTEXT`, отдельная тема десятого урока этого уровня), который устроен принципиально иначе, чем обычный B-tree индекс, и предназначен именно для такого поиска по содержанию текста, а не по его началу.

### Анти-паттерн 4: большие списки в IN и цепочки OR

Условие `IN (список)` (второй урок уровня «Начинающий») для короткого списка констант обычно обрабатывается сервером эффективно — как серия точечных поисков по индексу, один на каждое значение списка. Но список, сформированный динамически из результата другого запроса или переданный из приложения без ограничения, может неограниченно расти:

```sql
-- Потенциальная проблема при очень длинном списке id
SELECT * FROM products
WHERE id IN (5, 12, 47, 103, 201, /* ...ещё тысячи значений... */);
```

Похожая проблема возникает и с длинными цепочками `OR` по разным столбцам (в отличие от `IN`, объединяющего условия по одному и тому же столбцу):

```sql
-- Цепочка OR по разным столбцам — оптимизатору сложнее использовать
-- один составной индекс сразу для всех условий
SELECT * FROM orders
WHERE (customer_id = 42 AND status = 'paid')
   OR (customer_id = 77 AND status = 'pending')
   OR (customer_id = 91 AND status = 'paid');
```

Практическое правило: `IN` с разумно ограниченным числом значений (сотни, не десятки тысяч) — нормальная и эффективная конструкция; если список формируется из подзапроса, для которого нет естественного верхнего предела размера, часто эффективнее переписать логику через `JOIN` с временной или производной таблицей (первый урок уровня «Средний»), чем передавать в `IN` заранее не ограниченное множество значений. Для цепочек `OR` по одинаковой структуре условий, отличающихся только конкретными значениями, `UNION ALL` нескольких простых, каждый по своему индексу оптимизированных запросов (третий урок уровня «Средний») часто оказывается быстрее одного запроса с длинной дизъюнкцией, которую оптимизатору сложно эффективно разложить по индексам.

### Общий подход к починке: воспроизвести, диагностировать, переписать, сравнить

Все анти-паттерны этого урока объединяет общий алгоритм работы с ними, применимый на практике:

1. **Воспроизвести** — убедиться, что запрос действительно медленный на реалистичном объёме данных (на десяти строках любой из анти-паттернов безвреден).
2. **Диагностировать через EXPLAIN** — второй урок этого уровня: посмотреть `type`, `key`, `rows`, `Extra` и определить, какая часть условия мешает использованию ожидаемого индекса.
3. **Переписать запрос**, устраняя конкретный анти-паттерн — развернуть выражение, заменить leading-wildcard на полнотекстовый поиск, ограничить или переструктурировать список `IN`.
4. **Сравнить планы `EXPLAIN` до и после** — убедиться, что `type` действительно улучшился (например, с `ALL` на `range`/`ref`), а не просто «переписать и понадеяться».

Этот же алгоритм — фундамент капстоуна пятнадцатого урока этого уровня, где придётся различить два принципиально разных случая замедления: тот, что лечится индексом, и тот, что лечится именно переписыванием запроса (ровно то, что было продемонстрировано в этом уроке) — и объяснить, почему выбранное решение подходит именно этому случаю.

### Резюме

- **`SELECT *`** передаёт лишние данные по сети, читает ненужные столбцы с диска и разрушает покрывающие индексы — явный список столбцов не стоит ничего и защищает от всех трёх проблем.
- **Функция или вычисление над индексированным столбцом внутри условия** (`YEAR(created_at) = ...`, `price * 1.2 > ...`) не даёт использовать индекс, потому что серверу нужно применить вычисление к каждой строке — решение: перенести вычисление на константу, оставив столбец «голым».
- **`LIKE`-шаблон с ведущим `%`** индекс не использует ни при каких условиях (искомая подстрока может быть в любом месте значения); `LIKE 'префикс%'` — использует. Поиск по содержимому текста — задача `FULLTEXT`, а не обычного индекса.
- **Очень длинные `IN`-списки и цепочки `OR` по разным столбцам** сложны для оптимизатора; решение — ограничение размера списка/переход на `JOIN` с производной таблицей для `IN`, и `UNION ALL` из нескольких простых запросов для длинных `OR`-цепочек.
- Единый рабочий алгоритм: воспроизвести медленный запрос на реалистичном объёме → диагностировать через `EXPLAIN` → переписать, устраняя конкретный анти-паттерн → сравнить планы `EXPLAIN` до и после, чтобы подтвердить реальное улучшение.
