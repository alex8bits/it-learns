В этом уроке разберём, как соединять произвольное число таблиц в одном запросе, а также рассмотрим особый, на первый взгляд необычный случай — соединение таблицы **с самой собой** (self-join), который нужен для работы с иерархическими данными: деревом категорий и структурой подчинённости сотрудников.

### Соединение трёх и более таблиц: просто добавляем ещё один JOIN

Никакого нового синтаксиса для соединения нескольких таблиц не требуется — конструкция `JOIN ... ON ...` из тринадцатого урока просто повторяется столько раз, сколько нужно присоединить дополнительных таблиц, одна за другой:

```sql
SELECT
    o.id AS order_id,
    c.name AS customer_name,
    p.name AS product_name,
    oi.quantity,
    oi.price
FROM orders o
INNER JOIN customers c ON o.customer_id = c.id
INNER JOIN order_items oi ON oi.order_id = o.id
INNER JOIN products p ON p.id = oi.product_id;
```

Каждая новая строка `INNER JOIN` добавляет к уже собранному «широкому» набору данных ещё одну таблицу, соединяя её по собственному условию `ON`. Логику стоит читать последовательно, сверху вниз: сначала `orders` соединяется с `customers` (получаем заказ + имя клиента), затем к каждой такой строке присоединяются все связанные строки `order_items` (получаем заказ + клиент + позиция заказа — и если в заказе несколько товаров, строка заказа с клиентом «размножится» на несколько строк, по одной на каждую позицию), и, наконец, к каждой такой расширенной строке присоединяется `products` по `product_id` из `order_items` (получаем окончательный результат — заказ + клиент + конкретный товар + количество + цена). Порядок, в котором мы **пишем** `JOIN`'ы, обычно соответствует естественной логике связей (от заказа — к клиенту, от заказа — к его позициям, от позиции — к товару), хотя формально MySQL умеет самостоятельно определять эффективный порядок физического выполнения — программисту достаточно указать все нужные соединения и условия, а не заботиться о том, в каком порядке их реально обрабатывать «под капотом».

### Смешение INNER и LEFT JOIN в одной цепочке

`INNER JOIN` и `LEFT JOIN` из предыдущих двух уроков свободно комбинируются в одной цепочке соединений — важно только внимательно продумывать, какая часть данных должна сохраняться, даже если для неё нет пары, а какая обязана иметь совпадение. Например, хотим отчёт по всем клиентам (включая тех, у кого пока нет заказов), и, если заказы есть, — с товарами внутри них:

```sql
SELECT
    c.name AS customer_name,
    o.id AS order_id,
    p.name AS product_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
LEFT JOIN order_items oi ON oi.order_id = o.id
LEFT JOIN products p ON p.id = oi.product_id;
```

Здесь **все три** соединения — `LEFT JOIN`, потому что на каждом шаге мы хотим сохранить строку, даже если дальше по цепочке ничего не нашлось: клиента без заказов, заказ без товаров (гипотетически) и так далее. Если бы хотя бы одно из соединений в середине цепочки было `INNER JOIN`, оно «отрезало» бы все строки, дошедшие до этого шага с `NULL` вместо реальной связи, — и эффект `LEFT JOIN`, использованный на предыдущих шагах, был бы полностью нейтрализован ниже по цепочке. Практическое правило: если хотя бы одна таблица в цепочке присоединена через `LEFT JOIN`, и результат этого соединения (в том числе строки с `NULL`) должен присутствовать в финальном отчёте, все **последующие** соединения, зависящие от этой присоединённой таблицы, тоже нужно делать через `LEFT JOIN`, а не `INNER JOIN`.

### Self-join: соединение таблицы с самой собой

Всё, что мы разбирали до сих пор, было соединением **разных** таблиц. Но иногда связь существует внутри **одной и той же** таблицы — например, категория товаров может иметь родительскую категорию (тоже категорию, из той же самой таблицы `categories`), а сотрудник может иметь руководителя (тоже сотрудника, из той же таблицы `employees`). Такая связь называется **рекурсивной** (или иерархической): строка ссылается на другую строку своей же таблицы через внешний ключ, указывающий на первичный ключ этой же таблицы.

Рассмотрим таблицу сотрудников с самоссылающимся столбцом `manager_id`:

```sql
CREATE TABLE employees (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    manager_id INT NULL,
    salary DECIMAL(10, 2) NOT NULL,
    FOREIGN KEY (manager_id) REFERENCES employees(id)
);
```

Столбец `manager_id` — внешний ключ, но ссылается он не на другую таблицу, а на **ту же самую** `employees`: значение `manager_id` — это `id` другого сотрудника, который является руководителем текущего. У сотрудников самого верхнего уровня (например, генерального директора) `manager_id` будет `NULL` — у него нет руководителя внутри компании, что мы уже понимаем как законное, осмысленное отсутствие значения из одиннадцатого урока «Основ».

Чтобы вывести имя сотрудника **вместе с именем его руководителя** (а не просто числовым `manager_id`), таблицу `employees` нужно соединить **с самой собой** — формально это выглядит как обычный `JOIN`, но обеим «копиям» таблицы обязательно назначаются **разные алиасы**, иначе SQL не сможет различить, где «сотрудник», а где «его руководитель»:

```sql
SELECT
    e.name AS employee_name,
    m.name AS manager_name
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

Здесь `employees e` — это «сотрудник» в контексте текущей строки, а `employees m` — та же самая таблица, но выступающая в роли «руководитель». Условие `ON e.manager_id = m.id` находит строку `m`, чей `id` совпадает с `manager_id` строки `e`. Мы намеренно выбрали `LEFT JOIN`, а не `INNER JOIN`: сотрудник без руководителя (директор, `manager_id IS NULL`) всё равно должен остаться в отчёте, просто со значением `NULL` в `manager_name`; `INNER JOIN` в этом случае убрал бы директора из результата целиком, что почти наверняка не входило в задачу отчёта.

### Self-join для дерева категорий

Ровно та же техника применима к дереву категорий товаров, о котором мы говорили в одиннадцатом уроке как о примере иерархической структуры:

```sql
CREATE TABLE categories (
    id INT AUTO_INCREMENT PRIMARY KEY,
    parent_id INT NULL,
    name VARCHAR(100) NOT NULL,
    FOREIGN KEY (parent_id) REFERENCES categories(id)
);
```

Выведем каждую категорию вместе с названием её родительской категории:

```sql
SELECT
    child.name AS category_name,
    parent.name AS parent_category_name
FROM categories child
LEFT JOIN categories parent ON child.parent_id = parent.id;
```

Категории верхнего уровня (например, «Электроника» без родителя) получат `NULL` в `parent_category_name` — и снова именно `LEFT JOIN`, а не `INNER JOIN`, гарантирует, что такие «корневые» категории не пропадут из отчёта.

Важно понимать границу применимости этой техники на уровне «Начинающий»: обычный `self-join`, который мы разобрали, позволяет достать данные ровно **одного уровня** родительской связи — сотрудника и его непосредственного руководителя, категорию и её непосредственного родителя. Если нужно подняться на два уровня вверх («сотрудник, его руководитель и руководитель руководителя») или обойти дерево произвольной глубины целиком (например, «все подкатегории любого уровня внутри категории "Электроника"»), потребовался бы либо ещё один, третий `self-join` той же таблицы (что решает задачу только для заранее известного, фиксированного числа уровней и быстро становится неудобным), либо специальный инструмент — **рекурсивные общие табличные выражения** (`WITH RECURSIVE`), с которыми мы познакомимся на уровне «Средний». На уровне «Начинающий» достаточно уверенно работать с self-join'ом для одного уровня иерархии — это уже покрывает значительную часть практических задач.

### Резюме

- Соединение трёх и более таблиц не требует нового синтаксиса — `JOIN ... ON ...` из тринадцатого урока просто повторяется для каждой дополнительной таблицы, формируя последовательную цепочку.
- `INNER JOIN` и `LEFT JOIN` можно свободно комбинировать в одной цепочке; если ранний `LEFT JOIN` должен сохранять строки без пары, все зависящие от него дальнейшие соединения тоже должны быть `LEFT JOIN`, иначе эффект первого `LEFT JOIN` будет нейтрализован.
- Self-join — соединение таблицы **с самой собой**; применяется, когда строка ссылается на другую строку той же таблицы через внешний ключ (руководитель сотрудника, родительская категория).
- При self-join обеим «копиям» одной и той же таблицы обязательно назначаются **разные алиасы**, чтобы различать роли строк в условии `ON` и в списке `SELECT`.
- Для self-join с необязательной связью (директор без руководителя, корневая категория без родителя) используется `LEFT JOIN`, чтобы такие строки не пропадали из результата.
- Обычный self-join раскрывает ровно один уровень иерархии; обход дерева произвольной глубины требует рекурсивных CTE — тема уровня «Средний».

## Теоретические задания

### Вопрос 1: Как соединить в одном запросе три таблицы — `orders`, `order_items` и `products`?

- ✅ Выписать цепочку: `INNER JOIN order_items ON ...` и ещё `INNER JOIN products ON ...` — каждый `JOIN` со своим условием
<!-- нового синтаксиса не нужно: JOIN ... ON повторяется на каждую дополнительную таблицу -->
- ❌ Перечислить все таблицы в `FROM` через запятую, а условия соединения собрать в `WHERE` — error_text: технически возможно, но это устаревший стиль урока 13: он смешивает связь и фильтры, и при потере одного условия тихо даёт декартово произведение. Рекомендуемый способ — явные `JOIN ... ON`.
- ❌ Использовать оператор `MULTI JOIN` с одним общим условием `ON` в конце — error_text: оператора `MULTI JOIN` в SQL нет. Каждая таблица присоединяется собственной конструкцией `JOIN ... ON`, повторённой нужное число раз.
- ❌ Никак: один запрос соединяет не более двух таблиц — error_text: соединять можно сколько угодно таблиц — `JOIN ... ON` просто повторяется в цепочке. Реальные отчёты собирают по четыре-пять таблиц сразу, как в этом уроке.

### Вопрос 2: В цепочке `customers c LEFT JOIN orders o ... INNER JOIN order_items oi ON oi.order_id = o.id` — что случится с клиентом без заказов?

- ✅ Он отрежется на шаге `INNER JOIN`: у «пустой» пары `o.id` равен `NULL`, пары с `order_items` не находится, и строка теряется
<!-- INNER в середине цепочки нейтрализует эффект LEFT, сделанного раньше -->
- ❌ Он пройдёт всю цепочку и получит `NULL` во всех столбцах `order_items` — error_text: так было бы, будь второй `JOIN` тоже `LEFT`. `INNER` же требует совпадения — а у «пустой» пары `o.id` равен `NULL`, пары не находится, и строка не доходит до результата.
- ❌ Запрос завершится ошибкой: смешивать `INNER` и `LEFT` в одной цепочке нельзя — error_text: смешивать можно — это штатная возможность SQL, и урок этим пользуется. Проблема не в синтаксисе, а в результате: эффект `LEFT JOIN` нейтрализуется, хотя он был нужен.
- ❌ Клиент останется в результате одной строкой без позиций — error_text: одна строка с `NULL` на конце — поведение цепочки из `LEFT JOIN`. `INNER JOIN` в середине цепочки не «пропускает» строки без пары дальше — они отбрасываются целиком.

### Вопрос 3: Зачем при self-join (`FROM employees e ... JOIN employees m ...`) двум копиям таблицы дают разные алиасы `e` и `m`?

- ✅ Без разных имён СУБД не различит, где «сотрудник», а где «его руководитель», — и в `ON`, и в `SELECT` возникнет неоднозначность
<!-- алиас задаёт роль каждой копии одной и той же таблицы -->
- ❌ Алиасы создают две физические копии таблицы — без них соединить таблицу с собой нельзя — error_text: копии не создаются: обе ссылки указывают на одну и ту же таблицу. Алиасы — имена-роли, позволяющие обратиться к ней дважды в разных ролях, а не механизм копирования.
- ❌ Так требует внешний ключ: `manager_id` ссылается на алиас, а не на таблицу — error_text: внешний ключ объявляется в `CREATE TABLE` и ссылается на таблицу `employees`, а не на алиасы запроса. Алиасы живут только внутри `SELECT` и с ограничениями не связаны.
- ❌ Разные алиасы ускоряют соединение таблицы с самой собой — error_text: алиасы не влияют на скорость — они решают задачу различения двух ролей одной таблицы. Без них запрос с двумя одноимёнными копиями просто некорректен.

### Вопрос 4: Почему для отчёта «сотрудник — имя руководителя» в уроке выбран `LEFT JOIN employees m ON e.manager_id = m.id`, а не `INNER JOIN`?

- ✅ У директора `manager_id IS NULL`, и `LEFT JOIN` сохранит его в отчёте — с `NULL` в имени руководителя
<!-- необязательная связь: строки без пары должны остаться в результате -->
- ❌ `INNER JOIN` при self-join запрещён: таблица соединяется сама с собой — error_text: self-join с `INNER JOIN` синтаксически возможен — просто строки без руководителя исчезнут из результата. Выбор `LEFT` продиктован требованием отчёта, а не запретом СУБД.
- ❌ `LEFT JOIN` нужен, чтобы `manager_id` автоматически превращался в имя руководителя — error_text: превращение ссылки в имя — работа условия `ON e.manager_id = m.id` при любом виде `JOIN`. `LEFT` лишь решает судьбу строк, для которых пары не нашлось.
- ❌ `INNER JOIN` вернул бы директора со строкой `NULL` в имени руководителя — error_text: наоборот: NULL-подстановка — привилегия внешнего соединения урока 14. `INNER` молча исключает директора из результата целиком.

### Вопрос 5: Можно ли одним запросом вывести «сотрудник — его руководитель — руководитель руководителя»?

- ✅ Да: добавить к self-join ещё один — `LEFT JOIN employees mm ON m.manager_id = mm.id`
<!-- каждый следующий уровень иерархии — ещё один self-join; глубина должна быть известна заранее -->
- ❌ Нет, на уровне «Начинающий» это невозможно в принципе — error_text: возможно для фиксированного числа уровней: просто ещё один self-join той же таблицы с новой ролью. Произвольная глубина дерева — да, потребует рекурсивных CTE уровня «Средний», но два-три уровня — обычный `JOIN`.
- ❌ Только через рекурсивные CTE — error_text: рекурсивные CTE нужны для заранее неизвестной глубины дерева. Когда число уровней фиксировано (руководитель и его руководитель), достаточно цепочки обычных self-join.
- ❌ Да, но только если у всех сотрудников ровно два уровня подчинения — error_text: число уровней в данных может быть любым: у верхних сотрудников у второго self-join не найдётся пары, и `LEFT JOIN` оставит `NULL` — ровно как директор в отчёте с одним уровнем.
