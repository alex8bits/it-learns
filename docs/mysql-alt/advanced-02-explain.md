Для ответа на вопрос «как именно MySQL собирается выполнить этот запрос» существует команда `EXPLAIN` — она не выполняет запрос, а показывает **план** его выполнения, составленный оптимизатором.

### Что делает EXPLAIN

`EXPLAIN` ставится перед любым `SELECT` (а также перед `UPDATE`/`DELETE`/`INSERT ... SELECT` в современных версиях MySQL) и вместо результата запроса возвращает таблицу, описывающую, каким способом сервер планирует его выполнить:

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 42;
```

Важно зафиксировать сразу: `EXPLAIN` **не выполняет** сам запрос и не возвращает данные, которые бы вернул обычный `SELECT` — он показывает только план, составленный оптимизатором запросов (компонентом MySQL, который решает, в каком порядке соединять таблицы и какие индексы использовать, ещё до фактического чтения данных). У этого плана есть важное следствие: показанный план — это *намерение* оптимизатора на основе накопленной статистики о таблицах, а не гарантированно точное описание того, что произошло бы при полном исполнении на всех данных, — но на практике план оптимизатора почти всегда совпадает с реальным поведением сервера, и именно поэтому `EXPLAIN` — базовый рабочий инструмент, а не приближённая догадка.

### Столбцы плана: разбираем главное

Вывод `EXPLAIN` содержит по одной строке на каждую таблицу, участвующую в запросе (для запроса с несколькими `JOIN` строк будет несколько — план описывает порядок обращения к каждой из них). Разберём столбцы, важные для повседневной диагностики:

**`table`** — имя таблицы (или её алиас), к которой относится эта строка плана. В запросе с несколькими `JOIN` порядок строк в выводе показывает порядок, в котором сервер планирует обращаться к таблицам — это не обязательно тот порядок, в котором таблицы записаны в запросе: оптимизатор может решить, что эффективнее начать с другой таблицы.

**`type`** — тип доступа к таблице, самый важный столбец плана: он показывает, *каким способом* сервер собирается найти нужные строки. От лучшего к худшему для точечного поиска:

- `const` / `system` — таблица содержит не более одной подходящей строки (обычно поиск по первичному или уникальному ключу с константой) — быстрее не бывает;
- `eq_ref` — для каждой строки внешней таблицы находится ровно одна строка по уникальному индексу — типичный случай `JOIN` по первичному ключу;
- `ref` — поиск по неуникальному индексу, может найти несколько строк, но использует индекс, а не полное сканирование;
- `range` — поиск диапазона значений по индексу (`BETWEEN`, `<`, `>`, `IN` с несколькими значениями);
- `index` — сканируется **весь** индекс целиком (а не таблица), это дешевле полного сканирования таблицы, но всё же требует прохода по всем его записям;
- `ALL` — **полное сканирование таблицы** без единого индекса — ровно то, что было продемонстрировано в прошлом уроке как медленный вариант.

Увидеть `type = ALL` для большой таблицы в запросе, который выполняется часто, — почти всегда сигнал «здесь не хватает подходящего индекса» (если только запрос сознательно не должен читать почти все строки, о чём — четвёртый урок этого уровня).

**`key`** — имя индекса, который сервер фактически выбрал для этой таблицы (или `NULL`, если ни один индекс не подошёл — обычно вместе с `type = ALL`). Полезно сравнить `key` со столбцом `possible_keys`, который показывает все индексы, которые *теоретически подходили* по условию `WHERE`/`ON` — если `possible_keys` не пуст, а `key` показывает `NULL` или другой, не самый подходящий индекс, это повод разобраться, почему оптимизатор отклонил ожидаемый вариант (об этом — в третьем уроке этого уровня, где разбираются причины, по которым индекс может не сработать).

**`rows`** — оценка количества строк, которые сервер планирует прочитать для этой таблицы (не точное число, а статистическая оценка на основе накопленной информации о распределении данных). Резкое несоответствие между `rows` и реальным ожидаемым результатом запроса (например, план обещает прочитать миллион строк, а результат запроса — три строки) — характерный симптом отсутствия подходящего индекса: сервер вынужден проверить намного больше строк, чем в итоге попадёт в ответ.

**`Extra`** — дополнительные примечания о плане, среди которых особенно важны два:

- `Using filesort` — сервер не смог отсортировать результат «бесплатно» через порядок индекса и выполняет отдельную, дополнительную сортировку уже отобранных строк в памяти (или на диске, если строк слишком много). Для небольших результатов это не проблема, но для больших — заметный источник замедления, устранимый подходящим индексом (третий урок этого уровня разберёт, при каких условиях индекс избавляет от `filesort`);
- `Using temporary` — сервер создаёт временную таблицу для промежуточного хранения результатов (типично для некоторых сочетаний `GROUP BY`/`DISTINCT`/`UNION` без подходящего индекса) — тоже источник дополнительной работы, которого в ряде случаев можно избежать.

Ни `Using filesort`, ни `Using temporary` не являются сами по себе признаком ошибки в запросе — на маленьком результате они безвредны; тревожный сигнал — это их появление в сочетании с большим `rows` в плане того же запроса.

### Сквозной пример: читаем план целиком

Рассмотрим план запроса, соединяющего заказы с позициями:

```sql
EXPLAIN
SELECT o.id, oi.product_id, oi.quantity
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 42
ORDER BY o.created_at;
```

Без индекса по `orders.customer_id` типичный (упрощённый) план показал бы для таблицы `o` строку с `type = ALL`, `key = NULL` и большим значением `rows`, приблизительно равным общему числу строк в `orders` — сервер обязан проверить каждый заказ, чтобы найти те, что принадлежат клиенту 42. После создания `CREATE INDEX idx_orders_customer_id ON orders (customer_id);` (первый урок этого уровня) тот же план для таблицы `o` показал бы `type = ref`, `key = idx_orders_customer_id` и `rows`, приблизительно равное числу заказов именно этого клиента — на несколько порядков меньше. Для таблицы `oi` ожидаем `type = ref` по индексу внешнего ключа `order_id` (такой индекс MySQL создаёт автоматически для столбцов, участвующих в `FOREIGN KEY`, — двенадцатый урок уровня «Начинающий» вводил внешние ключи, но не упоминал явно, что они порождают индекс: это ровно тот механический эффект, который делает `JOIN` по внешнему ключу изначально дешёвым без специальных дополнительных действий).

### EXPLAIN ANALYZE: план и реальность одновременно

Начиная с MySQL 8.0.18 доступна расширенная форма — `EXPLAIN ANALYZE` — которая, в отличие от обычного `EXPLAIN`, **фактически выполняет** запрос и показывает не только предполагаемый оптимизатором план, но и реальное измеренное время выполнения каждого шага:

```sql
EXPLAIN ANALYZE
SELECT o.id, oi.product_id
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 42;
```

Вывод `EXPLAIN ANALYZE` организован как дерево вложенных шагов (в отличие от табличного `EXPLAIN`) и для каждого шага показывает предполагаемое и фактическое число строк, а также реальное время выполнения — это ценно именно тогда, когда обычный `EXPLAIN` показывает план, который *выглядит* правильным (использует нужный индекс), но запрос всё равно медленный: `EXPLAIN ANALYZE` помогает увидеть, на каком именно шаге в дереве уходит основное время. Поскольку `EXPLAIN ANALYZE` реально выполняет запрос, его не стоит использовать для тяжёлых пишущих операций или на продуктивной базе без осторожности — ровно так же, как не стоит бездумно гонять на проде любой дорогой аналитический `SELECT`.

### EXPLAIN — инструмент диагностики, а не генератор индексов

Важно с самого начала избежать ошибочного вывода «раз `EXPLAIN` показывает `type = ALL`, надо создать индекс». `EXPLAIN` только *показывает* текущий способ выполнения — решение, что с этим делать, требует понимания контекста: возможно, здесь действительно не хватает индекса (тема следующих уроков), а возможно, запрос отбирает такую большую долю таблицы, что полное сканирование — уже самый эффективный вариант, и никакой индекс здесь не поможет (сервер в такой ситуации сам, скорее всего, откажется от использования индекса, даже если он есть, — это разбирается в третьем уроке этого уровня). `EXPLAIN` даёт факты о плане; интерпретация этих фактов и выбор действия — отдельный навык, который курс будет развивать до самого капстоуна пятнадцатого урока этого уровня.

### Резюме

- `EXPLAIN` перед `SELECT` (и рядом других команд) показывает **план** выполнения запроса, составленный оптимизатором, не выполняя сам запрос.
- Ключевые столбцы плана: `table` (какая таблица), `type` (способ доступа: от лучшего `const`/`eq_ref`/`ref`/`range` до худшего `ALL` — полное сканирование), `key` (фактически выбранный индекс, в сравнении с `possible_keys`), `rows` (оценка числа читаемых строк), `Extra` (примечания, среди которых важны `Using filesort` и `Using temporary`).
- `type = ALL` на большой таблице в частом запросе — типичный сигнал недостающего индекса; резкое расхождение `rows` с ожидаемым размером результата — тоже.
- `EXPLAIN ANALYZE` (MySQL 8.0.18+) реально выполняет запрос и добавляет к плану фактическое измеренное время и число строк на каждом шаге — полезен, когда обычный `EXPLAIN` не объясняет реальную медлительность.
- `EXPLAIN` — инструмент диагностики: он показывает текущий способ выполнения, но не подсказывает автоматически правильное решение — интерпретация плана и выбор действия (индекс, переписывание запроса или ничего не менять) остаются за разработчиком.
