# Фильтрация строк WHERE

## Материал

### Все строки — это ещё не ответ

Семь уроков таблицы отвечали на ваши вопросы двумя способами: «дай всё»
(`SELECT *` и его столбцовые варианты) и «дай первые N» (`LIMIT` урока 3).
А реальные вопросы к базе звучат иначе: «дорогие товары», «покупатели не из
Москвы», «заказы за лето», «то, что закончилось». Вручную выискивать строки
в результате — не вариант: в боевой таблице сто тысяч строк, и «первые 10»
почти наверняка не те. Знакомая многим альтернатива — выгрузить всё в
электронную таблицу и отбирать руками: работает, пока строк сто; на ста
тысячах увязает и человек, и таблица. Фильтрация — работа сервера: он
перебирает строки несравнимо быстрее и не устаёт.

Нужен третий инструмент: сообщить серверу **условие** — какие строки нужны.
Это и есть `WHERE`. Там же ждёт обещание урока 7: `UPDATE ... WHERE` и
`DELETE ... WHERE` — урок 10, и условие в них будет ровно то, что выучим
сегодня. В литературе условие в `WHERE` называют по-разному: условие
отбора, критерий фильтрации, предикат — смысл один: выражение, которое для
каждой строки обращается в «да» или «нет». Да и само `WHERE` переводится
просто: «где» — «покажи строки, где цена больше 3000».

### WHERE: вопрос к каждой строке

```sql
SELECT name, price
FROM products
WHERE price > 3000;
```

Читается как предложение: «выбери name и price из products — где цена
больше 3000».

Ментальная модель: сервер проходит таблицу строка за строкой и задаёт
каждой один и тот же вопрос — «цена больше 3000?». Ответ — да или нет:
«да» — строка попадает в результат, «нет» — отбрасывается. Отсюда три
следствия. Условие пишется один раз, а проверяется для каждой строки.
`WHERE` ничего не меняет в таблице — он выбирает состав результата.
И фильтр — про **строки**, а список после `SELECT` — про **столбцы**:
два независимых решения (в примере выше по `stock` вообще не смотрят, хотя
могли бы).

Позиция в инструкции: сразу после `FROM`, до `LIMIT`. На наших шести
товарах урока результат такой:

```text
+--------------------------+----------+
| name                     | price    |
+--------------------------+----------+
| Клавиатура механическая  |  4990.00 |
| Монитор 27"              | 15990.00 |
+--------------------------+----------+
```

На наших товарах это выглядит так: «Коврик для мыши» за 690 отвечает «нет»
и отбрасывается; «Клавиатура механическая» за 4990 — «да» и попадает
в результат; когда строки закончатся, в ответе останутся ровно
подходящие.

### Шесть знаков сравнения

| Оператор | Смысл              | Пример: строки, у которых…   |
| -------- | ------------------ | ---------------------------- |
| `=`      | равно              | `price = 4990`               |
| `<>`     | не равно           | `city <> 'Москва'`           |
| `<`      | меньше             | `stock < 5`                  |
| `<=`     | меньше или равно   | `price <= 1290.50`           |
| `>`      | больше             | `price > 3000`               |
| `>=`     | больше или равно   | `created_at >= '2026-06-01'` |

Для «не равно» есть и второй знак — `!=`. В MySQL это синонимы: означают
одно и то же. В курсе пишем `<>`, но в чужом коде `!=` встречается
постоянно — теперь вы знаете оба.

Числа сравниваются по величине. Точное совпадение — «закончился склад»:

```sql
SELECT name, stock FROM products WHERE stock = 0;
```

```text
+-----------+-------+
| name      | stock |
+-----------+-------+
| Веб-камера|     0 |
+-----------+-------+
```

И самая коварная деталь — границы. `>=` включает равное, строгое `>` —
исключает: `price <= 1290.50` возьмёт мышь за 1290.50, а `price < 1290.50` —
уже нет. «Дороже 2000» — это `price > 2000`; «от 2000 и дороже» —
`price >= 2000`. Формулируя условие, всегда решайте, что делать с границей, —
иначе получите лишнюю или недостающую строку.

Две мелочи про числа. Числовые литералы пишутся без кавычек: `price > 3000`,
а не `price > '3000'`. Кавычки делают литерал строкой — серверу пришлось
бы неявно приводить её к числу, и полагаться на такое преобразование без
необходимости не стоит: тип литерала должен соответствовать типу столбца,
числа — числами, строки — строками. И точное равенство с деньгами — обычное равенство: `price = 4990`
найдёт клавиатуру, потому что `DECIMAL` хранит точное значение, без
«почти пяти тысяч» из-за округления (урок 5).

### Одна строка по id

Частный случай равенства заслуживает отдельной фразы: поиск по первичному
ключу. `id` — «имя строки» из урока 6, и достать конкретную строку проще
всего по нему:

```sql
SELECT * FROM products WHERE id = 4;
```

Один вопрос — не более одного ответа: условие по `id` вернёт одну строку,
если такой `id` существует, и ни одной — если нет; две — никогда:
уникальность гарантирована самим `PRIMARY KEY`. Так устроены
карточки товаров в интернет-магазинах: страница `/products/4` — почти
дословно этот запрос. А `id <> 4`, наоборот, вернёт все строки, кроме
четвёртой: равенство и неравенство симметричны и для ключей.

### Строки в условиях

Текст сравнивают те же знаки, но значение — строковый литерал в одинарных
кавычках, как в `INSERT` урока 4:

```sql
SELECT name, city
FROM customers
WHERE city = 'Москва';
```

Забыть кавычки — классика жанра:

```sql
SELECT name, city FROM customers WHERE city = Москва;
```

```text
ERROR 1054 (42S22): Unknown column 'Москва' in 'where clause'
```

Ошибка знакома по уроку 4: без кавычек `Москва` — не значение, а имя
столбца; такого столбца нет — 1054. Правило то же, что для `VALUES`:
строки — в кавычках, имена — без.

И деталь, которая удивляет: в стандартной настройке MySQL сравнение строк
не различает регистр — `'москва'`, `'Москва'` и `'МОСКВА'` друг другу
равны. Запрос `WHERE name = 'клавиатура механическая'` найдёт товар
«Клавиатура механическая». Отвечает за это настройка сравнения строк —
collation, большая тема продвинутой части курса; пока достаточно знать,
что регистр сравнением не ловится.

Неравенство для строк работает так же: `WHERE city <> 'Москва'` — «все,
кроме Москвы». А сравнение с пустой строкой — законная операция: `city = ''`
вернёт строки, где город записан пусто: пустая строка — это значение,
как учил урок 5. А вот строки, где города **нет вовсе** (`NULL`), не вернёт
ни это условие, ни любое другое сравнение — у NULL свой разговор, урок 11.

### Даты в условиях

Даты — то, ради чего фильтры затевают чаще всего: «заказы за лето»,
«покупатели с июня». Сравнение — с литералом в формате `ГГГГ-ММ-ДД`
(урок 5):

```sql
SELECT id, customer
FROM orders
WHERE created_at >= '2026-06-01';
```

Сервер сравнивает даты как точки на календаре: позже — больше, раньше —
меньше. Заказ от 2026-06-01 в выборку попадает (граница `>=` входит),
от 2026-05-28 — нет. Формат `ГГГГ-ММ-ДД` — не прихоть: он одинаково
упорядочивается и как дата, и как текст, поэтому путаницы не возникает.

Если столбец хранит ещё и время (`DATETIME` урока 5), литерал из одной
даты означает полночь: условие `created_at >= '2026-06-01'` возьмёт и заказ
от 2026-06-01 14:30, а `created_at <= '2026-06-01'` — уже нет: 14:30 позже
полуночи. Время в условиях подчиняется той же дисциплине границ, только
грань — не день, а секунда.

### Флаги: TRUE и FALSE в условиях

Четвёртый тип урока 5 — BOOL — сравнивается со своими литералами. Найти
неактивированные подарочные карты из урока 6:

```sql
SELECT code
FROM gift_cards
WHERE activated = FALSE;
```

Помните связку урока 5: `TRUE` и `FALSE` — имена единицы и нуля, поэтому
`activated = FALSE` и `activated = 0` — одно и то же условие, а
`activated = TRUE` — то же, что `activated = 1`. Вариант с `TRUE`/`FALSE`
читается лучше: «карта не активна» вместо «флаг равен нулю».

### WHERE и LIMIT: кто первый

Оба инструмента отвечают на «дай не всё» — и их регулярно путают. Порядок
строгий: сначала `WHERE` отбирает подходящие строки, потом `LIMIT` обрезает
уже отфильтрованный результат:

```sql
SELECT id, customer
FROM orders
WHERE created_at >= '2026-06-01'
LIMIT 2;
```

Из пяти летних заказов вернутся два первых:

```text
+----+-----------------+
| id | customer        |
+----+-----------------+
|  2 | Иван Сидоров    |
|  3 | Мария Волкова   |
+----+-----------------+
```

В инструкции части стоят в том же порядке: `WHERE` до `LIMIT` — и в тексте
запроса, и по смыслу. `LIMIT` без `WHERE` — «первые попавшие», `WHERE`
без `LIMIT` — «все подходящие», вместе — «первые из подходящих». И честная
деталь: какие именно строки окажутся «первыми», без сортировки формально
не гарантировано — управлять порядком строк будет `ORDER BY`, следующий
урок.

И про ожидания: `WHERE` без `LIMIT` может вернуть и ноль строк (ничего
не подошло — это нормальный пустой ответ, а не ошибка), и все строки
таблицы (подошло всё). Сколько строк вернёт фильтр — свойство данных,
а не синтаксиса.

### Где WHERE встретится ещё

`WHERE` — не принадлежность `SELECT`: он ограничивает и строки, которые
меняют `UPDATE` и `DELETE` (а вот у `INSERT` условия нет вовсе). Вспомните
разбор `DELETE`/`TRUNCATE`/`DROP` из
урока 7: `DELETE` умеет удалять часть строк именно потому, что к нему
прикручивается `WHERE`; `TRUNCATE` условий не понимает в принципе — он
всегда «всё». В уроке 7 мы чистили таблицы целиком — `TRUNCATE`
и `DELETE` без условия; в уроке 10 к ним присоединятся `UPDATE ... WHERE` и
`DELETE ... WHERE`, и обещание «удалить строго по условию» закроется. Условие
там будет то же, что сегодня, — а вот цена ошибки выше: фильтр в
разрушительной команде лучше перечитать до запуска, а не после.

### Чего WHERE пока не умеет

Честные границы на сегодня:

- несколько условий сразу («дороже 2000 **и** не Москва») — операторы
  `AND`/`OR`/`NOT`, тема следующего уровня; сейчас — одно сравнение;
- `NULL`: строки без значения не сравниваются вовсе — их не вернёт ни `=`,
  ни `<>`; для них свои инструменты (`IS NULL`) — урок 11;
- диапазон одним условием (`BETWEEN`), поиск по шаблону (`LIKE`) — тоже
  впереди.

Это не недоработки урока, а карта курса: у каждого пункта свой урок.

### Резюме

- `WHERE условие` — фильтр строк: один и тот же вопрос «да/нет» каждой
  строке; данные не меняет, результат — только подходящие строки.
- Шесть сравнений: `=` `<>` `<` `<=` `>` `>=`; `<>` и `!=` — синонимы.
- Граница: `>=` и `<=` включают равное, строгие `>` и `<` — нет; решайте
  заранее, что делать с граничным значением.
- Строки и даты — в одинарных кавычках; дата — `ГГГГ-ММ-ДД`, сравнивается
  по календарю.
- Без кавычек значение превращается в имя столбца — ошибка 1054.
- Стандартная настройка не различает регистр строк; почему — collation,
  продвинутая часть.
- Сначала `WHERE`, потом `LIMIT`: вместе — «первые из подходящих».
- Дальше: `UPDATE`/`DELETE` с условием — урок 10; `NULL` и `IS NULL` —
  урок 11; `AND`/`OR` и `LIKE` — следующий уровень.

## Теоретические задания

### Вопрос 1: `SELECT name, price FROM products WHERE stock > 10;` Что определяет условие WHERE?

- ✅ какие строки попадут в результат — оно проверяется для каждой строки таблицы
- ❌ какие столбцы попадут в результат — error_text: столбцы определяет список после SELECT; WHERE отбирает строки и может опираться на столбцы, которых в списке нет вовсе — как здесь: фильтр по stock при выводе name и price.
- ❌ сколько строк изменит сервер — error_text: WHERE в SELECT ничего не меняет — это фильтр результата; изменение строк — работа UPDATE и DELETE урока 10.

### Вопрос 2: Чем оператор `<>` отличается от `!=`?

- ✅ ничем: это синонимы — оба значат «не равно»
- ❌ `<>` работает только с числами, `!=` — с любыми значениями — error_text: оба знака — «не равно» для любых сравниваемых значений: чисел, строк, дат; ограничений нет ни у одного.
- ❌ `!=` проверяет ещё и тип, `<>` — только значение — error_text: приведение типов происходит одинаково для обоих знаков; различие только в написании, и выбор — вопрос стиля.

### Вопрос 3: В запросе `WHERE created_at >= '2026-06-01'` есть строка с `created_at = '2026-06-01'`. Попадёт ли она в результат?

- ✅ да: `>=` включает граничное значение
- ❌ нет: граница в условие не входит — error_text: за границу отвечает знак: `>=` — «больше или равно», равное включается; чтобы исключить границу, нужно строгое `>`.
- ❌ это зависит от остальных строк результата — error_text: условие проверяется для каждой строки независимо от остальных: граничная строка попадает в результат всегда, сколько бы строк ни было.

### Вопрос 4: Под условие `WHERE price > 5000` подходят 4 строки. Что вернёт `SELECT name FROM products WHERE price > 5000 LIMIT 2;`?

- ✅ две строки: LIMIT обрежет уже отфильтрованный результат
- ❌ все четыре: при WHERE лимит не работает — error_text: LIMIT работает всегда — только применяется к результату фильтра, а не к таблице целиком: из четырёх подходящих вернутся первые две.
- ❌ две строки, взятые из всей таблицы до фильтрации — error_text: порядок другой: сначала WHERE отбирает подходящие строки, затем LIMIT берёт первые из них; иначе «первые» могли бы оказаться неподходящими.

### Вопрос 5: `SELECT name FROM customers WHERE city = Москва;` — что ответит сервер?

- ✅ ошибку 1054: Москва без кавычек — имя столбца, которого нет
- ❌ строки покупателей из Москвы — error_text: без кавычек Москва — не значение, а идентификатор: сервер ищет столбец с таким именем и не находит его — ошибка 1054, знакомая по уроку 4.
- ❌ пустой результат: значения «Москва» ни у кого нет — error_text: чтобы сравнить со строкой, её пишут в кавычках: city = 'Москва'; без кавычек до сравнения дело не доходит — это ошибка, а не пустой результат.

### Задание 3: Первые летние заказы

Фильтр по дате и лимит в одном запросе.

<!-- Эталонное решение (для автора/бота-верификатора): SELECT id, customer, total FROM orders WHERE created_at >= '2026-06-01' LIMIT 2; -->

**statement:**
