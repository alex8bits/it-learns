# Command: MySQL Lesson Review Triage

## Goal

Разобрать ревью от внешнего бота и вынести по каждому пункту вердикт:
**ПРИНЯТЬ / ЧАСТИЧНО / ОТКЛОНИТЬ** с обоснованием.

Внешний ревьюер **не знаком** с планом курса (`docs/mysql.md`) и правилами создания
уроков (`docs/mysql-lesson-rule.md`), поэтому его выводы могут быть неточными.
Арбитр здесь — не ревью, а план + правила + сам урок. Ревью всегда касается
**последнего** урока в `docs/mysql/`; остальные уроки — только контекст.

Ревью передаётся в `$ARGUMENTS` (текстом или путём к файлу с ревью).
Если ревью не передано — попросить пользователя вставить текст ревью и остановиться.

## Scope

- Работаем **только с последним уроком** `docs/mysql/` (определение — шаг 1).
- Остальные уроки — контекст: что уже пройдено, эволюция сквозного датасета.
- После отчёта-триажа принятые правки **применяются сразу и без подтверждения**
  (шаг 7): правки из раздела «Итог» вносятся в файл урока, затем проходится
  чек-лист. Отклонённые пункты не трогаются. Коммит — не ответственность
  команды.
- Никаких записей в БД и сидеры (уроки — только markdown-файлы).

## Steps

### 1. Определить последний урок

«Последний» = максимальная позиция в **порядке курса**, а не по алфавиту.
Порядок уровней из плана: Основы (`basics`) → Начинающий (`beginner`) →
Средний (`intermediate`) → Продвинутый (`advanced`); внутри уровня — номер `<NN>`
из имени файла / frontmatter `lesson`.

1. Перечислить `docs/mysql/*.md`.
2. Взять файл с max (порядковый номер уровня, номер урока).
3. Санити-чек: ревью должно касаться темы этого урока (по упоминаемым вопросам,
   заданиям, терминам). Если содержимое ревью явно про **другой** урок — не выбирать
   молча: сообщить пользователю о расхождении (какой урок рассчитан как последний,
   какого касается ревью) и уточнить, какой разбирать. Расхождение означает, что
   либо ревью устарело, либо состав директории изменился после ревью.

### 2. Прочитать контекст

- **Полностью:** `docs/mysql.md` (план), `docs/mysql-lesson-rule.md` (правила),
  последний урок.
- Остальные уроки — frontmatter + заголовки секций (список пройденного для проверки
  границ тем). Полный разбор конкретного прошлого урока — только если вердикт по
  пункту зависит от него (например, ревью утверждает «это уже объяснялось» или
  «этот термин нигде не вводился»).

### 3. Разобрать ревью на пункты

Пронумеровать Р1..РN (каждое самостоятельное замечание — отдельный пункт).
Для каждого:

1. **Проверить факт** — действительно ли это так в уроке? Дать цитату или
   `docs/mysql/<файл>:<строка>`. Если факта нет — пункт отклоняется уже на этом шаге.
2. **Проверить по правилам** — это нарушение `mysql-lesson-rule.md`, противоречие
   плану `docs/mysql.md` или вкусовщина вне правил?
3. **Вынести вердикт** (шаг 5).

### 4. Верификация спорных SQL-замечаний

Если пункт — про поведение MySQL или соответствие `expected_rows` эталону, и его
нельзя разрешить чтением, прогнать SQL локально:

```bash
docker compose --profile testing up -d db-testing
# …запросы:
docker exec -i itlearns-db-testing mariadb -uroot it_learns_test
docker compose stop db-testing   # обязательно в конце
```

Нюанс: контейнер — MariaDB 11, а курс ведётся под MySQL 8.x. Отличия есть
(коллации, JSON, некоторые сообщения об ошибках) — использовать прогон как
ориентир, а не как истину, и учитывать это в формулировке вердикта.
Если проверка невозможна (Docker недоступен) — честно пометить это в обосновании.

### 5. Типичные ложные срабатывания внешнего ревьюера

Ревьюер не знает план и правила — прежде чем принимать пункт, сверить с этим списком:

- **Предлагает содержание будущих тем** («добавьте JOIN», «покажите GROUP BY») →
  границы тем: `mysql-lesson-rule.md` §4 + порядок в плане. ОТКЛОНИТЬ.
- **Хочет изменить структуру файла** (порядок секций, frontmatter, маркеры
  `**statement:**` / `**seed_sql:**`, формат `✅/❌`, `### Вопрос N`) → шаблон
  строгий и машиночитаемый (§2, §5): парсится при переносе в БД. ОТКЛОНИТЬ.
- **Требует практику там, где в плане «—»** → план, колонка «Практика». ОТКЛОНИТЬ.
- **«Слишком длинно / много воды»** при объёме в ориентире 1500–3000 слов →
  §1 правил: мотивация, сравнения с альтернативами, граничные случаи и «когда это
  не нужно» — не вода, а прямое требование правил. Объём замерить фактически, не
  верить ревью на слово:
  ```bash
  awk '/^## Материал/{f=1;next} /^## Теоретические/{f=0} f' docs/mysql/<файл> | wc -w
  ```
- **«Нет объяснения термина X»** → проверить: новый термин обязан вводиться в
  материале урока (§1); термин из пройденных тем — допустимо опираться на
  пройденное (§1, §4).
- **Предложения «улучшить» квиз сверх правил** (больше 5 вопросов, несколько
  правильных вариантов, `error_text` вида «неверно, попробуйте ещё») → тут ревью,
  скорее всего, право — это реальные требования §2.
- **Незнание платформенной механики практики**: самодостаточность `seed_sql`,
  детерминированность (`ORDER BY`, фиксированные даты), контракт результата
  (зачёт по последней инструкции), несколько инструкций в одной сессии — §3.
  Замечания, противоречащие этой механике, отклонять; замечания о её нарушении
  в уроке — принимать.

### 6. Вердикты

- **ПРИНЯТЬ (нарушение)** — факт подтверждён и является нарушением правил/плана
  или фактической ошибкой (семантика MySQL, `expected_rows` ≠ результат эталона,
  два правильных варианта и т.п.).
- **ПРИНЯТЬ (улучшение)** — необязательное предложение, которое по существу
  **строго лучше** текущего текста (критерии ниже). Не отклонять автоматом
  «раз необязательно»: сначала сравнить решения по существу. В таблице отчёта
  помечать «ПРИНЯТЬ (улучшение)».
- **ЧАСТИЧНО** — проблема реальна, но предложенное ревью решение нарушает правила.
  Принять проблему, отклонить предложенное решение и указать корректное в рамках
  правил.
- **ОТКЛОНИТЬ** — факт не подтверждён, противоречит правилам/плану, либо
  сравнение по существу показало, что предложение не лучше текущего
  (равноценно, длиннее без выигрыша, стирает полезную ловушку).

**Сравнение необязательных предложений по существу** (ПРИНЯТЬ-улучшение
vs ОТКЛОНИТЬ). Принимать, только если выполнены одновременно:

- точность/понятность: предложение устраняет реальный (а не теоретический)
  риск неверного прочтения или делает формулировку самодокументируемой;
- без потерь: не снижает точность, не раздувает объём сверх ориентира,
  не выходит за границы тем §4, не удаляет полезные ловушки и граничные случаи;
- самостоятельный выигрыш: не «тот же смысл другими словами» и не «длиннее,
  зато аккуратнее» без измеримой пользы.

Спорные случаи (сравнение не даёт явного победителя) — привести оба варианта
в обосновании и спросить пользователя, а не выбирать молча.

Каждый вердикт обосновывается ссылкой: `mysql-lesson-rule.md §…`, строка таблицы
уровня в `docs/mysql.md`, `docs/mysql/<файл>:<строка>`. Если пункт ревью непонятен
или неоднозначен — пометить это и спросить пользователя, а не додумывать.

### 7. Отчёт

```markdown
## Триаж ревью: docs/mysql/<последний урок>

Источник ревью: <файл / текст из аргументов> · Пунктов: N
(принято-нарушений: X, принято-улучшений: W, частично: Y, отклонено: Z)

| # | Замечание (кратко) | Вердикт | Обоснование |
|---|--------------------|---------|-------------|
| Р1 | … | ПРИНЯТЬ | … |

### Детали нетривиальных пунктов

(только там, где таблицы мало: цитаты, прогоны SQL, ссылки на правила)

### Итог: принятые пункты как конкретные правки

1. <файл:строка> — что именно изменить (формулировка в терминах формата урока)
```

После отчёта — **применить правки из раздела «Итог» без запроса подтверждения**
(режим закреплён пользователем): внести их в файл урока, сохраняя машиночитаемый
формат §5, затем пройти чек-лист из конца `mysql-lesson-rule.md` по изменённым
частям. Если принятых правок нет — файл урока не трогать. **Не коммитить**:
изменения остаются в working tree; коммит — не ответственность этой команды,
его делает пользователь или отдельный явный запрос.

## Примеры вердиктов

- Ревью: «добавьте в урок пример с JOIN» (урок = CREATE TABLE, уровень «Основы») →
  **ОТКЛОНИТЬ**: JOIN — «Начинающий» №13, непройденная тема (§4 границ тем).
- Ревью: «`expected_rows` задания 2 не соответствует `seed_sql`: строка с NULL
  отфильтруется условием» → проверить разбором/прогоном; если подтверждается →
  **ПРИНЯТЬ**: §3 — `expected_rows` обязан быть результатом реального прогона.
- Ревью: «перепишите вопросы в свободной форме, эмодзи ✅/❌ сбивают» →
  **ОТКЛОНИТЬ**: формат строгий, парсится при переносе в БД (§2, §5).

## Rules

1. Править только файл разбираемого урока и только правки из раздела «Итог»
   отчёта; применяются сразу после отчёта, без подтверждения (шаг 7).
   Коммитить правки команда не должна — изменения остаются в working tree.
2. Не выдумывать замечания и не расширять ревью своими: разбираем только то, что
   передано.
3. Каждый вердикт доказуем ссылкой на правило, план или строку урока.
4. Пунктов «ни о чём» не бывает только у автора ревью: если замечание непонятно —
   уточнить у пользователя, а не толковать в пользу отклонения.
